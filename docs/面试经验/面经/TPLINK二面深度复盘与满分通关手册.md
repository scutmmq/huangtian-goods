### Q1：TCP 三次握手与四次挥手深度拆解与异常状态排查

#### 1. 三次握手底层状态机与为什么不能“两次握手”？

```
      客户端 (Client)                               服务端 (Server)
         [CLOSED]                                      [LISTEN]
            │                                             │
   (1) 发送 SYN=1, seq=x ───────────────────────────────> │  [SYN_RCVD] (半连接队列)
         [SYN_SENT]                                       │
            │ <─────────────────────────────── (2) 回复 SYN=1, ACK=1, seq=y, ack=x+1
            │                                             │
   (3) 发送 ACK=1, seq=x+1, ack=y+1 ────────────────────> │  [ESTABLISHED] (全连接队列)
       [ESTABLISHED]                                      │
```

* **为什么三次握手绝不能是两次握手？（三大致命原因）**：
  1. **防止失效的历史重复连接请求造成服务端资源枯竭（头号考点）**：
     * 假设客户端发出的第一个连接请求 $SYN_1$ 因网络延迟严重滞留；
     * 客户端超时后重新发送了 $SYN_2$ 建立连接，通信完毕后断开；
     * 此时网络中的旧报文 $SYN_1$ 终于到达服务端。如果是“两次握手”，服务端只要收到 $SYN_1$ 回复 ACK 就**单方面认为新连接已经建立**，分配 Socket 缓冲区并傻傻等待客户端发数据；
     * 但客户端此时处于 CLOSED 状态，直接丢弃服务端的 ACK，导致服务端建立大量无效的“僵尸连接”，白白耗尽内存与端口资源！而在三次握手中，客户端收到服务端的 SYN+ACK 时，比对确认号发现是过期的历史连接，会向服务端发送 `RST` 报文终止该连接。
  2. **双方初始序列号（ISN, Initial Sequence Number）的双向可靠同步**：
     * 双方必须明确确认对方接收到了自己的 ISN，才能保证后续传输的数据不重、不漏、有序。
  3. **双向确认双方的“接收能力”和“发送能力”均正常**：
     * 客户端发、收均正常；服务端发、收均正常，必须通过三次往返才能完全闭环。

#### 2. 四次挥手底层状态机与为什么挥手需要四次？

```
      客户端 (Client)                               服务端 (Server)
       [ESTABLISHED]                                 [ESTABLISHED]
            │                                             │
   (1) 发送 FIN=1, seq=u ───────────────────────────────> │  [CLOSE_WAIT] (通知应用层)
       [FIN_WAIT_1]                                       │
            │ <─────────────────────────────── (2) 回复 ACK=1, seq=v, ack=u+1
       [FIN_WAIT_2]                                       │
            │                                             │ (服务端继续发送残留数据...)
            │ <─────────────────────────────── (3) 发送 FIN=1, ACK=1, seq=w, ack=u+1
            │                                         [LAST_ACK]
   (4) 发送 ACK=1, seq=u+1, ack=w+1 ────────────────────> │  [CLOSED]
       [TIME_WAIT] (等待 2MSL)                            │
            │
         [CLOSED]
```

* **为什么握手可以三次，而挥手必须四次？**：
  * **握手时**：服务端的 SYN（同步自身序列号）和 ACK（确认客户端序列号）可以**合并在同一个报文中发送**；
  * **挥手时（半关闭机制 Half-Close）**：客户端发送 FIN 只代表“客户端没有数据要发了”，但此时**服务端很可能还有未发送完毕的数据或者未处理完的业务逻辑**！因此服务端必须先回一个 ACK 告知客户端“我收到你的关闭请求了”，然后继续把剩下的数据发完；等服务端自己的数据彻底发完了，才能向客户端发送 FIN 报文。因此第二步与第三步无法合并，必须走四次！

#### 3. 线上高频 TCP 故障与排障实战（TP-LINK 必考！）

1. **SYN Flood（半连接洪水攻击）与防御**：
   * **原理**：攻击者伪造海量虚假 IP 地址向服务端发送 SYN 报文，服务端回复 SYN+ACK 后等待第三次握手；由于源 IP 是假的，服务端永远等不到 ACK，导致内核的**半连接队列（SYN Queue）被打爆**，正常合法用户无法建立连接。
   * **防御方案**：
     * 开启内核参数 **`net.ipv4.tcp_syncookies = 1`**：当半连接队列满时，服务端不分配物理控制块，而是通过源IP、源端口、时间戳哈希计算出一个 Cookie 作为初始序列号 ISN 发送。收到客户端 ACK 时逆向解算验证，合法才建连；
     * 增大半连接队列 `tcp_max_syn_backlog`，调小 SYN+ACK 重试次数 `tcp_synack_retries`。
2. **线上出现大量 `TIME_WAIT` 的根因与治理**：
   * **产生方**：**只有主动发起关闭连接的一方（Active Closer）才会进入 TIME_WAIT 状态**！
   * **危害**：占用大量本地 4 元组端口资源（`Local IP:Local Port:Remote IP:Remote Port`），端口耗尽后将无法发起新的对外连接。
   * **治理方案**：
     * 开启连接复用：`net.ipv4.tcp_tw_reuse = 1`（允许将处于 TIME_WAIT 超过 1 秒的 Socket 重新分配给新的连接）；
     * **架构根治**：在微服务之间避免使用短连接，全面升级为**长连接池**（如 HTTP Keep-Alive、HikariCP 连接池、gRPC）。
3. **线上出现大量 `CLOSE_WAIT` 的根因与排障（严重代码 Bug）**：
   * **产生方**：**被动关闭方（Passive Closer）**。收到客户端 FIN 回复 ACK 后进入 CLOSE_WAIT，等待自己发 FIN。
   * **致命根因**：**业务应用层代码存在严重 Bug，迟迟没有调用 `socket.close()` 或 `response.close()`！**
   * **排查方法**：使用 `netstat -antp | grep CLOSE_WAIT` 找到对应的进程 PID，使用 `jstack -l <pid>` 查看线程堆栈，排查是否由于线程池被耗尽、IO 阻塞或死锁，导致关闭连接的代码未被执行。

### Q2：TCP 流量控制（Flow Control）深度剖析（这就是你记忆中的“传输层限流”！）

很多同学面试时听到“限流”，只知道应用层的 Sentinel 或 Redis+Lua，但面试官问的是**计算机网络传输层的原生限流——TCP 流量控制（Flow Control）**！

#### 1. 流量控制的本质定位与滑动窗口机制
* **核心目标**：**点对点（End-to-End）的速率匹配**。防止发送方发得太快，导致接收方的**接收缓冲区（Receive Buffer）被打爆溢出丢包**。
* **实现基石：滑动窗口（Sliding Window）与通告窗口（rwnd）**：
  * TCP 的每个 ACK 确认报文中，首部都包含一个 16 位的 **`Window`（接收窗口 rwnd, Receive Window）** 字段；
  * 接收方实时监控自身内核接收缓冲区的剩余空闲字节数，并在 ACK 中通告给发送方：`rwnd = 接收缓冲区总大小 - 当前已接收但应用层未读取的大小`；
  * 发送方根据收到的 `rwnd`，严格限制自己未收到 ACK 的在途数据量：
    $$	ext{发送方当前可用发送窗口} \le 	ext{rwnd}$$

---

#### 2. 零窗口死锁（Zero Window Deadlock）与坚持定时器（Persist Timer）

* **死锁产生的惊险时序**：
  ```
  时间轴     发送方 (Sender)                                接收方 (Receiver)
    T1      发送大量数据 ─────────────────────────────────> 缓冲区被打满！
    T2      收到 ACK (rwnd = 0) <────────────────────────── 发送零窗口通告 (Window: 0)
            [发送方停止发送数据，进入等待...]
    T3                                                    应用层读取了数据，缓冲区清空！
    T4      [丢包了！] <────────── (更新窗口报文丢了!) ──────── 发送更新通告 (Window: 4096)
    T5      发送方一直在等非零窗口通告；接收方以为发送方收到了，一直在等发送方发新数据...
            --> 【双方陷入永久互相等待，TCP 连接彻底死锁冻结！】
  ```
* **破解法宝：坚持定时器（Persist Timer）与零窗口探测（Zero Window Probe, ZWP）**：
  * 当发送方收到 `rwnd = 0` 时，自动启动**坚持定时器（Persist Timer）**；
  * 定时器到期后（通常是指数退避，如 5s, 10s, 20s... 最大 60s），发送方强行向接收方发送一个只携带 **1 字节数据** 的**零窗口探测报文（Zero Window Probe）**；
  * 接收方收到探测报文后，**必须强制回复一个 ACK 报文，并在其中汇报当前最新的 `rwnd`**；
  * 若窗口仍为 0，复位坚持定时器继续等待；若窗口大于 0，死锁被成功打破，恢复正常传输！

---

#### 3. 糊涂窗口综合征（Silly Window Syndrome）与 Nagle 算法

* **什么是糊涂窗口综合征？**：
  * 接收方应用层读取极其缓慢（例如每次只 `read()` 1 个字节）；
  * 接收方一有 1 个字节空间，就立马向发送方通告 `rwnd = 1`；
  * 发送方收到后，真的发了 1 个字节数据。然而，**为了传输这 1 个字节有效载荷（Payload），TCP 头占 20 字节，IP 头占 20 字节，总共发了 41 字节的报文！** 41 字节里只有 1 字节有效数据，网络开销极其高昂，网络带宽被海量小包活活拖垮。
* **工业级解决方案（双管齐下）**：
  1. **接收方策略（Clark 算法）**：
     * 接收方只要空闲空间没有达到 **MSS（最大报文段长度）的一半** 或者 **接收缓冲区总大小的一半**，就强行对外宣称 `rwnd = 0`，拒绝接收小报文，直到攒够大空间再通告；
  2. **发送方策略（Nagle 算法）**：
     * 发送方对小数据包进行缓冲聚合。**只有满足以下两个条件之一时才允许发送数据**：
       ① 待发送的数据量达到了一个完整的 MSS；  
       ② 之前发出的所有数据包都已经收到了对方的 ACK。
     * *补充注意*：对于在线实时交互系统（如 FPS 游戏、SSH 终端），Nagle 算法会导致明显的打字延迟，通常在代码中通过 `socket.setTcpNoDelay(true)` 关闭 Nagle 算法。

### Q3：TCP 拥塞控制（Congestion Control）四大经典算法与现代 BBR

如果说流量控制是“防止把接收方打垮”，那么**拥塞控制就是“防止把整个互联网的中间路由器和交换机打垮”**！

#### 1. 经典拥塞控制的四大杀手锏算法（Tahoe / Reno 模型）

发送方内部维护一个核心变量：**拥塞窗口 `cwnd`（Congestion Window）**，单位通常是 MSS。

```
     cwnd 大小
        ▲
        │                                  超时重传 (Timeout)
        │                                        │  cwnd 瞬间砸回 1
        │                        / \             │     │
        │                       /   \            ▼     ▼
        │                      /     \ 收到 3 个重复 ACK (快重传)
        │            ssthresh ┌───────┐
        │            (门限值) │       │         │                    │       │  \ 拥塞避免 (线性加法增大)
        │                    │       └───\────────────────
        │                   /            快恢复 (ssthresh减半)
        │     慢启动       /
        │  (指数级增长)   /
        │               /
        └──────────────┴─────────────────────────────────► 时间
```

1. **慢启动（Slow Start）**：
   * 连接刚建立时，发送方根本不知道整个网络的承载极限，绝不能一上来就发几百兆数据；
   * 初始设 `cwnd = 1 ~ 10 MSS`；
   * **增长规律（指数翻倍）**：每收到一个 ACK，`cwnd` 增加 1；即**每一个往返时间（RTT），`cwnd` 直接翻倍**（$1 	o 2 	o 4 	o 8 	o 16 \dots$）；
   * 翻倍到达慢启动门限 `ssthresh`（Slow Start Threshold）时，踩刹车切换为拥塞避免。
2. **拥塞避免（Congestion Avoidance）**：
   * 从指数增长转为**线性增长（加法增大 Additive Increase）**；
   * 每经过一个 RTT，`cwnd` 仅增加 **1 个 MSS**，如同小心翼翼地试探网络的物理上限。
3. **快重传（Fast Retransmit）**：
   * **触发条件**：发送方**连续收到 3 个完全相同的重复确认报文（Triple Duplicate ACKs）**；
   * **物理判断**：接收方每收到一个失序的报文段，都会立刻给发送方回复一个期望序号的 ACK。连续收到 3 次重复 ACK，说明**虽然中间某个报文段丢了，但后续报文段已经顺利到达接收方，网络并没有彻底瘫痪**！
   * **执行动作**：**不等超时定时器（RTO）到期，立即主动重传丢失的报文段！**
4. **快恢复（Fast Recovery）**：
   * 既然收到了 3 个重复 ACK 说明网络还能传数据，就**绝不把 `cwnd` 暴力清零回到 1**！
   * 将 `ssthresh` 砍半（$	ext{ssthresh} = 	ext{cwnd} / 2$）；
   * 设置 `cwnd = ssthresh + 3 MSS`，直接进入拥塞避免阶段，系统吞吐量平滑过渡（乘法减小 Multiplicative Decrease，即著名的 **AIMD 加法增大乘法减小原则**）。

---

#### 2. 超时重传（RTO 到期）vs 快重传（3 个重复 ACK）在拥塞控制中的区别

| 异常现象 | 触发时机 | 网络拥塞严重程度 | 拥塞控制动作 |
| :--- | :--- | :--- | :--- |
| **超时重传 (RTO Timeout)** | 发送报文后，重传计时器超时仍未收到任何 ACK | **极度严重**（网络已瘫痪，中间路由器队列溢出） | `ssthresh = cwnd / 2`，**`cwnd` 强行砸回到 1 MSS**，重新从慢启动爬坡！ |
| **快重传 (Fast Retransmit)** | 连续收到 3 个重复的 ACK | **轻度拥塞或偶发丢包**（后续包仍能送达） | 立即重传丢失报文，执行**快恢复**（`cwnd` 减半），不降到 1！ |

---

#### 3. 现代颠覆性拥塞控制算法：Google BBR 算法

* **传统算法（Cubic / Reno）的致命缺陷（基于丢包 Loss-based）**：
  * 传统算法认为“只要丢包就是网络拥塞了，必须立刻降速”；
  * 在现代高带宽、长延迟网络（长肥管道，如跨国骨干网、无线 5G / Wi-Fi）中，无线信号干扰丢包是家常便饭。传统算法疯狂降速，导致百兆千兆带宽的实际利用率甚至不足 10%！
* **BBR（Bottleneck Bandwidth and RTT，基于模型 Model-based）的核心突破**：
  * **不以丢包作为网络拥塞的判定标志！**
  * BBR 实时监测链路的两个物理极值：
    1. **最大瓶颈带宽（BtlBw）**；
    2. **最小往返传播时延（RTprop）**。
  * **核心哲学**：将网络中正在传输的数据量控制在 **$	ext{BDP} = 	ext{BtlBw} 	imes 	ext{RTprop}$（带宽时延积）**，刚好让管道流满，同时在路由器队列中几乎不排队，做到了“最高吞吐量 + 最低网络延迟”的双重极致！Linux 4.9+ 已原生内置支持。

### Q4：流量控制（Flow Control）与拥塞控制（Congestion Control）的本质区别与协同工作机制

> 🗣️ **面试官如果问：“请你对比一下 TCP 的流量控制和拥塞控制，它们是如何协同工作的？”**  
> 一分钟满分回答模版：

```
┌────────────────────────────────────────────────────────────────────────┐
│                          【发送端的最终决策公式】                         │
│                                                                        │
│        发送方实际发送窗口 (Send Window) = min( rwnd,  cwnd )            │
│                                              │      │                  │
│                        受限于接收端能力 ──────┘      └───── 受限于网络环境
│                        (流量控制保护对端)                   (拥塞控制保护公网)
└────────────────────────────────────────────────────────────────────────┘
```

#### 1. 本质区别全景对比表

| 对比维度 | 流量控制 (Flow Control) | 拥塞控制 (Congestion Control) |
| :--- | :--- | :--- |
| **视角与范围** | **端到端（End-to-End）局部控制** | **全局性网络（Global Network）整体控制** |
| **保护目标** | 保护**接收方主机**，防止其接收缓存被溢出打爆 | 保护**中间网络链路**（路由器、交换机），防止全网拥塞瘫痪 |
| **核心指标** | **`rwnd`（接收窗口，Receive Window）** | **`cwnd`（拥塞窗口，Congestion Window）** |
| **控制主体** | 由**接收端**计算，在 TCP 报头中的 `Window` 字段显式通告 | 由**发送端**根据丢包/ACK 反馈通过算法动态估算推导 |
| **应对问题** | 接收端应用程序处理过慢、读取不及时 | 网络物理链路带宽受限、路由器缓冲区排队溢出 |

#### 2. 双方如何协同？（发送窗口的最终决定权）
* 发送方在任一时刻能够连续发出的最大字节数，严格取决于 **$\min(	ext{rwnd}, 	ext{cwnd})$**：
  * **场景 A**：接收端机器性能极好，通告 `rwnd = 100MB`，但中间网络发生拥塞，`cwnd` 只有 `10KB`。此时发送方最多只能发 `10KB`，以**拥塞控制为主导**，保护公网；
  * **场景 B**：公网是千兆光纤骨干网，`cwnd = 50MB`，但接收端 CPU 满载无法读取数据，通告 `rwnd = 100KB`。此时发送方最多只能发 `100KB`，以**流量控制为主导**，保护接收端。

## 第二部分：分布式与高并发核心（Redisson 分布式锁、看门狗、Redis 集群与双写一致性）

### Q2：Lua + Redis + Redisson 分布式锁：Lua 已经保证了原子性，为什么还要加分布式锁？

#### 1. 核心本质辨析：操作原子性 $
eq$ 业务临界区互斥
* **Lua 脚本的原子性**：只保证 **脚本内部的几条 Redis 命令在执行时不被其他 Redis 命令插队**（执行时间通常只有几毫秒）。它解决的是 `GET` 和 `DEL`、或者 `SETNX` 和 `EXPIRE` 两个操作之间的原子性。
* **分布式锁的业务目标**：保证的是 **跨网络、跨进程的“一整段耗时业务逻辑（临界区）”的互斥访问**！这整段业务可能要查库、RPC 远程调用、扣减库存、落单，耗时可能是 100ms、1秒甚至几秒。
* **为什么只用简单的 Redis + Lua 脚本做锁会翻车？（原生锁的四大致命缺陷）**
  1. **业务未执行完，锁已超时提前释放**：设置了 5 秒过期时间，若因为 GC 停顿或第三方网络慢，业务耗时 8 秒，第 5 秒锁被 Redis 自动清理，其他线程趁虚而入，导致**并发临界区彻底失效**；
  2. **不可重入性**：同一个线程如果调用了带锁的方法 A，方法 A 又调用了带同一把锁的方法 B，原生锁会把自己阻塞死锁；
  3. **缺乏高效的阻塞等待与自旋重试机制**：单纯的 `SETNX` 失败后，业务端只能要么直接报错，要么使用 `Thread.sleep` 轮询死等，浪费 CPU 和网络带宽；
  4. **Redis 主从切换丢失锁（异步复制）**：在主从架构中，Master 节点刚写入锁还没同步给 Slave 就宕机了，Slave 晋升为 Master，导致后来的线程再次加锁成功，一把锁被两个客户端同时持有。

#### 2. Redisson 带来了什么？
Redisson 是工业级的分布式锁客户端，它虽然底层也是用 Lua 脚本向 Redis 发送指令，但它封装了：
* **看门狗（Watchdog）自动续期**：只要业务线程还活着，后台线程自动续期，彻底解决“业务没跑完锁提前失效”；
* **基于 Hash 结构的可重入锁**：Key 是锁名，Field 是 `UUID:threadId`，Value 是重入计数器，支持同一线程无限重入；
* **基于 Redis Pub/Sub 的高效等待唤醒机制**：获取锁失败后订阅锁释放事件，有锁释放才唤醒重试，避免死循环轮询；
* **RedLock 红锁算法支持**：多节点容错，解决主从切换单点丢锁隐患。

> 🗣️ **面试一分钟口播模版**：
> “Lua 脚本的原子性只管 Redis 内部几毫秒的命令批处理不被打断；而分布式锁解决的是跨进程、耗时几百毫秒甚至几秒的业务代码块的互斥访问。
> 如果仅靠原生 Redis+Lua，存在业务没跑完锁提前超时、线程不可重入、以及获取锁失败只能轮询重试等缺陷。Redisson 正是在底层基于 Lua 实现了原子加锁的同时，补充了**看门狗后台自动续期、基于 Hash 的可重入计数、以及基于 Pub/Sub 的事件唤醒重试机制**，这才构成了一套工业级可靠的分布式锁。”

### Q3：分布式锁的看门狗机制（Watchdog）底层原理是什么？

#### 1. 工作流程与底层机制
1. **触发条件**：只有在调用 `lock()` **未显式指定 `leaseTime`（或者为 -1）** 时，看门狗机制才会生效。如果显式传入了超时时间（如 `lock(10, TimeUnit.SECONDS)`），Redisson 会严格按指定时间释放，不再启动看门狗。
2. **默认租期**：看门狗默认锁超时时间为 **30 秒**（由配置项 `lockWatchdogTimeout` 决定）。
3. **续期调度器（HashedWheelTimer）**：
   * 加锁成功的瞬间，Redisson 会在客户端后台启动一个基于 Netty 的时间轮定时任务（`Timeout task`）；
   * 续期周期间隔为 `leaseTime / 3`，即 **每隔 10 秒** 执行一次续期；
   * 续期操作同样是一段 **Lua 脚本**：判断当前锁的 Holder 是否依然是自己的 `UUID:threadId`，如果是，执行 `HEXISTS` 并通过 `PEXPIRE` 将过期时间**重新刷新为 30 秒**。
4. **注销与防死锁**：
   * **正常业务结束**：业务线程显式调用 `unlock()` 时，发送解锁 Lua 脚本，同时取消（cancel）后台的时间轮定时任务；
   * **服务器宕机崩溃**：如果持有锁的 JVM 进程突然 OOM 或宕机（kill -9），看门狗定时任务随进程一同死掉，停止续期；30 秒后 Redis 中的 key 自然过期，其他节点即可重新争抢，彻底避免了死锁。

### Q4：如何保证 Redis 和 MySQL 的数据最终一致性？（深度拆解 Cache-Aside 与 Binlog 补偿）

#### 1. 为什么是 Cache-Aside（旁路缓存）模式？
* **读取时**：先查 Redis，命中直接返回；未命中查 MySQL，写入 Redis 后返回。
* **更新时**：**先更新数据库，再删除缓存！**
* **为什么不能先删缓存再改数据库？**
  * 会发生经典读写并发脏数据：线程 A 先删缓存，还没来得及更数据库；线程 B 读请求进来发现缓存无数据，查出数据库旧值并写入缓存；接着线程 A 更新数据库成功。最终导致**缓存里常驻了旧脏数据，直到过期才会更新**！
* **为什么先改数据库再删缓存也会有极小概率不一致？**
  * 极端时序：缓存刚好失效，读请求读出旧值，写请求更新数据库并删缓存，随后读请求把旧值写入缓存。但由于数据库写操作比读操作慢得多，实际生产中这种概率极低。

#### 2. 工业级终极解决方案：Canal 异步监听 Binlog + MQ 重试
针对“删除缓存可能失败”导致的脏数据，工业级标准解法是**异步解耦与重试兜底**：
1. 业务应用只负责直接更新 MySQL 数据库，不主动碰缓存；
2. 部署 **Canal 伪装成 MySQL 的从节点（Slave）**，实时读取并解析 MySQL 的 **Binlog（Row 格式）**；
3. Canal 将数据变更事件写入 **Kafka / RocketMQ**；
4. 缓存同步微服务监听 MQ，提取主键 ID 执行 `redis.del(key)`；
5. 如果删除 Redis 失败，借助 MQ 消息重试机制进行指数退避重试，直至成功；若重试超限则投递死信队列（DLQ）触发人工报警。
* **优势**：业务代码完全解耦；强依赖 Binlog 顺序性，不会漏更新；高吞吐、最终一致性达到 99.999%。

### Q5：Redis 主从复制原理与同步机制（全量 RDB + 增量 backlog 缓冲区）

#### 1. 全量同步（Full Synchronization）
* **触发时机**：从节点（Slave）第一次连接主节点（Master），或者断开重连后 offset 已经超出复制积压缓冲区范围。
* **同步四步走**：
  1. 从节点发送 `psync ? -1` 握手请求；
  2. 主节点收到后，后台执行 `bgsave` 生成当前内存快照 **RDB 文件**，并记录此时此刻的复制偏移量（replication offset）；
  3. 主节点将 RDB 文件发送给从节点，从节点清空自身本地数据并加载 RDB；
  4. **复制缓冲区补齐**：在主节点生成和传输 RDB 期间产生的所有新写入命令，会被缓存在主节点的 **`replication buffer`** 中。RDB 加载完毕后，主节点将这部分缓冲区命令发送给从节点追加重放。

#### 2. 增量同步（Partial Resynchronization）
* **触发时机**：主从之间由于短时间网络抖动发生断开重连。
* **核心组件**：
  * **`repl_backlog_buffer`（复制积压缓冲区）**：主节点维护的固定大小（默认 1MB）的**环形写缓冲区**；
  * **`master_repl_offset`**：主节点当前写入偏移量；
  * **`slave_repl_offset`**：从节点已同步的偏移量。
* **执行逻辑**：从节点重连发送 `psync <runid> <offset>`。主节点比对 offset，若该 offset 还在环形缓冲区内，直接把两者的差量数据推送给从节点；若 offset 已经被新数据覆写，则被迫退化为全量同步。
* **心跳保活**：从节点每秒向主节点发送 `REPLCONF ACK <offset>`，用于检测心跳并确认数据同步进度。

### Q6：Redis Cluster 集群架构（16384 哈希槽、MOVED/ASK 重定向与 Gossip 协议）

#### 1. 16384 哈希槽（Hash Slot）机制
* Redis Cluster 没有采用简单的一致性哈希，而是将数据空间均分为 **16384 个槽（Slots 0~16383）**。
* **槽位计算**：$$	ext{Slot} = 	ext{CRC16}(	ext{key}) \pmod{16384}$$。
* **支持 HashTag**：如果 Key 中包含 `{}`，例如 `user:{1001}:info`，则只对花括号内部的内容 `1001` 计算 CRC16，确保同一用户的不同数据必定落到同一个槽位和物理节点，支持多 Key 事务与 Lua 脚本。

#### 2. 请求重定向：`MOVED` vs `ASK`
* **`MOVED` 永久重定向**：客户端发错节点，该槽位已明确归属另一个节点。节点返回 `-MOVED 1001 192.168.1.2:6379`。客户端收到后向新节点重新发起请求，并**更新本地的 Slot-Node 路由缓存映射表**。
* **`ASK` 临时重定向**：该槽位**正在迁移中（Slot Migration）**。节点返回 `-ASK 1001 192.168.1.2:6379`。客户端必须先向目标节点发送一条 `ASKING` 探测命令，再发送真正业务命令。客户端**不会更新本地路由缓存**。

#### 3. Gossip 协议去中心化协同
* 节点之间通过专用的集群总线端口（通信端口 = 服务端口 + 10000）以固定频率互发 `PING/PONG` 报文交换元数据。
* **故障判定**：某个节点在 `cluster-node-timeout` 内无响应，被标记为 `PFAIL`（主观下线）；当半数以上负责槽位的主节点都标记其为 PFAIL 时，广播通知标记为 `FAIL`（客观下线），触发从节点选举晋升。

### Q7：MySQL B+ 树数据结构深度剖析（为什么是 B+ 树而不是二叉树、红黑树或 B 树？）

| **二叉查找树 (BST)** | 插入有序数据时退化为单向链表，查找复杂度退化为 $O(N)$。 | 树高不可控，查询极慢。 |

### Q9：MySQL 索引的本质是什么？（聚簇索引、二级索引、回表与覆盖索引）

* **索引的本质**：**高效获取数据、排好序的数据结构**（以空间换时间，将无序的磁盘随机 I/O 转化为高效的有序二分查找）。
* **聚簇索引（Clustered Index）**：
  * 叶子节点存放的是**整行完整的用户数据（Row Data）**。
  * 每张表只能有且仅有一个聚簇索引（通常是主键 Primary Key；无主键则选第一个唯一非空索引；再无则自动生成隐藏的 6 字节 `row_id`）。
* **二级索引 / 辅助索引（Secondary Index）**：
  * 叶子节点存放的不是完整数据，而是**对应的索引列值 + 主键 ID**。
* **回表（Bookmark Lookup）**：
  * 当通过普通二级索引（如 `idx_name`）查询时，先在二级索引树找到对应的主键 ID，再拿着主键 ID 去聚簇索引树重新走一遍搜索拿到整行数据，这个过程称为回表。
* **覆盖索引（Covering Index）**：
  * 如果 `SELECT` 查询的列恰好被联合索引完全覆盖（如查询 `SELECT id, name, age FROM user WHERE name = 'zs'`，而建立了 `idx_name_age` 联合索引），二级索引的叶子节点已经包含所需全部字段，**直接返回，无需回表**，性能极大提升。

### Q10：MySQL 数据库连接池原理与关键核心参数（HikariCP / Druid）

#### 1. 为什么必须使用连接池？
创建一次 MySQL 物理连接的成本极其高昂：**TCP 三次握手 + MySQL 协议握手与安全密码加密验证 + MySQL 服务端分配线程与内存资源**。在高并发下频繁创建销毁连接会直接压垮数据库。连接池通过复用物理连接彻底消除了重复握手开销。

#### 2. HikariCP / Druid 核心参数详解与配置心法

| 参数名称（HikariCP） | 默认值 / 推荐值 | 物理含义与生产踩坑指南 |
| :--- | :---: | :--- |
| **`maximum-pool-size`** | 推荐 16 ~ 32 | **最大物理连接数**。切忌盲目设为几百！根据公式：$	ext{PoolSize} = (	ext{CPU核心数} 	imes 2) + 	ext{有效磁盘轴数}$。对于 8 核服务器，设为 16~20 吞吐量最高。连接过多会导致 MySQL 内部上下文切换暴增，吞吐反而雪崩。 |

| **`connection-timeout`** | 30000ms (30s) | 客户端从连接池借出连接的最大等待时间。超时则抛出 `SQLException: Connection is not available`。 |
| **`idle-timeout`** | 600000ms (10m) | 空闲连接在池中存活的最大时长，超出且当前连接数大于 min-idle 时被回收。 |
| **`max-lifetime`** | 1800000ms (30m) | **连接的最大生命周期**（核心！必须比 MySQL 端的 `wait_timeout` 短几分钟！）。若长于数据库的 `wait_timeout`，MySQL 会单方面断开底层的 TCP 连接，导致客户端借出连接执行 SQL 时报 `Communications link failure`。 |
| **`keepaliveTime`** | 30000ms (30s) | 定时向 MySQL 发送 `SELECT 1` 心跳保活探测，防止连接被网络防火墙假死切断。 |

## 第四部分：JVM 虚拟机与 Java 多线程高并发底层（调优实战、内存结构、线程池与拒绝策略）

### Q11：JVM 调优做过吗？怎么调的？（指标、排查路径与核心调优策略）

#### 1. 调优的核心黄金指标
* **吞吐量（Throughput）**：用户代码运行时间 / (用户代码运行时间 + 垃圾回收耗时)，目标 $\ge 95\%$；
* **STW 停顿时间（Pause Time）**：GC 造成的最大延迟，Web 交互场景目标单次 STW $\le 100	ext{ms} \sim 200	ext{ms}$；
* **GC 频次**：Young GC 数十秒一次，Full GC 数天一次甚至零 Full GC。

#### 2. 真实排查与调优三步 SOP
1. **指标监控与日志收集**：
   * 开启 GC 日志：`-Xlog:gc*,gc+phases=debug:file=gc.log:time,tags:filecount=5,filesize=50M`；
   * 线上通过 `jstat -gcutil <pid> 1000` 实时观测 Eden、Survivor、Old 区内存增长斜率与回收耗时。
2. **内存 Dump 与根因分析**：
   * 配置 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/logs/dump.hprof`；
   * 将 dump 文件拉取到本地，使用 **Eclipse MAT (Memory Analyzer Tool)** 打开，查看 **Leak Suspects** 报告，通过支配树（Dominator Tree）和不可达路径（Merge Shortest Paths to GC Roots）锁定大对象（如未分页的大列表、未关闭的 IO 流、`ThreadLocal` 遗留）。
3. **参数优化实战举措**：
   * **固定堆大小防震荡**：将 `-Xms` 与 `-Xmx` 设为完全一致（如 `-Xms4g -Xmx4g`），彻底消除堆扩容与缩容时的系统 STW 抖动；
   * **代际比例调整**：针对短生命周期对象极多导致过早进入老年代的现象，合理增大新生代 `-XX:NewRatio=2` 或增大 Survivor 比例；
   * **升级垃圾收集器**：放弃传统 CMS，全量切换为 **G1（设置 `-XX:MaxGCPauseMillis=100`）** 或 **ZGC**，将 STW 彻底压缩到 10ms 甚至亚毫秒级。

### Q13 & Q14：Java 线程池七大核心参数与线程生命周期流转机制

#### 1. 七大核心参数物理意义
```java

    int corePoolSize,                   // 1. 核心线程数（常驻常备军）
    int maximumPoolSize,                // 2. 最大线程数（核心 + 临时急救特遣队）
```

#### 2. 新任务提交时的四步流转状态机（核心 vs 最大的本质区别）
当调用 `threadPool.execute(task)` 时，底层按以下确定性次序执行：
1. **Step 1**：当前运行线程数 `< corePoolSize` $
ightarrow$ 无论池中是否有空闲线程，**立即创建新的核心线程**执行任务；
2. **Step 2**：当前运行线程数 $\ge corePoolSize$ $
ightarrow$ **尝试放入阻塞队列 `workQueue` 排队等待**；
3. **Step 3**：如果阻塞队列已满，但当前线程数 `< maximumPoolSize` $
ightarrow$ **破格创建非核心线程（临时线程）立即执行新任务**；
4. **Step 4**：如果阻塞队列已满，且当前线程数已达到 `maximumPoolSize` $
ightarrow$ **触发拒绝策略 `RejectedExecutionHandler`**。
* **生命周期区别**：核心线程默认长期存活不回收（除非显式开启 `allowCoreThreadTimeOut(true)`）；非核心线程一旦空闲超过 `keepAliveTime` 自动退出销毁。

### Q15：线程池拒绝策略有哪些？生产场景下如何自定义拒绝策略？

#### 1. JDK 4 大内置拒绝策略
1. **`AbortPolicy`（默认）**：直接抛出 `RejectedExecutionException` 异常，阻止系统继续放行；
2. **`CallerRunsPolicy`（调用者运行）**：由提交任务的主线程自己去执行该任务。**作用**：起到“天然限流防压垮”的效果，让生产线程降速；
3. **`DiscardPolicy`（静默丢弃）**：直接丢弃任务，不给任何通知；
4. **`DiscardOldestPolicy`（丢弃最老任务）**：丢弃队列头部的老任务，将新任务重新尝试入队。

#### 2. 生产实战：如何自定义拒绝策略？（面试场景实战题）
* **面试场景**：在资金交易、机器人核心调度、设备告警下发场景下，**任务绝对不能直接丢弃，但又不能把主线程永久卡死**，如何设计？
* **工业级自定义拒绝策略方案**：
  1. 实现 `RejectedExecutionHandler` 接口；
  2. 在 `rejectedExecution` 回调中，首先打印 Error 级别日志并上报 Prometheus 告警监控；
  3. **任务降级持久化兜底**：将任务对象序列化，存入 **Redis 延迟队列 / Kafka 死信队列 / 本地磁盘 RocksDB**；
  4. 后台启动补偿线程，在系统负载回落（如队列容量降至 50% 以下）时，自动从持久化存储中拉取任务重新补偿执行。

```java
public class GracefulDegradePolicy implements RejectedExecutionHandler {
    private static final Logger log = LoggerFactory.getLogger(GracefulDegradePolicy.class);
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        log.error("ThreadPool saturated! Task rejected. ActiveCount: {}, QueueSize: {}", 
                  executor.getActiveCount(), executor.getQueue().size());
        // 告警打点
        Metrics.counter("threadpool.rejected.count").increment();
        // 降级兜底持久化到 Redis / 磁盘，保证零数据丢失
        if (r instanceof BusinessTask task) {
            redisTemplate.opsForList().rightPush("TASK_DEGRADE_QUEUE", task);
        }
    }
}
```

## 第五部分：分布式消息队列（Kafka 幂等生产与防重复消费全链路）

### Q20：Kafka 如何防止消息重复发送与保证消息幂等？（从生产者端与消费者端分别阐述）

#### 1. 生产者端（Producer）：底层机制防止消息重复发送
在网络抖动时，Producer 发送消息到 Broker，Broker 写入成功后返回 ACK 超时，Producer 触发自动重试，极易造成消息重复写入。
* **终极武器：开启生产者幂等性（`enable.idempotence=true`）**：
  * **PID (Producer ID)**：Kafka Broker 会为每一个 Producer 实例分配一个全局唯一的 64 位整数 PID；
  * **Sequence Number**：Producer 发送到每个 `<Topic, Partition>` 的消息都会附带一个单调递增的序列号（从 0 开始）；
  * **Broker 端去重机制**：Broker 会在内存中缓存每个分区最近收到的 5 个 `Sequence Number`。只有当收到新消息满足：
    $$	ext{SeqNum}_{	ext{new}} == 	ext{SeqNum}_{	ext{last}} + 1$$
    时，Broker 才会真正落盘保存；如果收到的 $	ext{SeqNum}_{	ext{new}} \le 	ext{SeqNum}_{	ext{last}}$，说明是网络超时引起的重复发送，Broker **直接丢弃该重复消息，但仍向 Producer 返回成功的 ACK**！
* **事务保证（Kafka Transactions）**：通过设置 `transactional.id`，实现多个 Topic 分区的原子性写入（要么全部成功，要么全部回滚）。

#### 2. 消费者端（Consumer）：业务层绝对防重与幂等消费
因为如果 Consumer 在处理完业务逻辑后、提交 Offset 前发生崩溃重启，Rebalance 后新消费者必然会重复拉取到上一条消息。
* **三大业务级幂等设计**：
  1. **数据库唯一键约束（Unique Key）**：以业务全局流水号（如 `order_sn`、`trace_id`）建立唯一索引，重复消费时直接捕获 `DuplicateKeyException` 并忽略；
  2. **Redis `SETNX` 幂等防重表**：
     * 收到消息后，先执行 `redis.setnx("MSG_ID:" + msgId, 1, 24, TimeUnit.HOURS)`；
     * 若返回 false，说明已经处理过，直接提交 Offset 跳过；
  3. **状态机前置乐观锁流转**：
     * 业务更新带前置状态校验：`UPDATE t_order SET status = 'PAID' WHERE id = 101 AND status = 'UNPAID'`；
     * 如果重复执行，受影响行数为 0，业务逻辑安全短路。

### Q16：为什么使用多路混合检索？分开说说各自优缺点与互补性

* **向量语义检索（Dense Retrieval，如 text-embedding-v3）**：
  * **优点**：能够捕捉跨语种、同义词、自然语言长句的深层语义相似度（如输入“如何改善上网慢”，能精准召回“Wi-Fi 信道频宽优化”）。
  * **致命缺点**：对**具体型号（如 BE6500-Pro）、版本号（如 v1.0.2）、错误码（0x80070005）、IP 地址**等非自然语言符号极不敏感，余弦距离容易漂移。
* **BM25 倒排索引检索（Sparse Retrieval，如 Lucene / ES）**：
  * **优点**：专攻字面精确匹配，对专有名词、设备硬件型号、SKU、代码符号具有 100% 的定点命中能力。
  * **致命缺点**：完全无法理解语义，遇到同义词或措辞变化直接漏检。
* **为什么必须“双路混合 + RRF 融合”？**
  * 两者属于完全互补的检索范式。通过 **RRF（倒数排名融合，Reciprocal Rank Fusion）** 将两路量纲不同的分数统一排序，既防止了专有名词漏检，又保证了日常自然语言的泛化理解。

### Q18：向量检索的 HNSW 索引底层是什么？（分层可导航小世界图算法）

* **全称**：Hierarchical Navigable Small World（分层可导航小世界）。
* **核心数学思想**：**将一维跳表（Skip-List）的多层稀疏跃迁思想，推广到了高维空间图中**。
* **物理结构**：
  * 整个索引由自顶向下的多层有向图组成；
  * **最顶层（Layer N）**：节点极度稀疏，连线的物理跨度极大；
  * **最底层（Layer 0）**：包含全量所有数据节点，局部连线密集。
* **检索过程（自顶向下贪心跳跃）**：
  1. 从顶层唯一的 Entry Point 节点出发，计算所有邻居到 Query 的距离，跳向最近的节点（快速跨越全局盲区）；
  2. 当在当前层无法找到更近的节点时，进入下一层对应的节点继续进行贪心搜索；
  3. 直至下降到 Layer 0，以局部密集搜索收敛到 Top-K 最近邻。
* **性能优势**：将高维空间全量爆力穷举的 $O(N)$ 复杂度，直接大幅降低到了 **$O(\log N)$**！

### Q19：介绍一下 LangGraph 框架与 Agent 有向图编排机制

* **诞生的核心痛点**：传统 LangChain 的 Chains 属于简单的有向无环图（DAG），只能单向流动，**无法原生支持循环迭代（Looping）、反思纠错（Self-Reflection）、以及复杂多智能体协作（Multi-Agent Collaboration）**。
* **LangGraph 核心三要素**：
  1. **State（全局状态）**：贯穿图流转的集中上下文数据结构（TypedDict 或 Pydantic 对象），所有节点共同读写；
  2. **Nodes（节点）**：具体的函数或 Agent 动作（如：调用 LLM、调用工具、检索向量库）；
  3. **Edges（边与条件边）**：普通边定义确定性流转，条件边（`add_conditional_edges`）根据上一节点输出的 State 动态决定路由分支（例如：工具执行报错则回退到重试节点，反之走到汇总节点）。
* **工业级企业特性**：
  * **Checkpointer 状态持久化**：支持执行状态入库（PostgreSQL/Redis），实现故障断点续跑；
  * **Human-in-the-loop（人工介入）**：在敏感高危节点（如执行资金扣款、物理设备重启）支持挂起等待，待管理员人工点击审批后无缝恢复执行。

## 第七部分：手撕算法深度解析与最优代码模板

### 算法 1：0-1 背包问题（DP 状态转移与一维滚动数组压缩）

* **题目描述**：有 $N$ 件物品和一个容量为 $V$ 的背包。第 $i$ 件物品的体积是 $w[i]$，价值是 $v[i]$。每件物品只能选一次，求背包能装下的最大价值。

#### 1. 二维 DP 思路与状态转移
* 定义 $dp[i][j]$：前 $i$ 件物品放入容量为 $j$ 的背包所能获得的最大价值。
* 状态转移方程：
  $$dp[i][j] = \max(dp[i-1][j], dp[i-1][j - w[i]] + v[i]) \quad (j \ge w[i])$$

#### 2. 空间优化：一维滚动数组逆序遍历（面试最优解法）
* **核心关键点**：一维优化时，**背包容量 $j$ 必须从大到小逆序遍历**！因为逆序才能保证计算当前状态时，所引用的 $dp[j - w[i]]$ 依然是“上一层（还没放入当前物品）”的值，防止单件物品被重复放入。

```java
public class Knapsack01 {
    public static int maxValue(int V, int[] weight, int[] value) {
        int n = weight.length;
        // dp[j] 表示容量为 j 时的最大价值
        int[] dp = new int[V + 1];

        for (int i = 0; i < n; i++) {
            // 核心：逆序遍历，防止同一物品被多次装入
            for (int j = V; j >= weight[i]; j--) {
                dp[j] = Math.max(dp[j], dp[j - weight[i]] + value[i]);
            }
        }
        return dp[V];
    }
}
```

### 算法 2：最长不连续子序列 / 最长上升子序列（LIS）（DP $O(N^2)$ 与 贪心+二分 $O(N \log N)$）

> **💡 面试题解密**：面试官口中的“最长不连续子序列”，在算法中即指**最长上升子序列（Longest Increasing Subsequence, LIS）**（子序列本身就是非连续的元素组合）。

#### 解法 A：经典动态规划（$O(N^2)$，代码简洁，面试保底）
* **状态定义**：$dp[i]$ 表示以 $nums[i]$ 结尾的最长上升子序列的长度。
* **状态转移**：对于所有 $j < i$，若 $nums[i] > nums[j]$，则：
  $$dp[i] = \max(dp[i], dp[j] + 1)$$

```java
public class LongestIncreasingSubsequence {
    public int lengthOfLIS_DP(int[] nums) {
        if (nums == null || nums.length == 0) return 0;
        int[] dp = new int[nums.length];
        Arrays.fill(dp, 1);
        int maxLen = 1;

        for (int i = 1; i < nums.length; i++) {
            for (int j = 0; j < i; j++) {
                if (nums[i] > nums[j]) {
                    dp[i] = Math.max(dp[i], dp[j] + 1);
                }
            }
            maxLen = Math.max(maxLen, dp[i]);
        }
        return maxLen;
    }
}
```

#### 解法 B：贪心 + 二分查找（$O(N \log N)$，满分拔高解法）
* **核心思想**：为了让上升子序列尽可能长，我们要让子序列中每个位置上升的幅度**尽可能小**。
* 维护一个数组 `tail[k]`：表示目前所有长度为 $k+1$ 的上升子序列中，末尾元素的最小值。
* 遍历 `nums`，用二分查找定位 `num` 在 `tail` 中的插入位置；如果 `num` 比所有末尾都大，追加到末尾；否则替换掉第一个大于等于它的元素。

```java
public class LongestIncreasingSubsequenceBinary {
    public int lengthOfLIS(int[] nums) {
        if (nums == null || nums.length == 0) return 0;
        int[] tail = new int[nums.length];
        int res = 0; // 当前最长有效长度

        for (int num : nums) {
            int left = 0, right = res;
            // 二分查找第一个 >= num 的位置
            while (left < right) {
                int mid = left + (right - left) / 2;
                if (tail[mid] < num) {
                    left = mid + 1;
                } else {
                    right = mid;
                }
            }
            tail[left] = num;
            if (right == res) res++;
        }
        return res;
    }
}
```

## 第八部分：汉得信息高频考点加餐专题（MyBatis + Spring Cloud）

### 加餐 1：MyBatis 一级缓存与二级缓存原理、失效场景及生产踩坑

#### 1. 一级缓存（SqlSession 级别，默认开启）
* **底层结构**：基于 `PerpetualCache`，其内部本质就是一个 Java `HashMap`。
* **作用域**：仅在同一个 `SqlSession` 的生命周期内有效。
* **失效场景**：
  1. 执行了任何 `INSERT`、`UPDATE`、`DELETE` 操作（无论是否修改了同一张表，只要调用 `commit`，整个 SqlSession 缓存立即被清空）；
  2. 手动调用了 `sqlSession.clearCache()`；
  3. 两次查询传递的参数不同。
* **生产严重踩坑**：在 Spring Boot 环境下，如果方法**没有加 `@Transactional` 事务注解**，每次 MyBatis 执行查询都会新建一个全新的 `SqlSession`，执行完毕立即关闭！**此时一级缓存完全形同虚设，命中率为 0！**

#### 2. 二级缓存（Namespace / Mapper 级别，默认关闭）
* **作用域**：跨 SqlSession，只要是同一个 Mapper Namespace 即可共享。
* **开启条件**：
  1. 全局配置 `cacheEnabled=true`；
  2. 在对应 Mapper.xml 中加入 `<cache/>` 标签；
  3. 对应的 POJO 实体类**必须实现 `Serializable` 序列化接口**。
* **生产大坑（为什么大厂严禁开启 MyBatis 二级缓存？）**：
  * 二级缓存是**基于单机内存单应用**的。在现代微服务多实例集群环境下，实例 A 执行了修改，实例 B 的二级缓存根本感知不到，会导致**读取到陈旧严重的脏数据**。在分布式架构下必须使用 Redis 等集中式缓存替代。

### 加餐 2：MyBatis 中 `#{}` 和 `${}` 的底层本质区别与 SQL 注入防御

| 对比维度 | `#{}` (占位符) | `${}` (字符串直接拼接) |
| :--- | :--- | :--- |

### 加餐 3：Spring Cloud 服务发现机制与客户端负载均衡（Nacos / Eureka + LoadBalancer）

#### 1. 服务注册与发现底层全流程（以 Nacos / Eureka 为例）
1. **服务启动注册（Register）**：微服务实例启动时，读取 `bootstrap.yml` 中的注册中心地址，通过 HTTP RESTful 或 gRPC 向注册中心发送自身 IP、端口、服务名元数据；
2. **心跳保活（Heartbeat）**：客户端后台定时任务（默认每隔 5 秒）向注册中心发送轻量级心跳报文。若注册中心连续 15 秒未收到心跳标记为不健康，超过 30 秒剔除该实例；
3. **服务拉取与本地缓存（Pull / Cache）**：调用方（Consumer）通过注册中心获取提供者（Provider）的健康实例列表，并**缓存到本地 JVM 内存**中；同时开启定时拉取（每隔 30 秒）或长轮询/UDP 推送监听变更，即使注册中心全挂，本地缓存仍能保障正常服务调用。

#### 2. 客户端负载均衡（Spring Cloud LoadBalancer / Ribbon）vs 服务端负载均衡（Nginx）
* **服务端负载均衡（如 Nginx / F5）**：
  * 客户端直接将请求打到统一的 Nginx 代理服务器，由 Nginx 在其反向代理模块中决定将请求转发给哪台具体的后端实例；客户端不知道后端实例的拓扑存在。
* **客户端负载均衡（Spring Cloud LoadBalancer / OpenFeign）**：
  * **直接在 Consumer 服务内部执行负载算法**！
  * 调用方本地持有所有实例清单，通过内部拦截器（如 `LoadBalancerClientFilter`），在发出 HTTP/gRPC 请求前，在本地通过算法选出一台目标机器的真实 IP 和端口，直接建立网络连接发起通信。

#### 3. 常见负载均衡算法
* **轮询（Round Robin）**：基于原子计数器递增取模，请求均匀分布；
* **随机（Random）**：随机数生成器命中实例；
* **加权响应时间 / 响应时间最短（Weighted Response Time）**：统计各实例近期响应耗时，耗时越短权重越高，自动避开慢节点；
* **一致性哈希（Consistent Hash）**：相同参数/用户 ID 始终路由到同一台机器。
