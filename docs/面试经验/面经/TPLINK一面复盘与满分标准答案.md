## 一、 面试现场全景评估与面试官心理剖析

### 1. 为什么“整场都是我在说话，面试官没有引导”？
* **大批量校招面试的“打分表机制”**：TP-LINK 校招一面的技术官通常在半天内要面试 10~15 位候选人，每人严格控制在 20~25 分钟。面试官面前有一张标准评分表（包含：基础语言能力、数据库与中间件实操、项目深度、高并发理解）。
* **你的优势**：你能够主动、连贯、系统地阐述技术架构，省去了面试官苦思冥想“挤牙膏”的时间。面试官不打断，说明你在主动输出有效技术信息，正在对照你的陈述在后台勾选得分项。

### 2. 为什么“最后没有反问环节，直接结束了”？
* **严格的时间截断（Hard Cutoff）**：校招面试系统通常有下一个候选人排队叫号机制。当面试时间走到 22~24 分钟时，若所有考察项已大致问完，面试官会直接收尾交卷，给后台录入评价预留 1~2 分钟。**没有反问环节在校招一面中极其常见，绝非淘汰信号**。

### Q3：介绍一个项目并说说亮点（荒天商城订单库存与 AI 助手）

#### ⚠️ 现场回答核心 Bug 纠偏 1：Token 幂等的致命时序错误
* **现场表述**：“申请唯一 token，后端存储，开始支付，支付完成后，删除唯一 token，如果请求进来，唯一 token 还在，不处理。”
* **错误剖析**：
  * **逻辑完全颠倒！** 
  * 如果你“支付完成了才删 Token”，在用户点击支付后的 2 秒网络通信与落库时间内，**Token 始终存在于 Redis 中**。
  * 若用户网络卡顿短时间内连击了 3 次，第 2、第 3 次并发请求进来一查：“Token 还在！放行！”，导致并发请求全部进入后端重复支付，防并发重复点击彻底形同虚设！
* **正确规则**：**Token 必须在请求到达的一瞬间，通过 Lua 脚本原子执行“校验存在并立即删除（Check & Delete）”**！删成功的唯一请求放行，后续并发请求因 Token 已被删除直接阻断。

#### ⚠️ 现场回答核心 Bug 纠偏 2：库存术语的语病
* **现场表述**：“支付成功 回滚预占”
* **错误剖析**：
  * 支付成功绝不能叫“回滚（Rollback）预占”！“回滚”在数据库中代表“取消并恢复原状”。
  * 正确术语是：**“支付成功：核销/释放预占，执行真实物理扣减（Deduct）”**；只有在**超时未付或主动取消时**，才叫“解冻/回滚预占”。

#### 🏆 Q3 满分标准回答话术：
> “我的荒天商城项目主要有两个核心技术攻坚点：
> 
> **第一个是订单库存的‘预占与实扣两阶段一致性’**：
> * **下单阶段（只做预占）**：通过 Redisson 分布式锁与 Lua 脚本在 Redis 层面执行原子预占（`available_stock - 1, locked_stock + 1`），此时数据库物理总库存完全不动；同时将订单挂入 Redis ZSet 延时队列开启 10 分钟超时倒计时；
> * **支付阶段（真实出库）**：支付回调进来后，先校验订单处于待支付态，通过事务更新 MySQL 物理总库存（`locked_stock - 1, total_stock - 1`），提交成功后再删除 Redis 预占记录，并从延时队列中移除订单；
> * **防重防抖（幂等 Token 机制）**：进入结算页生成单次 Token，提交时利用 **Redis Lua 脚本原子执行‘检查存在即刻删除（Check & Del）’**，删成功者放行，其余并发请求因找不到 Token 直接拦截，彻底杜绝并发重复下单。
> 
> **第二个是 AI 购物助手的 ReAct 决策循环与安全风控**：
> * 基于 **WebFlux 响应式架构** 实现 `Thought -> Action -> Observation` 的闭环迭代；
> * 自主设计了**跨 Chunk 工具参数累积状态机（`ToolCallAccumulator`）**，解决大模型流式输出时碎片 JSON 字符串无法解析的难题，并设置 8 次最大迭代熔断；
> * **人在回路（HITL）风控**：大模型绝不能直接写库扣款，敏感操作只在 Redis 生成 15 分钟临时动作草稿（Draft），以交互卡片形式推送给前端，必须由用户在前端界面显式点击‘确认下单’才真正落库。”

### Q4：接口幂等除了唯一 Token，还有什么其他实现方式？

#### ⚠️ 现场回答核心 Bug 纠偏 3：去重表“业务结束删除”的严重漏洞
* **现场表述**：“在第一次点击支付时，就往去重表插入全局唯一标识，利用数据库的唯一索引，如果重复点击，插入失败说明业务还在进行中，业务结束删除这行去重表数据。”
* **错误剖析**：
  * **如果业务结束后删除了这行数据，幂等性在事后就会被击穿！**
  * 设想：业务执行成功了，去重表这行被删除了。但此时由于网络超时，前端未收到响应，浏览器自动重试，或者用户 5 秒后以为没成功又点了一次。
  * 此时去重表是空的，重试请求**再次插入成功并执行了支付**，引发灾难性的二次扣款！
* **正确规则**：去重表的数据**在业务结束后绝不能删除**，而是把状态从 `PROCESSING` 改为 `SUCCESS`（或者设置保留数天的生命周期）。重试请求进来命中唯一索引异常后，反查状态为 `SUCCESS`，直接幂等返回成功结果！

#### 🏆 Q4 满分标准回答话术（四大经典流派）：
> “除了 Token 机制，在工业级分布式架构中，根据不同业务场景还有以下 4 种经典的幂等实现方式：
> 
> 1. **数据库防重表 / 唯一索引法（存储层强一致保障）**：
>    * 以全局业务唯一 ID（如 `order_sn` 或支付流水号）在去重表建立**唯一索引（Unique Constraint）**；
>    * 请求到达时先插入该表，初始状态为 `PROCESSING`；并发请求因唯一索引冲突抛出 `DuplicateKeyException` 被直接阻断；
>    * **关键细节**：业务处理完毕后，**必须将状态更新为 `SUCCESS` 而坚决不能删除记录**！这样若后续发生网络超时引发客户端重试，系统捕获冲突后一查状态已是成功，直接给前端返回成功，绝不二次执行业务。
> 2. **业务状态机乐观更新法（更新类接口的天然幂等）**：
>    * 利用业务实体自身的单向状态机，在 SQL 更新时附加当前合法前置条件：
>      `UPDATE tb_order SET status = 'PAID' WHERE order_sn = ? AND status = 'PENDING';`
>    * 第一次执行成功（`affected_rows = 1`）；如果重复请求或重试进来，由于订单状态已变为 `PAID`，更新条件不满足，`affected_rows = 0`，天然具备幂等性。
> 3. **Redis 分布式互斥锁 / 短暂防抖标记（高并发轻量防刷）**：
>    * 请求进来时执行原子指令：`SET lock:idempotent:{userId}:{bizKey} 1 EX 5 NX`；
>    * 仅有抢到锁的线程允许向下执行，5 秒内同一用户的连击或网络抖动重试均直接返回‘请求处理中，请勿频繁点击’。
> 4. **数据库乐观锁版本号机制（数据变更接口）**：
>    * 表结构增加 `version INT DEFAULT 0`；
>    * 更新时带上版本号：`UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = #{oldVersion};`
>    * 若版本已被并发修改则更新失败，由应用层决定自旋或抛出冲突。”

### Q5：分布式锁除了 Redis 还有什么实现方式？Redisson 和原生 Redis 有什么区别？

#### ⚠️ 现场回答认知误区：为什么本地锁不行？
* **现场表述**：“`synchronized` 和 `ReentrantLock` 肯定不行，因为会阻塞线程……”
* **深层原理纠偏**：
  * 面试官听到你说“因为阻塞线程所以不能做分布式锁”，会立刻判定你没搞懂**进程边界**！
  * 本地锁在单机下阻塞线程是完全正确的。但在分布式环境下不能用的唯一根本原因，是**操作系统的虚拟内存隔离与 JVM 进程边界**！
  * `synchronized`（对象头 MarkWord 监视器）和 `ReentrantLock`（AQS）的锁状态全保存在**单台服务器的单个 JVM 进程堆内存中**。分布式部署有 10 台微服务节点，A 节点的 JVM 内存根本无法约束 B 节点的线程，因此必须借助**跨进程的独立第三方中间件**（如 Redis、ZooKeeper、MySQL）来实现分布式锁。

#### 🏆 Q5 满分标准回答话术：
> “**首先，单机锁无法做分布式锁的根本原因在于 JVM 内存隔离**：`synchronized` 和 `ReentrantLock` 的锁状态依赖于单机 JVM 进程内的对象监视器或 AQS 状态。在分布式多节点集群中，各个微服务的内存空间绝对独立互不相通，必须依赖中心化的第三方存储协调锁状态。
> 
> 除了 Redis，业界主流的分布式锁实现还有以下两种：
> 1. **基于 ZooKeeper / etcd（CP 强一致性模型，高安全场景首选）**：
>    * **原理**：基于 ZK 的**临时顺序节点（Ephemeral Sequential）+ Watcher 监听机制**；
>    * 客户端在锁目录下创建临时有序节点，只有序号最小的节点持有锁；其余节点仅监听前一个节点的删除事件；
>    * **核心优势**：**彻底杜绝了 Redis 的‘锁提前过期’问题**。因为是临时节点，如果业务节点挂掉或断网，心跳断开后 ZK 会自动删除临时节点释放锁，安全可靠，属于强一致性模型。
> 2. **基于 MySQL 关系型数据库（无额外中间件时的轻量方案）**：
>    * **方式一（排他行锁）**：在事务中执行 `SELECT ... FOR UPDATE` 显式锁定行；
>    * **方式二（唯一防重表）**：建立包含 `lock_name` 唯一索引的锁表，`INSERT` 成功代表加锁，事务提交或 `DELETE` 代表释放锁。
> 
> ---
> 
> **关于 Redisson 与原生 Redis 的区别**：
> **Redis 是底层的存储引擎，而 Redisson 是针对分布式并发场景进行了工业级封装的 Java 客户端 SDK。**
> 如果直接用原生 Redis（`SETNX + EX`）实现分布式锁，存在三大致命暗坑：
> 1. **锁超时不可控**：如果预设 10 秒过期，但业务执行了 15 秒，锁在第 10 秒自动过期，引发其他线程并发进入（锁穿透）；
> 2. **锁被他人误删**：线程 A 执行慢，锁过期后线程 B 拿到了锁；此时 A 执行完调用 `DEL key`，会把 B 刚刚获取的锁误删；
> 3. **不可重入**：单 Key 字符串无法支持同一线程内的重入调用。
> 
> **Redisson 帮我们彻底解决了这些问题**：
> 1. **看门狗机制（Watch Dog）**：获取锁后自动启动后台定时线程，默认每隔 10 秒检查一次，若业务未执行完自动将锁超时时间续租为 30 秒，绝不提前释放；
> 2. **Hash 结构实现可重入锁**：底层采用 Redis Hash 存储 `线程唯一标识 -> 重入次数`，同一线程多次加锁自增，退出时递减，计数归零才完全释放；
> 3. **完备的企业级高级锁**：开箱即用支持公平锁、读写锁、联锁（`MultiLock`）以及红锁（`RedLock`）。”

### Q6：Function Calling 是什么？底层工作机制是什么？

#### 🏆 Q6 满分标准回答话术：
> “**Function Calling（函数调用）是大模型官方提供的一种协议规范，它是连接非结构化自然语言与确定性业务系统之间的桥梁。**
> 
> 很多初学者误以为‘大模型直接帮我们执行了后台代码’，**其实完全不是，大模型本身没有任何执行环境权限**。其真实的底层执行流转包含三个严密的阶段：
> 
> 1. **接口声明阶段（Declaration）**：
>    * 后端向大模型发送请求时，通过 `tools` 字段传入本地受控函数的签名声明（采用标准的 **JSON Schema** 规范，详细描述函数名、业务用途、必需参数与字段类型）；
> 2. **意图决策阶段（LLM Reasoning & Output）**：
>    * 大模型扮演**‘意图识别与参数提取器’**。当它分析用户自然语言发现需要调用外部系统时，它会**放弃输出自然语言正文**，而是返回一个结构化的 `tool_calls` 报文，精准输出要调用的函数名以及拼装好的参数 JSON（例如 `{"goods_id": 1001, "buy_num": 2}`）；
> 3. **本地执行与闭环反喂阶段（Local Execution & Feed）**：
>    * 我们的后端服务拦截到这个工具调用事件，暂停文本推流，由本地的 `ToolExecutionDispatcher` 在安全的 Spring 容器中执行真实的业务代码或数据库查询；
>    * 执行完毕后，把真实的执行结果封装为 `role: "tool"` 的消息作为 **Observation**，再次追加发送给大模型，供大模型总结并输出最终的自然语言答案。
> 
> **总结**：Function Calling 赋予了大模型调用真实世界 API 的‘四肢’，是构建自主决策智能体（Agent）的基石。”

### Q7：你说使用了 Docker，聊聊 Docker 的好处与底层原理？

* **现场点评**：只答“部署方便、隔离空间”略显偏学生化。要从 **Linux 内核底层机制（Namespaces / Cgroups）** 与 **传统虚拟机架构对比** 切入，展现出深厚的基础内功。

#### 🏆 Q7 满分标准回答话术：
> “在实际工程开发与交付中，Docker 的核心价值与底层优势主要体现在以下四个维度：
> 
> 1. **‘一次构建，随处运行’（绝对的环境一致性）**：
>    * 传统运维中最头疼的是‘开发本地能跑、生产部署报错’的环境差异。Docker 将应用代码、运行时依赖环境（JRE、动态链接库）与系统级配置文件整体打包为不可变的**镜像（Image）**，确保从本地开发、测试沙箱到生产集群环境的 100% 镜像级一致。
> 2. **极速冷启动与极致轻量（相比虚拟机的降维打击）**：
>    * **传统虚拟机（VM）**：底层依赖 Hypervisor 虚拟化整套硬件，并在宿主机上额外运行一个庞大的 Guest OS 客户操作系统，动辄占用数 GB 内存，启动需数分钟；
>    * **Docker 容器**：**直接共享宿主机的操作系统内核**，容器本身在宿主机看来仅仅是一个普通的独立进程。内存开销仅几兆到几十兆，毫秒级启动与销毁。
> 3. **Linux 内核底层的安全隔离技术（底层面试高分点）**：
>    * Docker 的隔离完全依赖 Linux 内核的原生机制：
>      * 通过 **Namespaces（命名空间）** 实现视角隔离（PID 进程号、Network 网络栈、Mount 挂载点、IPC 进程间通信等各不干扰）；
>      * 通过 **Cgroups（控制组）** 实现物理资源的配额限制（硬性限制单个容器最多使用 2 核 CPU、4GB 内存，杜绝容器间抢占资源）。
> 4. **分层存储与极致带宽节约（UnionFS / Overlay2）**：
>    * 镜像采用联合文件系统分层构建，下层基础镜像（如 `openjdk:17-alpine`）完全只读共享。构建和发布微服务时，只需要上传变化的应用层增量碎片，大幅节省磁盘与网络拉取带宽，为云原生 K8s 自动化伸缩奠定了基石。”

## 三、 终局备战启示录（后续面试必须刻在脑海中的 3 大红线）

1. **红线 1：Token 幂等必须是“先查并删（Check & Delete 原子化）”**
   * 永远记住：Token 是“门票”，验票的瞬间门票就要作废撕毁。绝不能把事情做完了才删门票，否则并发全进来了！
2. **红线 2：去重表的数据绝不能业务做完就随手删除**
   * 去重表是“留存证据的存根”。存根如果销毁，网络超时的重试请求就会引发二次执行！去重表记录要靠状态机推进（`PROCESSING -> SUCCESS`），过期清理靠后台定期滚动或 TTL。
3. **红线 3：谈到分布式锁，第一反应必须是“进程内存隔离”**
   * 任何单机锁（`synchronized`, `ReentrantLock`）失效的根本原因只有一句话：**多机部署下，各个 JVM 虚拟机的内存地址空间是物理隔离的，本地锁无法跨越网络去影响别的服务器**。
