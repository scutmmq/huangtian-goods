### Q2：1000 个键值对存到 HashMap 中，如何设计才不会频繁扩容？（数学推导与源码实现）

#### 1. 核心数学推导与源码机制
* **HashMap 扩容阈值公式**：
  $$	ext{Threshold} = 	ext{Capacity} 	imes 	ext{LoadFactor}$$
  默认负载因子（LoadFactor）是 **0.75**。
* **要存 1000 个元素且不发生扩容**，必须满足：
  $$	ext{Capacity} 	imes 0.75 \ge 1000 \implies 	ext{Capacity} \ge rac{1000}{0.75} pprox 1333.33$$
* **为什么不能直接传 1024？**
  * 如果传 `1024`，阈值为 $1024 	imes 0.75 = 768$。当插入第 769 个键值对时，就会**立即触发一次昂贵的全量 rehash 扩容到 2048**！
* **HashMap 底层 `tableSizeFor` 的 2 的幂次方机制**：
  * 在构造方法 `new HashMap<>(initialCapacity)` 中，JDK 不会直接使用你传入的数字，而是通过位运算方法 `tableSizeFor(initialCapacity)`，找到**大于等于该值的最小 2 的幂次方**：
  * 寻找大于等于 1334 的最小 2 的幂，即为 **2048**！
* **阿里巴巴《Java开发手册》规约**：
  ```java
  // 最佳初始化公式：(int) ((float) expectedSize / 0.75F + 1.0F)
  int initialCapacity = (int) ((float) 1000 / 0.75F + 1.0F); // 结果为 1334
  Map<String, Object> map = new HashMap<>(initialCapacity); // 内部自动计算为 2048
  // 或者在 Guava 中直接使用：
  Map<String, Object> map = Maps.newHashMapWithExpectedSize(1000);
  ```

> 🗣️ **面试一分钟满分背诵**：
> “为了让存入 1000 个键值对时不发生任何扩容，我们需要将容量设为大于等于 $1000 / 0.75 = 1333.33$。
> 又因为 HashMap 底层数组长度强制要求为 2 的幂次方（通过 `tableSizeFor` 位运算实现），因此大于 1334 的最小 2 的幂是 **2048**。
> 最佳实践是调用 `new HashMap<>(1334)`，或者使用 Guava 的 `Maps.newHashMapWithExpectedSize(1000)`，内部会自动将 capacity 初始化为 2048，阈值为 1536，存入 1000 个元素绝不会触发一次扩容和数组搬迁。”

### Q3：Lua + Redis 除了做原子操作，在工程中还能做什么？（性能、限流、计算就地化）

除了“原子执行命令”这个最基础的功能外，在大型工业级系统里，Lua + Redis 还有四大核心杀手锏：

1. **大幅减少网络 RTT（往返时延），实现“多命令网络管道聚合”**：
   * 如果一段业务逻辑需要先 `GET`，在 Java 代码里判断，再 `HSET`，再 `EXPIRE`，需要 3 次网络往返（3 次 RTT）。在跨机房或微服务网络抖动时耗时翻倍；
   * 使用 Lua 脚本，把多条命令和判断逻辑全部打包成一段脚本，**只需 1 次网络请求**即可在 Redis 服务端内部执行完毕，极大减少了网络交互开销和连接占用。
2. **实现高精度的复杂分布式限流算法（滑动窗口 / 令牌桶）**：
   * 单纯用 Redis 命令无法优雅实现高精度的**滑动时间窗口限流**或**平滑令牌桶（Token Bucket）**。
   * 通过 Lua 脚本，可以把“获取当前时间戳、删除窗口外的过期记录（`ZREMRANGEBYSCORE`）、统计当前窗口数量（`ZCARD`）、超限则阻断否则加入当前请求（`ZADD`）”一气呵成完成。
3. **计算就地化与数据就地过滤（Data Locality，节省网络带宽）**：
   * 假设 Redis 中存了一个包含 5 万个元素的大 Hash 或大 Set，业务只需要其中符合某些特定条件的 10 条数据；
   * 如果在 Java 侧做，需要用 `HGETALL` 把 5 万条数据全拉回应用内存（打爆网络带宽和 JVM 堆），再做过滤；
   * 使用 Lua 脚本，直接在 Redis 内存端进行循环遍历和条件过滤，**只将最终计算好的 10 条结果返回给客户端**，极大节省内网带宽。
4. **分布式锁的安全释放与看门狗续期条件校验**：
   * 释放锁时必须“校验锁的持有者 `threadId` 是否是自己，是自己才删除”，这两步必须由 Lua 保证逻辑原子性；Redisson 的 Watchdog 看门狗自动续期（校验是否仍由本线程持有，是则刷新 TTL）同样重度依赖 Lua。

### Q4：JWT 实现的 Token 你是如何设置有效期并管理的？（双 Token 无感刷新 + Redis 黑名单主动失效）

#### 1. 痛点：纯无状态 JWT 的“失控缺陷”
* JWT 是自包含无状态的，一旦签发出去，**在到期之前服务端无法主动让其失效**！
* 导致两大安全灾难：① 用户修改了密码或被封号，旧 Token 依然能调用接口；② 用户点击“退出登录”，无法真正踢下线。

#### 2. 工业级最佳实践架构：双 Token + Redis 混合管理模式

```
[前端客户端] ──(携带短命 Access Token 15分钟)──> [网关/鉴权服务 (本地纯公钥验签，零Redis网络开销)]
     │
 (过期报 401)
     ▼
[前端请求拦截器] ──(携带长命 Refresh Token 7天)──> [认证中心 (比对 Redis 白名单/版本号)]
                                                            │
                                                     (签发全新 Access Token)
```

1. **双 Token 机制（区分使用频率与寿命）**：
   * **`Access Token`（短期访问令牌，15~30 分钟）**：前端放在内存或请求 Header 中，只负责高频接口鉴权。服务端无需查库查 Redis，直接解密验证签名，极致高性能；
   * **`Refresh Token`（长期刷新令牌，7 天）**：存放在 HttpOnly Secure Cookie 或本地安全存储中，且在 Redis 中存一份映射 `refresh_token:{userId}`；
   * **无感刷新（Silent Refresh）**：当 Access Token 过期时，前端网络拦截器（Axios Interceptor）拦截 401 错误，静默调用刷新接口换取新 Access Token，用户完全无感知。
2. **主动注销与权限变更管理（Redis 黑名单 + 用户版本号）**：
   * **场景 A：用户主动点击“退出登录”**：
     * 后端将该 JWT 的唯一标识 `jti`（JWT ID）写入 Redis 黑名单：`SET blacklist:{jti} 1 EX {剩余过期秒数}`；
     * 网关在必要接口校验该 key 是否在黑名单中。
   * **场景 B：修改密码 / 强制踢人下线 / 封号**：
     * 在 Redis 维护每个用户的全局令牌版本号：`user_token_version:{userId} = 2`；
     * JWT Payload 内部携带当前版本号 `version: 1`；
     * 每次请求比对版本号，若小于 Redis 中的最新版本号，直接拒绝访问。

### Q5：Spring 限流如何做？（单机 Guava 令牌桶 vs 分布式 Redis+Lua 与 Sentinel 规则中心）

在微服务架构中，限流分为 **单机进程内限流** 和 **分布式集群限流** 两个层次：

#### 1. 单机维度限流：Guava `RateLimiter`（令牌桶算法）
* **底层原理**：基于 Google Guava 的 **令牌桶算法（Token Bucket）**。
* **核心优势**：支持平滑突发流量。系统以恒定速率往桶里放令牌（如每秒 100 个），桶满则溢出；请求到来时必须先拿到令牌才能放行：
  ```java
  // 每秒生成 100 个令牌
  private RateLimiter rateLimiter = RateLimiter.create(100.0);

  public String doBusiness() {
      // 尝试在 500ms 内获取令牌，拿不到直接降级
      if (!rateLimiter.tryAcquire(500, TimeUnit.MILLISECONDS)) {
          return "系统繁忙，请稍后重试（限流降级）";
      }
      return orderService.createOrder();
  }
  ```
* 结合 Spring：可通过自定义注解 `@RateLimit` + Spring AOP 切面无侵入拦截 Controller 接口。

#### 2. 分布式维度限流（集群全局限流）：两种主流工业级方案
1. **Redis + Lua 滑动窗口 / 令牌桶限流**：
   * **适用场景**：轻量级微服务，无需引入重型中间件；
   * **实现方式**：以 `IP` 或 `userId + 接口名` 作为 Redis Key，通过一段原子的 Lua 脚本统计单位时间窗口（如 1 分钟）内的访问次数；超出配置阈值则直接返回 HTTP 429 Too Many Requests。
2. **Spring Cloud Gateway + Sentinel 规则中心（大厂首选）**：
   * **入口网关限流**：在微服务最外层的 Gateway 部署 Sentinel 过滤器，根据路由 Route ID 或客户端 IP 进行集群限流；
   * **业务内部熔断降级**：Sentinel 支持**QPS 限流、并发线程数限流、自适应系统保护（CPU 使用率超 80% 自动限流）**，配合 Nacos 实现限流规则秒级动态热推送。

### Q6：有做过 JVM 线上调优吗？（排障 SOP、jstat/jstack、老年代不降实锤泄漏、四大保命参数）

> 详见《海柔创新终极通关宝典》模块四 Q18，核心回答架构三步走：

1. **破除唯参数论（专业定调）**：调优是“目标驱动、代码治理为主、参数配置为辅”。现代 G1 追求自适应调节，盲目微调 `-Xmn` 反而破坏自平衡；
2. **现场排查与实战定位 SOP（把你的真实经历升华）**：
   * 收到老年代告警，第一步用 `jstat -gcutil <pid> 1000` 实时观测；
   * **核心铁律**：**如果 Full GC 后老年代迅速回落，说明是短时间突发并发大对象（如未分页全表查询）；如果 Full GC 持续进行但老年代死死卡在 95% 以上丝毫不降，实锤代码存在内存泄漏（对象被 GC Root 强引用）**！
   * 针对泄漏，使用 MAT 分析 Dump 文件的**支配树（Dominator Tree）**顺着 GC Roots 溯源到具体代码行（如 `ThreadLocal` 未 `remove()`），从代码层根治；
3. **部署时主动固化的 4 大保命参数**：
   * `-Xms4g -Xmx4g`：堆对齐，杜绝内存伸缩引发的全局 STW 抖动；
   * `-XX:MetaspaceSize=256m`：锁定元空间，防止启动期频繁类加载触发 Full GC；
   * `-XX:+HeapDumpOnOutOfMemoryError`：倒下前最后一秒自动保存内存快照；
   * `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0`：感知容器 Cgroups 限制，防止内存越界被 K8s 直接杀掉（OOMKilled 退出码 137）。

### Q7：MySQL 的间隙锁（Gap Lock）深度解析（产生原因、解决幻读、间隙锁死锁经典场景）

#### 1. 什么是间隙锁？为什么需要它？
* **产生背景**：在 MySQL InnoDB 存储引擎的 **可重复读（Repeatable Read, RR）** 隔离级别下，单纯的行锁（Record Lock）只能锁住已经存在的记录，无法锁住记录之间的“缝隙”。
* **间隙锁的作用**：锁定一个**开区间 `(A, B)`**，不包含记录 A 和 B 本身。**间隙锁的唯一目的就是：阻止其他事务在这个间隙中执行 `INSERT` 插入新记录，从而彻底消灭“幻读（Phantom Read）”！**
* **临键锁（Next-Key Lock）**：行锁 + 间隙锁的组合，锁定的是**左开右闭区间 `(A, B]`**，是 InnoDB 在 RR 级别下的默认加锁单位。

#### 2. 间隙锁在什么时候会产生？
1. **非唯一索引等值查询**：当对普通索引进行等值查询命中记录时，不仅给当前记录加行锁，还会给该记录前后的两个间隙加上 Gap 锁；
2. **唯一索引/主键查询不存在的记录**：比如表里有 ID=1, 5, 10，执行 `SELECT * FROM t WHERE id = 7 FOR UPDATE;`，由于 7 不存在，锁会退化为间隙锁，锁住 `(5, 10)` 这个开区间；
3. **范围查询**：执行 `SELECT * FROM t WHERE id > 10 FOR UPDATE;`，不仅锁住现有的记录，还会把 `(10, +∞)` 的所有间隙全锁上。

#### 3. 生产高频间隙锁死锁经典案例（重点考点！）
* **面试官最爱问**：“间隙锁之间会冲突吗？为什么会引发死锁？”
* **关键真相**：**间隙锁与间隙锁之间是相互兼容的！多个事务可以同时持有同一个区间的间隙锁！**
* **死锁产生时序图**：
  ```
  时间点   事务 A                                事务 B
    T1    SELECT * FROM t WHERE id = 7 FOR UPDATE; (持有 (5, 10) 间隙锁)
    T2                                          SELECT * FROM t WHERE id = 8 FOR UPDATE; (也持有 (5, 10) 间隙锁，兼容成功！)
    T3    INSERT INTO t VALUES (7); (被阻塞！等待事务 B 的间隙锁释放插入意向锁)
    T4                                          INSERT INTO t VALUES (8); (被阻塞！等待事务 A 的间隙锁释放插入意向锁)
    -->   【双方循环等待对方释放间隙锁，瞬间触发 Deadlock 死锁，MySQL 自动回滚其中一个事务！】
  ```

### Q8：Kafka 如何防重复消费？（自动提交弊端、业务唯一键、Redis防重表、状态机乐观锁）

1. **根源剖析**：
   * 消费者消费完业务逻辑，在提交 Offset 前，消费者服务崩溃或发生网络抖动触发了 **Consumer Group Rebalance**；
   * 新的消费者接管该 Partition 时，从上次未提交的 Offset 重新拉取，必然造成同一条消息被二次消费。
2. **防重三大法宝**：
   * **法宝 1：数据库唯一键约束（Unique Key）**：
     * 以消息全局唯一业务流水号（如 `order_sn`、`task_uuid`）作为唯一索引。重复消费时直接捕获 `DuplicateKeyException` 忽略，安全防重。
   * **法宝 2：Redis `SETNX` 幂等防重表**：
     * 处理前执行 `redis.setnx("PROCESSED_MSG:" + msgId, 1, 24, TimeUnit.HOURS)`；
     * 若返回 false，说明已经处理过，直接手动 commit offset 并跳过。
   * **法宝 3：状态机前置乐观锁流转**：
     * 更新时带前置状态校验：`UPDATE t_task SET status = 'DONE' WHERE id = 101 AND status = 'RUNNING'`；重复执行时受影响行数为 0，业务逻辑安全短路。

### Q9：A 服务是仓储系统，B 服务需要拿到准确的仓储数据，如何设计？（强一致 vs 最终一致性全景方案）

在海柔创新这种“仓储管理（A）与智能调度/销售服务（B）”的场景中，如何让 B 服务拿到准确的库存/库位数据，需要分场景设计：

#### 方案一：高频只读但允许微小延迟（最终一致性，性能最高，大厂主流）
* **架构**：**CDC（Change Data Capture）Canal 监听 A 库 Binlog + Kafka 异步同步 + B 本地/Redis 缓存**；
* **流程**：
  1. A 服务负责所有仓储数据的唯一写入口，更新 A 数据库；
  2. 部署 Canal 实时解析 A 库的 Binlog，将库存/库位变更事件发送到 Kafka；
  3. B 服务订阅 Kafka，将最新仓储数据更新到 B 自己的 Redis 缓存或本地数据库中；
  4. B 业务直接查自己的本地缓存，零 RPC 跨网络调用，QPS 达到几十万级。
* **兜底对账**：每隔 1 小时启动一次后台异步对账任务，比对 A 与 B 的数据校验和（Checksum），发现差异自动拉取 A 的最新快照做补偿覆盖。

#### 方案二：核心出库扣减必须强一致（强一致性，零延迟）
* **架构**：**A 服务暴露只读副本 RPC / 分布式锁控制**；
* **流程**：
  1. B 服务在执行高危决策（如分配搬运机器人、核验库存是否充足）时，必须通过 gRPC / OpenFeign 强同步调用 A 服务的查询接口；
  2. A 服务内部通过 Redis 预扣缓存（带版本号）查询，未命中走 MySQL 读写分离的主库实时读取；
  3. 涉及资金和扣减操作，采用分布式事务（如 Seata TCC 模式）或基于数据库版本号的 CAS 乐观锁进行最终确认。

### Q10：如果网络卡顿导致消息发送失败，如何处理？（重试退避、本地消息表、降级兜底、幂等结合）

在机器人调度与分布式微服务中，网络闪断是常态，必须建立**“重试 $ightarrow$ 本地落库 $ightarrow$ 补偿对账”**的三层容错：

1. **第一层：生产者客户端自动重试 + 指数退避（Exponential Backoff）**：
   * 发生超时或网络抖动，配置生产者重试次数 `retries = 3`，重试间隔指数递增（如 100ms $ightarrow$ 200ms $ightarrow$ 400ms），避免网络刚抖动时大量重试引发“惊群效应”把 Broker 打崩。
2. **第二层：本地消息表（Local Message Table，最可靠兜底机制）**：
   * 如果网络彻底断开（重试 3 次仍失败）：
   * 业务事务内将消息同时写入本地数据库的 `local_message_log` 表中，状态记为 `STATUS = PENDING`；
   * 后台启动定时任务（基于 XXL-JOB 或 Spring Task），每隔 10 秒扫描未发送成功的消息重新投递；成功后将状态置为 `SUCCESS`；超限 5 次报警并转入人工死信队列。
3. **第三层：必须结合消费者端幂等防重**：
   * 网络卡顿导致的重试，极大概率是**Broker 已经写成功但客户端没收到 ACK**！因此下游消费端**必须具备 Q8/Q11 中的唯一键幂等校验**，彻底杜绝重试导致的数据多发多扣。

### Q11：消息幂等有哪些方法？（生产者与消费者端 5 大核心手段）

| 层面 | 幂等手段 | 核心实现与业务落地 |
| :--- | :--- | :--- |
| **生产者端** | **Kafka 幂等生产 (PID + Seq)** | 配置 `enable.idempotence=true`。Broker 内存记录每个 Producer 的序列号，重复发送自动去重但返回 ACK。 |
| **消费者端** | **1. 数据库唯一索引 (Unique Key)** | 以业务流水号（如 `order_no`、`msg_uuid`）建立数据库唯一索引，并发重复消费直接报唯一键冲突被捕获忽略。 |
| **消费者端** | **2. Redis `SETNX` 防重标记** | 消费前执行 `redis.setnx(key, 1, 24h)`，若返回 0 代表处理中或已处理，直接跳过并提交 Offset。 |
| **消费者端** | **3. 状态机前置乐观锁流转** | 更新 SQL 带前置状态条件：`UPDATE t SET status='SUCCESS' WHERE id=1 AND status='INIT'`。重复执行受影响行数为 0。 |
| **消费者端** | **4. 一次性 Token 令牌机制** | 下发任务前服务端生成唯一 Token 放入 Redis，消费执行时调用 Lua 原子 `GET + DEL` 校验并删除令牌，无法二次使用。 |

### Q12：ABC 三个线程，需要 AB 并行，C 与 AB 同步（等 AB 都执行完再执行 C），如何做？（四种工业级解法）

#### 解法 1：`CompletableFuture.allOf()`（现代 Java 8+ 最优解，非阻塞无锁）
```java
CompletableFuture<Void> futureA = CompletableFuture.runAsync(() -> doTaskA());
CompletableFuture<Void> futureB = CompletableFuture.runAsync(() -> doTaskB());

// AB 并行执行，全部完成后自动异步执行 C
CompletableFuture.allOf(futureA, futureB)
                 .thenRun(() -> doTaskC());
```

#### 解法 2：`CountDownLatch(2)`（经典 JUC 闭锁解法）
```java
CountDownLatch latch = new CountDownLatch(2);

new Thread(() -> {
    try { doTaskA(); } finally { latch.countDown(); } // A 完成，计数 -1
}).start();

new Thread(() -> {
    try { doTaskB(); } finally { latch.countDown(); } // B 完成，计数 -1
}).start();

new Thread(() -> {
    try {
        latch.await(); // C 线程阻塞等待计数归零
        doTaskC();
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
}).start();
```

#### 解法 3：`Thread.join()`（最简基础原生解法）
```java
Thread threadA = new Thread(() -> doTaskA());
Thread threadB = new Thread(() -> doTaskB());

threadA.start();
threadB.start();

// 在主线程或 C 线程中等待 A 和 B 执行完毕
threadA.join();
threadB.join();
doTaskC();
```

#### 解法 4：`CyclicBarrier(2, taskC)`（循环栅栏解法）
* 设定栅栏大小为 2，栅栏打开时的触发动作（Barrier Action）设置为任务 C。线程 A 和 B 分别执行完毕后调用 `barrier.await()`，两个线程都到达栅栏时，自动优先执行任务 C。

### Q13：100 个文件，有一段文字，需要找到语义最相似的段落，如何设计？（完整 RAG 向量检索架构）

这是一道典型的 **RAG（检索增强生成）与高维向量相似度检索工程架构设计题**：

```
【离线知识入库链路】
100个文本文件 ──> [递归切块 300~500字 + 50 Overlap] ──> [Embedding 模型向量化 (1024维)] ──> [写入 pgvector / Milvus 构建 HNSW 索引]

【在线语义相似度匹配】
用户给定文字 ──> [生成 Query 向量] ──> [HNSW 向量余弦检索 Top-20] ──> [Cross-Encoder 重排模型打分] ──> 精选 Top-1 最相似段落
```

#### 完整设计步骤：
1. **第一步：文档解析与递归切块（Chunking）**：
   * 读取 100 个文件，清洗掉乱码；
   * 采用 `RecursiveCharacterTextSplitter` 按照自然段落递归切块为 **300~500 字符**的片段，设置 **50 字符滑动重叠（Overlap）**，防止关键长句被生硬切断；每个 Chunk 记录元数据 `{"doc_id": "file_01.txt", "chunk_index": 5}`。
2. **第二步：向量化与底层索引构建（Embedding & HNSW）**：
   * 调用文本嵌入模型（如 `text-embedding-v3` 或 `bge-large-zh`）将切块转化为 1024 维密集浮点向量；
   * 存入支持向量计算的数据库（如 PostgreSQL `pgvector`）；
   * 构建 **HNSW（分层可导航小世界图）** 索引，将搜索复杂度从穷举的 $O(N)$ 降至 $O(\log N)$。
3. **第三步：在线语义匹配与重排序（Reranking）**：
   * 将待比对的目标文字同样转化为 1024 维向量；
   * 在向量库中做 HNSW 余弦距离（Cosine Distance）快速初筛出前 20 个候选段落（Top-20）；
   * 将目标文字与这 20 个段落送入 **Cross-Encoder 交叉编码重排模型（bge-reranker-large）** 做逐字全注意力打分，精准剔除伪相关，输出相似度得分最高的 Top-1 黄金段落！
