## 一、 集合篇：隐藏在数据结构背后的乘数与双重阈值

### 陷阱 1：HashMap 初始容量陷阱（1000 为什么绝对不能设 1024？）

* ❌ **直觉错误**：计算机里都是 2 的幂次方，大于等于 1000 的最小 2 的幂是 1024，所以 `new HashMap<>(1024)` 正好装下 1000 个元素，不会扩容。
* 💡 **底层真相**：
  * HashMap 中真正决定何时扩容的不是数组长度（Capacity），而是 **扩容阈值（Threshold）**：
    $$\text{Threshold} = \text{Capacity} \times \text{LoadFactor}$$
  * 默认的负载因子（LoadFactor）是 **0.75**。
  * 如果你传入 `1024`：
    $$\text{Threshold} = 1024 \times 0.75 = 768$$
    当你存入第 **769** 个元素时，就会立即触发一次**全量数组扩容（resize），开辟 2048 大小的新数组并对已有 768 个节点进行全量 rehash 重新计算哈希桶！** 这带来了极其昂贵的 CPU 与内存开销。
  * **正确的数学推导**：
    $$\text{Capacity} \ge \frac{\text{ExpectedSize}}{\text{LoadFactor}} = \frac{1000}{0.75} \approx 1333.33$$
    HashMap 内部通过 `tableSizeFor` 位运算向上寻找大于等于 1334 的最小 2 的幂，即为 **2048**！
  * **规范推荐**：
    ```java
    // 阿里巴巴开发手册规约：(int) ((float) expectedSize / 0.75F + 1.0F)
    Map<String, Object> map = new HashMap<>((int) (1000 / 0.75F + 1.0F)); // 传入 1334，内部计算为 2048
    // 或使用 Guava：
    Map<String, Object> map = Maps.newHashMapWithExpectedSize(1000);
    ```

### 陷阱 2：HashMap 链表转红黑树的“双重阈值”陷阱（不是长度到 8 就转树！）

* ❌ **直觉错误**：只要单个哈希桶里的单向链表长度达到了 8，就会立刻树化（Treeify）转成红黑树。
* 💡 **底层真相**：
  * 转红黑树存在**双重硬性前置条件**，缺一不可：
    1. **条件一**：单桶链表节点数 $\ge 8$（`TREEIFY_THRESHOLD = 8`）；
    2. **条件二（隐藏机制）**：**整个 HashMap 的哈希桶数组容量必须 $\ge 64$（`MIN_TREEIFY_CAPACITY = 64`）！**
  * **源码物理机制**：
    * 当某个桶的链表长度达到 8 时，JDK 源码首先检查 `tab.length < MIN_TREEIFY_CAPACITY`；
    * 如果当前数组长度才 16 或 32，JDK 认为**当前碰撞严重大概率是因为数组容量太小导致的，转红黑树的开销远高于扩容**！此时会直接调用 `resize()` 扩容数组，将容量翻倍，让原本挤在一个桶里的节点在新老桶之间重新打散！
    * 只有当数组长度已经 $\ge 64$，且依然发生单桶长度 $\ge 8$ 的极端碰撞时，才会真正触发 `treeifyBin()` 转换为红黑树。

### 陷阱 3：ArrayList 扩容倍数与初始容量陷阱（不是翻倍，也不是初始占 10！）

* ❌ **直觉错误**：既然 HashMap 扩容是翻倍（2倍），那 ArrayList 也是 2 倍吧？另外 `new ArrayList<>()` 就会在内存中分配 10 个对象的空间。
* 💡 **底层真相**：
  1. **扩容倍数是 1.5 倍，而不是 2 倍**：
     * 源码实现：`int newCapacity = oldCapacity + (oldCapacity >> 1);`（原容量右移 1 位即除以 2，相加得 1.5 倍）。
     * **为什么不设计为 2 倍？（内存分配物理考量）**：
       如果每次都翻倍扩容（$1 \to 2 \to 4 \to 8 \to 16$），你会发现**任何一次新分配的内存块，都严格大于之前所有已释放的内存块总和**（$16 > 1+2+4+8=15$）。在物理内存碎片回收中，之前释放的内存将永远无法被本次扩容复用！而 1.5 倍扩容在几次扩容后，前面释放的连续内存总和可以容纳新分配的数组，极大提升了内存碎片复用率。
  2. **初始容量是惰性初始化的空数组（`{}`），不是 10**：
     * `new ArrayList<>()` 执行后，底层 `elementData` 只是指向了一个全局共享的空数组 `DEFAULTCAPACITY_EMPTY_ELEMENTDATA = {}`，此时内存占用为 0！
     * 只有当你第一次调用 `list.add(e)` 时，才会真正触发扩容逻辑，将数组大小一次性扩充为 **10**。这是一种极为经典的“按需延迟分配”内存节省设计。

### 陷阱 4：Arrays.asList 与 subList 的“伪装者”陷阱（修改与并发安全隐患）

* ❌ **直觉错误**：`Arrays.asList(arr)` 转成了 List，那我就可以正常像普通集合一样调用 `add()`、`remove()`；`list.subList(0, 5)` 截取出来的是一个独立的新 List。
* 💡 **底层真相**：
  1. **`Arrays.asList()` 返回的不是 `java.util.ArrayList`！**
     * 它返回的是 `java.util.Arrays` 内部的一个私有静态内部类 `Arrays$ArrayList`；
     * 该类只实现了 `get/set`，**根本没有实现 `add` 和 `remove` 方法**（直接继承自 `AbstractList`），如果调用 `add()` 会直接抛出 `UnsupportedOperationException`！
     * **底层共享指针**：该内部类底层直接持有外部原数组的引用。如果你修改了原数组的数据，这个 List 里的数据会同步发生改变！
  2. **`subList()` 只是一个“视图（View）”，不是新对象**：
     * `subList()` 底层并没有开辟新数组，它返回的是原 List 的内部子视图 `SubList`。
     * **踩坑惨案**：如果你拿到了 subList 后，原 List 发生了任何结构性修改（如原 List 增加了元素，导致其内部 `modCount` 改变），接着你再去遍历或访问 subList，会瞬间抛出 `ConcurrentModificationException`！

## 二、 多线程与并发篇：反直觉的任务状态机与资源极限

### 陷阱 5：线程池任务提交的“反直觉流转时机”（先排队还是先建非核心线程？）

* ❌ **直觉错误**：核心线程都在干活时，新来了任务，既然系统还有富余算力（最大线程数还没满），那肯定应该立即新建非核心线程去分担处理啊，等线程实在建满了才去队列排队。
* 💡 **底层真相**：
  * **标准流程恰恰相反！核心线程满了之后，新任务必须先去阻塞队列（workQueue）排队！只有当阻塞队列彻底被打满了，才会触发创建非核心线程！**
  * **四大状态机流转时序图**：
    ```
    新任务到达
       │
       ├─ (1) 工作线程数 < corePoolSize? ──[是]──> 创建核心线程执行任务
       │
       └─ [否] ──> (2) workQueue.offer() 阻塞队列未满? ──[是]──> 任务进入队列排队
                      │
                      └─ [否: 队列已满] ──> (3) 工作线程数 < maximumPoolSize? ──[是]──> 创建非核心线程救火执行
                                             │
                                             └─ [否: 最大线程也满了] ──> (4) 触发 RejectedExecutionHandler 拒绝策略
    ```
  * **为什么这么设计？（物理成本考量）**：
    * 创建 OS 物理线程是非常昂贵的（默认分配 1MB 栈内存，伴随 CPU 线程上下文切换开销）；
    * 放入内存阻塞队列只是普通的指针入队，开销极小。因此线程池优先利用内存队列削峰，只有在洪峰将队列彻底撑爆时，才紧急调用非核心线程救火。

---

### 陷阱 6：线程池大小配置的“CPU 核数陷阱”（8 核 CPU 配 8 个线程吗？）

* ❌ **直觉错误**：我的服务器是 8 核 CPU，为了防止线程切换，线程池核心线程数就应该配 8 个（或者配 16 个）。
* 💡 **底层真相**：
  * **配置线程数必须先问业务是“CPU 密集型”还是“I/O 密集型”！**
  * **场景一：CPU 密集型（复杂数学计算、视频编解码、加解密）**：
    * 线程几乎一直在占用 CPU 算力。
    * **最佳公式**：$$\text{Threads} = N_{\text{cpu}} + 1$$
    * *为什么加 1？*：为了防止因偶尔发生缺页中断（Page Fault）或其他微小暂停导致 CPU 空闲，额外的这 1 个线程能立刻顶上，保证 CPU 100% 吃满。
  * **场景二：I/O 密集型（绝大多数 Web 业务、查数据库、调用 RPC、读写文件）**：
    * 线程在发了网络请求后，90% 以上的时间都在挂起等待网络响应，此时 CPU 处于完全闲置状态！
    * 如果 8 核 CPU 只配 8 个线程，同时有 8 个请求在等数据库返回，此时 CPU 利用率可能连 **5%** 都不到，整机吞吐量极低！
    * **经典公式（Brian Goetz 提出）**：
      $$\text{Threads} = N_{\text{cpu}} \times \left(1 + \frac{\text{WaitTime}}{\text{ComputeTime}}\right)$$
    * 如果一个任务等待 I/O 时间是 100ms，CPU 计算时间是 10ms，WaitTime/ComputeTime = 10。对于 8 核服务器，最佳线程数 $= 8 \times (1 + 10) = \mathbf{88}$ 个线程！通用经验值可设为 **$2N \sim 4N$**，必须结合真实压测调整。

### 陷阱 7：Executors 快捷工厂的“安全幻觉”（newFixedThreadPool 为什么会 OOM？）

* ❌ **直觉错误**：`Executors.newFixedThreadPool(10)` 创建的线程池只有 10 个线程，容量固定，生产使用很稳定安全。
* 💡 **底层真相**：
  * 查看 `newFixedThreadPool` 的 JDK 源码：
    ```java
    public static ExecutorService newFixedThreadPool(int nThreads) {
        return new ThreadPoolExecutor(nThreads, nThreads,
                                      0L, TimeUnit.MILLISECONDS,
                                      new LinkedBlockingQueue<Runnable>()); // 致命祸根！
    }
    ```
  * `LinkedBlockingQueue` 的无参构造方法默认容量是 **`Integer.MAX_VALUE`（$2^{31}-1 \approx 21.4$ 亿）！**
  * **踩坑灾难**：在生产流量洪峰到来时，或者下游数据库出现死锁变慢时，这 10 个核心线程全部被卡死，后续进来的海量任务会源源不断涌入这个无界队列中排队。几百万个任务积压在堆内存里，瞬间引发 **`java.lang.OutOfMemoryError: Java heap space`**，整个微服务进程直接崩溃下线！
  * **规约**：阿里巴巴强制禁止使用 `Executors`，必须显式使用 `new ThreadPoolExecutor` 并传入有界队列（如 `ArrayBlockingQueue(500)`）。

### 陷阱 8：ThreadLocal 内存泄漏背后的“替罪羊”陷阱（真正泄漏的是 Key 还是 Value？）

* ❌ **直觉错误**：因为 `ThreadLocalMap` 的 `Entry` 继承了 `WeakReference`，它的 Key 是弱引用。当垃圾回收发生时 Key 会被回收变成 `null`，所以发生内存泄漏的是 Key。
* 💡 **底层真相**：
  * **Key 根本没有泄漏！弱引用恰恰是 JVM 设计师为了防止 Key 泄漏而专门引入的保护机制！**
  * **真正发生内存泄漏的是强引用的 Value！**
  * **物理引用链路剖析**：
    ```
    Thread 线程对象 (在线程池中常驻不销毁)
       │
       ▼
    threadLocals (ThreadLocalMap 内部哈希表)
       │
       ▼
    Entry[i]
       ├─ Key ──[弱引用]──> ThreadLocal 对象 (当外部无强引用时，GC 会将 Key 顺利回收为 null)
       │
       └─ Value ──[强引用]──> 巨大的业务对象 Object (无法被 GC 回收！)
    ```
  * **死锁逻辑闭环**：因为线程池的核心线程永远活着，这个 Entry 数组就永远被线程引用着。虽然 Key 变成了 `null`，但通过 Entry 强引用的 `Value` 却永远无法被访问，也永远无法被 GC 回收！日积月累，线程池各个线程的 Value 越积越多，最终堆内存暴涨。
  * **铁律**：使用 `ThreadLocal` 必须在 `finally` 块中显式执行 **`threadLocal.remove()`**！

## 三、 存储与数据库篇：物理存储块与连接池的直觉谬误

### 陷阱 9：数据库连接池大小陷阱（1000 并发需要设 1000 个连接吗？）

* ❌ **直觉错误**：系统峰值并发预计达到 1000，为了保证请求不排队，数据库连接池（如 HikariCP）的 `maximum-pool-size` 必须设到 500 甚至 1000。
* 💡 **底层真相**：
  * **数据库连接绝不是越多越好！连接数过多是导致数据库崩溃的头号元凶！**
  * **物理硬件极限**：
    * MySQL 服务端通常采用“一连接一线程”模型；
    * 假设数据库服务器是 **8 核心 CPU**。如果同时打开 1000 个连接并发执行 SQL，8 个物理核心必须在 1000 个线程之间疯狂进行**线程上下文切换（Context Switch）**；
    * CPU 的绝大部分算力都在保存寄存器、刷新 CPU L1/L2 缓存、调度线程栈，真正用来执行 SQL 查询的有效算力甚至不足 10%！系统耗时从几毫秒飙升到几千毫秒，最终引发整库雪崩。
  * **PostgreSQL / Oracle 官方测试公式**：
    $$\text{Optimal Connections} = (\text{CPU Core Count} \times 2) + \text{Effective Spindle Count}$$
  * 对于 8 核配 SSD 的现代数据库，连接池设在 **16 ~ 32** 之间能够跑出系统的**极限吞吐量峰值**！让多出来的请求在应用端内存中排队，其性能百倍优于让数据库在几百个连接间疯狂切上下文。

---

### 陷阱 10：HikariCP max-lifetime 与 MySQL wait_timeout 断连惨案

* ❌ **直觉错误**：连接池连接最大存活时间 `max-lifetime` 默认 30 分钟挺好的，MySQL 官方文档说默认超时是 8 小时（28800s），30 分钟肯定远小于 8 小时，绝对安全。
* 💡 **底层真相**：
  * **大厂生产环境 DBA 为了防止连接泄露和清理僵尸连接，绝不会保留默认的 8 小时，通常会强行将 MySQL 服务端的 `wait_timeout` 调成 10 分钟（600s）甚至更短！**
  * **惨案还原**：
    * MySQL 服务端规则：一个连接如果闲置超过 600 秒无读写，服务端单方面发送 TCP FIN 包关闭连接；
    * 客户端连接池规则：`max-lifetime` 设为 30 分钟（1800 秒）；
    * 某个连接闲置了 11 分钟后，MySQL 已经把它掐断了，但 HikariCP 并不知情；
    * 业务线程来借连接，HikariCP 把这个“早已死掉的僵尸连接”借给业务执行 SQL，瞬间抛出大名鼎鼎的断连异常：
      `Communications link failure / The last packet successfully received from the server was 660,000 milliseconds ago.`
  * **避坑铁律**：
    **HikariCP 的 `max-lifetime` 必须强制配置为比 MySQL 服务端的 `wait_timeout` 短 2~3 分钟！**（如果服务端是 600 秒，客户端必须设为 420~480 秒）。

### 陷阱 11：千万级 MySQL 大表 B+ 树高度直觉（千万数据树高真的有十几层吗？）

* ❌ **直觉错误**：一张表有 2000 多万行数据，普通的平衡二叉树深度都得二十多层，B+ 树再矮也得有十几层吧。
* 💡 **底层真相**：
  * **千万级大表的 B+ 树高度通常只有 3 层！**
  * **硬核数学推导**：
    * InnoDB 默认的数据页大小是 **16 KB**；
    * **非叶子节点页**：只存储 `主键 Key + 指针 Pointer`。
      * 假设主键是 `BIGINT`（占用 **8 字节**）；
      * InnoDB 中指向下一层的指针占用 **6 字节**；
      * 一个节点占用 $8 + 6 = 14$ 字节；
      * 一个 16KB 的非叶子数据页能容纳的指针数：
        $$N = \frac{16 \times 1024}{14} \approx \mathbf{1170} \text{ 个指针}$$
    * **三层 B+ 树容量计算**：
      * **根节点（第 1 层，1 个页）**：拥有 1170 个指针，指向第二层的 1170 个页；
      * **中间层（第 2 层，1170 个页）**：拥有 $1170 \times 1170 \approx \mathbf{136.89} \text{ 万个指针}$，指向第三层的 136.89 万个数据页；
      * **叶子节点（第 3 层，存放完整数据行）**：
        * 假设单行业务数据偏大，按 **1 KB** 计算，一个 16KB 叶子页能存 **16 条** 数据；
        * 三层 B+ 树总共可容纳的记录总数为：
          $$\text{Total Records} = 1170 \times 1170 \times 16 \approx \mathbf{21,902,400} \text{ 条（约 2190 万条！）}$$
  * **结论**：正因为扇出（Fan-out）极大（高达 1170），两千多万数据的表仅需 3 次磁盘 I/O 即可定位目标行，并且根节点常驻内存，实际仅需 1~2 次物理磁盘寻道！

## 四、 缓存与分布式篇：隐蔽的异步机制与时间差

### 陷阱 12：Redis 过期 Key 清理的“实时性幻觉”（EXPIRE 到了立刻删吗？）

* ❌ **直觉错误**：给 Key 设了 `EXPIRE user:101 60`，60 秒到期的一瞬间，Redis 就会立刻启动一个定时器把它从内存中抹掉。
* 💡 **底层真相**：
  * **Redis 内部根本没有一个常驻的定时器去盯每个 Key 的生命周期！为几百万个 Key 都起定时器会把 CPU 活活累死！**
  * Redis 依靠的是经典的 **惰性删除 + 定期抽样删除** 组合拳：
    1. **惰性删除（Passive Deletion）**：只有当客户端下一次主动执行 `GET user:101` 时，Redis 才会去比对当前时间戳。如果发现已过期，此时才顺手把它从内存中删掉，并返回 nil；
    2. **定期抽样删除（Active Deletion）**：Redis 默认每秒运行 10 次（由 `hz` 参数控制）：
       * 随机抽取 20 个带有过期时间的 Key；
       * 检查并删除其中已过期的 Key；
       * 如果已过期 Key 的比例超过 **25%**，则继续重复抽查；如果低于 25%，停止本次抽查，等待下一次循环。
  * **生产隐患**：如果你的系统瞬间产生了数百万个带有过期时间的冷数据 Key，而这些 Key 之后**再也没有被任何请求访问过**，定期删除又刚好没抽中它们，它们会长年赖在内存里不走！直到内存打满触发 `maxmemory` 淘汰策略。

### 陷阱 13：Redis 字典 Rehash 的负载因子陷阱（不仅不是 0.75，还会突变到 5！）

* ❌ **直觉错误**：既然 Java HashMap 负载因子是 0.75，那 Redis 的 Dict 扩容阈值也应该是 0.75 吧。
* 💡 **底层真相**：
  * Redis 字典的负载因子计算公式：$$\text{LoadFactor} = \frac{\text{ht[0].used}}{\text{ht[0].size}}$$
  * **Redis 的负载因子是动态变化的，存在一个极其硬核的“避开写时复制（COW）机制”**：
    1. **正常状态下**：当 $\text{LoadFactor} \ge \mathbf{1}$ 时，触发渐进式扩容（分配 2 倍空间的 `ht[1]`）；
    2. **特殊状态下（突变到 5！）**：
       * 当 Redis 正在执行 `BGSAVE`（生成 RDB 快照）或 `BGREWRITEAOF`（AOF 重写）时，Redis 会 `fork()` 出子进程；
       * Linux 底层采用 **写时复制（Copy-On-Write）** 技术。如果父进程在此时进行大量内存写入或哈希表扩容重分配，会导致原本共享的物理内存页发生大量物理拷贝分裂，极度消耗服务器内存和 CPU！
       * 因此，Redis 会**主动将扩容负载因子强行提高到 $\ge \mathbf{5}$**！尽可能在子进程工作期间延缓哈希表扩容；
    3. **缩容状态下**：当 $\text{LoadFactor} < \mathbf{0.1}$ 时，触发缩容。

---

### 陷阱 14：Redis 分布式锁超时设置（设个 10 秒绝对安全吗？）

* ❌ **直觉错误**：给分布式锁加上 10 秒过期时间：`SET lock:order_101 uuid EX 10 NX`，我的业务只跑 2 秒，10 秒足够安全了。
* 💡 **底层真相**：
  * **网络抖动或 JVM Full GC STW 会彻底击碎固定超时锁的安全性！**
  * **致命并发冲突时序**：
    ```
    时间轴      线程 A (Thread-1)                           线程 B (Thread-2)
      T1       获得锁 (锁有效期 10 秒)
      T2       业务执行中，突然遭遇网络慢 I/O 
               或发生 JVM Full GC 停顿了 12 秒！
      T10      ───────────────── 锁在第 10 秒自动过期 ─────────────────
      T11                                                  成功抢到锁 (认为临界区安全)
      T12      线程 A 从 STW 中苏醒，继续执行写操作         线程 B 正在执行写操作
               【两个线程同时进入临界区并发修改数据，分布式锁彻底形同虚设，产生脏数据！】
    ```
  * **正规解法**：必须使用具备 **自动续期看门狗（Watchdog）** 的成熟组件（如 Redisson）。只要持有锁的线程未执行完毕，看门狗后台时间轮每隔 10 秒（`lockWatchdogTimeout / 3`）向 Redis 发送 Lua 脚本重置 TTL 为 30 秒；若节点宕机，看门狗随之死亡，30 秒后自然释放防止死锁。

## 五、 消息队列与网络协议篇：物理独占与状态残留

### 陷阱 15：Kafka 消费者实例数盲目扩容的“闲置惨剧”

* ❌ **直觉错误**：突发海量消息积压，原来的 3 个消费者实例消费太慢，我赶紧在 K8s 上拉起 10 个消费者实例，消费速度一定能翻 3 倍以上。
* 💡 **底层真相**：
  * **如果该 Topic 只有 3 个 Partition，那么多出来的 7 个消费者实例会彻底“躺平闲置（Idle）”，1 条消息都拿不到！**
  * **Kafka 消费端物理独占铁律**：
    * **同一个 Consumer Group（消费者组）内，一个 Partition 在同一时刻只能被某一个 Consumer 独占消费！**（反之，一个 Consumer 可以同时负责多个 Partition）。
    * 这是因为单 Partition 内部依靠递增 Offset 实现严格有序，如果允许多个 Consumer 并发拉取同一个 Partition，局部保序机制将被彻底击穿。
  * **扩容正道**：要想水平提升消费并发能力，**必须先通过命令行增加 Topic 的 Partition 分区数，然后再等比例增加 Consumer 实例数**！

### 陷阱 16：TCP TIME_WAIT 为什么必须苦等 2MSL？

* ❌ **直觉错误**：客户端主动关闭连接，发送完第四次挥手的最后一个 ACK 报文后，既然握手挥手都走完了，为什么不能直接关闭释放端口，非要占着端口等 1~2 分钟（2MSL）？
* 💡 **底层真相**：
  * MSL（Maximum Segment Lifetime）是任何报文在网络中的最大存活时间（RFC 793 推荐 2 分钟，Linux 常设 60 秒）。2MSL 就是 2 倍的报文生存时间。
  * **苦等 2MSL 的两大不可替代原因**：
    1. **保证客户端发送的最后一个 ACK 能够可靠到达服务端**：
       * 假设客户端发送的 ACK 报文在公网上丢了；
       * 服务端因为迟迟没收到 ACK，会触发超时重传 FIN 报文；
       * 如果客户端不等待 2MSL 而是直接关闭，当重传的 FIN 到达时，客户端端口早已关闭，会向服务端回复 RST 错误报文，导致服务端无法正常平滑进入 CLOSED 状态；
       * 等待 2MSL 使得客户端有足够时间在收到重传的 FIN 后，重新补发 ACK。
    2. **彻底消灭网络中的“迷途旧报文”，防止新连接被脏数据污染**：
       * 等待 2MSL 可以保证本次连接所产生的所有网络数据包在网络中彻底消亡；
       * 避免后续在**完全相同的 IP 和端口**建立新连接时，由于网络延迟刚到达的老数据包被当成新连接的数据读取，从而引发严重的数据错乱！

## 六、 直觉陷阱全景对照一览表（考前面试速查）

| 考察领域 | 候选人凭直觉的常见回答 (❌ 陷阱) | 工业级底层物理真相 (💡 正解) | 核心背诵公式 / 物理机制 |
| :--- | :--- | :--- | :--- |
| **HashMap 初始容量** | 存 1000 个元素传入 1024 | 1024 阈值仅 768，存到 769 个就会触发全量 rehash 扩容，必须传 2048 | $\text{Cap} \ge 1000 / 0.75 \approx 1334 \to \mathbf{2048}$ |
| **HashMap 链表转树** | 链表长度达到 8 立刻转红黑树 | 必须同时满足数组长度 $\ge 64$，否则优先通过 `resize()` 扩容打散 | `TREEIFY_THRESHOLD=8` 且 `MIN_TREEIFY_CAPACITY=64` |
| **ArrayList 扩容机制** | 满了翻倍扩容；new 时分配 10 个空间 | 扩容为 1.5 倍（便于内存碎片复用）；初始为空数组，首次 `add` 才分配 10 | `oldCapacity + (oldCapacity >> 1)`，延迟按需分配 |
| **Arrays.asList** | 返回的是常规 ArrayList，可随意增删 | 返回的是私有静态内部类，调 `add/remove` 报不支持异常，底层共享原数组 | 继承 `AbstractList` 未覆写写操作；直接引用原数组 |
| **线程池任务流转** | 核心满后先建非核心线程，最后进队列 | 核心满后**优先进队列排队**，队列打满后才紧急创建非核心线程救火 | 线程创建物理成本极高，内存队列成本极低 |
| **线程池大小配置** | 8 核服务器核心线程配 8 个或 16 个 | 区分 CPU 密集型（$N+1$）与 I/O 密集型（$N \times [1 + WT/ST]$，可达几十） | 等待时间长则 CPU 极度空闲，需增加线程吃满吞吐 |
| **newFixedThreadPool** | 固定线程数很安全 | 底层是容量为 $2^{31}-1$ 的无界队列，任务积压直接导致 JVM 堆 OOM 崩溃 | `LinkedBlockingQueue` 默认容量 21 亿 |
| **ThreadLocal 泄漏** | Key 是弱引用被 GC 了，所以泄漏的是 Key | Key 被回收正是保护机制，**真正泄漏的是 Entry 强引用的 Value** | 线程池核心线程不死，引用链一直存在，必须 `remove()` |
| **数据库连接池大小** | 1000 并发需要配几百上千连接 | 连接过多导致 CPU 剧烈上下文切换，吞吐量反而断崖下跌，8 核配 16~32 最佳 | $\text{Connections} = (\text{Cores} \times 2) + \text{Spindles}$ |
| **连接存活 max-lifetime** | 默认 30 分钟小于 MySQL 8 小时，安全 | DBA 常调小 `wait_timeout`（如 10 分钟），连接闲置被杀，借出报连接重置 | 客户端 `max-lifetime` 必须比服务端短 2~3 分钟 |
| **千万级表 B+ 树高度** | 数据量达两千万，树深至少十几层 | 树高仅为 **3 层**！根节点常驻内存，实际通常仅需 1~2 次磁盘 I/O | 16KB 页可存 1170 指针，$1170 \times 1170 \times 16 \approx 2190 \text{万}$ |
| **Redis 过期 Key 机制** | 设置过期时间到了立刻在内存抹除 | 没有常驻定时器，由“惰性删除 + 每秒 10 次随机抽样 20 个”配合工作 | 长期不被访问的过期冷数据会残留，需内存淘汰策略兜底 |
| **Redis 字典扩容阈值** | 和 Java 一样恒定是 0.75 | 正常是 $\ge 1$；遇 `bgsave/bgrewriteaof` 写时复制（COW）时飙升到 $\ge 5$ | 防 COW 物理页大量拷贝；缩容阈值是 $< 0.1$ |
| **分布式锁超时设置** | 设置 10 秒固定超时足够业务执行 | 遇到 Full GC STW 或网络卡顿，锁提前失效被别人抢占，临界区双写击穿 | 必须依靠 Redisson 时间轮看门狗 10s 自动续期 |
| **Kafka 消费者扩容** | 消费积压直接加消费者实例数 | 分区数不变时，多出来的消费者独占不到任何分区，处于完全闲置状态 | 一个 Partition 在同组内只能被一个 Consumer 独占 |
| **TCP 挥手等 2MSL** | 挥手完毕直接关闭连接即可 | 保证最后 ACK 到达服务端（允许重传 FIN）；让网络迷途老报文彻底死掉 | 防服务端无法关闭；防新建同端口连接被老脏数据污染 |
