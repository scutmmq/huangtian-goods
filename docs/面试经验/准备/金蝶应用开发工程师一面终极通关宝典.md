### 1. 凯通科技实习：复杂拓扑大屏性能优化（15s → 200ms）与“丢根告警”逆向排障闭环

#### 🔥 考官必问 1：“说说你在凯通科技印象最深的一次 Bug 排查经历，你是怎么定位并解决的？”
* **S (背景)**：在浙江电信综合网管系统中，网络故障会产生海量告警风暴。系统需要通过拓扑依赖树进行“根因分析”，把衍生告警挂载到根告警下派发工单。但线上偶发出现**“衍生告警到了，根告警却丢失了，导致漏派核心故障工单”**的严重问题。
* **T (任务)**：独立排查该偶发缺陷，在不影响现有高并发告警接入的前提下彻底修复，并确保零回归风险。
* **A (行动 - 展现极强的调试与排障方法论)**：
  1. **日志链路追踪与复现**：通过梳理告警归并流水日志，我发现网络层面上报的告警存在**乱序到达（子告警先到、父告警晚到数秒）**以及**跨层级传递（A → B → C 中间节点 B 未上报）**的情况；
  2. **定位代码缺陷**：阅读原有逆向追溯源码发现，旧逻辑在向上查找父节点时，遇到当前时间窗口内尚未入库的中间节点就直接终止了递归，导致树链断裂；
  3. **架构修复**：我重构了逆向追溯算法，引入**“状态兜底回溯 + 延迟缓冲重挂机制”**，当发现断链时穿透查询静态资产拓扑表补齐链路；
  4. **工程规范闭环**：为了验证各种极端拓扑形态（单链、星型、环路死锁防护、乱序到达），我编写了 **188 行高覆盖率的 JUnit 单元测试**，覆盖了全部边界分支。
* **R (结果)**：上线后彻底清零了“丢根告警”故障，核心故障工单派发准确率达到 100%，获团队高度认可。

#### 🔥 考官必问 2：“拓扑大屏从 15 秒优化到 200ms 是怎么做的？如果先加载骨架，数据没过来时用户点击岂不是置灰不能用？”
* **满分三层回答**：
  1. **瓶颈诊断**：原接口把 8 大云池上万个网元节点的“静态拓扑结构”与“实时性能/告警指标（多表慢聚合）”耦合在一个几十兆的大 JSON 里同步返回，导致 SQL 慢、网络传输慢、前端主线程解析卡死；
  2. **动静分离与并行渐进加载**：
     * **第一阶段（200ms 骨架秒开）**：优先从 Redis 缓存直接拉取轻量级的“网元节点坐标 + 连线拓扑骨架 + 基础资产属性”；
     * **第二阶段（异步分批注水）**：前端根据当前可视区域（Viewport），异步并发拉取实时告警状态与性能指标，局部高亮渲染；
  3. **回应“置灰质疑”**：首屏 200ms 渲染出的绝不是死板置灰图！由于已包含网元 ID、设备名称与拓扑连线，**运维人员在第一秒就能立刻进行画布缩放、拖拽漫游、链路走向查看、网元定位搜索以及静态台账抽屉查看**；而告警红黄灯在随后 1~2 秒内流式点亮，彻底消除了 15 秒白屏转圈和浏览器崩溃弹窗。

### 2. 云智易实习：视频巡检 XXL-JOB 分片调度与专属线程池防反压演进

#### 🔥 考官必问：“你们的定时巡检是怎么设计的？线程池参数怎么配的？如果调度中心挂了或任务卡死怎么办？”
* **四步演进主线**：
  1. **痛点**：早期单线程 `while(true)` 串行拉取几百路海康摄像头 RTSP 流抓拍，单设备网络抖动阻塞 5 秒就会导致整轮巡检耗时超过 5 分钟，严重滞后；
  2. **线程池异步解耦（7 大参数精准配置）**：
     * 严禁使用 `Executors` 无界队列，显式构造 `ThreadPoolExecutor`；
     * **参数推导**：结合 Little's Law（$QPS \times RT$）理论与**下游边缘流媒体芯片硬件解码通道上限（8~16 路 RTSP）+ JVM 堆内 RGB 图像展开内存开销（单图 4~8MB）**，将 `corePoolSize` 和 `maximumPoolSize` 严谨锁定为 **8**；队列选用有界 `ArrayBlockingQueue(500)`；线程工厂自定义命名为 `"patrol-worker-%d"` 方便 `jstack` 排障；
     * **拒绝策略**：采用 `CallerRunsPolicy`，当队列饱和时由提交任务的主线程亲自执行，形成**天然的反压限流（Backpressure）**，绝不丢弃巡检任务；
  3. **分布式扩展与高可用（XXL-JOB 分片广播）**：
     * 引入 XXL-JOB 分片广播模式（`shardIndex` / `shardTotal`），通过 `device_id % shardTotal == shardIndex` 让多台执行器节点均匀分摊设备，单轮耗时从 5 分钟压降至 **25 秒以内**；
     * **容灾兜底**：在执行器内部设计了轻量级本地看门狗（Watchdog），若连续 3 个周期未收到 XXL-JOB 调度中心心跳，自动切换为本地定时降级触发，确保客户现场安防巡检永不中断；
  4. **防任务卡死**：底层 Socket 强制设置 `connectTimeout/readTimeout = 5s`，外层通过 `Future.get(10, TimeUnit.SECONDS)` 配合 `future.cancel(true)` 主动中断超时线程。

### 3. OpsMind 企业数字员工：RAG 文档切分策略、双路召回重排与“引用溯源高亮”实现

> 💡 **金蝶高频考点**：牛客面经多次提到，金蝶考官看到简历上有 AI/Agent 项目，必问**“文档切分策略（Chunking）”**与**“引用溯源是怎么实现的”**！

#### 🔥 考官必问 1：“你们的 RAG 知识库从文档入库到检索生成的全流程是怎样的？文档切分策略怎么设计的？”
* **1. 离线知识入库与结构化切分（Chunking 策略）**：
  * **痛点**：如果直接按固定字数（如 500 字）粗暴切分企业运维手册或财务制度 PDF，会把完整的表格、代码块或跨段落流程从中间截断，导致语义支离破碎；
  * **三级结构化切分方案**：
    1. **按 Markdown/文档标题层级切分（Parent-Child 父子文档切片）**：先识别 `# / ## / ###` 标题树，保持章节完整性；
    2. **递归字符切分（RecursiveCharacterTextSplitter）**：依次按段落 `\n\n`、句子 `。！？` 进行切分，设定每个子块 `chunk_size = 512 tokens`，并保留 **`chunk_overlap = 64 tokens`（约 10%~15% 的滑动窗口重叠区）**，确保上下文跨块语义不断裂；
    3. **表格与代码块特殊保护**：检测到 Markdown 表格或配置代码块时，将其作为独立原子块保留，并在每个分块头部自动拼接**“所属文档名 + 章节路径面包屑”**（如 `[网络排障手册 > 第三章 BGP路由 > 3.2 邻居震荡]`），大幅增强向量表征的语义锚点！
* **2. 在线多路混合检索与重排（Hybrid Search + Rerank）**：
  * **双路召回**：
    * **稠密向量检索（PostgreSQL `pgvector` HNSW 索引）**：捕捉语义相似性（召回 Top 30）；
    * **稀疏关键词检索（BM25 全文检索）**：精准匹配专有名词、错误码（如 `ERR-5002`、单据号、IP 地址，召回 Top 30）；
  * **RRF 倒数秩融合**：通过公式 $\text{Score} = \sum \frac{1}{60 + \text{rank}_i}$ 将两路结果统一归一化合并去重；
  * **Cross-Encoder 精排（Reranker）**：对合并后的 Top 20 候选块做深度交叉注意力打分，截取最高分的 **Top 5** 注入 Prompt 上下文。

#### 🔥 考官必问 2：“在企业级问答中，为了防止大模型幻觉，你们的‘引用溯源（Citation）与原文定位高亮’是怎么实现的？”
* **满分工程链路**：
  1. **入库元数据绑定（Metadata Tagging）**：在文档解析切分阶段，每个 Chunk 在存入数据库时，都在 JSONB `metadata` 字段中持久化记录了：`doc_id`（文档唯一 ID）、`doc_title`、`page_no`（PDF 页码）、`start_offset / end_offset`（字符起止偏移量）以及 `chunk_id`；
  2. **Prompt 强约束内联角标**：在组装给大模型的上下文中，我们将每个 Chunk 格式化为 `<chunk id="102" doc="财务报销规范.pdf" page="5">...内容...</chunk>`，并在 System Prompt 中强制规定：**“必须严格依据提供的 chunk 回答；每当引用某段事实时，必须在句末标注对应的 `[102]` 角标；若上下文无答案，直接回答未知，严禁编造”**；
  3. **后端正则解析与前端联动高亮**：后端流式输出时解析出 `[102]` 角标，关联查出该 `chunk_id` 对应的 `doc_id`、页码和原文片段返回前端；用户点击角标 `[102]` 时，前端 PDF/文档预览组件直接跳转到第 5 页，并根据 `start_offset` 对原文段落进行黄色背景高亮展示，实现 100% 可信溯源！

### 4. 荒天商城：库存防超卖（Redis+Lua）与跨服务数据最终一致性（Cache-Aside + Canal）

#### 🔥 考官必问：“高并发下怎么防止库存超卖？Redis 和 MySQL 的数据一致性怎么保证？”
* **防超卖双保险**：
  1. **第一层（内存原子拦截）**：使用 **Redis + Lua 脚本** 将“查库存、判断库存 `>= 扣减量`、执行 `decrby`”封装为单命令原子操作，单机支撑数万 QPS，挡住 99% 无效请求；
  2. **第二层（数据库底线兜底）**：异步落库更新 MySQL 时，SQL 必须带上乐观锁前置条件：`UPDATE t_stock SET count = count - #{num} WHERE sku_id = #{skuId} AND count >= #{num}`，利用 InnoDB 行锁确保库存绝对不会扣成负数。
* **缓存与数据库双写最终一致性（Cache-Aside + Canal）**：
  * **标准写流程**：**先更新 MySQL 数据库，事务提交成功后，再删除 Redis 缓存**（绝不先删缓存，防止读写并发导致旧数据回填）；
  * **极端删缓存失败兜底**：引入 **Canal 伪装成 MySQL 从库监听 Binlog 日志**，一旦捕获到数据库变更，异步投递消息到 Kafka/MQ 重试删除对应的 Redis Key，确保极端网络抖动下的最终一致性。

### Q1：在财务/供应链 ERP 系统中，金额与单价字段在 Java 和数据库中如何存储与计算？为什么严禁用 float/double？

* **1. 为什么严禁用 `float` / `double`？**
  * `float` 和 `double` 采用 **IEEE 754 二进制浮点数标准**。像十进制的 `0.1` 在转换为二进制时是一个无限循环小数（`0.0001100110011...`），发生截断误差（例如在 Java 中 `0.1 + 0.2 == 0.30000000000000004`）。在金蝶的财务总账、凭证核算或税务系统中，差一分钱都会导致借贷不平，引发严重的财务事故！
* **2. 工业级标准规范（Java + 数据库）**：
  * **Java 层面**：必须使用 **`java.math.BigDecimal`**！
    * **避坑铁律 1（构造器陷阱）**：**严禁使用 `new BigDecimal(0.1)`**（会把 double 的精度误差直接带进去），**必须使用字符串构造器 `new BigDecimal("0.1")` 或 `BigDecimal.valueOf(0.1)`**！
    * **避坑铁律 2（除法与舍入模式）**：调用 `divide(divisor, scale, RoundingMode.HALF_UP)` 时，**必须显式指定小数位数和舍入模式（如四舍五入 `HALF_UP` 或银行家舍入法 `HALF_EVEN`）**，否则遇到除不尽（如 `1 / 3`）会直接抛出 `ArithmeticException: Non-terminating decimal expansion`！
    * **避坑铁律 3（等值比较）**：比较两个金额大小是否相等，**严禁用 `equals()`**（因为 `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` 返回 `false`，它会比较标度 scale），**必须使用 `a.compareTo(b) == 0`**！
  * **数据库层面**：
    * MySQL / PostgreSQL / Oracle 中必须使用定点数类型 **`DECIMAL(19, 4)`** 或 **`NUMERIC(19, 4)`**（或者将金额统一换算为最小货币单位“分”，用 `BIGINT` 整型存储）。

### Q2：客户在系统中导出百万级财务明细/订单报表时发生 JVM OOM，你如何排查并彻底重构优化？

> 💡 **业务痛点**：企业级 ERP 系统最常见的高频生产故障就是“月底财务集中导出几十万行大 Excel 报表，直接把服务器内存打爆（`OutOfMemoryError: Java heap space`）”。

* **1. 根因分析**：
  * 传统做法：第一，用 MyBatis `selectList()` 一次性把 100 万条数据库记录全部查出加载进 JVM 堆内存 `List<OrderVO>`；第二，使用 Apache POI 的 `XSSFWorkbook` 在内存中构建完整的 DOM 树，双重内存暴涨直接触发 Full GC 甚至 OOM 宕机。
* **2. 工业级四步根治方案（完整四步闭环）**：
  1. **第一步：数据库读取层（游标分页/流式查询，拒绝全量加载与深分页）**：
     * 采用 **基于主键游标的分批拉取**：`SELECT * FROM t_finance_detail WHERE id > #{lastMaxId} ORDER BY id ASC LIMIT 5000`（每次只拉 5000 条，耗时仅几毫秒，绝不用 `LIMIT 900000, 5000` 深分页）；
     * 或者使用 MyBatis 的 **`ResultHandler` 流式查询（`fetchSize = Integer.MIN_VALUE`）**，边读边处理，内存中始终只驻留几千条数据；
  2. **第二步：Excel 生成层（采用阿里 EasyExcel 流式写磁盘）**：
     * 替换原生 POI，使用 **EasyExcel**。它底层基于 SAX 事件驱动模型与临时磁盘文件缓冲，写完一批立即刷入磁盘释放堆内存，哪怕导出 100 万行数据，JVM 堆内存占用也能稳定控制在 **几十 MB 以内**；
  3. **第三步：交互架构层（同步改异步 + OSS 下载中心）**：
     * 百万级导出绝不能让 HTTP 请求同步阻塞等待几十秒（会导致网关 504 超时）；
     * **异步化改造**：用户点击“导出” → 后端生成一条“导出任务记录（状态：生成中）”并投递到专属线程池/MQ，立即返回前端提示“报表正在后台生成，完成后将在通知中心提醒”；后台生成完毕后上传至 **MinIO / 阿里云 OSS**，通过 WebSocket 推送下载链接；
  4. **第四步：系统级并发限流与文件缓存复用（防多用户并发打爆磁盘 I/O）**：
     * 使用 Redis 或 `Semaphore` 信号量限制全系统**同时执行大报表导出的最大并发数（如最多同时跑 5 个导出任务）**，超出的进入队列排队；并对相同查询条件生成的报表文件做 MD5 缓存复用，避免重复导出。

### Q3：企业级开发中经常需要与外部系统（银行、税务、OA、WMS）做接口对接，如何保证接口的高可靠、幂等与安全？

* **五维标准架构回答（完整五维闭环）**：
  1. **第一维：安全性（防篡改、防重放攻击）**：
     * 采用 **AppKey + AppSecret 签名验签机制（HMAC-SHA256）**：请求头携带 `timestamp`（时间戳，超过 5 分钟直接拒绝防重放）、`nonce`（随机唯一流水号，存入 Redis 防二次重放）以及对请求体排序计算的 `signature` 签名；
  2. **第二维：幂等性（防网络抖动重复扣款/重复生单）**：
     * 双方约定全局唯一的业务单据号或请求流水号 `request_id`；
     * 接收方通过 **“Redis `SETNX` 防重令牌 + 数据库唯一索引（Unique Key）+ 业务状态机前置乐观锁”** 确保同一笔单据无论重发多少次，结果完全一致；
  3. **第三维：高可靠与最终一致性（本地消息表 + 指数退避重试）**：
     * 遇到网络闪断或对方服务短暂不可用，通过 **本地消息表（`local_message_log`）** 在本地事务中保存待发送报文，由后台任务按**指数退避策略（10s → 30s → 2m → 10m）**异步重试；超过最大次数触发钉钉/企微告警转人工介入；
  4. **第四维：超时控制与线程池隔离熔断（防外部接口拖垮自身系统）**：
     * 调用外部接口必须显式设置 `connectTimeout`（如 3s）和 `readTimeout`（如 5s），严禁无限等待；并使用独立线程池隔离外部调用，配合 Sentinel 熔断器，一旦对方系统宕机立即快速失败降级；
  5. **第五维：可观测性与审计留痕（接口调用日志表）**：
     * 企业级跨系统对接经常需要排查联调问题与定责。必须通过 AOP 将每次外部调用的**请求 URL、入参报文、响应报文、HTTP 状态码、耗时（RT）、异常堆栈**异步持久化到接口审计日志表（`t_api_invoke_log`），出了问题一查一个准！

### Q4：单点登录（SSO）是如何实现的？如果集团客户有多个子系统，如何实现一次登录全网通行与主动强制下线？

* **核心架构（认证中心 Auth Center + 双 Token + Redis 全局会话）**：
  1. **一次登录全网通行流程**：
     * 用户访问子系统 A（如财务系统），未携带有效 Token，被重定向到统一的 **SSO 认证中心**；
     * 用户输入账号密码登录成功，SSO 认证中心生成全局会话 Ticket，并在 Redis 中写入登录态 `sso:session:{userId}`，同时颁发 **Access Token（JWT，有效期 15 分钟）** 与 **Refresh Token（有效期 7 天）**；
     * 用户后续访问子系统 B（如供应链系统）时，网关层直接通过公钥本地验签 JWT（零跨网开销），校验通过即可无感通行；
  2. **如何解决纯 JWT 无法主动注销/强制下线的痛点？**
     * **网关 + Redis 令牌版本号/黑名单机制**：当管理员将某员工账号禁用或用户点击退出登录时，将该 Token 的唯一标识 `jti` 写入 **Redis 黑名单（`SET sso:blacklist:{jti} 1 EX 剩余秒数`）**，或递增该用户的 `token_version`；
     * API 网关在校验 JWT 签名通过后，做一次极速的 Redis 校验，实现毫秒级全系统强制下线。

### Q5：Spring 声明式事务 @Transactional 在哪些典型场景下会失效？底层 AOP 代理原理是什么？

* **底层原理**：Spring 事务基于 **AOP 动态代理**（默认 JDK 动态代理或 CGLIB 字节码增强）。当调用目标方法时，实际上是先进入代理对象的 `TransactionInterceptor`，开启事务（`setAutoCommit(false)`）→ 调用真实业务方法 → 无异常则 `commit()`，捕获到指定异常则 `rollback()`。
* **6 大经典事务失效场景（背熟！）**：
  1. **同类内部自调用（最常考！）**：类内部的普通方法 A 直接调用本类的 `@Transactional` 方法 B（`this.b()`），由于绕过了 Spring 代理对象，不会触发 AOP 拦截，事务直接失效！*(解法：注入自身的代理对象或使用 `AopContext.currentProxy()`)*；
  2. **方法非 `public` 修饰**：`@Transactional` 标注在 `private`、`protected` 或包可见方法上，Spring AOP 无法生成代理拦截，事务失效；
  3. **异常被内部 `try-catch` 生吞**：业务代码自己 `catch` 了异常却没有重新向上抛出，代理对象感知不到异常，会正常提交事务；
  4. **抛出了受检异常（Checked Exception）但未配置 `rollbackFor`**：`@Transactional` 默认**只对 `RuntimeException` 和 `Error` 回滚**！如果抛出 `IOException` 或自定义受检异常，默认不回滚！*(解法：显式配置 `@Transactional(rollbackFor = Exception.class)`)*；
  5. **事务传播行为配置错误**：如配置了 `Propagation.NOT_SUPPORTED`（以非事务方式运行）或 `NEVER`；
  6. **数据库引擎不支持事务**：如 MySQL 旧表使用了 MyISAM 引擎而非 InnoDB。

### Q6：线上客户反馈某个业务查询列表极其缓慢（超过 10 秒），你的标准排查 SOP 与 SQL 优化手段是什么？

* **标准四步排查与治理 SOP**：
  1. **第一步（定位慢接口与慢 SQL）**：
     * 查看 SkyWalking / Prometheus 链路追踪，或者查看数据库的慢查询日志（MySQL `slow_query_log` / PostgreSQL `pg_stat_statements`），抓出耗时超过阈值的具体 SQL 语句；
  2. **第二步（执行计划深度剖析 `EXPLAIN`）**：
     * 在数据库执行 `EXPLAIN`（或 `EXPLAIN ANALYZE`），重点检查：
       * `type` 列：是否出现了全表扫描 `ALL`（目标至少优化到 `range`、`ref` 或 `const`）；
       * `key` 列：实际是否命中了预期的索引；
       * `Extra` 列：是否出现了 `Using filesort`（文件排序，未走索引排序）或 `Using temporary`（使用临时表聚合）。
  3. **第三步（排查索引失效的 6 大元凶）**：
     * 违反**联合索引最左前缀原则**（如建立 `(a, b, c)` 索引，查询条件却只有 `b` 和 `c`）；
     * 在索引列上做了**函数计算、表达式运算或类型隐式转换**（如字符串字段 `phone` 传了数字 `WHERE phone = 138000`，导致索引失效全表扫描）；
     * 模糊查询以通配符开头 `LIKE '%abc'`；
     * 使用 `OR` 连接了未建索引的列，或负向查询 `!= / NOT IN`；
  4. **第四步（架构与 SQL 重构调优）**：
     * **覆盖索引优化**：建立包含查询字段的联合索引，避免回表查询（`Using index`）；
     * **深分页优化**：将 `LIMIT 500000, 20` 改写为**延迟关联（先通过覆盖索引查出主键 ID，再 INNER JOIN 原表）**：
       ```sql
       SELECT t1.* FROM t_order t1
       INNER JOIN (SELECT id FROM t_order WHERE status = 1 ORDER BY create_time DESC LIMIT 500000, 20) t2
       ON t1.id = t2.id;
       ```
     * **小表驱动大表**：多表关联时确保关联字段都有索引，且用小结果集驱动大表。

### 一、Java 核心基础与集合框架（Q7 ~ Q10）

#### Q7：面向对象三大特性是什么？接口（Interface）与抽象类（Abstract Class）的区别？重载（Overload）与重写（Override）的区别？
* **三大特性**：封装（隐藏内部细节，暴露安全接口）、继承（复用父类代码并扩展）、多态（同一方法调用因运行时子类实例不同表现不同行为，底层基于 JVM `invokevirtual` 虚方法表动态分派）。
* **接口 vs 抽象类**：
  1. **设计目的**：接口是自上而下的**“行为契约规范（Can-do）”**；抽象类是自下而上的**“模板共性抽取（Is-a）”**；
  2. **语法差异**：类只能单继承抽象类，但可实现多个接口；接口只有 `public static final` 静态常量且无构造器，抽象类可拥有普通成员变量和构造器（供子类初始化通用状态）。
* **重载 vs 重写**：
  * **重载（Overload，编译期静态分派）**：发生在同一个类中，方法名相同，**参数列表（个数、类型、顺序）必须不同**，返回值和访问修饰符不限；
  * **重写（Override，运行期动态分派）**：发生在父子类之间，方法名与参数列表完全相同，遵循**“两同两小一大”**（方法名参数同；子类返回值类型和抛出受检异常范围 $\le$ 父类；子类访问权限 $\ge$ 父类）。

#### Q8：`String` 为什么不可变？`String`、`StringBuilder`、`StringBuffer` 有什么区别？
* **`String` 不可变原因**：内部存储字符的数组被 `private final` 修饰且未暴露修改方法，类本身被 `final` 修饰不可被子类继承篡改；
* **不可变的四大好处**：① 实现**字符串常量池**安全共享，节省内存；② **天然线程安全**；③ 作为 `HashMap` 的 Key 时**哈希值恒定不变**，可缓存 `hash` 值提升寻址效率；④ 保障网络连接、类加载等安全性。
* **三者区别**：`String` 每次拼接都会新建对象；`StringBuilder` 可变、非线程安全但**单线程拼接性能最高**；`StringBuffer` 方法加了 `synchronized` 锁，线程安全但有同步开销。

#### Q9：`ArrayList` 与 `LinkedList` 的区别？`HashMap` 的底层原理与扩容机制是什么？存 1000 个元素怎么初始化？
* **`ArrayList` vs `LinkedList`**：
  * `ArrayList` 基于**动态连续数组**，支持 $O(1)$ 随机访问，默认容量 10，满后按 **1.5 倍**（`old + (old >> 1)`）扩容；
  * `LinkedList` 基于**双向链表**，随机访问 $O(n)$，每个节点多占两个指针内存且对 CPU 缓存不友好；95% 场景首选 `ArrayList`。
* **`HashMap` 底层原理**：
  * JDK 1.8 采用 **数组 + 链表 + 红黑树**。当链表长度 **$\ge 8$ 且数组容量 $\ge 64$** 时转为红黑树（容量 $< 64$ 先扩容）；节点数 $\le 6$ 时退化为链表；
  * **哈希与寻址**：`(h = key.hashCode()) ^ (h >>> 16)` 高低位异或扰动，配合 `(n - 1) & hash` 位与寻址；
  * **存 1000 个元素初始化**：扩容阈值 $= \text{Capacity} \times 0.75$。若传 1024，在存到第 $1024 \times 0.75 = 768$ 个元素时就会触发扩容！正确公式为 $1000 / 0.75 + 1 \approx 1334$，内部通过 `tableSizeFor` 向上取最小 2 的幂，实际容量为 **2048**！

#### Q10：`HashMap` 为什么线程不安全？`ConcurrentHashMap` 在 JDK 1.7 和 1.8 中是如何保证线程安全的？
* **`HashMap` 线程不安全原因**：JDK 1.7 头插法并发扩容会造成环形链表死循环；JDK 1.8 尾插法虽解决了死循环，但并发 `put` 时会发生**数据覆盖丢失**，且 `size++` 非原子。
* **`ConcurrentHashMap` 演进**：
  * **JDK 1.7**：采用 **Segment 分段锁**（继承自 `ReentrantLock`），默认 16 个分段，锁粒度较大；
  * **JDK 1.8**：采用 **Node 数组 + 链表/红黑树 + CAS + `synchronized`**。
    1. **写安全**：槽位为空时通过 **CAS** 无锁写入首节点；槽位非空时使用 **`synchronized` 仅锁住当前槽位的链表或红黑树头节点**，锁粒度极细；
    2. **读无锁**：Node 的 `val` 和 `next` 指针均用 **`volatile`** 修饰，基于 Happens-Before 原则保证可见性，读操作全程零加锁。

### 二、Java 多线程、并发锁、AQS 与 JVM（Q11 ~ Q14）

#### Q11：`synchronized` 与 `ReentrantLock` 的区别？AQS 的核心原理是什么？
* **`synchronized` vs `ReentrantLock`**：
  * `synchronized` 是 JVM 原生关键字，非公平、不可中断、自动释放锁；
  * `ReentrantLock` 是 JUC API 类，支持**公平/非公平切换、`tryLock(timeout)` 超时获取、可响应中断、绑定多个 `Condition` 条件队列精准唤醒**，必须在 `finally` 中手动 `unlock()`。
* **AQS 核心四步法**：
  1. **定位**：JUC 锁与同步器的底座，采用**模板方法设计模式**；
  2. **三大支柱**：① `volatile int state`（状态计数器，CAS 修改，在 ReentrantLock 中表示重入次数）；② **CLH 双向 FIFO 等待队列**（带 Dummy Head 虚拟头节点，前驱节点的 `waitStatus = SIGNAL(-1)` 负责在释放锁时唤醒后继）；③ **`LockSupport.park() / unpark()`** 阻塞与唤醒线程；
  3. **加锁解锁**：抢锁失败封装为 Node 尾插进队，将前驱设为 `SIGNAL` 后 `park` 挂起；释放锁时 `state--` 为 0，从 `tail` 往前扫描找到最靠近 `head` 的有效节点调用 `unpark` 唤醒（因为入队时先赋 `prev`、再 CAS `tail`、最后赋 `next`，从后往前找绝对不会漏掉正在入队的节点）。

#### Q12：线程池 `ThreadPoolExecutor` 的 7 大核心参数与任务执行流转顺序是什么？
* **7 大核心参数**：`corePoolSize`（核心线程数）、`maximumPoolSize`（最大线程数）、`keepAliveTime`（非核心线程空闲存活时间）、`unit`（时间单位）、`workQueue`（有界阻塞队列，如 `ArrayBlockingQueue`）、`threadFactory`（自定义命名线程工厂）、`handler`（拒绝策略：默认 `AbortPolicy` 抛异常、生产推荐 `CallerRunsPolicy` 主线程代跑反压限流、`DiscardPolicy`、`DiscardOldestPolicy`）。
* **四大阶段执行顺序（必背避坑！）**：
  * 提交任务 → ① 当前线程数 `< corePoolSize` 时，直接创建核心线程执行 → ② 核心线程满了，**先进入 `workQueue` 阻塞队列排队** → ③ **只有当阻塞队列也塞满了**，才创建非核心临时线程扩容至 `maximumPoolSize` → ④ 队列满且达到最大线程数，触发拒绝策略 `handler`！

#### Q13：JVM 运行时内存区域是如何划分的？类加载过程与双亲委派模型是什么？
* **JVM 内存划分**：
  * **线程私有（无 GC）**：程序计数器（唯一无 OOM）、Java 虚拟机栈（存栈帧：局部变量表、操作数栈、方法出口）、本地方法栈；
  * **线程共享（有 GC）**：Java 堆 Heap（存对象实例，分新生代 `Eden:S0:S1 = 8:1:1` 与老年代）、方法区（JDK 1.8 为**元空间 Metaspace**，使用本地物理内存存类元信息、常量池、静态变量）。
* **类加载 5 阶段**：加载（Loading）→ 验证（Verification）→ 准备（Preparation，静态变量赋零值）→ 解析（Resolution）→ 初始化（Initialization，执行 `<clinit>` 赋真实值）。
* **双亲委派模型**：
  * 加载类时先委派给父加载器（`Application → Platform/Extension → Bootstrap`），父加载器找不到才自己加载；
  * **核心作用**：**防止 Java 核心 API 被篡改**（如自定义 `java.lang.String` 不会被加载），避免类的重复加载。

#### Q14：JVM 垃圾回收（GC）如何判断对象可回收？常见的垃圾回收算法与回收器有哪些？
* **判断对象可回收**：**可达性分析算法**——从 **GC Roots**（虚拟机栈局部变量引用的对象、静态属性引用的对象、常量引用的对象、活跃线程、`synchronized` 锁对象）出发向下搜索，不可达对象进入回收。
* **分代回收算法**：新生代对象朝生夕死，采用**复制算法（Copying）**；老年代对象存活率高，采用**标记-清除（Mark-Sweep）或标记-整理（Mark-Compact）**。
* **主流回收器**：CMS（并发标记清除，低延迟但有内存碎片）、**G1（Garbage-First，JDK 9+ 默认，将堆划分为多个相等大小的 Region，兼具高吞吐与可预测停顿时间）**、ZGC（超低延迟亚毫秒级停顿）。

### 三、Spring 全家桶、MyBatis、MySQL 与 Redis（Q15 ~ Q21）

#### Q15：谈谈你对 Spring IoC 和 AOP 的理解？Spring Bean 的生命周期是怎样的？三级缓存如何解决循环依赖？
* **IoC 与 AOP**：IoC 将对象创建与依赖组装权交给容器，通过 DI 注入解耦；AOP 基于动态代理（JDK 接口代理 / CGLIB 子类代理）将事务、日志、权限等横切逻辑无侵入织入。
* **Bean 生命周期 4 大步**：
  1. **实例化（Instantiation）**：通过反射调用构造器创建 Bean 原始对象；
  2. **属性赋值（Populate）**：通过 `@Autowired` 注入依赖属性；
  3. **初始化（Initialization）**：执行 `Aware` 接口回调 → `BeanPostProcessor` 前置处理 → `@PostConstruct` / `InitializingBean.afterPropertiesSet()` → `BeanPostProcessor` 后置处理（**AOP 动态代理在此步生成！**）；
  4. **销毁（Destruction）**：容器关闭时执行 `@PreDestroy`。
* **三级缓存解决循环依赖（A 依赖 B，B 依赖 A）**：
  * 一级缓存 `singletonObjects`（成品单例池）、二级缓存 `earlySingletonObjects`（提前曝光的半成品对象）、三级缓存 `singletonFactories`（ObjectFactory 工厂，用于提前生成 AOP 代理对象）。A 实例化后先将工厂放入三级缓存，再去填充 B，B 从缓存拿到 A 的早期引用完成创建，从而打破死循环（注：构造器注入无法通过三级缓存解决循环依赖）。

#### Q16：Spring、Spring MVC、Spring Boot 和 Spring Cloud 之间是什么关系与区别？
* **演进关系**：
  1. **Spring Framework**：提供最核心的 **IoC 容器与 AOP 基石**；
  2. **Spring MVC**：基于 Spring 构建的 Web 层框架，核心是 `DispatcherServlet` 前端控制器 → `HandlerMapping` 路由 → `HandlerAdapter` 参数绑定与执行 Controller → `HttpMessageConverter` 返回 JSON；
  3. **Spring Boot（微观脚手架）**：遵循**“约定优于配置”**，通过 **`@EnableAutoConfiguration` 自动装配、Starter 依赖管理、内嵌 Tomcat 容器**，解决传统 Spring 繁琐 XML 配置问题，快速构建单个微服务；
  4. **Spring Cloud（宏观分布式治理全家桶）**：依托 Spring Boot 构建，提供**服务注册发现（Nacos/Eureka）、负载均衡（LoadBalancer）、声明式调用（OpenFeign）、配置中心（Nacos）、熔断限流（Sentinel）、API 网关（Gateway）**，解决多服务分布式协同治理问题。

#### Q17：MyBatis 中 `#{}` 和 `${}` 的区别？MyBatis 一级缓存和二级缓存是什么？
* **`#{}` vs `${}`**：`#{}` 是 `PreparedStatement` 预编译占位符 `?`，自动加单引号，**100% 防止 SQL 注入**；`${}` 是字符串直接原样拼接，有 SQL 注入风险，仅在动态传表名、列名或 `ORDER BY` 字段时配合白名单使用。
* **两级缓存**：
  * **一级缓存（默认开启）**：`SqlSession` 级别缓存（基于内部 PerpetualCache HashMap），同一个事务会话内相同查询直接走内存，执行 update/commit 后清空；
  * **二级缓存（默认关闭）**：`Mapper Namespace` 跨会话级别缓存，多个 `SqlSession` 共享，但在多表联查或分布式环境下极易产生脏读，生产环境通常禁用并改用 **Redis**。

#### Q18：MySQL 索引底层为什么用 B+ 树？聚簇索引（主键索引）与非聚簇索引（二级索引）有什么区别？什么是回表和覆盖索引？
* **为什么用 B+ 树**：非叶子节点只存索引和指针（16KB 页存 1170 个指针，**3 层即可容纳 2190 万条数据**，仅需 1~2 次磁盘 I/O）；叶子节点存所有数据且用双向链表连接，范围查询与排序极快。
* **聚簇索引 vs 二级索引（InnoDB）**：
  * **聚簇索引（主键索引）**：叶子节点直接存储**完整的行记录数据**（表数据文件本身就是按主键 B+ 树组织的）；
  * **二级索引（辅助索引）**：叶子节点存储的是**索引列的值 + 对应的主键 ID**。
* **回表与覆盖索引**：
  * **回表**：通过二级索引查到主键 ID 后，再去聚簇索引 B+ 树查一次完整行数据的过程；
  * **覆盖索引**：如果查询的列（如 `SELECT id, name FROM user WHERE name = '张三'`）刚好全部包含在二级索引树中，无需回表直接返回（`Extra: Using index`），性能大幅提升！

#### Q19：MySQL 事务四大特性（ACID）底层实现原理？四大隔离级别与 MVCC 是什么？
* **ACID 底层**：原子性靠 **Undo Log**；持久性靠 **Redo Log（WAL 预写日志 + 顺序写盘）**；隔离性靠 **MVCC + 锁**；一致性由前三者共同保障。
* **四大隔离级别**：读未提交（脏读） → 读已提交（RC，解决脏读，每次 SELECT 生成新 ReadView） → **可重复读（RR，MySQL 默认，事务首次 SELECT 生成固定 ReadView 解决快照读幻读 + Next-Key Lock 临键锁解决当前读幻读）** → 串行化。

#### Q20：Redis 常用数据类型有哪些？缓存穿透、缓存击穿、缓存雪崩怎么解决？
* **5 大基础类型**：`String`、`Hash`、`List`、`Set`、`ZSet`。
* **三大缓存危机解法**：
  1. **穿透（查根本不存在的 ID，绕过缓存直击 DB）**：**布隆过滤器（BloomFilter）前置拦截 + 缓存空对象（设短 TTL 如 60s）**；
  2. **击穿（单个超级热点 Key 过期瞬间被海量并发打穿）**：**热点 Key 逻辑永不过期 + Redisson 分布式互斥锁（只有抢到锁的线程查 DB 重建缓存）**；
  3. **雪崩（大批 Key 同一时刻集体过期或 Redis 宕机）**：**过期时间加上随机抖动值（Jitter）打散 + Redis 主从哨兵/Cluster 集群高可用 + Sentinel 限流降级**。

#### Q21：项目中用过哪些设计模式？请结合实际代码举例说明。
* **五大实战设计模式（脱口而出）**：
  1. **单例模式（Singleton）**：DCL 双重检查锁定单例（加 `volatile` 防指令重排）及 Spring 默认的单例 Bean；
  2. **模板方法模式（Template Method）**：JUC 的 **AQS**（封装排队阻塞通用骨架，子类实现 `tryAcquire`）以及项目中统一的外部接口对接抽象基类（统一封装验签、日志、异常重试，子类只实现具体报文组装）；
  3. **策略模式 + 工厂模式（Strategy + Factory）**：在商城与 ERP 系统中，针对微信支付、支付宝、银企直连等不同支付渠道，定义统一的 `PaymentStrategy` 接口，通过 `Map<String, PaymentStrategy>` 配合 Spring 依赖注入彻底消除满屏的 `if-else`；
  4. **代理模式（Proxy）**：Spring AOP 动态代理实现 `@Transactional` 事务拦截与接口审计日志。

### 代码 1：Java 8 Stream API 列表分组、过滤与 BigDecimal 聚合计算（金蝶最爱考的数据处理题）

> 💡 **真题还原**：给定一个订单商品列表 `List<OrderItem>`，请过滤出状态有效（`status == 1`）的记录，按商品分类 `category` 进行分组，并计算每个分类下的**总金额**与**平均单价**（注意金额精度）。

```java
import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.*;
import java.util.stream.Collectors;

public class KingdeeStreamDemo {
    static class OrderItem {
        String category;
        BigDecimal price;
        int status; // 1: 有效, 0: 作废

        public OrderItem(String category, String price, int status) {
            this.category = category;
            this.price = new BigDecimal(price);
            this.status = status;
        }
        public String getCategory() { return category; }
        public BigDecimal getPrice() { return price; }
        public int getStatus() { return status; }
    }

    public static void main(String[] args) {
        List<OrderItem> items = Arrays.asList(
            new OrderItem("财务软件", "1200.50", 1),
            new OrderItem("财务软件", "800.30", 1),
            new OrderItem("供应链云", "3000.00", 1),
            new OrderItem("财务软件", "999.00", 0) // 作废单据
        );

        // 1. 按分类分组，计算每个分类下的有效订单总金额 (BigDecimal 累加)
        Map<String, BigDecimal> sumByCategory = items.stream()
            .filter(item -> item.getStatus() == 1)
            .collect(Collectors.groupingBy(
                OrderItem::getCategory,
                Collectors.reducing(BigDecimal.ZERO, OrderItem::getPrice, BigDecimal::add)
            ));

        // 2. 按分类分组，计算每个分类下的平均单价 (保留 2 位小数，四舍五入)
        Map<String, BigDecimal> avgByCategory = items.stream()
            .filter(item -> item.getStatus() == 1)
            .collect(Collectors.groupingBy(
                OrderItem::getCategory,
                Collectors.collectingAndThen(
                    Collectors.toList(),
                    list -> {
                        BigDecimal sum = list.stream()
                            .map(OrderItem::getPrice)
                            .reduce(BigDecimal.ZERO, BigDecimal::add);
                        return sum.divide(BigDecimal.valueOf(list.size()), 2, RoundingMode.HALF_UP);
                    }
                )
            ));

        System.out.println("各分类总金额: " + sumByCategory);
        System.out.println("各分类平均价: " + avgByCategory);
    }
}
```

### 代码 2：SQL 经典高频题（分组聚合 Having + 窗口函数求各部门薪资 Top3）

-- 题目 1：查询订单表 t_order 中，2026年累计消费总金额超过 10000 元的客户 ID 及总金额，按总金额降序排列

### 代码 3：DCL 双重检查锁定单例模式与标准二分查找

```java
public class CoreTemplates {
    // 1. DCL 双重检查锁定单例（必加 volatile 防指令重排）
    private static volatile CoreTemplates instance;
    private CoreTemplates() {}

    public static CoreTemplates getInstance() {
        if (instance == null) {
            synchronized (CoreTemplates.class) {
                if (instance == null) {
                    instance = new CoreTemplates();
                }
            }
        }
        return instance;
    }

    // 2. 标准闭区间二分查找
    public static int binarySearch(int[] arr, int target) {
        if (arr == null || arr.length == 0) return -1;
        int left = 0, right = arr.length - 1;
        while (left <= right) {
            int mid = left + ((right - left) >> 1);
            if (arr[mid] == target) return mid;
            else if (arr[mid] < target) left = mid + 1;
            else right = mid - 1;
        }
        return -1;
    }
}
```

### 1. 软技能高频追问（针对“服务族 | RBU | 贵阳”岗位特性）

#### ❓ 追问 1：“你如何理解服务族 RBU 的‘应用开发工程师’？和纯底层研发有什么不同？”

  * “我认为 RBU 的应用开发工程师是**连接金蝶先进技术底座（如苍穹 aPaaS 平台）与大型企业真实核心业务场景的桥梁**。相比于只写通用底层组件，应用开发不仅要求扎实的 Java、数据库与微服务功底，更要求我们具备**极强的业务抽象能力、跨系统集成联调能力以及快速排查客户现场复杂问题的能力**。看到自己写的代码真正帮一家大型企业跑通财务核算或供应链流转，这种直接创造业务价值的成就感正是我非常向往的。”

#### ❓ 追问 2：“如果在项目交付过程中，客户提出了紧急的需求变更，或者发现线上数据对不上，你会怎么处理？”
* 🗣️ **满分回答**：
  * “我会遵循**‘先稳住现场与排查定界、再评估影响与协同推进’**的原则：
    1. 如果是线上数据异常，第一时间保留现场日志，利用请求流水号、数据库审计记录与事务链路快速定位是接口重发、并发竞争还是边界逻辑遗漏，先给出临时止血方案并修复闭环；
    2. 如果是紧急需求变更，先与客户或实施顾问沟通清楚背后的**真实业务诉求**（很多时候客户要的是某种业务结果，可以通过配置或更轻量的方式实现），评估对现有模块与交付工期的影响，与项目经理对齐优先级后高效交付。”
