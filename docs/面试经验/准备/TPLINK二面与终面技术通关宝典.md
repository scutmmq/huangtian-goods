### Q1：TCP 三次握手与四次挥手深度剖析（为什么握手不能两次？TIME_WAIT 与 CLOSE_WAIT 排查）

#### 1. 为什么三次握手不能是“两次握手”？（核心本质）
* **如果只有两次握手，服务端发送完 SYN+ACK 就单方面认为连接建立**：
  * **历史失效报文引起的资源耗尽（历史连接/旧连接重现）**：
    客户端发送的第一个连接请求报文段 $SYN_1$ 因网络拥塞在某个网络路由器节点滞留；
    客户端超时后重新发送了第二个连接请求 $SYN_2$，成功建立连接并传输完毕后关闭了连接；
    此时滞留的旧报文 $SYN_1$ 终于到达服务端。如果只有两次握手，服务端收到 $SYN_1$ 立即建立新连接并分配缓冲区内存，一直傻傻等待客户端发数据；而客户端此时并没有发起连接，直接忽略服务端的确认，导致服务端单向建立大量“僵尸连接”，**耗尽内存资源与端口**！
  * **三次握手才能保证双方“序列号（ISN）”与“双向收发能力”的对齐确认**。

#### 2. 三次握手中的内核队列：半连接队列 vs 全连接队列
```
客户端 ──[SYN]──> 服务端 (内核放入【半连接队列 (SYN Queue)】，状态变为 SYN_RCVD)
客户端 <──[SYN+ACK]── 服务端
客户端 ──[ACK]──> 服务端 (内核从半连接队列取出，放入【全连接队列 (Accept Queue)】，状态变为 ESTABLISHED)
                                      │
                                      ▼
                             用户进程调用 accept() 取出连接
```
* **SYN Flood（洪水攻击）**：攻击者短时间内伪造海量虚假 IP 发送 SYN 包，但不回应第三次 ACK，导致服务端的**半连接队列瞬间被占满**，正常用户无法建立连接。
* **防护手段**：开启操作系统的 `net.ipv4.tcp_syncookies = 1`。当半连接队列满时，服务端不保存连接状态，而是根据源 IP、端口和时间戳哈希计算出一个 Cookie 作为序列号发回，客户端回应 ACK 时校验合法的 Cookie 才直接创建连接。

#### 3. 为什么四次挥手客户端要有 `TIME_WAIT` 状态？为什么必须是 2MSL？
* **MSL（Maximum Segment Lifetime，最大报文段生存时间）**：任何报文在网络中的最长存活寿命（默认通常为 30 秒或 60 秒）。
* **客户端在发送完最后的 ACK 后，必须在 `TIME_WAIT` 状态等待 $2 	imes MSL$**，原因有二：
  1. **防止最后的 ACK 丢失，确保被动关闭方能够正确关闭**：
     若客户端最后的 ACK 丢失，服务端因收不到 ACK 会重新发送 FIN 报文。$2MSL = 1MSL(	ext{ACK 丢失耗时}) + 1MSL(	ext{重传 FIN 到达耗时})$。等待 2MSL 确保即使 ACK 丢了，客户端能收到重传的 FIN 并重发 ACK；
  2. **彻底消灭网络中迷途的残留旧报文**：
     确保本次连接产生的所有数据包都已在网络中自然消亡，防止新建连接（复用相同四元组：源IP、源端口、目的IP、目的端口）时把上一次连接的旧数据包当作新数据错收。

#### 4. 生产高频故障排查：线上大量 `TIME_WAIT` vs 大量 `CLOSE_WAIT`

| 异常状态 | 发生在谁身上 | 根本原因 | 工业级生产排查与排障手段 |
| :--- | :--- | :--- | :--- |
| **大量 `TIME_WAIT`** | **主动关闭连接的一方**<br>(常见于反向代理 Nginx 或高并发 Web 客户端) | 业务端存在大量**短连接**（高 QPS 下不断新建连接后立刻主动 `close()`）。 | 1. 开启 HTTP 的 **Keep-Alive 长连接**（让连接复用，避免频繁断开）；<br>2. 调整 Linux 内核参数复用端口：`net.ipv4.tcp_tw_reuse = 1`；<br>3. 扩大可用本地端口范围：`net.ipv4.ip_local_port_range`。 |
| **大量 `CLOSE_WAIT`** | **被动关闭连接的一方**<br>(常见于后端 Java/Go 业务应用服务) | **自身代码存在连接泄露 Bug**！对方已经发了 FIN 报文关闭连接，而我方代码在收到关闭信号后，**没有调用 `socket.close()` 释放连接资源**！ | 1. 立即排查后端代码：`HttpClient` 连接池是否未释放、DB 连接/流对象是否有未关闭的 `InputStream`；<br>2. 检查是否有死锁或重度阻塞导致应用线程卡死无法执行关闭代码。 |

### Q2：TCP 如何实现绝对可靠传输？（滑动窗口、超时重传、流量控制与 BBR 拥塞控制）

#### 1. 基础可靠三大基石
* **校验和（Checksum）**：检测数据在传输中是否被破坏，破坏则丢弃；
* **序列号（Seq）与确认应答（ACK）**：按序接收，解决网络乱序、丢包与重复包问题；
* **超时重传（RTO）与快速重传（SACK）**：
  * **超时重传**：发送方启动定时器，超过 RTO（动态计算的往返时间平滑值）未收到 ACK 则重发；
  * **快速重传（Fast Retransmit）**：无需等待定时器超时！当发送方连续收到 **3 个重复的 ACK**（Dup ACK），立即意识到某一个报文丢失，立刻触发该报文的重传；配合 **SACK（选择性确认）**，只重传丢失的那一片，不重发后续已收到的报文。

#### 2. 流量控制（Flow Control） vs 拥塞控制（Congestion Control）
* **流量控制（端到端）**：
  * **目的**：防止发送方发得太快，撑爆接收方的 **接收缓冲区（Receive Buffer）**。
  * **手段**：通过 TCP 报头中的 **滑动窗口（Window Size, rwnd）** 动态告知对方自己还能接收多少字节。
  * **零窗口死锁与探测报文（Zero Window Probe）**：如果接收方窗口为 0，发送方暂停发送；接收方腾出空间后发出的窗口更新 ACK 若在网络中丢了，双方会陷入相互等待的死锁！因此发送方会启动持续定时器，定期发送 **1 字节的窗口探测报文** 探活。
* **拥塞控制（网络全局）**：
  * **目的**：防止发送方把过多数据塞入整个网络路由器，导致网络交换机队列溢出并雪崩丢包。
  * **经典四步算法（CUBIC 传统流派）**：
    1. **慢启动（Slow Start）**：拥塞窗口 $cwnd$ 从 1 开始呈**指数级爆炸增长**（$1 
ightarrow 2 
ightarrow 4 
ightarrow 8$）；
    2. **拥塞避免（Congestion Avoidance）**：当 $cwnd$ 达到慢启动阈值 $ssthresh$ 时，改为**线性加法增大**（+1）；
    3. **拥塞发生（Fast Retransmit）**：一旦发生丢包，阈值 $ssthresh$ 砍半；
    4. **快恢复（Fast Recovery）**：$cwnd$ 设置为减半后的阈值，快速恢复数据传输。
  * **Google BBR 算法（现代革命性算法，TP-LINK 高频加分项）**：
    传统 CUBIC 算法以“丢包”作为网络拥塞的触发标志，但在无线 WiFi 或长距离高带宽网络中，丢包往往是偶发物理抖动而非拥塞，导致 CUBIC 盲目减速大幅降低吞吐！**BBR 放弃了丢包检测，直接测量网络的“最大瓶颈带宽（BtlBw）”与“最小往返时延（RTprop）”，永远让数据量维持在管道的最大物理容量，榨干网络吞吐！**

### Q3：TCP 黏包与半包产生本质与三大工业级解决方案

#### 1. 产生根本原因：TCP 是面向无边界的“流（Stream）协议”
* **TCP 不知道上层应用业务协议的边界**：
  * **黏包（Packet Splice）**：发送方发送了两个独立的请求 `Hello` 和 `World`，由于发送端开启了 **Nagle 算法**（合并小数据包减少网络传输开销）或接收端处理不及时，接收缓冲区里将两段数据粘在一起读出：`HelloWorld`；
  * **半包（Packet Fragment）**：发送的数据大于了 TCP 的最大报文段长度（MSS）或网络 MTU（通常 1500 字节），数据包被操作系统强行切片，接收方一次只读到了半截数据：`Hel`。

#### 2. 三大工业级终极解决方案

```
  方案一：固定长度 (Fixed-Length)
  [Hello               ] [World               ] -> 不足部分补空格/0，浪费带宽！

  方案二：特殊分隔符 (Delimiter)
  [Hello
] [World
] -> 遇到特殊字符作为结尾，内容中出现换行需转义

  方案三：自包含长度协议头 (Header-Length / TLV 模式，业界标准黄金实践！)
  +----------------+----------------+
  | Length (4 字节)| Body (实际内容) |
  +----------------+----------------+
  | 5              | Hello          |
  | 5              | World          |
```

> 💡 **生产实现（Netty 落地）**：在后端开发中，通常直接使用 Netty 提供的 `LengthFieldBasedFrameDecoder` 解码器，在数据帧头部用 2 或 4 个字节明确声明 Body 长度，完美彻底解决黏包与半包！

### Q4：高并发网络 I/O 模型演进与 Epoll 底层机制（Select vs Poll vs Epoll，LT vs ET）

#### 1. I/O 模型全景对比矩阵

| I/O 模型 | 核心运作机制 | 核心缺陷与瓶颈 |
| :--- | :--- | :--- |
| **阻塞 I/O (BIO)** | 调用 `read()/write()` 时，线程挂起等待直到网卡数据就绪并拷贝到用户态。 | 一个连接必须绑定一个线程，并发数受限于系统线程数，内存开销巨大。 |
| **非阻塞 I/O (NIO)** | 调用 `read()` 无数据立即返回 `EWOULDBLOCK`，通过用户态死循环轮询。 | 轮询极度浪费 CPU 算力，空转消耗资源。 |
| **I/O 多路复用** | 一个线程通过 `select/poll/epoll` 监听成千上万个 Socket 的就绪事件。 | **单线程管理海量连接，高并发核心基石**。 |

#### 2. Select vs Poll vs Epoll 核心底层机制对比

| 对比维度 | `select` | `poll` | `epoll` (Linux 现代高并发黄金标准) |
| :--- | :--- | :--- | :--- |
| **最大连接数限制** | 默认 **1024**（由 `FD_SETSIZE` 宏决定） | 无硬编码限制（基于链表），但连接多时性能暴跌 | **仅受限于操作系统最大文件描述符数**（如几十万） |
| **文件描述符传递开销** | 每次调用都要把所有 fd 从用户态**全量拷贝**到内核态 | 同样每次都要进行全量用户态/内核态拷贝 | **零重复拷贝**！通过 `epoll_create` 在内核维护一张**红黑树**，增删改 fd 仅通知变动 |
| **事件通知检测复杂度** | $O(N)$ 轮询扫描整个 fd 集合 | $O(N)$ 轮询扫描整个链表 | **$O(1)$ 中断回调就绪链表**！网卡有数据触发硬件中断，仅把活跃的 fd 挂入双向链表，`epoll_wait` 只取就绪链表！ |

#### 3. Epoll 水平触发（LT） vs 边缘触发（ET）的本质区别

```
  数据到达缓冲区 (水位上升) ──>
  【水平触发 (LT - Level Triggered，默认模式)】
  只要缓冲区里有数据，每次 epoll_wait 都会反复通知！容错率高，但系统调用次数多。

  【边缘触发 (ET - Edge Triggered，极致性能模式)】
  只有当缓冲区状态从“无数据”变成“有数据”的那一瞬间（跳变边缘）通知一次！
  后续即使还有剩余数据，绝不再通知！
  ⚠️ 生产规范：使用 ET 模式必须搭配【非阻塞 I/O (O_NONBLOCK)】+【while 循环读到返回 EAGAIN 为止】，否则会导致未读完的数据永久滞留！
```

#### 1. HTTP 1.0 $

* **HTTP 1.0**：每个请求必须新建一次 TCP 连接，三次握手四次挥手极其浪费；
* **HTTP 1.1**：

* **二进制分帧（Binary Framing Layer）**：将原来的 ASCII 纯文本格式改为二进制帧（Headers 帧和 Data 帧）；
* **多路复用（Multiplexing，解决应用层队头阻塞）**：
  * 同一个 TCP 连接上可以并发交替传输多个数据流（Stream），每个帧被打上 Stream ID。客户端与服务端能够乱序收发不同请求的数据，在接收端根据 Stream ID 重新组装！**彻底消除了应用层的队头阻塞**！
* **头部压缩（HPACK）**：维护动态静态字典，只传输差异 Header，大幅节省带宽；
* **服务端推送（Server Push）**：服务器可以在客户端请求 HTML 时，主动推送 CSS 和 JS。

#### 3. HTTP 2.0 $
ightarrow$ 3.0 (QUIC)（从 TCP 革命到 UDP 拥抱）
* **为什么 HTTP 2.0 还不够完美？—— TCP 层面的队头阻塞！**
  * HTTP 2.0 的多路复用把所有请求绑在**同一个 TCP 连接**上。
  * 一旦网络中发生了一个数据包丢包，TCP 的滑动窗口协议为了保证按序交付，**会把后续所有 Stream 全部卡住，直到丢失的包重传成功！此时一个丢包会让整条连接上的并发请求全部降速**！
* **HTTP 3.0 的终极解法：放弃 TCP，基于 UDP 实现 QUIC 协议！**

### Q7：局域网核心通信协议攻坚（路由器与硬件强相关：ARP、ICMP Ping、DHCP、NAT 穿透）

> 💡 **TP-LINK 专属灵魂考点**：路由器的核心职责就是负责局域网寻址、IP 分配与公网路由转换！

#### 1. ARP 协议（地址解析协议，Address Resolution Protocol）
* **核心功能**：在同一个局域网中，**将已知的逻辑 IP 地址解析为物理网卡 MAC 地址**。
* **工作机制**：
  1. **ARP 请求（广播广播）**：主机 A 想给 IP 为 `192.168.1.5` 的主机 B 发数据，先查本地 ARP 缓存表。若无，在局域网内发送 ARP 广播帧（目的 MAC 为 `FF:FF:FF:FF:FF:FF`），问：“谁是 192.168.1.5？请告诉我你的 MAC！”
  2. **ARP 应答（单播响应）**：主机 B 收到后，回复单播报文：“我是 192.168.1.5，我的 MAC 是 `AA:BB:CC:DD:EE:FF`”。主机 A 将映射关系记录在 ARP 缓存表（有 TTL 老化时间）。
* **ARP 欺骗攻击（ARP Spoofing）与防护**：
  * 黑客主机向路由器和受害者冒充对方的 MAC 地址，截获局域网全部流量。
  * **防御**：路由器绑定静态 ARP 表，开启交换机动态 ARP 检查（DAI）。

#### 2. ICMP 协议（互联网控制报文协议）与 Ping / Traceroute
* **Ping 底层原理**：
  * 发送端封装 ICMP 报文，类型为 **Echo Request（回显请求，Type=8）**；
  * 目标主机收到后，回复一个 **Echo Reply（回显应答，Type=0）**；
  * 计算往返耗时 RTT 与丢包率。
* **Traceroute（路由跟踪）底层原理（巧妙利用 TTL 递增！）**：
  * IP 报头中有一个字段叫 **TTL（Time to Live，生存跳数）**，每经过一个路由器减 1，为 0 时路由器将丢弃该包并向源主机回送 **ICMP Time Exceeded（超时差错报文，Type=11）**；
  * Traceroute 发送第一个包 $TTL=1$，第一个路由器收到后 TTL 减为 0，丢包并回传 ICMP 超时，源主机由此得知第一跳路由器的 IP；
  * 随后发送 $TTL=2$ 探测第二跳……依次类推，直到到达目的主机，精准画出整条网络路径！

#### 3. DHCP 协议（动态主机配置协议，DORA 四步流程）
局域网设备接入 WiFi 后自动获取 IP 的过程：
1. **DHCP Discover（发现，广播）**：客户端无 IP，发送广播向局域网喊话：“谁是 DHCP 服务器？我需要一个 IP！”
2. **DHCP Offer（提供，广播或单播）**：路由器 DHCP 服务保留一个空闲 IP，发回包含 IP、子网掩码、租期的 Offer；
3. **DHCP Request（请求，广播）**：客户端正式申请该 IP；
4. **DHCP Ack（确认）**：路由器确认分配，客户端绑定 IP 并开始上网。

#### 4. NAT 与 NAPT（网络地址转换，路由器核心功能）
* **背景**：IPv4 地址枯竭，家庭设备使用的是私网 IP（`192.168.x.x`），无法直接在公网上路由。
* **NAPT（网络端口地址转换）**：
  * 路由器拥有唯一的公网 IP；
  * 内部主机 `192.168.1.100:5000` 访问百度时，经过路由器，路由器将源 IP 和端口改写为自己的公网 IP 和随机分配的端口 `202.100.1.1:8888`，并在内核记录 **NAT 映射表**；
  * 百度回包到 `202.100.1.1:8888`，路由器查表将目的地址换回 `192.168.1.100:5000` 并转发给内部主机。

### Q8：物联网与音视频通信协议（MQTT QoS 0/1/2、WebSocket 全双工、RTSP 视频拉流）

#### 1. MQTT 协议（轻量级物联网发布/订阅协议）
* **特点**：极其轻量（固定报头仅 2 字节），专为低带宽、不可靠网络、资源受限设备（如摄像头、传感器）设计。
* **QoS（服务质量）三大等级（TP-LINK 智能硬件必考！）**：
  * **QoS 0（At most once，最多一次）**：只管发送，不保证送达，网络丢包就丢了（适用于高频上报的环境温度数据）；
  * **QoS 1（At least once，至少一次）**：必须收到 PUBACK 确认，超时未收则重传，**确保必须送达，但可能重复**（需业务层幂等，适用于开关门锁状态）；
  * **QoS 2（Exactly once，恰好一次，最安全也最重）**：四步握手（PUBLISH -> PUBREC -> PUBREL -> PUBCOMP），**通过序列号严格确保仅且仅送达一次，绝不重复**（适用于金融支付或敏感指令）。

#### 2. WebSocket 协议 vs HTTP 轮询
* **全双工双向通信**：基于单一 TCP 连接，客户端和服务端可以同时主动推送数据；
* **握手过程**：复用 HTTP 协议的 80/443 端口，通过在 HTTP 报头加入 `Upgrade: websocket` 与 `Sec-WebSocket-Key` 进行协议升级握手，握手完成后脱离 HTTP 直接走二进制帧通信。

#### 3. RTSP / RTMP / WebRTC 视频流通信（安防摄像头核心）
* **RTSP（Real Time Streaming Protocol）**：
  * **控制面与数据面分离**：RTSP 本身运行在 TCP 之上，只负责播放控制（SETUP, PLAY, PAUSE, TEARDOWN，像遥控器）；真正的音视频数据流由底层的 **RTP（基于 UDP 高速传输音视频帧）** 与 **RTCP（监控服务质量）** 传输；
  * **WebRTC**：毫秒级超低延迟点对点传输（P2P），内置 ICE/STUN/TURN NAT 穿透与防抖动网络算法，现代 IPC 监控云查看首选。

### 1. JVM 内存结构、垃圾收集器演进（CMS vs G1 vs ZGC）与线上 OOM 排查 SOP

#### 1. JVM 运行时数据区的物理本质
* **程序计数器（Program Counter Register）**：CPU 时间片轮转切换时记录当前线程执行到哪一行字节码指令。**唯一一个在 JVM 规范中没有规定任何 OOM 的区域**！
* **虚拟机栈与本地方法栈**：线程私有，每个方法调用产生一个栈帧（局部变量表、操作数栈、动态链接、方法出口）。深度溢出报 `StackOverflowError`，动态扩容申请不到内存报 `OutOfMemoryError`。
* **堆（Heap）**：分代假说（绝大部分对象朝生夕死），`Eden:S0:S1 = 8:1:1`，空间分配担保。
* **元空间（Metaspace）**：移出永久代，使用本地内存（Native Memory），存放类元数据，受限于操作系统物理内存。

#### 2. 四代垃圾回收器演进的本质动力：**“如何缩短 STW（Stop The World）停顿时间”**
1. **Parallel Scavenge / Old**：追求**吞吐量优先**，多线程并行回收，但 Full GC 停顿长达数秒；
2. **CMS（Concurrent Mark Sweep）**：**第一款并发收集器**，开启“并发标记”时代。
   * **四阶段**：初始标记（STW） $
ightarrow$ 并发标记（耗时最长，与用户线程并发） $
ightarrow$ 重新标记（STW，修正在并发期间变动的对象） $
ightarrow$ 并发清除；
   * **两大致命缺陷**：基于**标记-清除**产生大量内存碎片，无法分配大对象时提前触发 Full GC；产生“浮动垃圾（Floating Garbage）”。
3. **G1（Garbage-First）**：**“化整为零，可预测停顿”**。
   * 彻底打破物理分代，将堆切分成几千个大小相等的 **Region（1MB~32MB）**；
   * 优先回收**垃圾最多、收益最高（Garbage-First）**的 Region；基于**标记-整理（Copy 复制算法）**，彻底消除内存碎片；通过 `-XX:MaxGCPauseMillis` 设定目标停顿时间。
4. **ZGC（Z Garbage Collector）**：**单色指针与读屏障革命**。
   * 将 STW 停顿压制在 **1毫秒以内**！
   * 采用 **染色指针（Colored Pointers）** 在 64 位指针头部存放元数据标志位，配合 **读屏障（Load Barrier）** 实现对象在并发转移（Relocation）时的自愈修复！

#### 3. 线上 OOM 排查四步极速 SOP
1. **定位高负载线程**：`top` 找到高 CPU/内存 Java 进程 PID $
ightarrow$ `top -Hp <PID>` 找到最占资源的线程 TID $

### 2. MySQL 三大日志（Redo/Undo/Binlog 与两阶段提交）、MVCC 与 B+ 树物理优势

#### 1. 三大日志的分工与两阶段提交
* **Undo Log（回滚日志）**：实现**原子性（A）**与 MVCC 版本链。记录相反的操作（INSERT 记 DELETE，UPDATE 记旧值），回滚时逆向执行。
* **Redo Log（重做日志）**：实现**持久性（D）**与 Crash-Safe。WAL（Write-Ahead Logging）机制，顺序写磁盘 `ib_logfile`，断电重启通过 Redo Log 重放脏页。
* **Binlog（归档日志）**：MySQL Server 层的逻辑日志，用于**主从复制**与数据恢复。
* **两阶段提交（Two-Phase Commit）的物理必要性**：
  * **问题**：如果写完 Redo Log 还没写 Binlog 机器突然断电，重启后 Redo 恢复了数据，但从库根据 Binlog 同步就会少这一条，主从永久不一致！
  * **解法**：`Prepare 阶段`（写 Redo Log 并置为 prepare 状态） $
ightarrow$ `Commit 阶段`（写 Binlog 并刷盘，最后将 Redo Log 置为 commit 状态）。**以此为事务最终生效的唯一标尺，保证物理一致**！

#### 2. MVCC（多版本并发控制）核心推导
* **解决什么问题**：读写不加锁，并发读写不冲突（快照读）。
* **底层两大支撑**：
  1. **Undo Log 版本链**：每条记录隐藏两个字段：`trx_id`（最后修改事务 ID）和 `roll_pointer`（回滚指针，指向历史版本）。
  2. **ReadView（读视图）**：生成快照时活跃的事务 ID 数组（包含 `min_trx_id`、`max_trx_id`、`creator_trx_id`、`m_ids`）。
* **可见性法则**：事务只能看到比自己更早提交的版本，活跃未提交的版本不可见，顺着 Undo Log 回滚指针找历史可见版本。

#### 3. 为什么 B+ 树是数据库索引的最优解？（三点物理对比）
1. **相比二叉树/红黑树**：B+ 树是“高扇出、极矮胖”（三层可存 2000 万数据），**只经历 2~3 次磁盘 I/O 寻道**，而二叉树树高几十层，磁盘 I/O 慢几百倍；
2. **相比 B 树（B-Tree）**：
   * B 树每个节点都存完整行数据，导致单个 16KB 页存的 Key 极少，树高变大；**B+ 树非叶子节点只存 Key+指针，一个页能存上千个索引，让树极度矮胖**；
3. **相比哈希索引**：B+ 树所有叶子节点构成**双向有序链表**，天然支持 `WHERE age BETWEEN 18 AND 30` 的高效范围查询与排序。

### 3. Redis 8 大内存淘汰策略记忆心法、双写一致性与击穿/穿透/雪崩防线

#### 1. 8 大淘汰策略心法公式：`1 (默认不淘汰) + 2 大范围 (volatile / allkeys) 各配算法`

```
volatile 范围（只动带过期时间的 key）：
2. volatile-lru    (最久未被使用)
3. volatile-lfu    (使用频次最低)
4. volatile-random (随机淘汰)
5. volatile-ttl    (快要过期的先淘汰)
---
allkeys 范围（所有 key 一视同仁挑选）：
6. allkeys-lru     (全部 key 中最久未用)
7. allkeys-lfu     (全部 key 中使用频次最低)
8. allkeys-random  (全部 key 随机淘汰)
```
* **LRU vs LFU 差异**：LRU 容易因突发批量扫描发生“缓存污染”（把原本的热点挤掉）；LFU 引入“访问计数器”，彻底免疫突发扫描！
* **Redis LRU 底层**：不是双向链表，而是 **近似采样 LRU**（随机抽取 5 个样本淘汰最旧的，省去 16 字节前后指针开销）。

#### 2. 双写一致性最优解：Cache-Aside Pattern + 延迟双删 / Canal
* **先更新数据库，再删除缓存**：
* 兜底防线：
  * **延迟双删**：写数据库后先删一次，延时 500ms（等待其他并发读请求把脏数据载入完）再删一次；
  * **Canal 监听 Binlog 异步删除**：将缓存删除与业务逻辑解耦，即使删除失败通过 MQ 自动重试，保证最终一致性。

#### 3. 缓存穿透、击穿、雪崩三兄弟与布隆过滤器

| 灾难名称 | 发生本质与现象 | 工业级解决方案 |
| :--- | :--- | :--- |
| **缓存穿透** | 故意访问大量**数据库和缓存中都不存在**的虚假 Key，请求直接穿透到 DB。 | 1. **布隆过滤器（Bloom Filter）** 在网关层前置拦截；<br>2. 缓存空值并设置短过期时间（如 60 秒）。 |
| **缓存击穿** | 某一个**极端热点的 Key 突然到期失效**，瞬间海量并发打向 DB。 | 1. 热点数据永不过期（后台异步刷新）；<br>2. 互斥分布式锁（未命中缓存时抢分布式锁，只有一个线程查库回写）。 |
| **缓存雪崩** | **海量 Key 在同一时间大面积集中过期**，或 Redis 单机宕机。 | 1. 过期时间增加**随机扰动值**（如 `10分钟 + Random(0~300秒)`），打散过期时间；<br>2. Redis 部署哨兵/集群高可用架构。 |

### 场景一：服务器突然宕机，如何保证数据绝对不丢失？（纵深防御 4 步法）

面试官问：“业务跑得好好的，机器电源被拔了或者服务器突然宕机，你如何从系统架构上保证数据一条都不丢？”

#### 架构破局 4 步法（面试标准满分回答）
1. **第一步：单机内存态到磁盘态的强刷盘（WAL 预写日志）**：
   * 内存数据在断电时瞬间挥发。任何写操作**必须先写顺序日志后写内存**；
   * **MySQL**：配置 `innodb_flush_log_at_trx_commit = 1`，每次事务提交强制将 Redo Log 物理刷盘到磁盘；
   * **Redis**：配置 AOF 为 `appendfsync always`（极度重要数据）或 `everysec`，断电最多丢失 1 秒数据。
2. **第二步：防御物理磁盘损坏 —— 跨机器多副本与共识复制（Replication & Consensus）**：
   * 单机如果物理主板烧毁，磁盘直接损坏，单机落盘也无济于事。必须使用分布式多副本；
   * **方案**：采用 **Raft / Paxos 共识算法**，或者 MySQL 半同步复制（Semi-Sync Replication）：**主库必须等待至少一个从库接收并写入 Relay Log 确认后，才向客户端返回写入成功**！
3. **第三步：消息队列处理中宕机的补偿（ACK 确认机制与状态机）**：
   * 如果从 MQ（Kafka/Pulsar/RocketMQ）拉出数据正在处理时服务器宕机：
   * **机制**：消费者**绝对不能开启自动 ACK**！必须在业务处理完成且落库成功后，才手动调用 ACK；若宕机未 ACK，MQ 超时后会自动将消息重新投递给其他节点；
   * 业务表设计状态机（`status = PENDING`），更新时带版本号乐观锁（CAS），保证重试时的幂等性。
4. **第四步：优雅停机（Graceful Shutdown）与事后兜底对账**：
   * 针对主动发版或平滑重启：监听操作系统的 `SIGTERM` 信号，拒绝接收新流量，等待线程池中已有的在途任务全部执行完毕后再注销容器；
   * 后台维护低频对账任务（XXL-JOB），定时扫描状态滞留在 `PENDING` 超过阈值的单据，执行状态对账与补偿修复。

### 场景二：海量数据查找 —— 40万或40亿数据，给三个数字，如何快速判断存不存在？

面试官问：“给你 40 万个数字，再给你 3 个数字，怎么判断在不在？如果数据量变成 40 亿个数字呢？”

#### 1. 当数据量较小（40 万个数字）：
* **40 万个整数的物理体积**：$400,000 	imes 4 	ext{ 字节} pprox 1.6 	ext{ MB}$！
* **解法**：
  * **内存完全无压力**！直接加载到内存中的 `HashSet`，查询时间复杂度为 $O(1)$；
  * 或者直接数组排序，进行**二分查找（Binary Search）**，时间复杂度为 $O(\log N)$，空间复杂度极低。

#### 2. 当数据量跃升至海量（40 亿个数字，面试核心考点！）：
* **痛点**：若使用哈希表存 40 亿个 64 位整数，加上指针和哈希节点开销，需要超过 **30 GB ~ 60 GB** 内存，单机内存直接爆掉！
* **终极解法：BitMap（位图法，秒杀全场！）**：
  * **数学计算（极度惊艳）**：
    每个数字不管多大，只需要用 **1 个 bit（0 或 1）** 来标识它是否存在！
    $$40 	ext{ 亿 bits} = rac{4,000,000,000}{8 	imes 1024 	imes 1024} 	ext{ MB} pprox \mathbf{476 	ext{ MB}}！$$
  * **结论**：**原本需要几十 GB 的数据，用一个 500MB 的 BitMap 字节数组即可在内存中轻松容纳！**
  * **底层寻址定位公式（位运算极速定位）**：
    判断数字 $N$ 是否存在：
    ```java
    int byteIndex = N / 8; // 定位在第几个 byte
    int bitIndex = N % 8;  // 定位在当前 byte 的第几个 bit
    boolean exists = (bitmap[byteIndex] & (1 << bitIndex)) != 0;
    ```
    时间复杂度是物理极限的 **$O(1)$**，给 3 个数字做 3 次位运算即可瞬时得出结论！
* **延伸扩展（如果数据稀疏或包含字符串）**：
  * 若数据分布极其稀疏：使用 **Roaring BitMap**（按高 16 位分桶，动态根据数据密度选用 ArrayContainer 或 BitMapContainer，进一步压缩空间）；
  * 若数据是复杂字符串（如 URL/身份证）：使用 **布隆过滤器（Bloom Filter）** 进行多哈希映射，或者采用 **Hash 取模分治**，将数据切分成 1000 个磁盘小文件分别排重。

### 智力题 3：1000 瓶药水 1 瓶有毒，最少几只小白鼠 24 小时内找出？（二进制编码模型）

* **题目**：1000 瓶无色无味的药水，其中 1 瓶有剧毒，老鼠喝了任何剂量的毒药会在 24 小时后死亡。你只有 24 小时时间，最少用几只小白鼠可以一次性测出哪瓶是毒药？
* **答案**：**10 只小白鼠**！
* **数学建模（状态空间二进制编码）**：
  * 每只老鼠在 24 小时后只有两种状态：**死 (1) 或 活 (0)**。
  * $N$ 只老鼠能够表达的状态组合数为 $2^N$ 种；
  * $2^9 = 512 < 1000$，而 **$2^{10} = 1024 > 1000$**，因此 10 只老鼠完全可以覆盖 1000 瓶药水！
* **实操喂药方案**：
  * 把 1000 瓶药水按照二进制编号：`0000000001` 到 `1111101000`（10 位二进制）；
  * 10 只老鼠分别代表二进制的 10 个 Bit 位（第 0 位 ~ 第 9 位）；
  * 如果第 $K$ 瓶药水的二进制表示中第 $i$ 位是 1，就把第 $K$ 瓶药水喂给第 $i$ 只老鼠喝；
  * 24 小时后，观察哪几只老鼠死了。若第 0、2、5 只老鼠死亡，对应的二进制数为 `...0000100101`，换算成十进制即可精准锁定对应的毒药瓶号！

### 智力题 4：两根不均匀香每根烧完 1 小时，如何测出 15 分钟与 45 分钟？（两头同时点燃法）

* **题目**：两根材质不均匀的香，每根完全烧完刚好需要 1 小时。如何用它们精准测量出 45 分钟和 15 分钟？
* **解题核心思路（双向燃烧速度翻倍）**：
  * 一根香点燃两头，不管材质多不均匀，**两头相遇烧完的时间必定恰好是 30 分钟（半小时）**！
* **测量 45 分钟步骤**：
  1. 同时点燃 **第一根香的两头**，以及 **第二根香的一头**；
  2. 当第一根香两头烧完熄灭时，时间刚好过去 **30 分钟**；此时第二根香还剩下正好可以烧 30 分钟的长度；
  3. 在第一根香熄灭的瞬间，**立即点燃第二根香的另一头**！
  4. 此时第二根香变为两头同时燃烧，剩下的 30 分钟长度将在 **15 分钟** 内烧完；
  5. 从一开始到第二根香完全熄灭，总时间就是：$30 + 15 = \mathbf{45 	ext{ 分钟}}$！
* **测量 15 分钟步骤**：
  * 同上流程，第二根香被点燃两头开始，到其完全熄灭的时间段，就是精准的 **15 分钟**！

> 2. 针对生成端，核心监控 **Faithfulness（防幻觉真实性）**。通过**动态 Nonce 标签隔离检索上下文**防止指令越狱，并在 Prompt 中设定**严格置信度拒答边界**，将真实忠实度从 73% 提高至 94.6%。  
> 整套评测已封装为自动化脚本嵌入日常迭代，有效防止了效果退化。”

### Q2：RAG 检索全流程端到端详解（6 步时序图与工业级实现）

#### 1. 端到端 6 步架构流水线

```
用户提问 Query
    │
    ▼
【Step 1: Query 预处理与实体补全】─── 代词指代消解、实体提取、同义词扩展
    │
    ├─────────────────────────────────────────┐
    ▼ (并发双路召回)                            ▼
【Step 2A: 向量语义召回 (Dense)】           【Step 2B: BM25 稀疏召回 (Sparse)】
DashScope text-embedding-v3                 本地 Lucene / ES 倒排索引
pgvector halfvec 余弦相似度检索              精准匹配专有名词、设备型号、告警码
    │                                         │
    └──────────────────┬──────────────────────┘
                       ▼
【Step 3: RRF 倒数排名融合 (Reciprocal Rank Fusion)】─── 归一化双路打分，合并初筛 Top-20
                       │
                       ▼
【Step 4: Cross-Encoder 深度重排序 (Reranker)】─── Query-Doc 逐字交叉注意力打分，精选 Top-3
                       │
                       ▼
【Step 5: 安全清洗与动态 Nonce 隔离包装】─── 注入 <UNTRUSTED_KNOWLEDGE nonce="uuid"> 沙箱
                       │
                       ▼
【Step 6: Prompt 组装与流式推理 (SSE)】─── 结合置信度约束注入 LLM，流式打字机响应前端
```

#### 2. 关键设计哲学（为什么不是单一向量检索？）
1. **单一向量检索的死穴**：向量 Embedding 是“有损压缩”，擅长理解模糊自然语言（如“上网慢怎么办”），但对**精确符号（如路由器固件版本 `v1.2.0-rc3`、错误代码 `ERR_SOCKET_TIMEOUT`）极其迟钝**，容易出现语义相近但关键参数完全不符的情况。
2. **BM25 结合的必要性**：传统倒排索引恰好专攻精确字面匹配，两者融合互补，兼顾“语义泛化”与“精确命中”。
3. **Cross-Encoder Rerank 的核心价值**：双塔向量检索无法进行 Query 和 Document 的跨词交叉注意力运算。Rerank 模型采用单塔架构计算深度交互注意力，能把伪相关的上下文彻底剔除，将注入大模型的上下文窗口压缩到最精简的 Top-3，既节省 Token 成本又消除幻觉。

#### 3. 现场一分钟高分口述模版（直接背诵）
> “我的 RAG 检索链路是一套标准的 6 步工程化流水线：  
> 第一步是 **Query 预处理与代词补全**，解析多轮对话上下文；  
> 第二步是 **双路并行召回**，一路走 pgvector 向量检索捕获语义相似度，另一路走 BM25 倒排索引精确捕获设备型号和错误码；  
> 第三步通过 **RRF（倒数排名融合）算法**把两路不同量纲的分数融合，初筛出 Top-20 候选集；  
> 第四步通过 **Cross-Encoder 交叉编码器（bge-reranker）** 进行深度注意力打分，精准提纯出最高相关的 Top-3，极大压低 LLM 上下文噪音；  
> 第五步做 **动态 Nonce 安全包装**，给召回片段加上随机沙箱标记，严防提示词注入攻击；  
> 最后一步**组装严格的防幻觉 System Prompt**，通过 SSE 流式向前端推送答案。”

### Q3：半精度存储（halfvec）底层原理与工程价值（FP32 vs FP16、HNSW 内存优化）

#### 1. 计算机体系结构与 IEEE 754 浮点数底层
* **单精度浮点数（FP32，Single-Precision）**：遵循 IEEE 754 标准，占 **32 位（4 字节）**。
  * 结构：1 位符号位 + 8 位指数位 + 23 位尾数位。
  * 1024 维向量占用：$1024 	imes 4 	ext{ Bytes} = 4096 	ext{ Bytes} = \mathbf{4	ext{KB}}$。
* **半精度浮点数（FP16，Half-Precision）**：占 **16 位（2 字节）**。
  * 结构：1 位符号位 + 5 位指数位 + 10 位尾数位。
  * 1024 维向量占用：$1024 	imes 2 	ext{ Bytes} = 2048 	ext{ Bytes} = \mathbf{2	ext{KB}}$。

#### 2. 在项目中的工程落地
* 采用 **PostgreSQL 16 + pgvector 插件**，将向量字段由原先的 `vector(1024)` 重构为：
  ```sql
  -- 启用半精度存储，单条从 4KB 压缩为 2KB
  ALTER TABLE knowledge_chunks ADD COLUMN embedding halfvec(1024);
  
  -- 构建半精度 HNSW 向量索引
  CREATE INDEX idx_knowledge_halfvec_hnsw 
  ON knowledge_chunks USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);
  ```

#### 3. 三大工程量化收益（面试绝杀点）
1. **存储与物理内存直降 50%**：
   * 100 万条 1024 维知识向量，原先需要 4GB 纯向量存储，切换后仅需 **2GB**。
2. **HNSW 索引内存驻留率翻倍，检索延迟降低 ~30%**：
   * **性能瓶颈根源**：向量检索的性能杀手是 **HNSW 索引超出操作系统 Buffer Pool 内存大小，导致频繁触发磁盘 Swap 与随机 I/O 读取**。
   * 体积减半后，相同内存下能常驻两倍规模的 HNSW 图索引，彻底消除了磁盘换页颠簸，检索 P99 延迟降低约 30%。
3. **余弦相似度精度损失 <0.5%（微乎其微）**：
   * 向量检索关注的是高维空间中向量之间的**夹角相对大小（余弦排序）**，而不是绝对浮点数值。1024 维空间下尾数精度的轻微截断对 Top-10 最终排序结果的影响极小，经实测召回准确率损失在 0.5% 以内。

#### 4. 现场一分钟高分口述模版（直接背诵）
> “我的半精度存储是指在 **PostgreSQL 16 + pgvector** 中，将原本 32 位的单精度浮点向量（FP32，4字节）重构成 **16 位半精度浮点向量（FP16 / halfvec，2字节）**。  
> 它的核心收益有三点：  
> 1. **存储与内存占用直减 50%**，1024 维向量单条从 4KB 压缩至 2KB；  
> 2. **极大提升了 HNSW 索引的内存命中率**。高维向量检索最怕索引超出内存导致磁盘频繁随机 I/O，体积减半使得有限物理内存能够全量驻留 HNSW 索引图，彻底避免了磁盘 Swap，检索延迟降低了近 30%；  
> 3. **精度近乎无损**。高维空间下余弦距离对尾数截断不敏感，实测 Top-10 召回精度损失小于 0.5%。这是极其典型的用微小精度代价换取翻倍系统吞吐和成本节省的优秀工程实践。”

### Q4：YAML 案例回归（EvalRunner）与大模型自动化质量门禁（AI 领域的单元测试）

#### 1. 为什么大模型系统必须做“案例回归”？
* **传统编程 vs 大模型编程**：传统代码是确定性逻辑，单元测试（JUnit）能保证代码行为稳固。但大模型是**概率采样黑盒**，具备极其脆弱的**提示词敏感性（Prompt Fragility）**。
* **典型生产灾难（Prompt Regression）**：为了修复 Case A（比如让模型语气更温和），工程师微调了 System Prompt，结果导致原本能正常调用的核心业务 Tool（比如故障工单创建、退款草稿），在场景 B 中**突然不再被触发，或者参数提取格式错乱**。

#### 2. 什么是 YAML 案例回归？
我们在项目中将高频核心业务抽离成声明式的 **YAML 黄金测试用例集（如 `eval-cases.yaml`）**：
```yaml
cases:
  - id: "CASE_001_NETWORK_ROUTER_RESTART"
    description: "用户报障要求重启机房指定路由器"
    input_query: "机房 2 号交换机端口流量突刺，赶紧帮我发一个重启指令"
    expected_tools:
      - "execute_device_restart"       # 必须命中的底层核心 Tool
    expected_params:
      target_device: "switch_02"       # 核心参数必须提取正确
    forbidden_regex:
      - "(未知指令|抱歉我无法|暂不支持)"  # 违禁词断言（防拒答与幻觉）
    min_faithfulness_score: 0.85       # RAG 真实性得分底线
```

#### 3. YAML 案例回归 vs 传统 JUnit 单元测试对比矩阵

| 对比维度 | 传统 Java 单元测试（JUnit） | 大模型 YAML 案例回归（EvalRunner） |
| :--- | :--- | :--- |
| **本质定位** | 针对确定性代码逻辑的白盒测试 | 针对概率性 AI 系统的**数据驱动型端到端/集成回归测试** |
| **断言机制** | **硬比对**：`assertEquals(期待值, 实际值)` | **软硬复合断言**：<br>1. **硬断言**：Tool 是否被唤起、参数 Schema 是否完备<br>2. **软断言**：违禁词正则匹配、RAG 忠实度打分 |
| **用例承载** | 硬编码在 Java 类中（修改需重新编译代码） | 纯文本声明式 YAML（**测试数据与测试逻辑彻底解耦**） |
| **多角色协同**| 必须具备 Java 开发能力的程序员才能写 | Prompt 工程师、产品经理、业务专家均可随时提 PR 补充用例 |
| **CI/CD 门禁**| `mvn test` 编译失败即阻断 | `POST /dev/ai/eval/run` 自动化跑批，**核心用例 100% Pass，总 Pass 率 <95% 则禁止发版** |

#### 4. 为什么不直接写 JUnit，而选择 YAML 数据驱动？
1. **热更新与零编译解耦**：线上发现 Bad Case 时，直接往 `eval-cases.yaml` 追加一条规则即可，不需要改动 Java 测试代码和重新编译构建；
2. **表达复合断言更直观**：大模型测试包含多轮输入、工具期望、参数校验、违禁黑名单等复杂层级结构，YAML 的层级语法与 JSON/Schema 天然互通，维护成本极低。

#### 5. 现场一分钟高分口述模版（直接背诵）
> “大模型本质上是概率系统，微调一次 Prompt 或加一个 Tool，极易产生‘修复了 A 却搞崩了 B’的提示词退化（Regression）问题。  
> 为此我们落地了 **YAML 案例回归系统（EvalRunner）**，你可以把它理解为 **针对大模型和 Agent 的‘数据驱动型单元与回归测试’**：  
> 1. 我们将生产中高频关键的业务场景（如设备重启、工单创建）抽离为声明式的 **YAML 黄金测试集**，定义了每个用例的输入、**期望触发的 Tool（如 `draft_create_order`）**、参数 Schema 以及违禁词正则；  
> 2. 在 Spring Boot 中自研了测试执行器 `EvalRunner`，在 CI/CD 流水线发版前自动跑批运行全部用例；  
> 3. 它不强求字面完全一致，而是**断言底层关键行为的确定性**。我们设定了硬性发布门禁：**核心业务 Tool 触发准确率必须 100%、整体通过率高于 95% 才允许合入部署**。这从工程机制上彻底防范了提示词修改引发的线上业务退化。”
