### 实战 1：云智易视频巡检——设备通信与架构演进（单线程 → 线程池 → XXL-JOB 分片）

* **1. 业务背景与痛点（一句话讲清）**：
  * 系统需要周期性轮巡园区内数百台海康 IPC 摄像头，拉取 RTSP 视频流抓拍关键帧并进行画面质量检测。早期采用单线程 `while(true)` 串行轮询，一旦某台摄像头因弱网握手超时卡顿 5 秒，后续所有设备全部排队阻塞，导致单轮巡检耗时超过 **5 分钟**，严重滞后。
* **2. 专属业务线程池异步解耦（7 大参数精准配置）**：
  * 我遵循《阿里 Java 开发手册》，严禁使用 `Executors` 默认无界队列，显式通过 `ThreadPoolExecutor` 构造专属线程池：
  * **核心线程数 `corePoolSize = 8`，最大线程数 `maximumPoolSize = 8`**：
    * *理论依据*：结合利特尔法则（$QPS \times RT$）评估日常吞吐；
    * *物理硬约束（最打动考官）*：第一，下游海康摄像头与流媒体网关芯片的**硬件解码并发通道上限为 8~16 路 RTSP 码流**，开多了会导致设备端芯片过载花屏断流；第二，单张 1080P 高清抓拍图在 JVM 堆内解码展开为 RGB 像素矩阵需占用 **4~8MB 内存**，8 个并发严格将内存峰值控制在 **60MB 以内**，若盲目开到 64 并发会瞬间吃掉 500MB+ 堆内存引发频繁 Full GC 甚至 OOM；
  * **阻塞队列**：选用 `new ArrayBlockingQueue<>(500)` 有界数组队列（连续内存空间，无链表节点指针开销，防 OOM）；
  * **线程工厂**：自定义 `ThreadFactory` 将线程命名为 `"video-patrol-worker-%d"`，方便线上用 `jstack` 快速定位问题；
  * **拒绝策略**：选用 **`CallerRunsPolicy`**。当队列打满且 8 个线程全忙时，由提交任务的调度主线程亲自去执行该任务，从而减缓主线程拉取新任务的速度，形成**天然的反压限流（Backpressure）**，保证巡检任务 100% 零丢失！
* **3. 分布式分片与断网容灾自愈**：
  * 引入 **XXL-JOB 分片广播（Sharding Broadcast）**，多台执行器节点通过 `device_id % shardTotal == shardIndex` 均匀分摊摄像头，单轮巡检耗时从 5 分钟压降至 **25 秒以内**；
  * **看门狗逃生舱（Watchdog）**：在执行器内部维护一个轻量级 `ScheduledExecutorService` 心跳检测。若连续 3 个周期未收到 XXL-JOB 调度中心指令（如调度中心宕机或网络隔离），自动切换为本地定时降级触发，确保园区安防巡检永不瘫痪；
  * **防任务卡死**：底层 Socket 强制设置 `connectTimeout = 3s, readTimeout = 5s`，外层通过 `Future.get(10, TimeUnit.SECONDS)` 监控，超时立即调用 `future.cancel(true)` 中断释放线程。

### 实战 2：凯通科技网管系统——大屏界面加载卡顿（15s → 200ms）优化全过程

> 💡 **格力考官视角**：无论是智能家居 App 还是工厂设备监控上位机，“界面/大屏加载卡顿优化”都是必问的核心实战题！

* **1. 定位卡顿根因**：
  * 浙江电信 8 大云池拓扑监控大屏包含上万个网元节点与连线。原有接口在打开页面时，同步做多表慢 SQL 关联查询（同时查静态设备拓扑 + 实时性能指标 + 活跃告警计数），并组装成一个几十兆的超大 JSON 一次性返回，导致后端查询加网络传输长达 **15 秒**，且前端浏览器主线程解析大 JSON 时直接卡死无响应。
* **2. 三步重构优化方案**：
  1. **动静分离 + Redis 骨架预热（首屏 200ms 秒开）**：
     * 将极少变动的“设备节点坐标、连线关系、静态台账属性”与高频变动的“实时告警/性能数据”彻底解耦；
     * 静态拓扑骨架预热存储在 **Redis** 中。用户打开大屏时，首屏接口直接从 Redis 内存读取骨架数据，**200ms 内立刻渲染出完整拓扑图**；
  2. **回应“数据没来时页面是不是置灰不能点”的追问**：
     * 绝不是死板置灰！因为 200ms 返回的骨架中已经包含了网元 ID、设备型号、IP 与连线拓扑，运维人员在**第一秒就能立即进行画布缩放、拖拽漫游、区域搜索定位、以及点击节点查看设备静态资产台账**；
  3. **可视区域（Viewport）异步多线程分批注水 + SQL 批量优化**：
     * 前端根据当前屏幕可视区域，异步分批请求实时告警状态，流式点亮红黄绿状态灯；
     * 后端消除循环单条查库的 $N+1$ 问题，改用批量 `IN` 查询并建立联合覆盖索引，数据库 CPU 占用率下降 60% 以上。

### 实战 3：凯通科技网管系统——生产环境“丢根告警”复杂 Bug 逆向排查与 188 行单测闭环

* **1. 故障现象**：
  * 网管系统需要根据设备拓扑依赖树进行“根因分析”，把下游衍生告警自动挂载到上游“根告警”下生成一张核心故障工单。但线上偶发出现**“衍生告警收到了，根告警却丢失了，导致漏派核心抢修工单”**的严重问题。
* **2. 排查与定位过程（体现极强的 Debug 能力）**：
  * 我通过捞取生产环境告警流水日志并按毫秒级时间戳比对，发现了两个隐藏的物理现象：
    1. **网络乱序到达**：由于底层交换机与采集器缓冲不同，子设备的衍生告警往往比父设备的根告警**早到 2~5 秒**；
    2. **跨层级断链上报**：在 `A → B → C` 的链路中，中间设备 B 可能因为瞬时闪断未上报状态，旧代码的递归回溯函数遇到 B 缺失时直接 `return null` 终止了向上查找，导致根设备 A 被丢弃！
* **3. 修复与单测闭环**：
  * 我重构了逆向追溯算法：当实时告警缓存中找不到中间节点 B 时，自动**穿透查询静态物理拓扑配置表**补齐父子链路，并引入**延迟窗口重挂机制**处理乱序到达；
  * 为确保万无一失，我严格遵循编码规范编写了 **188 行 JUnit 单元测试**，模拟了单链、星型拓扑、环路死循环防御、乱序到达等全部极端场景，上线后故障率降为 0。

### 实战 4：上位机/服务端与智能硬件采用 TCP 通信时，丢包、粘包与设备假死如何处理？

> 💡 **格力智能空调联网 / 工业控制设备通信最核心的底层问题！**

* **1. TCP 粘包与半包的成因与解决**：
  * **成因**：TCP 是**面向字节流（Byte Stream）**的传输协议，本身没有消息边界概念；发送端 Nagle 算法会将多个小数据包合并发送（产生粘包），接收端网卡 MTU 限制或缓冲区读取不及时会将大包拆开（产生半包）。
  * **工业级解决方案（自定义 TLV 帧协议 + 长度帧解码器）**：
    * 制定严格的二进制通信帧格式：**`魔数 Magic (2B, 如 0xCAFE 过滤非法垃圾包) + 协议版本 (1B) + 指令类型 (1B) + 数据长度 Length (4B) + 数据体 Body (N字节) + CRC16 校验码 (2B)`**；
    * 在 Netty / Socket 接收层配置 **`LengthFieldBasedFrameDecoder`**，先读取 4 字节的 `Length` 字段，严格在缓冲区攒够 `Length` 个字节并校验 `CRC16` 无误后，才组装成一个完整的数据包交给业务线程处理。
* **2. 设备网络假死（拔网线 / 断电）如何秒级感知？**：
  * **为什么不用 TCP Keep-Alive？**：操作系统默认的 TCP Keep-Alive 空闲探测周期长达 **7200 秒（2 小时）**，且工作在内核态——如果设备端应用进程发生死锁或卡死，只要内核没崩依然会回 ACK，服务端根本无法感知业务假死；
  * **应用层心跳（Netty `IdleStateHandler`）**：设备每 10 秒发送一次轻量 Ping 心跳帧；服务端配置 30 秒读空闲检测（连续 3 个周期未收到任何数据），一旦触发 `READER_IDLE` 事件，服务端主动关闭僵尸连接、清理会话缓存并将设备标记为“离线”。
* **3. 控制指令下发如何保证不丢、不重、不乱序？**：
  * **不丢**：采用**本地消息表 + 应用层 ACK 确认 + 指数退避重试**；
  * **不重（幂等）**：每条控制指令携带全局唯一递增流水号 `seq_id`，设备端记录 `last_seq_id`，收到小于等于当前值的重复指令直接回 ACK 但不重复执行硬件动作。

### 一、Java 核心基础必问（Q1 ~ Q4）

#### Q1：面向对象三大特征是什么？接口（Interface）与抽象类（Abstract Class）有什么区别？
* **三大特征**：
  1. **封装**：隐藏对象内部状态细节，仅通过公开方法暴露安全访问入口；
  2. **继承**：子类复用父类的属性和方法，并可扩展新功能（`is-a` 关系）；
  3. **多态**：同一方法调用因运行时真实对象不同而表现出不同行为（编译看左边父类引用，运行看右边子类实例，底层靠 JVM `invokevirtual` 虚方法表动态分派实现）。
* **接口 vs 抽象类**：
  * **设计理念**：抽象类是自下而上的**“共性模板抽取（Is-a）”**，可包含普通成员变量、构造器和具体方法；接口是自上而下的**“行为契约规范（Can-do）”**，只能有 `public static final` 静态常量，无构造器；
  * **继承限制**：Java 类只能单继承一个抽象类，但可以实现多个接口。

#### Q2：`String` 为什么设计成不可变的（Immutable）？`String`、`StringBuilder`、`StringBuffer` 有什么区别？
* **`String` 不可变的原因与好处**：
  * 底层存储数据的 `char[]`（JDK 9+ 为 `byte[]`）被 `private final` 修饰，且类本身被 `final` 修饰不可继承，未提供任何修改内部数组元素的方法；
  * **四大好处**：① 保障**字符串常量池（String Pool）**安全共享，节省大量堆内存；② **天然线程安全**，多线程共享无需加锁；③ **安全充当 HashMap 的 Key**，其 `hash` 值只需计算一次即可缓存复用，不会因为内容改变导致哈希寻址丢失；④ 保障类加载器名、网络连接地址等系统安全性。
* **三者区别**：
  * `String`：不可变，每次 `+=` 拼接都会创建新对象，循环拼接严禁使用；
  * `StringBuilder`：可变字符序列，非线程安全，**单线程下拼接性能最高（推荐）**；
  * `StringBuffer`：可变字符序列，方法加了 `synchronized` 同步锁，线程安全但有锁开销。

#### Q3：`ArrayList` 和 `LinkedList` 有什么区别？`HashMap` 底层原理与扩容机制是什么？
* **`ArrayList` vs `LinkedList`**：
  * `ArrayList` 基于**动态连续数组**，支持 $O(1)$ 下标随机访问，默认容量 10，满后按 **1.5 倍**（`old + (old >> 1)`）扩容；
  * `LinkedList` 基于**双向链表**，随机访问需遍历 $O(n)$，每个节点额外占用前后两个引用指针内存，且内存不连续对 CPU 缓存不友好；日常开发 95% 场景首选 `ArrayList`。
* **`HashMap` 底层原理**：
  * JDK 1.8 采用 **数组 + 链表 + 红黑树**。当单个链表长度 **$\ge 8$ 且数组总容量 $\ge 64$** 时转为红黑树（若容量 $< 64$ 则优先扩容 `resize()`）；当节点数 $\le 6$ 时退化为链表；
  * **寻址公式**：高 16 位与低 16 位异或扰动 `(h = key.hashCode()) ^ (h >>> 16)`，再执行 `(n - 1) & hash` 位与寻址（要求容量必须是 2 的幂）；
  * **初始化防扩容公式**：负载因子默认 `0.75`。若已知要存 **1000 个元素**，应传入 `1000 / 0.75 + 1 = 1334`，HashMap 内部通过 `tableSizeFor` 位运算向上取最小的 2 的幂，实际分配容量为 **2048**！

#### Q4：` == ` 和 `equals()` 的区别？为什么重写 `equals()` 必须重写 `hashCode()`？
* **`==` vs `equals()`**：
  * `==`：如果是基本数据类型，比较的是**值**是否相等；如果是引用类型，比较的是两个引用指向的**内存地址**是否相同；
  * `equals()`：`Object` 默认实现就是 `==`，但 `String`、`Integer` 等类重写了 `equals()` 用于比较对象的**内容**是否相等。
* **为什么重写 `equals` 必须重写 `hashCode`？**
  * Java 规范规定：**如果两个对象 `equals()` 相等，它们的 `hashCode()` 必须相同**！
  * 当把自定义对象作为 Key 存入 `HashMap` 或 `HashSet` 时，集合会**先比对 `hashCode()` 确定桶位置，相等时再用 `equals()` 比对内容**。如果只重写 `equals` 不重写 `hashCode`，两个内容完全相同的对象会继承 `Object` 默认按内存地址生成的不同哈希值，导致散列到不同桶里，出现“明明存进去了却 `get` 不出来、或者 `HashSet` 存进重复元素”的严重 Bug！

### 二、Java 多线程、并发锁与 JVM 必问（Q5 ~ Q9）

#### Q5：Java 创建线程有哪几种方式？线程有哪些生命周期状态？`sleep()` 和 `wait()` 有什么区别？
* **四种创建方式**：
  1. 继承 `Thread` 类；
  2. 实现 `Runnable` 接口（无返回值）；
  3. 实现 `Callable<V>` 接口配合 `FutureTask`（可获取返回值、可抛出受检异常）；
  4. **生产环境唯一推荐：使用 `ThreadPoolExecutor` 线程池**（实现线程复用、控制最大并发、统一管理）。
* **Java 线程 6 大状态（`Thread.State`）**：
  * `NEW`（新建）$\to$ `RUNNABLE`（可运行，包含操作系统就绪 Ready 和运行中 Running）$\to$ `BLOCKED`（等待进入 `synchronized` 同步块锁）$\to$ `WAITING`（无限期等待，如 `Object.wait()`、`Thread.join()`、`LockSupport.park()`）$\to$ `TIMED_WAITING`（限期等待，如 `Thread.sleep(ms)`、`wait(timeout)`）$\to$ `TERMINATED`（终止）。
* **`sleep()` vs `wait()` 核心区别**：
  1. **所属类不同**：`sleep()` 是 `Thread` 类的静态方法；`wait()` 是 `Object` 类的实例方法；
  2. **最重要区别（是否释放锁！）**：**`sleep()` 在休眠期间绝对不会释放它持有的锁**；而 **`wait()` 必须在 `synchronized` 块内调用，调用后会立即释放持有的对象监视器锁**，进入等待队列直到被 `notify()/notifyAll()` 唤醒。

#### Q6：`synchronized` 和 `ReentrantLock` 有什么区别？底层锁升级过程是怎样的？
* **五大核心区别**：
  1. **实现层面**：`synchronized` 是 JVM 原生关键字（基于 C++ `ObjectMonitor`）；`ReentrantLock` 是 JUC 包下的 Java API 类（基于 **AQS** 实现）；
  2. **锁的释放**：`synchronized` 由 JVM 在代码执行完或抛异常时自动释放锁；`ReentrantLock` **必须在 `finally` 块中手动调用 `unlock()`**，否则会发生死锁；
  3. **公平性**：`synchronized` 只能是非公平锁；`ReentrantLock` 支持**公平锁与非公平锁**（构造器传 `true/false`）；
  4. **可中断与超时获取**：`synchronized` 拿不到锁只能死等；`ReentrantLock` 支持 `tryLock(timeout)` 超时放弃和 `lockInterruptibly()` 响应中断；
  5. **条件唤醒**：`ReentrantLock` 可绑定多个 `Condition` 对象实现精准分组唤醒，而 `synchronized` 的 `notify` 只能随机唤醒。
* **`synchronized` 锁膨胀升级状态机**：
  * **无锁 $\to$ 偏向锁（单一线程通过 CAS 在对象头 Mark Word 记录线程 ID）$\to$ 轻量级锁（轻度交替竞争，线程通过 CAS 自旋尝试修改锁记录指针）$\to$ 重量级锁（竞争激烈，向操作系统申请互斥量 Mutex，未抢到锁的线程挂起进入内核态阻塞）**。

#### Q7：聊聊你对 AQS（AbstractQueuedSynchronizer）的理解？`ConcurrentHashMap` 为什么线程安全？
* **AQS 核心四句话**：
  1. **定位**：JUC 并发包的核心基石（`ReentrantLock`、`Semaphore`、`CountDownLatch` 的底座），采用**模板方法设计模式**；
  2. **三大支柱**：① `volatile int state`（同步状态计数器，通过 CAS 原子修改，在 ReentrantLock 中代表重入次数）；② **CLH 双向 FIFO 等待队列**（带 Dummy Head 虚拟头节点，前驱节点的 `waitStatus = SIGNAL(-1)` 负责在释放锁时唤醒后继）；③ **`LockSupport.park() / unpark()`** 负责阻塞和唤醒线程；
  3. **加锁解锁**：拿锁失败封装为 Node 尾插进队，把前驱状态设为 `SIGNAL` 后安心 `park`；释放锁时 `state--` 到 0，从 `tail` 往前扫描找到最靠近 `head` 的有效节点调用 `unpark` 唤醒（**因为入队时先赋 `prev`、再 CAS `tail`、最后赋 `next`，从后往前遍历 `prev` 链绝对不会漏节点**）。
* **`ConcurrentHashMap` 线程安全原理（JDK 1.8）**：
  * 抛弃 1.7 的 Segment 分段锁，采用 **Node 数组 + 链表/红黑树 + CAS + `synchronized`**；
  * **写安全**：桶为空时用 **CAS** 无锁写入首节点；桶非空时用 **`synchronized` 仅锁住当前桶的链表/红黑树头节点**（锁粒度极细，不同桶完全并发）；
  * **读无锁**：Node 的 `val` 和 `next` 指针均用 **`volatile`** 修饰，保证跨线程内存可见性，读操作全程零加锁。

#### Q8：`volatile` 关键字有什么作用？它能保证原子性吗？
* **两大核心作用**：
  1. **保证多线程间的内存可见性**：写 `volatile` 变量时，JVM 会发送 Lock 前缀指令强制将 CPU 缓存行数据立即刷新回主内存，并通过 MESI 缓存一致性协议使其他 CPU 核心的缓存行失效，迫使其他线程从主存读取最新值；
  2. **禁止指令重排序（保证有序性）**：通过插入读写**内存屏障（Memory Barrier）**，禁止编译器和 CPU 对指令重排（最典型应用：DCL 双重检查锁定单例模式中，防止 `instance = new Singleton()` 的“分配内存、初始化对象、赋引用”三步重排导致其他线程拿到半初始化对象）。
* **能保证原子性吗？**：
  * **不能！** 比如 `volatile int count = 0; count++;` 依然不是线程安全的，因为 `count++` 包含“读-改-写”三步独立指令，多线程并发依然会相互覆盖。需要保证原子性必须使用 `AtomicInteger`（CAS）或加锁。

#### Q9：JVM 运行时内存区域是如何划分的？垃圾回收（GC）是如何判断对象存活及回收的？
* **JVM 内存划分**：
  * **线程私有区（随线程生灭，无 GC）**：① **程序计数器**（记录字节码行号，唯一不会发生 OOM 的区域）；② **Java 虚拟机栈**（存栈帧：局部变量表、操作数栈、方法出口，递归过深报 `StackOverflowError`）；③ **本地方法栈**；
  * **线程共享区（GC 主战场）**：① **Java 堆（Heap）**（存所有对象实例，分为新生代 `Eden : S0 : S1 = 8 : 1 : 1` 和老年代）；② **方法区（JDK 1.8 改用元空间 Metaspace）**（存类元信息、常量池、静态变量，直接使用本地物理内存）。
* **GC 核心原理**：
  * **判断对象可回收**：采用**可达性分析算法（Reachability Analysis）**——从 **GC Roots**（虚拟机栈引用的对象、静态属性引用的对象、常量引用的对象、活跃线程、`synchronized` 持有的对象）出发向下搜索，不可达的对象标记回收；
  * **分代收集算法**：新生代对象朝生夕死，采用**复制算法（Copying）**；老年代对象存活率高，采用**标记-清除（Mark-Sweep）或标记-整理（Mark-Compact）算法**。

### 三、操作系统与计算机网络必问（Q10 ~ Q13 —— 格力应用软件岗极高频！）

#### Q10：操作系统中“进程（Process）”和“线程（Thread）”有什么根本区别？进程间通信（IPC）有哪些方式？
* **根本区别**：
  1. **资源分配 vs 调度执行**：**进程是操作系统进行资源分配（独立虚拟内存地址空间、文件句柄）的基本单位**；**线程是操作系统进行 CPU 调度和执行的基本单位**；
  2. **内存隔离 vs 共享**：不同进程间地址空间相互隔离；同一进程内的多个线程**共享进程的堆内存和方法区**，仅各自独享程序计数器和栈，因此线程上下文切换无需切换页表，开销比进程小得多。
* **五大进程间通信（IPC）方式**：
  1. **管道（Pipe / 命名管道 FIFO）**；
  2. **消息队列（Message Queue）**；
  3. **共享内存（Shared Memory —— 速度最快的 IPC，直接读写同一块物理内存，需配合信号量同步）**；
  4. **信号量（Semaphore —— 进程间互斥与同步计数器）**；
  5. **套接字（Socket —— 支持跨网络跨机器进程通信）**。

#### Q11：死锁产生的四个必要条件是什么？在工程开发中如何预防和排查死锁？
* **四大必要条件（缺一不可）**：
  1. **互斥条件**：资源同一时刻只能被一个线程占用；
  2. **请求与保持条件**：线程已持有一个资源，又请求新资源被阻塞时，对已持有资源保持不放；
  3. **不可剥夺条件**：线程已获得的资源在使用完前不能被强行剥夺；
  4. **循环等待条件**：多个线程形成头尾相接的环形等待链（A 等 B，B 等 A）。
* **预防手段**：① **按固定全局顺序加锁**（破坏循环等待）；② 使用 `ReentrantLock.tryLock(timeout)` 超时自动放弃并释放已持有的锁（破坏请求与保持）；
* **线上排查**：`jps -l` 查进程号 $\to$ **`jstack -l <pid>`** 直接打印死锁线程栈与代码行号。

#### Q12：TCP 和 UDP 有什么区别？在格力智能家居或工业软件中分别怎么选型？
| 对比维度 | **TCP（传输控制协议）** | **UDP（用户数据报协议）** |
| :--- | :--- | :--- |
| **连接性** | **面向连接**（通信前必须先经过三次握手建立连接） | **无连接**（想发直接发，无需握手建立连接） |
| **可靠性** | **绝对可靠**（序列号、ACK 确认、超时重传、流量控制、拥塞控制，不丢不乱） | **不可靠、尽最大努力交付**（不保证送达、不保序，可能丢包） |
| **传输单位与边界** | **面向字节流**（无消息边界，存在粘包与半包问题） | **面向数据报（报文）**（保留消息边界，整包收发，无粘包） |
| **首部开销与速度** | 首部最少 **20 字节**，状态机复杂，有一定延迟开销 | 首部固定仅 **8 字节**，极度轻量，实时性极高 |
| **格力典型场景** | **空调远程控制指令下发、固件 OTA 升级、订单支付交易、MQTT 长连接** | **局域网智能家电广播发现（UDP 一键配网）、实时音视频监控流、高频传感器采样** |

#### Q13：简述 TCP 三次握手与四次挥手的过程？为什么握手是三次，而挥手需要四次？
* **三次握手（建立连接）**：
  1. 客户端发 `SYN=1, seq=x`；
  2. 服务端回 `SYN=1, ACK=1, seq=y, ack=x+1`；
  3. 客户端回 `ACK=1, seq=x+1, ack=y+1`。
  * **为什么必须三次（不能两次）？**：第一，双向确认双方的收发能力均正常；第二，**防止网络中滞留的“历史失效连接请求报文”突然到达服务端，导致服务端错误开启连接白白浪费资源**。
* **四次挥手（断开连接）**：
  1. 客户端发 `FIN=1`（表示客户端数据发完了）；
  2. 服务端回 `ACK=1`（进入 `CLOSE_WAIT`）；
  3. **服务端把剩余未发完的数据全部传完后**，发送 `FIN=1`；
  4. 客户端回 `ACK=1`（进入 `TIME_WAIT` 等待 **`2MSL`** 后关闭）。
  * **为什么挥手需要四次？**：因为 TCP 是**全双工通信**。客户端发 `FIN` 只代表它不再发数据了，但**服务端此时可能还有未处理完或未发完的数据**，所以服务端必须先回 `ACK`，等手里剩余数据全部发完后才能发自己的 `FIN`，中间的 `ACK` 和 `FIN` 不能合并！

### 四、MySQL、MyBatis、Spring 与 Redis 必问（Q14 ~ Q18）

#### Q14：MySQL 索引底层为什么使用 B+ 树而不是 B 树或红黑树？哪些情况会导致索引失效？
* **为什么用 B+ 树？**：
  1. **非叶子节点只存索引不存行数据，扇出极高**：InnoDB 一页 16KB，非叶子节点存 `主键8B + 指针6B = 14B`，一页能存 1170 个指针，**树高仅 3 层就能存 2190 万条数据（只需 1~2 次磁盘 I/O）**；而 B 树非叶子节点夹杂行数据导致树变高；
  2. **叶子节点双向链表连接**：B+ 树所有行数据都在叶子节点且由双向指针串联，极度适合 `BETWEEN ... AND ...` 范围查询与排序。
* **6 大经典索引失效场景**：
  1. 违反**联合索引最左前缀原则**；
  2. 在索引列上做**函数计算、表达式运算**；
  3. 发生**隐式类型转换**（如字符串列 `phone` 传了数字 `WHERE phone = 138000`）；
  4. 模糊查询以 `%` 开头（`LIKE '%abc'`）；
  5. `OR` 前后存在未建索引的列；
  6. 优化器评估全表扫描比走索引回表更快。

#### Q15：MySQL 事务的四大特性（ACID）底层靠什么实现？默认隔离级别是什么？
* **ACID 底层机制**：
  * **原子性（A）**：靠 **Undo Log（回滚日志）** 实现；
  * **持久性（D）**：靠 **Redo Log（重做日志，WAL 预写日志 + 顺序写磁盘）** 实现；
  * **隔离性（I）**：靠 **MVCC（多版本并发控制 ReadView）+ 锁机制（行锁/间隙锁/临键锁）** 实现；
  * **一致性（C）**：由 A、I、D 共同保障。
* **默认隔离级别**：MySQL 默认是 **可重复读（Repeatable Read, RR）**，通过 MVCC 解决快照读幻读，通过 **Next-Key Lock（记录锁 + 间隙锁 Gap Lock）** 解决当前读幻读。

#### Q16：MyBatis 中 `#{}` 和 `${}` 的区别是什么？如何防止 SQL 注入？
* **`#{}`（预编译占位符 —— 必选）**：解析为 `?`，底层使用 JDBC `PreparedStatement` 预编译，参数安全填入并自动加单引号，**100% 阻断 SQL 注入**；
* **`${}`（字符串直接拼接 —— 慎用）**：原样拼接进 SQL，有严重 **SQL 注入风险**，仅用于动态传入表名、列名或 `ORDER BY` 排序字段名（且必须在代码中做严格白名单校验）。

#### Q17：谈谈你对 Spring IoC 和 AOP 的理解？`@Transactional` 事务在什么情况下会失效？
* **IoC 与 AOP**：
  * **IoC（控制反转）**：将对象创建与依赖组装权交给 Spring 容器，通过 DI（依赖注入）实现模块解耦；
  * **AOP（面向切面编程）**：基于**动态代理（有接口用 JDK 动态代理，无接口用 CGLIB 字节码生成子类）**，将日志审计、权限校验、事务管理等公共逻辑无侵入织入业务方法。
* **`@Transactional` 经典失效场景**：
  1. **同类内部方法自调用**（`this.b()` 绕过了 Spring 代理对象，最常考！）；
  2. 方法不是 `public` 修饰；
  3. 异常被方法内部 `try-catch` 生吞未抛出；
  4. 抛出了受检异常但未配置 `@Transactional(rollbackFor = Exception.class)`。

#### Q18：Redis 有哪些常用数据类型？为什么快？缓存穿透、击穿、雪崩怎么解决？
* **5 大基础数据类型**：`String`（缓存/计数器）、`Hash`（存对象/设备最新状态快照）、`List`（队列）、`Set`（去重/交并集）、`ZSet`（排行榜/延迟队列）。
* **为什么单线程还极快**：纯内存操作 + 高效底层数据结构（跳表/压缩列表）+ 无多线程上下文切换与锁竞争 + **`epoll` I/O 多路复用**。
* **三大缓存问题**：
  1. **缓存穿透（查不存在的数据直击 DB）**：布隆过滤器（BloomFilter）前置拦截 + 缓存空值（设短过期时间）；
  2. **缓存击穿（单个热点 Key 过期瞬间高并发打 DB）**：热点数据逻辑永不过期 + Redisson 分布式互斥锁重建；
  3. **缓存雪崩（大批 Key 同时过期）**：过期时间加随机值（Jitter）打散 + Redis 主从哨兵/Cluster 高可用。

```java
    int left = 0;
    int right = fn.length - 1;
    int mid =                      // ❌【Bug 1】不要在循环外算，也不要放循环末尾！应放循环第一行
    while (left != right) {        // ❌【Bug 2】致命漏查与死循环！不能写 !=，必须写 <=
        if (fn[mid] < value) {
            left = mid + 1;
        } else if (fn[mid] > value) {
```

  3. **找不到统一返回 `-1`**！

```java
public class BinarySearchDemo {
```

### 代码 2：反转单链表（迭代三指针法）+ 快慢指针判环

> 🧠 **四步口诀**：**① 存后继 (`next = curr.next`) → ② 扭指针 (`curr.next = prev`) → ③ `prev` 前移 (`prev = curr`) → ④ `curr` 前移 (`curr = next`)。**

```java
public class LinkedListDemo {
    static class ListNode {
        int val;
        ListNode next;
        ListNode(int val) { this.val = val; }
    }

    // 1. 反转单链表
    public static ListNode reverseList(ListNode head) {
        ListNode prev = null, curr = head;
        while (curr != null) {
            ListNode next = curr.next; // ① 暂存后继节点
            curr.next = prev;          // ② 反转指针指向前驱
            prev = curr;               // ③ prev 前移
            curr = next;               // ④ curr 前移
        }
        return prev;
    }

    // 2. 快慢指针判断链表是否有环
    public static boolean hasCycle(ListNode head) {
        ListNode slow = head, fast = head;
        while (fast != null && fast.next != null) {
            slow = slow.next;          // 慢指针走 1 步
            fast = fast.next.next;     // 快指针走 2 步
            if (slow == fast) return true;
        }
        return false;
    }
}
```

### 代码 3：快速排序（QuickSort —— 挖坑填数法，最不容易错！）

> 🧠 **口诀**：**左边界 `arr[left]` 挖出当 `pivot`；先从右往左找小的填左坑，再从左往右找大的填右坑；相遇填回 `pivot`，递归排左右。**

```java
public class QuickSortDemo {
    public static void quickSort(int[] arr, int left, int right) {
        if (left >= right) return;
        int i = left, j = right, pivot = arr[left]; // 1. 左边挖坑，保存基准值
        while (i < j) {
            while (i < j && arr[j] >= pivot) j--;   // 2. 先从右往左找比 pivot 小的
            if (i < j) arr[i] = arr[j];             //    填到左坑
            while (i < j && arr[i] <= pivot) i++;   // 3. 再从左往右找比 pivot 大的
            if (i < j) arr[j] = arr[i];             //    填到右坑
        }
        arr[i] = pivot;                             // 4. 相遇点填回基准值
        quickSort(arr, left, i - 1);                // 5. 递归排左半边
        quickSort(arr, i + 1, right);               // 6. 递归排右半边
    }
}
```

```java
import java.util.*;

public class HashAndStackDemo {
    // 1. 两数之和：边走边算还差多少 (need = target - nums[i])
    public static int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> map = new HashMap<>();
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            if (map.containsKey(need)) return new int[]{map.get(need), i};
            map.put(nums[i], i);
        }
        return new int[0];
    }

    // 2. 有效的括号：遇左括号直接压入对应的右括号

        Deque<Character> stack = new ArrayDeque<>();
        for (char c : s.toCharArray()) {
            if (c == '(') stack.push(')');
            else if (c == '[') stack.push(']');
            else if (c == '{') stack.push('}');
            else if (stack.isEmpty() || stack.pop() != c) return false;
        }
        return stack.isEmpty();
    }
```

### 代码 5：动态规划双子星——最大子数组和（Kadane）+ 0-1 背包（一维逆序）

```java
public class DpTemplates {
    // 1. 最大连续子数组和：前面的累加和 curSum < 0 是负资产就扔掉重开，否则接着加
    public static int maxSubArray(int[] nums) {
        int curSum = nums[0], maxSum = nums[0];
        for (int i = 1; i < nums.length; i++) {
            curSum = Math.max(nums[i], curSum + nums[i]);
            maxSum = Math.max(maxSum, curSum);
        }
        return maxSum;
    }

    // 2. 0-1 背包问题：外层正序遍历物品 i，内层必须从大到小逆序遍历容量 j！
    public static int knapsack01(int V, int[] weight, int[] value) {
        int[] dp = new int[V + 1];
        for (int i = 0; i < weight.length; i++) {
            for (int j = V; j >= weight[i]; j--) {
                dp[j] = Math.max(dp[j], dp[j - weight[i]] + value[i]);
            }
        }
        return dp[V];
    }
}
```

```java
public class Singleton {

    private static volatile Singleton instance;

                if (instance == null) {          // 第二次检查：确保多线程下只创建一个实例

                }
            }
        }
```
