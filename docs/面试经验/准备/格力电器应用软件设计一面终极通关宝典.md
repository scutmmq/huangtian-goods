### 追问 1：云智易视频巡检项目——设备通信是怎么做的？多线程同步与线程池参数怎么设计的？

* **1. 架构重构与痛点（30 秒讲清）**：
  * 原系统用单线程循环串行拉取几百台摄像头的 RTSP 视频流抓拍，一旦某台设备弱网超时卡顿 5 秒，整轮巡检就会阻塞超过 5 分钟。我将其重构为**“XXL-JOB 分片广播 + 专属有界线程池并发执行”**架构。
* **2. 线程池 7 大参数配置与原因**：
  * 显式使用 `ThreadPoolExecutor` 创建：
    * **核心与最大线程数设为 `8`**：一方面依据 $QPS \times RT$ 理论评估，更重要的是受限于**下游边缘流媒体硬件解码通道上限（8~16 路）**以及 **JVM 堆内高清图 RGB 展开的内存占用（单图 4~8MB，8 并发控制在 60MB 内存以内防 OOM）**；
    * **阻塞队列**：选用有界 `ArrayBlockingQueue(500)`（连续内存数组，杜绝无界队列导致内存溢出）；
    * **拒绝策略**：采用 `CallerRunsPolicy`，队列满时由调用方主线程亲自执行，形成**天然反压限流（Backpressure）**，确保巡检任务零丢失。
* **3. 异常兜底与防卡死**：
  * 底层网络 Socket 强制设置 `connectTimeout = 3s`、`readTimeout = 5s`；外层通过 `Future.get(10, TimeUnit.SECONDS)` 监控任务耗时，一旦超时立刻调用 `future.cancel(true)` 发送中断信号释放工作线程。

### 追问 2：凯通科技网管项目——大屏界面加载卡顿（15s $\to$ 200ms）是如何优化的？

> 💡 **格力考官视角**：在应用软件/上位机/监控大屏开发中，“界面卡顿优化”是必考题！

* **满分三步优化话术**：
  1. **定位卡顿根因**：原有接口在打开大屏时，同步关联查询上万个设备节点的静态拓扑坐标与实时告警指标，SQL 聚合慢且一次性返回几十兆 JSON，导致主线程阻塞长达 15 秒；
  2. **动静分离 + 异步多线程分批加载**：
     * **首屏秒开（200ms）**：将低频变动的“设备节点坐标与拓扑连线骨架”预热到 Redis 缓存中，前端首屏只拉取轻量骨架，200ms 内立刻渲染出拓扑图，用户马上可以进行缩放、拖拽、搜索和查看设备静态台账；
     * **状态异步注水**：后台通过多线程异步拉取当前可视区域（Viewport）内的实时告警状态与性能数据，分批流式点亮节点颜色；
  3. **后端批量聚合查询优化**：消除循环单条查库的 $N+1$ 问题，改用批量 `IN` 查询并配合联合覆盖索引，数据库 CPU 负载下降 60% 以上。

### 追问 3：上位机/服务端与硬件设备采用 TCP 通信时，遇到丢包、粘包或设备假死怎么处理？

> 💡 **格力智能家居/工业控制核心场景题**：智能空调联网或工厂设备通信最核心的底层问题！

* **1. 为什么会出现 TCP 粘包与半包？怎么解决？**
  * **原因**：TCP 是**面向字节流（Byte Stream）**的协议，本身没有消息边界概念；发送方 Nagle 算法会把小数据包合并发送（粘包），接收方缓冲区限制或网卡 MTU 分片会把大包拆开（半包）。
  * **解决方案（TLV 自定义帧协议 + 长度解码器）**：
    * 设计定长消息头 + 变长消息体协议：**`魔数 Magic (2B, 如 0xCAFE) + 协议版本 (1B) + 指令类型 (1B) + 数据长度 Length (4B) + 数据体 Body (NB) + CRC16 校验码 (2B)`**；
    * 在 Netty / Socket 接收端使用 `LengthFieldBasedFrameDecoder`，先读取 4 字节的长度字段，严格攒够指定字节数并校验 CRC 通过后，才向上层业务交付一个完整数据包。
* **2. 设备网络假死（拔网线/断电）怎么快速发现？**
  * 不能依赖操作系统默认的 TCP Keep-Alive（默认长达 2 小时才探测一次，且无法感知应用进程死锁假死）；
  * **应用层心跳机制**：设备每 10 秒发送一次轻量 Ping 心跳包；服务端通过 `IdleStateHandler` 检测**读空闲（如连续 30 秒未收到任何报文）**，立即主动关闭僵尸 Socket 连接，将设备状态置为“离线”并触发告警或重连机制。

### 一、Java 核心基础必问（4 题）

#### Q1：面向对象三大特征是什么？接口（Interface）与抽象类（Abstract Class）有什么区别？
* **三大特征**：
  1. **封装**：隐藏对象内部属性细节，仅通过公开方法暴露安全访问入口（高内聚、低耦合）；
  2. **继承**：子类复用父类的属性和方法，并可扩展新功能（`is-a` 关系）；
  3. **多态**：同一方法调用由于对象实例不同而表现出不同行为（编译时看左边父类引用，运行时看右边真实子类对象，底层依靠 JVM `invokevirtual` 方法表动态分派实现）。
* **接口 vs 抽象类**：
  * **语义不同**：抽象类是对一类事物的**共性模板抽取（Is-a）**，可包含普通成员变量、非抽象方法和构造器；接口是对行为规范的**契约定义（Can-do）**，只能有 `public static final` 常量，无构造器；
  * **单继承 vs 多实现**：Java 类只能单继承一个抽象类，但可以实现多个接口。

#### Q2：`ArrayList` 和 `LinkedList` 有什么区别？分别适用于什么场景？
* **底层结构**：`ArrayList` 基于**动态连续数组（`Object[]`）**；`LinkedList` 基于**双向链表（`Node` 含 `prev/next` 指针）**。
* **随机访问效率**：`ArrayList` 实现 `RandomAccess` 接口，通过下标寻址为 **$O(1)$**；`LinkedList` 必须从头或尾遍历，为 **$O(n)$**。
* **插入与删除**：`ArrayList` 在尾部追加均摊 $O(1)$（默认容量 10，满后按 **1.5 倍** `old + (old >> 1)` 扩容），在中间插删需移动数组元素 $O(n)$；`LinkedList` 头尾插删 $O(1)$，但每个节点要额外消耗前后两个引用指针的内存空间，且内存不连续对 CPU 缓存行（Cache Line）不友好。
* **工程选型**：95% 以上的读多写少及顺序遍历场景首选 **`ArrayList`**（若已知大小，初始化指定容量避免扩容拷贝）。

#### Q3：`HashMap` 底层实现原理？为什么线程不安全？高并发下用什么代替？
* **底层结构**：JDK 1.8 采用 **数组 + 链表 + 红黑树**。当单个链表长度 **$\ge 8$ 且数组容量 $\ge 64$** 时树化为红黑树（若容量 $< 64$ 先扩容）；节点数 $\le 6$ 时退化为链表。
* **寻址与扩容**：通过 `(h = key.hashCode()) ^ (h >>> 16)` 高低 16 位异或扰动，配合 `(n - 1) & hash` 位与寻址。负载因子 0.75（存 1000 个元素应初始化为 `1000 / 0.75 + 1 = 1334` $\to$ 实际取 2 的幂 **2048**）。
* **为什么线程不安全？**
  1. JDK 1.7 并发扩容头插法会导致环形链表死循环；
  2. JDK 1.8 改用尾插法解决了死循环，但在并发 `put` 时，两个线程同时判断槽位为空会发生**数据覆盖丢失**，且 `size++` 非原子导致计数不准。
* **并发替代方案**：使用 **`ConcurrentHashMap`**（JDK 1.8 采用 **空桶 CAS 无锁写入 + 非空桶 `synchronized` 仅锁链表/红黑树头节点 + `volatile` 全程无锁读**）。

#### Q4：Java 中受检异常（Checked）和运行时异常（Unchecked）有什么区别？`final`、`finally`、`finalize` 的区别？
* **异常分类**：
  * `Exception` 分为两类：**受检异常**（如 `IOException`、`SQLException`，编译期强制要求 `try-catch` 或 `throws` 声明）与 **运行时异常**（`RuntimeException` 及其子类，如 `NullPointerException`、`IndexOutOfBoundsException`、`ArithmeticException`，由程序逻辑错误引起，编译器不强制捕获）。
* **三者区别**：
  * `final`：修饰类（不可继承，如 `String`）、修饰方法（不可重写）、修饰变量（基本类型值不可变，引用类型指向的对象地址不可变）；
  * `finally`：异常处理块的一部分，无论是否发生异常（哪怕 `try` 里有 `return`），`finally` 中的代码都会执行，常用于**关闭文件流、释放数据库连接或 `ReentrantLock.unlock()`**；
  * `finalize`：`Object` 类的方法，GC 回收对象前调用的钩子，因运行时间不确定且影响 GC 性能，现已废弃。

### 二、操作系统与计算机网络必问（4 题 —— 格力应用软件岗极高频！）

#### Q5：操作系统中“进程（Process）”和“线程（Thread）”有什么根本区别？进程间通信（IPC）有哪些方式？
* **根本区别**：
  1. **资源分配 vs 调度执行**：**进程是操作系统进行资源分配（独立虚拟内存地址空间、文件描述符）的最小基本单位**；**线程是操作系统进行 CPU 调度和执行的最小基本单位**；
  2. **内存共享与隔离**：不同进程间内存相互隔离；同一进程内的多个线程**共享进程的堆内存（Heap）和方法区**，仅各自独享私有的程序计数器和栈空间（Stack）；
  3. **开销与健壮性**：进程创建与上下文切换需要切换页表，开销极大，但一个进程崩溃不影响其他进程；线程切换轻量高效，但一个线程发生未捕获 OOM 可能导致整个进程退出。
* **进程间通信（IPC）五大经典方式**：
  1. **管道（Pipe / 命名管道 FIFO）**；
  2. **消息队列（Message Queue）**；
  3. **共享内存（Shared Memory —— 速度最快的 IPC 方式，直接映射同一块物理内存，需配合信号量同步）**；
  4. **信号量（Semaphore —— 用于进程间互斥与同步计数器）**；
  5. **套接字（Socket —— 支持跨机器网络通信）**。

#### Q6：死锁（Deadlock）产生的四个必要条件是什么？在开发中如何预防和排查死锁？
* **四大必要条件（缺一不可）**：
  1. **互斥条件**：资源同一时刻只能被一个线程占用；
  2. **请求与保持条件**：线程已持有一个资源，又提出新资源请求被阻塞时，对已持有资源保持不放；
  3. **不可剥夺条件**：线程已获得的资源在未使用完前不能被强行剥夺；
  4. **循环等待条件**：多个线程之间形成头尾相接的环形等待资源链（A 等 B，B 等 A）。
* **预防与规避手段**：
  * **破坏循环等待（最常用）**：强制所有线程按照**完全相同的全局顺序（如按账户 ID 从小到大）**申请锁；
  * **破坏请求与保持/不可剥夺**：使用 `ReentrantLock.tryLock(timeout, TimeUnit.SECONDS)` 带超时取锁，超时拿不到立刻释放已持有的全部锁并退避重试；
* **线上排查指令**：使用 `jps -l` 找到 Java 进程 PID $\to$ 执行 **`jstack -l <pid>`**，在输出底部直接查看 `Found one Java-level deadlock` 定位具体代码行号。

#### Q7：TCP 和 UDP 有什么区别？分别适用于什么场景？
| 对比维度 | **TCP（传输控制协议）** | **UDP（用户数据报协议）** |
| :--- | :--- | :--- |
| **连接性** | **面向连接**（通信前必须先经过三次握手建立连接） | **无连接**（想发直接发，无需握手建立连接） |
| **可靠性** | **绝对可靠**（序列号、ACK 确认、超时重传、流量控制、拥塞控制，不丢不乱） | **不可靠、尽最大努力交付**（不保证送达、不保序，可能丢包） |
| **传输单位与边界** | **面向字节流**（无消息边界，存在粘包与半包问题） | **面向数据报（报文）**（保留消息边界，整包收发，无粘包） |
| **首部开销与速度** | 首部最少 **20 字节**，状态机复杂，有一定延迟开销 | 首部固定仅 **8 字节**，极度轻量，实时性极高 |
| **格力典型场景** | **设备控制指令下发、固件 OTA 升级、订单支付交易、HTTP/MQTT 通信** | **局域网智能家居设备广播发现（UDP 配网）、实时音视频监控流、高频传感器周期采样** |

#### Q8：简述 TCP 三次握手与四次挥手的过程？为什么握手是三次，而挥手需要四次？
* **三次握手（建立连接）**：
  1. 客户端发 `SYN=1, seq=x`（进入 `SYN_SENT`）；
  2. 服务端回 `SYN=1, ACK=1, seq=y, ack=x+1`（进入 `SYN_RCVD`）；
  3. 客户端回 `ACK=1, seq=x+1, ack=y+1`（双方进入 `ESTABLISHED`）。
  * **为什么必须三次握手（不能两次）？**：第一，为了确认双方的**接收与发送能力均正常**；第二，**防止网络中滞留的“历史失效连接请求报文”突然到达服务端，导致服务端错误开启连接白白浪费资源**。
* **四次挥手（断开连接）**：
  1. 客户端发 `FIN=1`（表示我没数据要发了，进入 `FIN_WAIT_1`）；
  2. 服务端回 `ACK=1`（进入 `CLOSE_WAIT`，客户端进入 `FIN_WAIT_2`）；
  3. **服务端把剩余未发完的数据传完后**，调用 close 发送 `FIN=1`（进入 `LAST_ACK`）；
  4. 客户端回 `ACK=1`（客户端进入 `TIME_WAIT` 等待 **`2MSL`** 后关闭，服务端收到即关闭）。
  * **为什么挥手比握手多一次（需要四次）？**：因为 TCP 是**全双工通信**。当客户端发送 `FIN` 时，仅代表客户端不再发数据了，但**服务端可能还有未处理完或未发送完的响应数据**；所以服务端必须先回一个 `ACK` 告诉客户端“我知道你要关了”，等服务端把手里剩余的数据全部发完后，才能发送自己的 `FIN` 报文，因此中间的 `ACK` 和 `FIN` 不能合并，必须分成四步！

### 三、MySQL、MyBatis 与 Spring 框架必问（4 题）

#### Q9：MySQL 索引底层为什么使用 B+ 树而不是 B 树（B-Tree）或红黑树？
1. **为什么不用红黑树？**：红黑树是二叉树，面对千万级数据时树高达到 20 多层，意味着要发生 20 多次磁盘随机 I/O，极慢；而 B+ 树是多路平衡查找树，**2000 万数据树高仅 3 层（1~2 次磁盘 I/O）**；
2. **为什么用 B+ 树而不用 B 树？**
   * **非叶子节点纯存索引，扇出率极高**：B+ 树非叶子节点不存完整行数据（只存 `主键 8B + 指针 6B = 14B`），16KB 的页能存 1170 个指针；而 B 树非叶子节点夹杂着行数据，导致树变高、I/O 次数增加；
   * **叶子节点双向链表，天然支持范围查询**：B+ 树所有数据都在叶子节点，且叶子节点之间用**双向指针连接**，执行 `WHERE create_time BETWEEN ... AND ...` 或 `ORDER BY` 时直接顺着链表扫描即可；而 B 树需要跨层反复中序遍历回溯。

#### Q10：MyBatis 中 `#{}` 和 `${}` 的区别是什么？如何防止 SQL 注入？
* **`#{}`（预编译占位符 —— 推荐）**：
  * MyBatis 在解析时会将 `#{}` 替换为 `?`，底层使用 JDBC 的 **`PreparedStatement` 进行预编译**，参数值在编译后安全填入并自动加上单引号。因为 SQL 语法树在传参前就已经固定，**能 100% 防止 SQL 注入攻击**。
* **`${}`（字符串直接拼接 —— 高危）**：
  * 直接把参数内容原样拼接到 SQL 字符串中（不加引号），采用 `Statement` 执行，存在严重的 **SQL 注入风险**（例如传入 `' OR 1=1 --`）。
* **何时才不得不用 `${}`？**：只有在动态传入**表名、列名或 `ORDER BY` 排序字段名**（如 `ORDER BY ${columnName} DESC`）时才使用，且必须在 Java 代码中对入参做严格的**白名单校验**！

#### Q11：谈谈你对 Spring IoC（控制反转）和 AOP（面向切面编程）的理解及实际应用？
* **IoC（控制反转）与 DI（依赖注入）**：
  * **核心思想**：将对象创建、组装与生命周期管理的控制权，从业务代码自身的 `new` 转移（反转）给 **Spring IoC 容器**统一管理；容器在运行时通过构造器或 `@Autowired` 反射自动将依赖对象注入进来，实现组件间的**彻底解耦**。
* **AOP（面向切面编程）**：
  * **核心思想**：将遍布在各个业务模块中的非业务公共逻辑（横切关注点）抽取出来，在不动业务源码的前提下，通过 **动态代理（有接口用 JDK 动态代理，无接口用 CGLIB 字节码生成子类）** 动态织入。
  * **你在项目中的真实应用**：① `@Transactional` 声明式事务管理；② 统一接口请求出入参日志与耗时审计记录；③ 基于自定义注解 + Redis 的接口防重幂等校验与权限拦截。

#### Q12：Redis 在你们项目中主要用来做什么？为什么 Redis 单线程还能这么快？
* **三大实战应用**：
  1. **高频热点数据缓存**（如凯通网管大屏的静态拓扑骨架、商城商品详情，降低数据库压力）；
  2. **分布式锁与幂等防重**（利用 Redisson 看门狗或 `SETNX` 控制定时任务与接口幂等）；
  3. **原子计数器与库存预扣**（利用 Redis + Lua 脚本保证多步操作原子性）。
* **为什么单线程还极快（单机 10 万+ QPS）？**：
  1. **纯内存操作**（纳秒级寻址）；
  2. **底层高效数据结构**（SDS、压缩列表/Listpack、跳表 SkipList、渐进式 Rehash 哈希表）；
  3. **单线程避免了多线程上下文切换与锁竞争开销**；
  4. **非阻塞 I/O 多路复用机制（Linux `epoll`）**，单线程同时监听成千上万个客户端 Socket 事件。
