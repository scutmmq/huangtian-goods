## 专题一：MySQL 数据库连接池底层与间隙锁死锁深度穿透

### 1. HikariCP 为什么号称光速？核心参数底层原理与生产避坑

#### (1) HikariCP 的光速三大微观优化
1. **字节码级别的极致精简**：全库只有一百多 KB 代码，很多方法内联（Inlining），消除了冗余的方法调用栈；
2. **`FastList` 取代 `ArrayList`**：传统 `ArrayList.remove(obj)` 必须从头遍历查找目标连接（$O(N)$ 复杂度）；HikariCP 针对连接“借出后后借先还”的特性，自研 `FastList` 从尾部逆序向前查找删除，耗时几乎为 $O(1)$，且去掉了数组越界检查；
3. **`ConcurrentBag` 无锁并发容器与 `ThreadLocal` 缓存**：
   * 每个工作线程借出连接时，优先从自身的 `ThreadLocal` 缓存中直接获取上一次使用过的连接（**完全零锁、零 CAS 开销，FastPath 耗时仅纳秒级**）；
   * 本地未命中时，才进入 `ConcurrentBag` 的无锁共享队列通过 CAS 争抢。

#### (2) 生产核心参数详解与配置心法
* **`maximum-pool-size`（最大连接数）**：
  * **经验公式（PostgreSQL / Oracle 官方推导）**：
    $$	ext{Connections} = (	ext{CPU Core Count} 	imes 2) + 	ext{Effective Spindle Count}$$
  * **为什么不能设为几百？**：MySQL 一个物理连接对应服务端一个工作线程。连接数过多会导致 CPU 核心在几百个线程之间疯狂进行**线程上下文切换（Context Switch）**，导致 CPU 算力全浪费在切线程上，数据库吞吐量反而雪崩。对于 8 核服务器，设为 **16~32** 是吞吐量峰值。
* **`max-lifetime`（连接最大存活时间，默认 30 分钟）**：
  * **避坑铁律**：**必须严格比 MySQL 服务端的 `wait_timeout`（通常为 8 小时或被 DBA 调成 10 分钟）短 2~3 分钟！**
  * **踩坑惨案**：如果客户端 `max-lifetime` 设为 30 分钟，而 MySQL 的 `wait_timeout` 是 10 分钟；当一个连接闲置 11 分钟后，MySQL 服务端会单方面向客户端发送 TCP FIN 包掐断该连接。此时客户端不知情，借出连接执行 SQL，抛出臭名昭著的：`Communications link failure / Connection reset by peer`。
* **`connection-timeout`（获取连接最大超时时间，推荐 30000ms / 30s）**：
  * 客户端借不到连接时的最长排队等待时间。超时抛出 `SQLException: Connection is not available`。

### 2. MySQL 间隙锁（Gap Lock）产生本质与死锁日志分析

#### (1) 间隙锁核心定位与触发机制
* **定位**：在 **可重复读（Repeatable Read, RR）** 隔离级别下，锁定一个开区间 `(low, high)`，不包含记录本身，专门为了**阻止并发 `INSERT` 插入新数据，从而彻底杜绝幻读（Phantom Read）**！
* **触发场景**：
  1. 普通辅助索引的等值查询；
  2. 唯一索引查询不存在的记录（退化为锁住两边缝隙的间隙锁）；
  3. 范围查询。

#### (2) 间隙锁死锁经典场景（为什么死锁？推导时序）
* **核心规律**：**间隙锁与间隙锁之间互不冲突、是兼容的！但间隙锁与插入意向锁（Insert Intention Lock）互斥！**
* **经典死锁场景还原**：
  * 表结构：`id` 主键，表中仅有记录：`1, 5, 10`。
  * **时序 T1**：事务 A 执行 `SELECT * FROM t WHERE id = 7 FOR UPDATE;`。记录 7 不存在，事务 A 获得 `(5, 10)` 的间隙锁。
  * **时序 T2**：事务 B 执行 `SELECT * FROM t WHERE id = 8 FOR UPDATE;`。记录 8 也不存在，由于间隙锁互相兼容，事务 B **也成功获得了 `(5, 10)` 的间隙锁**！
  * **时序 T3**：事务 A 执行 `INSERT INTO t VALUES (7);`。插入新行需要申请 `(5, 10)` 上的插入意向锁，发现事务 B 正持有该区间的间隙锁，事务 A 被**阻塞挂起等待**！
  * **时序 T4**：事务 B 执行 `INSERT INTO t VALUES (8);`。同样需要申请插入意向锁，发现事务 A 正持有该区间的间隙锁，事务 B 也被**阻塞挂起等待**！
  * **死锁爆发**：事务 A 等待事务 B 释放锁，事务 B 等待事务 A 释放锁，形成循环等待依赖。
* **排查与查看**：执行 `SHOW ENGINE INNODB STATUS;`，查看 `LATEST DETECTED DEADLOCK` 日志段落，定位死锁事务持有的 `lock_mode X locks gap before rec` 与等待的 `insert intention`。

### 2. 查出问题后，到底如何从根本上修复？（代码层根治 vs 架构层限流 vs 参数层固化）

很多同学只知道排查，不知道“查出后怎么修”。工业级修复包含三大维度的组合拳：

#### (1) 代码级彻底根治（最关键、最有效手段）
1. **解决 `ThreadLocal` 内存泄漏**：
   * **根因**：线程池中的核心线程常驻不销毁，线程的 `ThreadLocalMap` 强引用着 Value；
   * **修复**：在拦截器或业务代码的 `finally` 块中**强制显式调用 `threadLocal.remove()`**！
2. **解决大集合全表扫描（OOM 头号杀手）**：
   * **根因**：导出报表或数据同步时，一次性 `SELECT *` 查出 50 万条数据装进内存 `List<Order>`；
   * **修复**：改为**流式查询（Cursor / Stream）** 或 **分批分页拉取（`id > last_id LIMIT 1000`）**，结合写出一条清理一条，内存占用恒定在几十 KB。
3. **关闭未关闭的资源流**：使用 Java 7+ 的 `try-with-resources` 确保数据库连接、文件 IO 流、网络 Socket 严格关闭。

#### (2) 架构级限流与熔断兜底
* 如果排查发现老年代升高不是因为泄漏，而是**由于外部大促或突发秒杀流量暴增导致的并发临时对象堆积**：
* **修复举措**：在接口入口处引入 **Sentinel 或 Redis + Lua 进行限流**，把超出系统承载 QPS 的请求在网关层直接快速失败返回 429，防止大流量将堆内存打爆拖垮整机。

#### (3) 参数层固化 4 大保命基线
1. `-Xms4g -Xmx4g`：初始堆与最大堆对齐，杜绝堆扩容缩容 STW；
2. `-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m`：锁定元空间防启动频繁 Full GC；
3. `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/logs/dump.hprof`：保留崩溃案发现场；
4. `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0`：容器化环境感知 Cgroups 配额防 OOMKilled（137）。

## 专题三：Java 多线程底层、AQS 与线程生命周期通信机制

### 1. AQS（AbstractQueuedSynchronizer）底层物理结构与加锁释放流程

* **AQS 的物理本质**：JUC 并发包（`ReentrantLock`、`Semaphore`、`CountDownLatch`）的核心底座。
* **两大核心成员**：
  1. **`volatile int state`（核心状态位）**：
     * 在 `ReentrantLock` 中代表锁的持有状态（`state = 0` 未加锁；`state = 1` 已加锁；`state > 1` 代表可重入次数）；
     * 在 `CountDownLatch` 中代表剩余计数器。
  2. **双向 FIFO 链表（CLH 队列变体）**：
     * 存放等待获取锁的线程封装节点（`Node`），包含 `prev`、`next` 指针、等待线程 `thread` 以及等待状态 `waitStatus`（如 `SIGNAL = -1` 代表后继节点需要被唤醒）。

```
Head (虚拟头节点) <───> Node 1 (Thread-A, waitStatus=-1) <───> Node 2 (Thread-B) <─── Tail
```

#### 加锁与释放底层流程（以 ReentrantLock 独占非公平锁为例）：
1. **加锁（`acquire`）**：
   * 线程调用 `lock()`，首先尝试通过 CAS 将 `state` 从 0 改为 1（插队争抢）；
   * 若成功，将 exclusiveOwnerThread 设为当前线程；
   * 若失败，判断是否为当前线程重入（`state = state + 1`）；
   * 若仍失败，将当前线程封装成 `Node.EXCLUSIVE` 节点，通过 CAS 自旋追加到双向链表尾部（`addWaiter`），随后调用 **`LockSupport.park(this)`** 将该线程挂起休眠。
2. **释放锁（`release`）**：
   * 线程调用 `unlock()`，`state` 减 1；当 `state == 0` 时，清空持有者指针；
   * 找到队列头部（Head）的有效后继节点，调用 **`LockSupport.unpark(node.thread)`** 将其唤醒；
   * 被唤醒的线程从 `park()` 处继续执行，重新通过 CAS 争夺锁。

### 2. Java 线程生命周期 6 大状态迁移图与精确触发时机

在 `java.lang.Thread.State` 枚举中，Java 线程定义了标准的 **6 大生命周期状态**：

```
                    ┌──────────────┐
                    │     NEW      │ (创建但尚未 start())
                    └──────┬───────┘
                           │ thread.start()
                           ▼
               ┌───────────────────────┐
  ┌───────────>│       RUNNABLE        │<───────────┐
  │ 获得锁     │ (可运行: 正在CPU运行   │  获得锁/唤醒 │
  │ 放行       │  或就绪排队等分配时间片)│  超时退出    │
  │            └─────┬───────────┬─────┘            │
  │                  │           │                  │
等待进入监视器锁      │           │                  │
  ▼                  ▼           ▼                  │
┌──────────────┐   ┌─────────┐   ┌────────────────┐ │
│   BLOCKED    │   │ WAITING │   │ TIMED_WAITING  │ │
│(阻塞等待锁)  │   │(无限等待)│   │  (超时等待)    │ │
└──────────────┘   └────┬────┘   └───────┬────────┘ │
  ▲                     │                │          │
  └─────────────────────┴────────────────┴──────────┘
                        │ 任务正常完成或抛出未捕获异常
                        ▼
                 ┌──────────────┐
                 │  TERMINATED  │ (死亡终止)
                 └──────────────┘
```

#### 各状态精确触发时机速查：
* **`BLOCKED`（阻塞状态）**：**唯有** 线程在等待获取 `synchronized` 监视器锁时才会进入！
* **`WAITING`（无限等待状态）**：线程调用 `Object.wait()`、`Thread.join()`、`LockSupport.park()` 时进入，必须等待其他线程显式调用 `notify()` 或 `unpark()` 唤醒。
* **`TIMED_WAITING`（超时等待状态）**：带有时间限制的方法，如 `Thread.sleep(ms)`、`Object.wait(ms)`、`LockSupport.parkNanos()`。

---

### 3. 线程间通信与优雅中断机制（为什么不用 stop()？interrupt() 如何正确阻断）

#### (1) 为什么绝不能使用 `Thread.stop()`？
* `stop()` 是暴力的强行杀线程机制。它被调用时，会瞬间释放该线程持有的所有锁，**哪怕此时线程正在修改多个共享变量的临界区中途**！
* 会导致对象内部状态严重破坏、数据不一致，且不会给任何资源释放清理的机会。因此自 JDK 1.2 起已被全面废弃（Deprecated）。

#### (2) 现代优雅协作式中断机制：`interrupt()`
* **核心哲学**：**中断在 Java 中只是一个“信号标志位（Flag）”，它不会直接把线程掐死，而是礼貌地通知目标线程：“请你在合适的时机自己停下来”**。
* **两大中断场景处理规范**：
  1. **场景 A：线程正处于 `WAITING / TIMED_WAITING` 阻塞中（如 sleep / wait）**：
     * 此时调用 `thread.interrupt()`，JVM 会强制将线程唤醒，并抛出 **`InterruptedException`**；
     * **致命注意点**：抛出异常的同时，**线程的中断标志位会被 JVM 自动复位为 false**！
     * **正确规范**：在 `catch (InterruptedException e)` 中，要么向上继续抛出，要么必须执行 `Thread.currentThread().interrupt()` **重新恢复中断标志**，让上层代码感知到中断。
  2. **场景 B：线程处于正常 CPU 计算密集型循环中**：
     * 线程不会自动停下来，必须在循环内部主动检测中断标志：
     ```java
     while (!Thread.currentThread().isInterrupted()) {
         // 执行业务计算...
     }
     // 退出循环后执行收尾清理工作
     cleanResources();
     ```

## 专题四：Redis 五大核心数据结构底层物理实现全景

### 1. String 底层：SDS（简单动态字符串）的 3 大物理优势
Redis 没有直接使用 C 语言的原生字符数组 `char[]`，而是自研了 **SDS（Simple Dynamic String）**：
* **结构包含**：`len`（已用长度）、`alloc`（分配总空间）、`flags`（类型标头）、`buf[]`（实际字符数组）。
* **三大物理优势**：
  1. **获取长度复杂度 $O(1)$**：C 字符串获取长度需要从头遍历到 ` `（$O(N)$）；SDS 直接读取 `len` 属性即可；
  2. **空间预分配与惰性释放，杜绝缓冲区溢出（Buffer Overflow）**：字符串追加修改时，SDS 自动检查剩余容量，不够自动扩容（小于 1MB 翻倍，大于 1MB 每次多给 1MB）；字符串截短时不立即释放内存，便于下次复用；
  3. **二进制安全（Binary Safe）**：C 字符串以 ` ` 作为结束标志，无法存储包含 ` ` 的图片、音频等二进制内容；SDS 依靠 `len` 决定长度，buf 内部可以存放任何二进制数据。

---

### 2. List 底层：Quicklist（双向链表 + ZipList 压缩列表）
* **演进背景**：纯双向链表（LinkedList）的每个节点需要前后指针，在 64 位系统下仅指针就占 16 字节，内存碎片严重；纯压缩列表（ZipList）虽然内存连续紧凑，但在数据量大时，插入或删除会导致连锁更新（Cascading Update）。
* **Quicklist 设计**：
  * **宏观上是一条双向链表**；
  * **链表中的每一个节点（Node）内部，包裹着一个紧凑的压缩列表（ZipList / Listpack）**；
  * 完美平衡了“双向链表的高效增删”与“压缩列表的连续内存高缓存命中与低指针碎片”。

---

### 3. Hash 底层：Dict（字典）与渐进式 rehash 底层机制
* **Dict 内部结构**：包含两个哈希表 `ht[0]`（正常使用）和 `ht[1]`（扩容备用）。
* **渐进式 rehash（大厂高频深挖）**：
  * **痛点**：若字典内有几百万条数据，一次性把全部数据 rehash 迁移到新表，会导致 Redis 主线程长时间阻塞卡死。
  * **渐进式迁移流程**：
    1. 为 `ht[1]` 分配两倍容量空间，将字典维护的计数器 `rehashidx` 设为 0，表示正式进入 rehash 状态；
    2. **分摊到日常请求中**：在 rehash 期间，每一次对该字典进行增删改查操作时，Redis 会顺带将 `ht[0]` 上 `rehashidx` 索引处的整个 bucket 槽位上的所有节点**平摊迁移到 `ht[1]`**，并将 `rehashidx++`；
    3. **后台定时任务兜底**：服务器空闲时，定时任务每次花 1 毫秒迁移部分槽位；
    4. **迁移完毕**：`rehashidx` 重新置为 -1，将 `ht[1]` 赋值给 `ht[0]`，释放原 `ht[0]` 空间。

---

### 4. ZSet 底层：跳表（SkipList）+ 哈希表（Dict）的复合设计
* **为什么 ZSet 要同时依赖两个数据结构？**
  1. **哈希表（Dict）**：存储 `Member -> Score` 的映射，实现根据成员名以 **$O(1)$ 复杂度查询其分数**；
  2. **跳表（SkipList）**：存储所有节点，并按 `Score` 从小到大排序。
* **跳表物理设计**：
  * 底层包含全量有序链表；
  * 每个节点通过**随机层高算法（1 到 32 层，以 1/4 概率向上增加层数）**建立多级前向跳跃指针 `forward`；
  * 范围查询（`ZRANGEBYSCORE`）与根据排名获取（`ZRANK`）利用跳跃指针自顶向下快速二分定位，平均查找复杂度为 **$O(\log N)$**。

## 专题五：Kafka 底层核心机制与高并发高可用生产场景实战

### 1. Kafka 极致吞吐四大杀手锏底层剖析（顺序写盘、零拷贝、PageCache、批压缩）

1. **顺序写磁盘（Sequential Disk I/O）**：
   * Kafka 是追加写日志（Append-only），磁头无需反复来回寻道，顺序读写机械硬盘吞吐高达数百 MB/s。
2. **零拷贝技术（Zero-Copy via `sendfile`）**：
   * 消费网络传输调用 Linux `sendfile()`，数据从内核态 PageCache 直接传输给网卡 Socket 缓冲区，**跳过了数据拷贝至 JVM 堆用户态内存的开销，将 4 次拷贝压降为 2 次，4 次上下文切换压降为 2 次**。
3. **充分利用操作系统 PageCache（页缓存）**：
   * 消息直接写入 OS PageCache，读写完全由操作系统内核做内存缓冲，JVM 进程堆几乎零内存开销，彻底杜绝 JVM GC 停顿。
4. **分区分段（Partition + Segment）与批量压缩**：
   * 水平物理切分支持并行 IO，批处理结合 Snappy 压缩极大压缩网络封包。

---

### 2. 消息可靠性底层：ISR、LEO（Log End Offset）与 HW（High Watermark）

```
Leader Partition:    [0] [1] [2] [3] [4] [5]  <-- LEO = 6
                              ▲
                              │ HW = 3 (所有 ISR 均同步完毕的位置)
Follower 1:          [0] [1] [2]  <-- LEO = 3
Follower 2:          [0] [1] [2]  <-- LEO = 3
```
* **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合（滞后时间超过 `replica.lag.time.max.ms` 会被踢出 ISR）；
* **LEO（Log End Offset）**：当前副本最后一条写入消息的下一个偏移量（待写入位置）；
* **HW（High Watermark 高水位）**：**ISR 集合中所有副本最小的 LEO**！
  * **核心铁律**：**只有小于等于 HW 的消息才被视为“提交成功（Committed）”，只有这部分消息才允许暴露给消费者消费！** 杜绝了尚未同步的消息被消费后 Leader 宕机导致的数据不一致。

---

### 3. 生产场景应对：海量积压三步抢救 SOP 与网络卡顿本地消息表兜底

#### (1) 海量积压三步抢救 SOP
1. **排查下游**：先看下游数据库是否死锁、慢 SQL 或连接池耗尽，排查消费者报错；
2. **常规水平扩容**：紧急将 Topic 分区数扩容，同时将 Consumer 实例等比例扩容（Consumer 数 $\le$ Partition 数）；
3. **极端应急分流**：紧急上线临时的“搬砖消费者”，不做业务逻辑，快速将积压消息批量转投到开有 50 个分区的临时 Topic，再挂 50 个业务消费者全速消化洪峰。

#### (2) 网络卡顿本地消息表兜底
* 发送消息前，在同一个数据库本地事务中将消息写入 `local_message_log`（状态为 `PENDING`）；
* 异步线程发送 Kafka，收到成功 ACK 后将本地状态改为 `SUCCESS`；
* 定时任务轮询超过 10 秒未成功的消息，结合指数退避重试重新投递，超限报警转人工，结合下游唯一键幂等，保证极端弱网下 100% 不丢指令。

## 专题六：Spring 生态限流降级与微服务治理

### 1. 四大限流算法数学模型对比（固定窗口、滑动窗口、漏桶、令牌桶）

| 算法类型 | 核心设计原理 | 优势 | 致命缺陷与痛点 |
| :--- | :--- | :--- | :--- |
| **固定窗口计数器** | 划分固定 1 秒时间段，计数超过阈值拒绝。 | 实现极简，内存极小。 | **临界突刺问题**：在第 0.9 秒与第 1.1 秒各进来 100 个请求，窗口跨界处 0.2 秒内承受了 200 个并发，打爆系统。 |

| **令牌桶算法 (Token Bucket)**<br>*(Guava RateLimiter 核心)* | 以恒定速率往桶里扔令牌，桶满则溢出；请求拿到了令牌即可放行。 | **既限制了平均速率，又允许一定程度的突发流量**（只要桶里积攒了令牌即可短时爆发）。 | 工业界单机限流的最优选择！ |

## 专题九：算法专项特训：动态规划推导、贪心与二分查找通用模板

### 1. 动态规划（DP）推导心法五步法（如何写出状态转移方程）
> 面试被卡死往往是因为“跳过了前两步，直接去凑方程”。任何 DP 严格按五步推导：

1. **Step 1：确定 `dp` 数组及下标的物理含义**（例如 $dp[i][j]$：背包容量为 $j$ 时，前 $i$ 个物品能取得的最大价值）；
2. **Step 2：推导状态转移方程**（从最后一步反推：当前物品选还是不选？选就是 $dp[i-1][j - weight[i]] + value[i]$，不选就是 $dp[i-1][j]$）；
3. **Step 3：`dp` 数组初始化 base case**（容量为 0 时价值为 0，物品数为 0 时价值为 0）；
4. **Step 4：确定遍历顺序**（先遍历物品还是先遍历背包？正序还是逆序？）；
5. **Step 5：举例推导打印 `dp` 数组验证**。

---

### 2. 0-1 背包问题核心推导与一维滚动数组逆序代码模板

* **为什么一维数组必须「从大到小逆序遍历」？**
  * 在一维优化后，当前状态公式为：`dp[j] = Math.max(dp[j], dp[j - weight[i]] + value[i])`；
  * 如果正序遍历：小容量 $j$ 的状态先被更新成了“已放入当前物品”，那么大容量 $j'$ 计算时，引用的 `dp[j' - weight[i]]` 已经包含了当前物品，导致**同一个物品被多次放入（退化为完全背包）**！
  * **逆序遍历保证计算 $dp[j]$ 时，所参考的 $dp[j - weight[i]]$ 依然是“上一层物品计算后的未装入旧值”！**

```java
public class Knapsack01 {
    public static int knapsack(int V, int[] weight, int[] value) {
        int n = weight.length;
        int[] dp = new int[V + 1];

        for (int i = 0; i < n; i++) { // 遍历物品
            for (int j = V; j >= weight[i]; j--) { // 核心：逆序遍历背包容量！
                dp[j] = Math.max(dp[j], dp[j - weight[i]] + value[i]);
            }
        }
        return dp[V];
    }
}
```

### 3. 最长上升子序列（LIS）双解法：DP $O(N^2)$ 与 贪心+二分 $O(N \log N)$

#### 解法 A：经典 DP（$O(N^2)$，代码易写）
* $dp[i]$：以 $nums[i]$ 结尾的最长上升子序列长度。
```java
public int lengthOfLIS_DP(int[] nums) {
    if (nums == null || nums.length == 0) return 0;
    int[] dp = new int[nums.length];
    Arrays.fill(dp, 1);
    int max = 1;
    for (int i = 1; i < nums.length; i++) {
        for (int j = 0; j < i; j++) {
            if (nums[i] > nums[j]) {
                dp[i] = Math.max(dp[i], dp[j] + 1);
            }
        }
        max = Math.max(max, dp[i]);
    }
    return max;
}
```

#### 解法 B：贪心 + 二分查找（$O(N \log N)$，满分最优解）
* 维护 `tail[k]`：长度为 $k+1$ 的上升子序列中，最小的末尾值。
```java
public int lengthOfLIS_Binary(int[] nums) {
    if (nums == null || nums.length == 0) return 0;
    int[] tail = new int[nums.length];
    int res = 0; // 当前最长有效长度

    for (int num : nums) {
        int left = 0, right = res;
        while (left < right) {
            int mid = left + (right - left) / 2;
            if (tail[mid] < num) left = mid + 1;
            else right = mid;
        }
        tail[left] = num;
        if (right == res) res++;
    }
    return res;
}
```

### 4. 二分查找边界经典无 Bug 模板（左闭右闭与上下界查找）

* **最经典的左闭右闭模板（区间 `[left, right]`）**：
  * 初始化：`left = 0, right = nums.length - 1`；
  * 循环条件：`while (left <= right)`；
  * 中点防溢出：`int mid = left + (right - left) / 2`；
  * 更新指针：`left = mid + 1` 或 `right = mid - 1`。
* **查找第一个大于等于 target 的左边界（常用于 LIS 二分定位）**：
  ```java
  public int lowerBound(int[] nums, int target) {
      int left = 0, right = nums.length; // 区间 [left, right)
      while (left < right) {
          int mid = left + (right - left) / 2;
          if (nums[mid] < target) {
              left = mid + 1;
          } else {
              right = mid;
          }
      }
      return left;
  }
  ```
