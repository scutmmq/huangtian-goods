### Q1：成百上千台工业机器人/AGV 高频上报遥测状态，如何设计高吞吐、低延迟的接入层？

> 💡 **业务场景**：每台机器人每隔 100ms~500ms 上报一次当前坐标 $(X, Y, Z)$、电量、速度、激光雷达雷达避障距离、运行状态。500 台机器人每秒产生数千次高频上报，直接打进 MySQL 必死无疑。

#### 工业级分层架构方案：
```
[500台机器人 / AGV] ──(MQTT / Netty TCP 长连接)──> [接入层网关 (Netty 集群)]
                                                          │ 零拷贝直接转发
                                                          ▼
                                              [Kafka 分区消息队列 (批量缓冲削峰)]
                                                          │
                                         ┌────────────────┴────────────────┐
                                         ▼                                 ▼
                         [实时计算服务 (Flink / 内存消费)]       [时序数据库 (InfluxDB / IoTDB)]
                                         │                                 │
                         更新 Redis 机器人最新快照 (缓存)             历史运行轨迹归档 (冷数据)
```

1. **协议选型与网关接入**：
   * 采用 **Netty 自定义 TCP 长连接** 或 **MQTT 协议（QoS 0 或 QoS 1）**；
   * 网关只负责两件事：**鉴权验签 + 协议解码（拆包解包）**。网关主线程绝不做耗时数据库 I/O；
2. **异步管道削峰（Kafka 批处理）**：
   * 网关收到遥测数据后，将其序列化为 Protobuf 二进制数据段，直接发送到 **Kafka 遥测 Topic**（Producer 开启批量发送 `batch.size=64KB`, `linger.ms=10`, 配合 Snappy 压缩）；
3. **动静分离存储（Redis 内存快照 + 时序数据库轨迹）**：
   * **当前最新状态（高频只读）**：消费端以 `robot_id` 为 Key，将最新坐标与电量原子更新写入 **Redis Hash 缓存**（QPS 支撑数十万，调度算法直接读 Redis 计算机器人避障）；
   * **历史行驶轨迹（大批量写、低频读）**：批量异步写入 **时序数据库（如 InfluxDB、TDengine、IoTDB）**，高效压缩时间序列数据，释放关系型数据库压力。

### Q2：下发给机器人/机械臂的控制指令，遇到弱网抖动如何保证 100% 绝对不丢、严格保序且防重复执行？

> 💡 **业务痛点**：车间 Wi-Fi 信号遮挡，下发给机械臂的“抓取 $\to$ 旋转 $\to$ 放置”指令如果乱序、丢失或重复执行，会导致机器人撞机或工件损坏！

#### 1. 绝对不丢：本地消息表（Local Message Table）+ 指数退避重试
* 上位机生成指令时，在同一个本地数据库事务中保存业务订单与 `local_message_log`（状态为 `PENDING`）；
* 异步网络发送；只有收到机器人返回的业务级 ACK 确认报文后，才将状态更新为 `SUCCESS`；
* 若网络断开未收到 ACK，启动重试，采用**指数退避（100ms $\to$ 200ms $\to$ 400ms）**重新投递；超过 5 次失败触发人工介入与机台停机安全保护。

#### 2. 严格保序：单机器人逻辑单分区（Single Partition FIFO）
* **物理铁律**：**Kafka 只有在同一个 Partition 内部才能保证严格有序**！
* 生产者发送指令时，**必须以 `robot_id` 作为 Message Key**。相同机器人的所有指令必然通过哈希路由到同一个 Partition 中，由同一个消费线程按 Offset 递增严格顺序下发；
* 生产端配置 `max.in.flight.requests.per.connection = 1`，杜绝因重试导致的网络包乱序。

#### 3. 防重复执行：状态机前置乐观锁 + 唯一流水号
* 机器人端维护当前任务流水号 `last_task_seq`；
* 收到指令先比对序列号：若当前收到任务的 `seq <= last_task_seq`，说明是因网络重传导致的重复消息，机器人**直接返回 ACK 但在底层安全短路丢弃，坚决不二次执行机械动作**；
* 数据库更新带前置状态约束：`UPDATE t_robot_task SET status='RUNNING' WHERE task_id=101 AND status='WAITING'`，避免并发重复执行。

### Q3：机器人设备心跳机制与网络假死判定（TCP Keep-Alive vs Netty 应用层心跳）

* **面试官最爱问**：“TCP 协议本身不是自带 Keep-Alive 吗？为什么你们在上层还要做应用层心跳？”
* 🗣️ **满分回答**：
  1. **TCP Keep-Alive 的致命缺陷**：
     * **检测周期过长**：操作系统默认的 `tcp_keepalive_time` 通常是 **7200 秒（2 小时）**！工业控制系统要求秒级感知机器人掉线，2 小时黄花菜都凉了；
     * **无法感知应用层死锁与假死**：TCP Keep-Alive 运行在操作系统的内核态。如果工业控制器或机器人上位机的 Java 进程发生 Full GC STW、线程死锁或内存溢出导致业务假死，**此时内核协议栈依然会正常响应 TCP Keep-Alive 探测包**！服务器会误认为设备健康，但实际上它已经无法处理任何调度业务；
  2. **应用层心跳黄金设计（Netty IdleStateHandler）**：
     * 机器人每隔 **5 秒** 发送一个极其轻量的应用层心跳帧（Ping）；
     * 服务端 Netty 管道添加 **`IdleStateHandler(15, 0, 0, TimeUnit.SECONDS)`**（读空闲检测）；
     * 如果连续 **15 秒（3 个周期）** 未收到该机器人的任何数据包，触发 `userEventTriggered` 读空闲事件；
     * **执行动作**：服务端主动掐断该僵尸连接（`ctx.close()`），并将该机器人标记为 `OFFLINE`（离线），触发调度系统自动将该机器人的在途任务重新分配给其他空闲机器人。

### Q4：上位机调度系统与硬件通信时，TCP 粘包与半包是如何解决的？（TLV 变长协议设计）

* **产生根因**：TCP 是面向字节流的协议，没有消息保护边界。多个小指令会被 Nagle 算法合并粘包；大报文超过 MTU 会被切片产生半包；
* **工业级最佳解决方案：TLV 格式（Type-Length-Value）自定义协议头**：
  ```
  +---------------+---------------+-----------------+--------------------+
  | 协议魔数(2B)   | 消息类型(2B)   | 数据体长度(4B)   | 实际控制载荷(Payload) |
  | 0xCAFE        | 0x0001(调度)  | Length: 256     | 具体的工控二进制字节流  |
  +---------------+---------------+-----------------+--------------------+
  ```
* **Netty 优雅落地**：在 Netty ChannelPipeline 中添加 **`LengthFieldBasedFrameDecoder`**（自定义长度帧解码器）：
  * 指定长度字段偏移量（Offset）与长度字段所占字节数（4 字节）；
  * Netty 自动在内核缓冲区积攒满一个完整长度的报文后，才向上层 Handler 投递一个完整的业务对象，从根本上消灭粘包半包！

### Q5：1000 个键值对存入 HashMap，如何初始化容量才不会频繁扩容？（数学推导 2048）

* ❌ **直觉陷阱**：脱口而出 1024（以为大于等于 1000 的最小 2 的幂是 1024）；
* 💡 **底层推导**：
  * 扩容取决于阈值：$$\text{Threshold} = \text{Capacity} \times \text{LoadFactor} = 1024 \times 0.75 = 768$$
  * 传 1024，在存入第 **769** 个元素时就会立即触发一次全量数组扩容并全局 rehash；
  * **正解公式**：
    $$\text{Capacity} \ge \frac{\text{ExpectedSize}}{\text{LoadFactor}} = \frac{1000}{0.75} \approx 1333.33$$
    HashMap 内部通过 `tableSizeFor` 位运算找到大于等于 1334 的最小 2 的幂，即为 **2048**！
  * 阿里规范代码：`Map<String, Object> map = new HashMap<>((int) (1000 / 0.75F + 1.0F));`（传入 1334，内部计算为 2048）。

### Q6：专属业务线程池参数到底怎么配？为什么核心和最大设为 8？（硬件物理瓶颈推导）

* 💡 **回答要点**：
  * **参数**：`corePoolSize = 8`, `maximumPoolSize = 8`, `ArrayBlockingQueue(500)`, `CallerRunsPolicy`；
  * **为什么不是几十？**：
    1. **下游边缘设备硬件限制**：海康摄像头与边缘流媒体网关芯片硬件解码并发上限就是 8~16 路 RTSP 码流，开多了端口带宽塞满、摄像头 CPU 打满花屏断流；
    2. **内存防线**：每张高清抓拍图片解码为 RGB 像素矩阵占用 4~8MB，8 并发控制在 60MB 内存；若开 64 并发直接占用 500MB+ 内存引发频繁 GC；
    3. **CallerRunsPolicy**：队列满时由调度主线程自己执行，形成**天然的反压限流（Backpressure）**，强行减缓生产速度。

### Q7：丢给线程池的任务执行过长或卡死了，系统如何发现和自愈？

1. **源头硬超时**：所有底层网络 Socket 强制配置 `connectTimeout` 与 `readTimeout`（如 5 秒），杜绝无限阻塞；
2. **执行层超时与中断**：`Future.get(10, TimeUnit.SECONDS)` 捕获 `TimeoutException`，超时调用 `future.cancel(true)` 发送 `Thread.interrupt()`，任务内部循环主动检测 `isInterrupted()` 优雅提前退出；
3. **监控埋点与排障**：Micrometer 监控活跃线程数与任务最大持续时间，异常告警后用 `jstack -l <pid>` 顺着线程名字查看线程堆栈。

### Q8：MySQL 千万级大表 B+ 树高度是多少？为什么只有 3 层？慢查询如何排查？

1. **树高为什么只有 3 层？（千万级大表硬核推导）**：
   * InnoDB 页大小 16KB，非叶子节点存 `主键(8B) + 指针(6B) = 14B`；
   * 一个页能存 $16\text{KB} / 14\text{B} \approx \mathbf{1170} \text{ 个指针}$；
   * 根节点 1170 指针 $\to$ 第二层 $1170 \times 1170 \approx 136$ 万指针 $\to$ 第三层每个叶子页存 16 条数据，总容量 $= 1170 \times 1170 \times 16 \approx \mathbf{2190} \text{ 万条}$！所以两千多万数据树高仅为 3，只需 1~2 次物理磁盘 I/O。
2. **慢查询排查四步法**：
   * 开启慢查询日志 `log_min_duration_statement = 200`（记录超 200ms 的 SQL）；
   * 通过 `pg_stat_statements` 或 MySQL `slow_query_log` 抓出 Top 10 耗时 SQL；
   * 拿慢 SQL 执行 `EXPLAIN (ANALYZE, BUFFERS)` 分析执行计划，看是否出现 `Seq Scan` 全表扫描；
   * 优化联合索引（遵守最左前缀原则），并用 `CREATE INDEX CONCURRENTLY` 避免建索引时锁表。

### Q9：如何保证 Redis 缓存与 MySQL 数据库的双写最终一致性？（Cache-Aside + Canal）

* ❌ **错误做法**：先写数据库再写缓存（并发写导致脏数据）；先删缓存再写数据库（读写并发导致旧数据回填）。
* 💡 **大厂标准解法：Cache-Aside + Canal 监听 Binlog 异步补偿**：
  1. **写流程**：先更新 MySQL 数据库，事务提交成功后，**立即删除（Delete）Redis 缓存**；
  2. **读流程**：先查 Redis，命中直接返回；未命中查 MySQL，查到后写入 Redis 并返回；
  3. **极端异常双保险（Canal 异步对账）**：
     * 如果第 1 步删缓存由于网络抖动失败，部署 **Canal 伪装成 MySQL 从库监听 Binlog 日志**；
     * 解析到变更事件后，发送到 MQ 并由消费者**重试删除对应的 Redis Key**，彻底保障两端数据的最终一致性！

### Q10：Lua 脚本已经保证了原子性，为什么还要 Redisson 分布式锁与看门狗？

* **本质区别**：
  * **Lua 脚本原子性**：只保证脚本内部几条 Redis 命令连续执行不被打断（耗时仅几毫秒）；
  * **分布式锁**：保护的是跨网络、跨进程的**一整段耗时业务代码临界区（可能耗时几百毫秒甚至几秒）**！
* **原生锁三大缺陷**：业务没跑完锁提前超时失效、不可重入、只能自旋死等；
* **Redisson 看门狗机制（Watchdog）**：
  * 默认锁过期时间为 30 秒；
  * 只要持有锁的线程未执行完毕，后台 Netty 时间轮定时器**每隔 10 秒（`leaseTime / 3`）自动发送 Lua 脚本重置过期时间为 30 秒**，彻底杜绝业务未完锁提前超时的并发灾难；节点崩溃后看门狗随之死亡，30 秒后自然释放防止死锁。

### 代码 1：斐波那契数列生成 + 二分查找标准无 Bug 模板

```java
public class Solution {
    // 函数一：生成长度严格小于 20 的斐波那契数列 (1, 2, 3, 5, 8...)
    public static int[] generateFibonacci(int n) {
        if (n <= 0 || n >= 20) throw new IllegalArgumentException("0 < n < 20");
        int[] fib = new int[n];
        fib[0] = 1;
        if (n > 1) fib[1] = 2;
        for (int i = 2; i < n; i++) {
            fib[i] = fib[i - 1] + fib[i - 2];
        }
        return fib;
    }

    // 函数二：标准无 Bug 二分查找
    public static int binarySearch(int[] arr, int target) {
        if (arr == null || arr.length == 0) return -1;
        int left = 0, right = arr.length - 1; // 明确 [left, right]
        while (left <= right) {               // 必须是 <=
            int mid = left + ((right - left) >> 1); // 防溢出
            if (arr[mid] == target) return mid;
            else if (arr[mid] < target) left = mid + 1;
            else right = mid - 1;
        }
        return -1; // 遵循 JDK 规范，未找到返回 -1
    }
}
```

### 代码 2：DCL 双重检查锁定单例模式（volatile 防指令重排）

```java
public class Singleton {
    // 核心点 1：必须加 volatile！禁止 JVM 底层指令重排序 (分配内存 -> 初始化对象 -> 建立引用)
    private static volatile Singleton instance;

    // 核心点 2：私有化构造方法，防止外部反射/new 实例化
    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查：避免无谓加锁开销
            synchronized (Singleton.class) {
                if (instance == null) {          // 第二次检查：防止并发重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

### 代码 3：0-1 背包问题一维滚动数组逆序遍历模板

```java
public class Knapsack01 {
    public static int knapsack(int V, int[] weight, int[] value) {
        int[] dp = new int[V + 1];
        for (int i = 0; i < weight.length; i++) {
            // 核心灵魂：必须逆序遍历背包容量！防止当前物品被重复装入！
            for (int j = V; j >= weight[i]; j--) {
                dp[j] = Math.max(dp[j], dp[j - weight[i]] + value[i]);
            }
        }
        return dp[V];
    }
}
```
