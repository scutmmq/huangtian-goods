# AI 购物助手待解决问题

本文基于 2026-06-30 对 `com.scutmmq.ai` 模块的代码逻辑阅读整理，不包含运行环境联调结论。

## 当前结论

购物助手已经具备一期可用能力：商品搜索、商品详情、订单查询、地址查询、店铺查询，以及下单、加购、注册店铺、修改资料等确认草稿。整体架构方向正确，尤其是只读工具和草稿工具分离，能避免模型绕过用户确认直接执行写操作。

但如果目标是满足用户完整日常购物需求，还需要先解决下面这些问题。

## P0：草稿无法稳定挂回助手消息

### 问题

`AiMessageVO` 会通过 `assistant_message_id` 查询草稿，但创建草稿时没有写入 `assistantMessageId`。

### 影响

前端从消息列表恢复历史对话时，可能拿不到对应的确认卡片。用户看到助手说“已生成草稿”，但消息对象里没有 draft 信息，确认入口可能丢失。

### 代码证据

- `AiAssistantService.toMessageVO(...)` 使用 `aiActionDraftService.findByAssistantMessageId(m.getId())` 回查草稿。
- `AiActionDraftService.create(...)` 创建 `AiActionDraft` 时没有设置 `assistantMessageId`。
- `AiAssistantService.AiRunRunnable.persistDraftIfPresent(...)` 调用 `aiActionDraftService.create(...)` 时也没有传入当前 `assistantMessageId`。
- `AiActionDraftMapper.selectByAssistantMessageId(...)` 已经按 `assistant_message_id` 查询，说明数据库和查询逻辑已经预留了这个关联。

### 建议修复

1. 给 `AiActionDraftService.create(...)` 增加 `Long assistantMessageId` 参数。
2. 在创建草稿时调用 `draft.setAssistantMessageId(assistantMessageId)`。
3. 在 `AiRunRunnable.persistDraftIfPresent(...)` 中传入当前 run 的 `assistantMessageId`。
4. 增加一个服务层测试，验证生成草稿后 `listMessagesAsVO(...)` 能返回对应 draft。

## P0：加入购物车草稿缺少业务前置校验

### 问题

`DraftAddCartItemTool` 只检查 `productId` 和 `quantity` 是否存在，没有校验数量是否合法、商品是否存在、是否下架、库存是否足够，也没有同步“不能购买自己店铺商品”的规则。

### 影响

用户可能生成一个本来就无法执行的加购草稿，直到点击确认后才失败。体验上会显得 AI 助手“不靠谱”，也会和下单草稿的严谨程度不一致。

### 代码证据

- `DraftCreateOrderTool` 已经提前校验登录用户、商品存在、商品上架、库存、地址归属、自家店铺限制。
- `DraftAddCartItemTool.execute(...)` 当前只复制参数并生成 payload。

### 建议修复

1. 将 `DraftAddCartItemTool` 的校验逻辑向 `DraftCreateOrderTool` 对齐。
2. 至少补齐这些校验：`quantity > 0`、商品存在、商品未下架、库存充足、非本人店铺商品。
3. 草稿 summary 中展示商品名、单价和数量，不只展示商品 ID。

## P1：日常电商客服工具还不完整

### 问题

当前工具覆盖了“买之前”和“生成购买动作”，但对“买之后”的日常场景覆盖不足。

### 缺口

- 查询物流或发货进度。
- 取消订单。
- 申请退货退款。
- 查询退货审核状态。
- 查询支付状态或解释待支付、已支付、超时取消等状态。
- 查询购物车内容。
- 管理收货地址，例如新增、修改、设置默认地址。
- 查询优惠券、活动、满减或促销信息。

### 影响

用户一旦从“我要买什么”进入“我的订单怎么了”，助手就只能回答一部分问题，无法完成完整购物闭环。

### 建议修复

优先补三个高频工具：

1. `get_my_cart`：查询购物车内容。
2. `get_order_detail`：查询单个订单详情，包含商品、付款、发货、售后状态。
3. `draft_apply_return` 或 `draft_cancel_order`：仍然走草稿确认，避免模型直接执行售后动作。

## P1：推荐能力偏关键词搜索

### 问题

`search_products` 目前主要依赖后端 SQL `LIKE` 搜索，并加入了拆字兜底。这能解决一部分中文模糊匹配问题，但还不是完整推荐系统。

### 影响

用户表达“适合送朋友的礼物”“预算 100 左右的宿舍好物”“想买运动用的轻便鞋”这类意图时，模型只能把自然语言压成关键词，推荐质量不稳定。

### 建议修复

1. 增加类目、价格、评分、销量、库存等排序策略。
2. 引入同义词或标签映射，例如“衣服”关联“毛衣、外套、连衣裙”。
3. 如果后续数据量变大，可以考虑商品向量召回或标签召回，不必一开始就上复杂推荐系统。

## P1：历史工具结果回放方式比较粗糙

### 问题

`loadHistoryExcluding(...)` 会把历史 tool 消息包装成 user 消息，并提示模型“上一轮工具调用结果，可直接复用”。这个办法实用，但会让模型上下文角色语义变得不够准确。

### 影响

随着多轮对话变长，模型可能混淆真实用户输入和系统回放数据，尤其是历史工具结果较多时。

### 建议修复

1. 对历史工具结果做更结构化摘要，而不是原样拼接到 user 消息。
2. 只回放最近一次和当前问题相关的工具结果。
3. 给工具结果增加类型标识，例如商品搜索结果、地址列表、订单列表，方便模型复用。

## P2：写操作草稿的字段校验可以更严格

### 问题

修改用户资料、注册店铺、修改店铺资料等草稿会过滤系统字段，但对字段格式校验偏少。

### 影响

用户可能生成明显不合法的数据，例如错误手机号、错误邮箱、错误生日格式、非法性别枚举。最终可能由业务 Service 拦截，但 AI 草稿阶段的反馈不够友好。

### 建议修复

1. 在 draft 工具层提前校验常见格式。
2. 对枚举字段明确允许值，非法值直接返回工具错误，让模型追问用户。
3. summary 中用中文字段名展示变更内容，避免用户看到内部字段名。

## P2：运行可观测性还可以增强

### 问题

当前日志比较完整，但还缺少面向产品体验的统计指标。

### 建议补充指标

- 每次会话平均工具调用次数。
- 草稿生成成功率。
- 草稿确认成功率。
- 工具执行失败率。
- AI Provider 超时率。
- 用户取消草稿比例。

这些指标可以帮助判断助手是否真的满足日常需求，而不是只看功能是否接入。

## 推荐修复顺序

1. 先修草稿 `assistantMessageId` 关联问题。
2. 再补齐 `DraftAddCartItemTool` 的前置校验。
3. 增加购物车查询、订单详情、取消订单或售后草稿工具。
4. 优化搜索推荐能力。
5. 补字段格式校验和体验指标。

修完前两项后，可以认为 AI 购物助手达到“基础日常购物可用”。补完第三项后，才更接近“完整日常电商助手”。
