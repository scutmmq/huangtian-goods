## 一、 零基础快速建立 ES 认知总览

### 1.1 为什么有了 MySQL，还要有 Elasticsearch？
* **生活趣味比喻**：
  - **MySQL 就像一本字典正文**：按照页码顺序从第 1 页写到第 1000 页（**正排索引，按照 ID 找内容**）。如果你想找“第 50 页写了什么”，翻开第 50 页瞬间就找到了；但如果你想找“整本字典里哪几页出现过‘人工智能’四个字？”，你必须**把整整 1000 页逐字逐句通读一遍（全表扫描 `WHERE content LIKE '%人工智能%'`）**，在千万级大表下，磁盘 I/O 瞬间打爆，查询卡死几秒甚至几十秒！
  - **Elasticsearch 就像字典末尾的【词语检索表】**：它在书的末尾提前整理好了一张清单（**倒排索引 Inverted Index**）：
    - 词语“人工智能” $\rightarrow$ 出现在第 5 页、第 88 页、第 990 页；
    - 词语“后端开发” $\rightarrow$ 出现在第 12 页、第 56 页、第 990 页。
    你想要找包含某个词的句子，只要看一眼词汇清单，**纳秒级就能直接拿到目标页码（文档 ID）**，再精准去翻书，速度快成千上万倍！

### 1.2 核心概念与 MySQL 架构横向对照表

| Elasticsearch 概念 | MySQL 对应概念 | 核心功能与理解 |
| :--- | :--- | :--- |
| **Index（索引）** | **Table（数据表）** | 数据的逻辑容器（ES 7.x+ 彻底废除 Type，一个 Index 就是一张物理表）。 |
| **Document（文档）** | **Row（单行数据记录）** | 真正存储的一条数据，在 ES 中以 **JSON 格式** 序列化呈现。 |
| **Field（字段）** | **Column（列 / 字段）** | 文档中的一个属性（如 `goods_name`、`price`、`create_time`）。 |
| **Mapping（映射定义）** | **Schema（表结构 DDL）** | 定义字段的数据类型（`keyword`, `text`, `integer`）、分词规则与索引选项。 |
| **Shard（分片）** | **分表分库的数据碎片** | 将一个大索引水平拆分成多个微型 Lucene 实例，实现分布式并发与水平扩展。 |
| **Primary / Replica** | **主库 / 从库（主从复制）** | Primary 负责写，Replica 负责读与高可用容灾，主分片故障时从分片秒级晋升。 |

## 二、 核心底层结构：倒排索引、FST 与 Posting List 压缩黑科技

```
                         倒排索引三大核心层级结构
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Term Index (词项索引)   : FST (有限状态转换机)，极度压缩常驻内存，前缀二分查找 │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Term Dictionary (词项字典): 磁盘上的排好序的词语全量库 (Term1, Term2...)   │
├────────────────────────────────────────────────────────────────────────┤
│ 3. Posting List (倒排列表) : 包含该词的 [文档ID列表 + 词频TF + 出现位置Offset]│
└────────────────────────────────────────────────────────────────────────┘
```

### 2.1 倒排索引的三大组成部分
1. **Posting List（倒排列表）**：
   - 记录某个词在哪些文档中出现过。不仅仅包含 `DocId` 数组，还记录了词频 **TF（Term Frequency，用于算分）** 以及在文本中的字符偏移量 **Offset（用于搜索高亮显示）**；
2. **Term Dictionary（词项字典）**：
   - 搜索引擎将所有文档中的词汇抽取出来，去重后按字典序排好的一本词典。如果一个索引有数亿个词项，词典高达几个 GB，**完全放进内存会爆内存，放在磁盘上二分查找又太慢（需要多次磁盘 I/O）**！
3. **Term Index（词项索引，内存加速引擎）**：
   - ES 的杀手锏！它不记录所有的词，而是抽取 Term Dictionary 中词语的**前缀树索引**；
   - 底层采用 **FST（Finite State Transducer，有限状态转换机）**。FST 拥有极高压缩比（能将词典体积压缩到原先的 $1/10$ 以下），**可以全部常驻 JVM 内存**！
   - **查询链路**：客户端搜索词语 $\rightarrow$ 内存中通过 FST 毫秒级定位到 Term Dictionary 在磁盘上的 Block 块偏移量 $\rightarrow$ 仅进行 1 次磁盘 I/O 读出对应词项 $\rightarrow$ 拿到 Posting List，速度飞快！

---

### 2.2 Posting List 压缩黑科技：FOR 编码与 Roaring Bitmap
* **面试官深挖**：“如果一个热门词（如‘手机’）在 1000 万个文档里都出现过，这个 Posting List 的数组里就有 1000 万个 32 位整型 ID，占用了 40MB 内存。ES 是如何压缩倒排列表的？”

#### 1. FOR (Frame of Reference) 增量压缩编码（针对稠密数据）
* **原理**：不直接存原始 ID，而是存**前后两个 ID 的差值（Delta）**，再按块用最小的 bit 位存储：
  ```
  原始文档 ID 列表 : [10001, 10003, 10004, 10008, 10012]
  计算差值 (Delta): [10001,     2,     1,     4,     4]  (差值极小！)
  ```
* 差值最大的数只有 4，用 **3 个 bit（最大表示 7）** 就能存下！原本每个 ID 需要 32 bit（4 字节），压缩后每个 ID 只要 3 bit，**体积压缩了 10 倍以上**！

#### 2. Roaring Bitmap 位图压缩（针对稀疏数据）
* 如果文档 ID 极度分散（如 `[3, 80000, 2000000]`），计算 Delta 依然很大；
* 此时 ES 采用 **Roaring Bitmap**：
  - 将 32 位整型 ID 拆为两部分：高 16 位和低 16 位；
  - 高 16 位决定放入哪个桶（Bucket / Container）；
  - 低 16 位根据元素密集程度自适应选择用 **Array Container（稀疏数组）** 还是 **Bitmap Container（密集位图）** 存储，在内存占用与位运算交并集速度上达到理论极限！

### 2.3 文本打分算法演进：从 TF-IDF 到 BM25
* **TF-IDF 原理**：
  - **TF（词频）**：词在当前文档出现次数越多，得分越高；
  - **IDF（逆向文档频率）**：词在全网所有文档中出现越普遍（如“的”、“是”），权重越低；越罕见的词（如“量子纠缠”），权重越高；
* **BM25（Best Matching 25，现代 ES 默认算法）的超越之处**：
  - **解决了 TF 的饱和度非线性衰减问题**：在传统 TF-IDF 中，如果一个词出现了 100 次，其得分是出现 1 次的 100 倍（容易被刷关键词的外挂作弊打满分）；
  - BM25 引入了**饱和上限参数 $k_1$**：当词频达到一定次数后，得分增长会趋于平缓，不再无限飙升；
  - 引入了**文档长度惩罚参数 $b$**：一篇短推文如果出现了该词，其权重远高于一篇包含该词的长篇万字论文，排查更加公正精准！

## 三、 数据写入全链路：内存缓冲、近实时搜索与 Translog 刷盘机制

> 💡 **大厂技术面灵魂大题**：“请详细描述向 Elasticsearch 写入一条文档时，从发起请求到可以被搜索、再到真正持久化落盘，底层经历了哪些步骤？为什么 ES 被称为‘近实时’（Near Real-Time）而不是强实时？”

```
                         ES 核心写入与落盘全景架构
  ┌─────────────┐
  │ 客户端写入   │ (POST /index/_doc/1)
  └──────┬──────┘
         │
         ▼
  ┌─────────────────────────────────┐
  │ 协调节点 (Coordinating Node)    │ ──► 计算 hash(id) % 分片数，路由到 Primary 分片
  └──────┬──────────────────────────┘
         │
         ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ 核心分片节点 (Primary Shard)                                           │
  │                                                                        │
  │ 1. 并发双写:                                                            │
  │    ├─────────────────────────────┐                                     │
  │    ▼                             ▼                                     │
  │  【Index Buffer 内存缓冲区】   【Translog 预写事务日志 (写到磁盘缓冲)】    │
  │  (此时数据还不能被搜索到!)    (保障 Crash-Safe 崩溃不丢数据)             │
  │    │                             │                                     │
  │    │ 2. Refresh (默认每 1 秒)    │                                     │
  │    ▼                             │                                     │
  │  【OS Filesystem Cache】         │                                     │
  │  • 生成一个全新的不可变 Segment  │                                     │
  │  • 此时【变成可被搜索到 🎉】     │                                     │
  │  • 这就是【近实时 NRT】的秘密!  │                                     │
  │    │                             │                                     │
  │    │ 3. Flush (每 30 分钟 / Translog 达到 512MB)                       │
  │    ▼                             ▼                                     │
  │  【物理磁盘 Hard Disk】 ◄────────┴─────────────────────────────────────┤
  │  • 调用 Linux 系统的 fsync() 将 OS Cache 中的 Segment 强制物理刷盘     │
  │  • 清空并截断已提交的旧 Translog 文件                                  │
  └────────────────────────────────────────────────────────────────────────┘
```

### 3.1 详细三步流水线解析

#### 第一步：双写 Index Buffer 与 Translog
* 协调节点通过哈希路由定位到目标主分片（Primary Shard）；
* 主分片将文档同时写入两处：
  1. 写入内存中的 **`Index Buffer`**（索引缓冲区）；
  2. 写入操作系统的 **`Translog`**（事务日志缓冲区），并向客户端返回成功。
* **注意**：此时数据仅仅停留在内存 Buffer 里，**客户端立即发起检索是绝对查不到该条数据的！**

#### 第二步：`Refresh` 机制 —— 近实时搜索（Near Real-Time）的底层真相
* **默认频率**：每隔 **1 秒钟**（由参数 `index.refresh_interval: "1s"` 控制），或者 Index Buffer 内存被写满时；
* **执行动作**：
  1. 将 `Index Buffer` 中的文档解析生成一个全新的 **Lucene Segment（段文件）**；
  2. 将 Segment 写入**操作系统的文件系统缓存（OS Filesystem Cache）**，清空 Index Buffer；
  3. 打开该 Segment 供外部搜索读取！
* **为什么叫“近实时”（NRT）？**
  - 因为 Segment 已经进入了操作系统的内存 Cache，此时执行 Search 查询能够立刻命中；
  - **耗时仅在内存中发生，没有触发昂贵的物理磁盘 `fsync`**！
  - 从写入到被搜索到，通常有 **1 秒钟的时延**，因此被称为“近实时”！

#### 第三步：`Flush` 机制 —— 真正的数据落盘（Commit Point）
* **触发时机**：每隔 **30 分钟**，或者 `Translog` 日志大小达到 **512MB**；
* **执行动作**：
  1. 触发一次 `Refresh`，清空残留的 Index Buffer；
  2. 调用操作系统的 **`fsync()` 系统调用**，将 OS Cache 中积攒的所有 Segment 文件**真正强行刷入物理磁盘**；
  3. 在磁盘上写入一个 Commit Point（提交点）；
  4. 删除旧的 Translog 日志，开启新的 Translog。

### 3.2 深度追问：Segment（段）的“只读不可变性”与段合并（Merge）
* **为什么 Lucene 的 Segment 必须设计为不可变的（Read-only）？**
  1. **零锁并发**：只读文件天然没有并发读写冲突，查询完全不需要加锁，吞吐量极高；
  2. **充分利用操作系统的文件缓存**：只要 OS Cache 载入了该段，只要内存够就永远有效，绝不脏读；
  3. **倒排索引连续压缩**：不可变文件才能使用 FST 和 FOR 进行极限物理压缩。
* **既然 Segment 不可变，那删除（DELETE）和更新（UPDATE）怎么做？**
  - **删除操作**：ES 不会真的去物理磁盘抹除数据，而是生成一个 **`.del` 标记文件**，将要删除的文档 ID 记录进去。搜索时正常查出来，但在组装结果前将标记删除的文档过滤剔除；
  - **更新操作**：本质是**“先逻辑删除旧文档，再新增一条新文档”**（版本号自增）。
* **段合并（Segment Merge）**：
  - 随着每秒一次的 Refresh，磁盘上会产生海量微小碎片 Segment；
  - ES 后台线程会自动触发 **Segment Merge**：将多个小 Segment 读取出来合并成一个大的 Segment，**在合并过程中真正物理丢弃那些被标记为 `.del` 的垃圾文档**，随后将老旧小 Segment 物理删除，释放磁盘碎片。

## 四、 数据查询全链路：Query Then Fetch 两阶段与分布式聚合底层原理

> 💡 **大厂技术面灵魂大题**：“ES 集群在执行分页搜索时，协调节点是怎么从成百上千个分片中汇总数据的？Query 阶段和 Fetch 阶段分别干了什么？”

```
                    分布式查询 Query Then Fetch 两阶段
┌──────────────────┐
│ Client 发起查询   │ (例如: 查询关键词 "iPhone", 从第 100 条开始取 10 条)
└────────┬─────────┘
         │
         ▼
┌─────────────────────────────────┐
│ 协调节点 (Coordinating Node)    │
└────────┬────────────────────────┘
         │
         │ 1. 【Query 阶段 (初筛与打分)】:
         │    • 广播发送 Search 请求至涉及的各个分片 (Primary 或 Replica 选其一)
         ├────────────────────────────────────────┬────────────────────────────────────────┐
         ▼                                        ▼                                        ▼

└────────┬─────────┘                     └────────┬─────────┘                     └────────┬─────────┘
         │                                        │                                        │
         └────────────────────────────────────────┼────────────────────────────────────────┘
                                                  │
                                                  ▼
                                 ┌─────────────────────────────────┐
                                 │ 协调节点本地内存多路堆排序归并   │
                                 │ • 汇总所有分片的 [ID+Score] 列表 │
                                 │ • 重新全局排序，锁定全局前 100~110 的文档 ID
                                 └────────────────┬────────────────┘
                                                  │
                                                  │ 2. 【Fetch 阶段 (精准拉取详情)】:
                                                  │    • 仅向拥有这最终 10 条有效数据的分片发起单点查询
                                                  ├──────────────────┬─────────────────────┐
                                                  ▼                  ▼                     ▼
                                           ┌──────────────┐   ┌──────────────┐      ┌──────────────┐
                                           │ Shard 1      │   │ Shard 2      │      │ Shard 3      │
                                           │ 拿 Doc #102  │   │ 拿 Doc #305  │      │ 拿 Doc #991  │
                                           │ 整行 _source │   │ 整行 _source │      │ 整行 _source │
                                           └──────┬───────┘   └──────┬───────┘      └──────┬───────┘
                                                  │                  │                     │
                                                  └──────────────────┼─────────────────────┘
                                                                     │
                                                                     ▼
                                                      组装完整结果，向 Client 返回 🎉
```

### 4.1 核心两阶段拆解
1. **第一阶段：Query 阶段（轻量元数据初筛）**
   - 协调节点收到客户端搜索请求后，将查询语句以轮询负载均衡（Round-Robin）的方式并行广播到各个分片（在主分片和副本分片中任选一个）；
   - 每个分片在本地利用 Lucene 倒排索引找出匹配的文档，使用 BM25 算法计算相关性评分；
   - **关键细节**：分片**绝不返回文档整行数据（`_source`）**，而是仅构建一个优先级队列（小顶堆），**只返回排在前面的 `(doc_id, score)` 轻量级元数据**给协调节点；
2. **第二阶段：Fetch 阶段（精准定向拉取整行数据）**
   - 协调节点将所有分片传回的 `(doc_id, score)` 汇总到自己的内存中，进行**全局多路归并排序**；
   - 锁定用户真正需要的分页区间（如第 100 到 110 条的这 10 个文档 ID）；
   - 协调节点**仅向包含这 10 个文档 ID 的具体分片发起点对点单行拉取请求**；
   - 目标分片从磁盘读取完整的 `_source` 文档体，回传给协调节点；
   - 协调节点将这 10 条完整文档拼装后返回给客户端。
* **为什么必须分两个阶段？**
  - 如果在 Query 阶段每个分片就一股脑把完整大文本 `_source` 全部传过来，几百个分片会把网络带宽瞬间占满，协调节点内存直接撑爆！**先查轻量 ID 排序，再按需回捞详情，极大降低了网络 I/O 与内存开销！**

## 五、 海量数据三大分页方案对比：`from + size` vs `scroll` vs `search_after`

> 💡 **与 MySQL 深分页深度联动**：深分页不仅是关系型数据库的痛点，也是分布式搜索引擎的大忌！面试官极爱对比三者区别。

| 分页机制 | 工作原理 | 核心优点 | 致命缺陷与风险 | 典型适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **1. `from + size`** | 协调节点向各分片请求 `from + size` 条数据，在内存中归并排序后截取后 `size` 条。 | 支持随机任意页码跳转，使用最简单。 | **深分页时引发协调节点 OOM 崩溃！** 默认受 `max_result_window = 10000` 保护截断，禁止超过 1 万条。 | Web 前台轻量浅分页（前 100 页以内）。 |
| **2. `scroll` (快照滚动)** | 第一次查询建立类似数据库快照的视图（保持上下文游标 Context），每次拿着 `scroll_id` 连续向后批量拉取。 | 性能恒定，不增加额外内存排序开销。 | **非实时（快照视图，后续数据修改无法感知）**；游标上下文长期持有会**白白消耗大量集群堆内存**！ | 海量数据全量离线导出、数据迁移批处理。 |
| **3. `search_after` 【大厂首选】** | **完全无状态的游标分页**！每次查询必须带上上一页最后一条记录的**排序值数组（Sort Values）**，底层直接利用倒排索引在各分片快速寻址跳过。 | **内存零消耗、性能极致恒定**！无页码上限限制，完美支持数亿级深度翻页。 | **无法支持随机跳页**（必须一页一页往后翻）；要求排序字段中**必须包含至少一个全局唯一字段（如 `_id`）打破平局**。 | **App 瀑布流、无限滚动下拉、分布式大表深分页首选！** |

### 5.1 生产级 `search_after` 落地核心 DSL 示例

```json
// 第一页查询 (按创建时间和主键倒序排序)
POST /orders/_search
{
  "size": 20,
  "query": { "term": { "status": 1 } },
  "sort": [
    { "create_time": "desc" },
    { "_id": "desc" }  // 必须加上全局唯一字段，防止同分平局导致数据跳跃！
  ]
}

// 响应结果最后一条记录包含排序特征:
// "sort": [ 1725699000000, "order_10099" ]

// 第二页查询: 直接把上一页最后的 sort 数组作为 search_after 传入！
POST /orders/_search
{
  "size": 20,
  "query": { "term": { "status": 1 } },
  "search_after": [ 1725699000000, "order_10099" ],
  "sort": [
    { "create_time": "desc" },
    { "_id": "desc" }
  ]
}
```

## 六、 索引设计与分词器：`text` vs `keyword` 的生死抉择与 IK 中文分词

### 6.1 `text` vs `keyword` 深度对比表（面试高频坑点）

```
                     text 与 keyword 底层存储差异
   输入内容: "华为 Mate60 Pro"
   ┌────────────────────────────────────────────────────────┐
   │ • text 类型   : 经分词器拆为 ["华为", "mate60", "pro"]  │
   │                每个词项独立写入倒排索引，用于全文模糊检索 │
   ├────────────────────────────────────────────────────────┤
   │ • keyword 类型: 不分词！将 "华为 Mate60 Pro" 作为一个整体 │
   │                完整原样存入，用于精确等值查找、聚合与排序 │
   └────────────────────────────────────────────────────────┘
```

| 维度 | `text` 字段类型 | `keyword` 字段类型 |
| :--- | :--- | :--- |
| **是否经过分词器** | ✅ **经过分词器拆词**（分析为一个个独立的 Term）。 | ❌ **不分词**，将整个字符串原封不动保存。 |
| **查询匹配方式** | 使用 **`match`** 全文模糊检索（查询词也会被分词匹配）。 | 使用 **`term`** 精确匹配（大小写敏感、完全相等）。 |
| **是否支持聚合与排序** | ❌ **默认严禁聚合与排序**（强行开启 `fielddata: true` 会撑爆内存）！ | ✅ **天然完美支持聚合（Aggregations）与排序（Sort）**（底层利用 Doc Values 列存）。 |
| **典型适用字段** | 商品标题、商品详情长文本、用户评价、新闻正文。 | 订单号、手机号、商品状态码、用户标签、身份证号。 |

### 6.2 中文分词利器：IK 分词器两大模式与热词动态更新

#### 1. `ik_smart` vs `ik_max_word`
* 待分词语句：**`中华人民共和国国歌`**
  - **`ik_smart`（最粗粒度切分，适合作为搜索条件使用）**：
    `["中华人民共和国", "国歌"]`（占用索引空间小，语义更精准）；
  - **`ik_max_word`（最细粒度穷尽拆分，适合用于文档入库建立索引）**：
    `["中华人民共和国", "中华人民", "中华", "华人", "人民共和国", "人民", "共和国", "共和", "国歌"]`（尽可能召回所有可能匹配的结果）。
* **工业界标准设计**：**索引时使用 `ik_max_word` 细粒度建索引；查询时使用 `ik_smart` 粗粒度匹配**，兼顾高召回率（Recall）与高精准度（Precision）！

#### 2. 动态热词扩展字典（Hot Words Dynamic Reloading）
* 当网络流行词或新产品出现（如“遥遥领先”、“黑神话悟空”），默认词库无法识别，会被拆成单个单字。
* **工业级解法**：在 `IKAnalyzer.cfg.xml` 中配置 **`location/remote_ext_dict`** 指向内部 Nginx 服务器上的字典接口。字典接口下发 `Last-Modified` 和 `ETag` 响应头，IK 分词器每隔 1 分钟发送 HEAD 请求探测变更，**秒级实现全集群热词热更新，无需重启 ES 集群！**

## 七、 集群架构、分片机制与 Master 选举防脑裂演进

### 7.1 核心节点角色四分法
1. **Master-eligible Node（候选主节点）**：有资格被选举为主节点的机器，负责维护集群元数据、索引创建与删除、分片迁移平衡；
2. **Data Node（数据节点）**：真正存储数据分片、执行 CRUD、搜索和聚合计算的“苦力”节点，消耗大量磁盘 I/O、内存和 CPU；
3. **Coordinating Node（协调节点）**：只负责接收客户端 HTTP 请求、计算路由分发并汇总归并两阶段结果，纯充当微服务网关角色；
4. **Ingest Node（预处理节点）**：负责在文档入库前执行类似 Logstash 的管道数据转换（如字符串修剪、IP 自动转地理坐标）。

---

### 7.2 脑裂（Split-Brain）现象与防范机制演进

#### 什么是脑裂？
* 假设 5 台机器的集群中，由于网络抖动（机房交换机故障），集群被断开隔离成了两个网络孤岛（左边 2 台，右边 3 台）。
* 如果两边各自都认为对方挂了，并且**两边各自选举出了一个不同的 Master 节点**，同一个集群变成了两个大脑，**数据产生严重写入分叉与覆盖破坏**，这就是毁灭性的“脑裂”！

#### 演进防护机制：
1. **ES 7.x 以前（老版本过半机制）**：
   - 必须在配置文件中人工计算并配置：
     $$\mathbf{discovery.zen.minimum\_master\_nodes = \left(\frac{N}{2}\right) + 1}$$
     （$N$ 为 Master 候选节点总数）。只有拿到了过半候选节点赞成票的节点才能当选 Master，另一侧无法凑齐过半直接停止服务，防止分裂；
2. **ES 7.x 及以上（现代选举算法）**：
   - 彻底废除了繁琐的 `minimum_master_nodes` 配置；
   - 引入了类似 **Raft 协议的仲裁多数派选举（Quorum-based Election）**；
   - 启动时通过 `cluster.initial_master_nodes` 指定初始法定节点，随后集群动态维护最新的仲裁法定配置，**从内核算法层彻底根治了脑裂隐患**！

### 8.1 业务背景与架构选型思考
* **痛点**：在《荒天商城》中，商品不仅包含基础信息，还挂载有分类、品牌、规格属性（SPU/SKU）、库存与实时销量。如果直接在 MySQL 中查询，涉及 4 张表的 `LEFT JOIN` 以及模糊匹配 `WHERE title LIKE '%...%'`，多条件组合筛选时索引完全失效，接口 RT 高达数秒；
* **破局**：采用**“MySQL 负责高频事务写入 + Elasticsearch 负责复杂多维搜索”**的读写分离异构宽表架构。

### 8.2 工程落地四大核心细节
1. **CDC 增量监听无业务侵入**：
   - 放弃业务代码中同时写 MySQL 和写 ES 的“双写”方案（容易因网络抖动导致分布式事务不一致）；
   - 采用阿里巴巴开源的 **Canal** 伪装成 MySQL 从库，监听 Binlog（ROW 格式），彻底与业务代码解耦；
2. **异构宽表扁平化重构（De-normalization）**：
   - ES 极度不擅长复杂的跨索引 Join 关联（如父子文档 Parent-Child 性能损耗极大）；
   - 同步服务在消费 MQ 时，将多张子表字段扁平化合并到同一个单层索引文档 `mall_product` 中，**空间换时间**；
3. **批量合并 Bulk API 提升吞吐**：
   - 消费者不在收到单条变更时就发 HTTP 请求给 ES，而是在本地内存窗口累积 **500 条或等待 1 秒**，使用 ES 的 **`_bulk` API** 批量提交，将写入 QPS 吞吐提升 8 倍以上；
4. **主从微秒级延迟补偿与最终一致性**：
   - 面对极端情况下 Binlog 消费的百毫秒级延迟，后台配置每日离线对账任务，比对 MySQL 与 ES 数据差额做静默校准补漏。

## 九、 Elasticsearch 核心 15 道大厂高频面试真题与标准满分回答

### Q1：什么是倒排索引？它相比传统 MySQL B+ 树索引有什么优势？
* **满分回答**：
  > “1. **倒排索引定义**：
  >    - 传统正排索引是**‘以文档为中心找词语’**（由文档 ID 定位其包含的各个文本内容）；
  >    - 倒排索引是**‘以词语为中心找文档’**：将所有文本分词为独立的 Term（词项），维护一张字典，记录每个 Term 出现过的所有文档 ID 列表（Posting List）。
  > 2. **相比 B+ 树的核心优势**：
  >    - **全文模糊匹配效率碾压**：MySQL 面对 `LIKE '%华为%'` 前导通配符时，B+ 树由于无法从最左前缀二分，会导致灾难性的全表扫描；而倒排索引只要拿‘华为’两个字在词项字典中利用 FST 内存结构做 $O(\log N)$ 前缀匹配，纳秒级即可直接拿到包含该词的千万级文档 ID，无需逐行扫描；
  >    - **天然支持海量多条件组合交并集**：倒排索引的 Posting List 底层采用 Roaring Bitmap 位图压缩，多个查询条件（如‘品牌=华为’ AND ‘价格在 5000~6000’）在底层直接执行 CPU 并行按位‘与’运算，极速完成复杂筛选。”

### Q2：详细讲讲 ES 写入数据的全过程？为什么说 ES 是近实时（NRT）而不是强实时？
* **满分回答**：
  > “1. **完整写入流水线**：
  >    - 协调节点根据 `hash(id) % shards` 路由定位到具体 Primary 分片；
  >    - 主分片并发执行双写：一边写入内存中的 **`Index Buffer`**，一边写入磁盘缓冲中的事务日志 **`Translog`**；
  >    - 主分片写入成功后，并行同步给各个副本分片（Replica），副本写入后返回客户端成功。
  > 2. **近实时（Near Real-Time）的核心机制**：
  >    - 数据刚写入 `Index Buffer` 时是**完全不可被检索的**；
  >    - ES 依靠 **`Refresh` 机制**（默认每秒一次）：将 Index Buffer 中的数据解析并构建成一个轻量的新 Segment，写入**操作系统的文件系统缓存（OS Filesystem Cache）**；
  >    - 一旦进入 OS Cache，Segment 即可直接被外部搜索命中，全程没有触发昂贵的物理磁盘 `fsync` 刷盘！
  >    - 正因为写入后需要等待约 1 秒的 Refresh 周期才能被搜索到，因此 ES 是‘近实时’搜索引擎。”

### Q3：ES 是如何保证写入数据不丢失的（Crash-Safe 崩溃恢复）？
* **满分回答**：
  > “1. **依靠 Translog 预写事务日志（WAL 机制）**：
  >    - 虽然 Refresh 阶段生成 Segment 只是写到了 OS Cache 内存中（若此时物理机断电，OS Cache 内存会全部丢失）；
  >    - 但在写入 Index Buffer 的同时，ES 已经同步把操作记入了磁盘上的 `Translog` 文件（默认每次请求或每 5 秒执行一次物理刷盘）；
  > 2. **崩溃恢复流程**：
  >    - 当节点发生突发宕机重启时，ES 会自动读取物理磁盘上最后一次成功的 **Commit Point（提交点）**；
  >    - 并自动扫描该提交点之后记录在 `Translog` 中的所有操作日志，在内存中**重放（Replay）**这些写入动作重新构建 Segment，确保内存中尚未真正物理刷盘的数据 100% 完整复原！”

### Q4：ES 查询的两阶段（Query Then Fetch）分别干了什么？为什么不直接一次查出所有字段？
* **满分回答**：
  > “1. **Query 阶段（打分与初筛）**：
  >    - 协调节点将查询广播给涉及的分片；各分片在本地计算 BM25 得分，**仅将排在前面的轻量级 `(doc_id, score)` 优先级队列返回给协调节点**，不包含文档内容实体；
  > 2. **Fetch 阶段（精准拉取整行详情）**：
  >    - 协调节点在内存中将各分片返回的 ID 做全局多路堆排序归并，锁定用户真正需要的那一屏数据（如前 20 条 ID）；随后仅向持有这 20 条数据的特定分片发起单点精确拉取完整 `_source` 文档体，组装返回。
  > 3. **为什么不一次性返回全部数据**：
  >    - 如果集群有 100 个分片，用户查前 10 条。若每个分片都把 10 条带有大文本/图片的完整文档传给协调节点，网络将传输 1000 条大对象，网络带宽瞬间被塞死，协调节点 JVM 堆内存也会发生严重的 GC 抖动甚至 OOM；**‘先查轻量元数据排序，再按需回捞详情’**是分布式搜索引擎控制网络与内存开销的核心精髓。”

### Q5：深分页中，`from + size` 为什么会引发 OOM？生产环境大表深分页首选什么方案？
* **满分回答**：
  > “1. **`from + size` 引发 OOM 的原因**：
  >    - 执行 `from 100000, size 20` 时，如果有 10 个分片，**每个分片各自都必须在本地排好前 100020 条数据传给协调节点**；
  >    - 协调节点需要在内存中汇总并排序 $10 \times 100020 \approx 100$ 万条数据，随着 offset 翻倍，协调节点内存瞬间被打满引发 OOM，因此 ES 原生设置了 `max_result_window = 10000` 强行阻断大偏移量；
  > 2. **生产环境首选：`search_after`**：
  >    - **彻底无状态，性能极度恒定**：客户端每次翻页携带上一页最后一条数据的排序特征值数组（Sort Values）；
  >    - 各分片底层直接定位到该游标之后的数据返回，协调节点内存开销恒定为 `size` 条，彻底消除内存汇总压力，是大厂 App 瀑布流和大数据深分页的标准选型。”

### Q6：`text` 和 `keyword` 有什么本质区别？我们在建索引时应该怎么选？
* **满分回答**：
  > “1. **本质区别**：
  >    - **`text`**：字段会经过分词器（Analyzer）拆词，被切分成多个独立的词项进入倒排索引。主要用于全文模糊检索（`match`），**默认严禁用于聚合（Aggregation）和排序（Sort）**；
  >    - **`keyword`**：字段**绝不分词**，整个字符串被当作一个不可分割的完整原子整体写入倒排索引，并且底层会自动维护 **Doc Values（列式存储）**，天然专门用于**精确等值匹配（`term`）、聚合分析和范围排序**。
  > 2. **生产选型准则**：
  >    - 像商品标题、新闻正文、用户评价等需要分词模糊匹配的选 `text`；
  >    - 像订单号、状态码、手机号、枚举分类、标签等需要精确匹配或统计聚合的坚决选 `keyword`；
  >    - 若某个字段既要全文检索又要精确聚合，可配置为包含 `fields: { raw: { type: "keyword" } }` 的多字段（Multi-fields）模式。”

### Q7：IK 分词器的 `ik_smart` 和 `ik_max_word` 有什么区别？生产中如何做动态热词扩展？
* **满分回答**：
  > “1. **两大模式区别**：
  >    - `ik_smart` 是**最粗粒度切分**，追求词语语义的紧凑性与精确度，拆出的词少，占用索引小；
  >    - `ik_max_word` 是**最细粒度穷尽拆分**，尽可能把所有包含的词语组合全部切分出来，追求高召回率。
  >    - **生产最佳组合**：**建索引时用 `ik_max_word`（保证入库信息最全），前端检索时用 `ik_smart`（保证搜索词不碎）**，完美兼顾精准度与召回率。
  > 2. **热词动态扩展方案**：
  >    - 生产严禁为了加一个新词而重启集群。通过在 `IKAnalyzer.cfg.xml` 中配置 **`remote_ext_dict`** 指向内部配置中心或 Nginx HTTP 接口；
  >    - 服务端下发带有 `Last-Modified` 和 `ETag` 的词库文件，IK 分词器内置线程每分钟自动轮询增量拉取，实现秒级无感知在线热词热更新。”

### Q8：ES 集群的 Master 节点是干什么的？如何防止发生“脑裂”（Split-Brain）？
* **满分回答**：
  > “1. **Master 节点核心职责**：
  >    - 负责管理集群层面的全局元数据：创建/删除索引、跟踪集群所有节点的状态、决定分片在各个数据节点上的分配与故障迁移。它**不参与具体文档的搜索与增删改查计算**，避免负载过重；
  > 2. **防脑裂机制**：
  >    - **老版本（7.x 以前）**：严格遵循过半原则，设置 `discovery.zen.minimum_master_nodes = (候选节点数 / 2) + 1`，网络分区时未达半数的孤岛分区无法选出 Master，杜绝双主；
  >    - **新版本（7.x+）**：引入基于 Raft 协议的法定多数派仲裁算法，在集群启动时指定初始候选集，由算法内核自适应保障原子选举，彻底消灭脑裂配置漏洞。”

### Q9：Segment 为什么设计成不可变的？删除和更新操作底层到底是怎么执行的？
* **满分回答**：
  > “1. **不可变性的优势**：
  >    - 无需加排他锁，天然线程安全，并发读性能达到硬件极限；
  >    - 能够被操作系统内核的 OS Cache 永久强缓存，无缓存脏读失效开销；
  >    - 支持对 Posting List 进行极限字典压缩。
  > 2. **删除与更新的底层实现**：
  >    - **删除（DELETE）**：不直接修改磁盘 Segment，而是在对应段生成一个 **`.del` 位图文件**将该文档标记为已删除。搜索时正常读出，最终返回前由过滤链丢弃；
  >    - **更新（UPDATE）**：先将旧文档标记写入 `.del` 逻辑删除，同时在新的活动 Segment 中插入一条完整的新版本文档；
  >    - **物理清理时机**：后台在执行 **Segment Merge（段合并）** 时，会将参与合并的所有段中被标记在 `.del` 上的垃圾文档真正物理剔除，释放磁盘空间。”

### Q10：什么是 Doc Values？为什么 ES 聚合排序不用倒排索引而用 Doc Values？
* **满分回答**：
  > “1. **倒排索引在聚合排序上的软肋**：
  >    - 倒排索引的结构是 `Term -> DocList`（行转列）。如果要对 100 万条搜索结果按‘价格’排序，倒排索引必须在内存中把这 100 万条文档全部反向遍历找价格字段，时间复杂度极高且产生巨大的内存抖动；
  > 2. **Doc Values（正向列式存储）的破局**：
  >    - Doc Values 本质上是与倒排索引伴生的**列式存储（Column-oriented Storage）**：结构是 `DocId -> FieldValue`；
  >    - 数据按列连续存放在磁盘与 OS Cache 中，排序和聚合只需顺着连续内存地址极速流式读取，**支持极快的随机访问与向量化执行**，性能相比传统行存提升数个数量级！”

### Q11：海量数据写入 ES 时，有哪些经典的性能调优手段？
* **满分回答**：
  > “在大数据量批量灌库时，可采用大厂经典的**‘四步写入吞吐极速调优法’**：
  > 1. **批量写入（Bulk API）**：使用 Bulk 批量提交，单批次大小控制在 5MB ~ 15MB 之间，避免零散 HTTP 开销；
  > 2. **拉长或临时关闭 Refresh 间隔**：将 `index.refresh_interval` 临时调为 `-1`（或 30s），写入期间不生成无用的小 Segment，省下大量 CPU；全部写完后再恢复 1s 并手动 refresh；
  > 3. **大批量初始化时将副本数设为 0**：`index.number_of_replicas: 0`，避免主副本双向网络传输与同步索引开销，数据全部灌完后再将副本数调整回 1 异步同步；
  > 4. **调整 Translog 刷盘阈值**：将 `index.translog.durability` 改为 `async`（异步刷盘），配合更大的 `translog.flush_threshold_size`（如 1GB），大幅削减磁盘 I/O 压力。”

### Q12：如果线上某个 ES 查询很慢，你一般通过什么手段排查和定位瓶颈？
* **满分回答**：
  > “1. **利用 Profile API 分析底层执行耗时**：
  >    - 在查询 DSL 中加入 `"profile": true`，ES 会递归打印出 Lucene 底层每一个查询子句（如 `BooleanQuery`, `TermQuery`）在每个分片上的真实执行耗时（以纳秒为单位），瞬间定位出是哪个字段过滤或分词查询成为了慢瓶颈；
  > 2. **排查慢查询日志（Slow Log）**：
  >    - 在索引中配置 `index.search.slowlog.threshold.query.warn: 2s`，自动捕获执行超过 2 秒的长耗时 DSL 语句；
  > 3. **检查集群资源健康状态**：
  >    - 查看是否有由于 JVM 堆内存设置不合理（如超过 32GB 导致指针压缩失效）引发的频繁 GC 停顿；
  >    - 查看操作系统的 **Filesystem Cache 是否被其他进程抢占**（ES 极度依赖操作系统的文件缓存，官方推荐留 50% 物理内存给 OS Cache）。”

### Q13：为什么官方强烈建议给 ES 分配的 JVM 堆内存不能超过 32GB？
* **满分回答**：
  > “1. **指针压缩（Compressed OOPs）失效**：
  >    - 64 位操作系统下指针占用 8 字节，JVM 通过压缩普通对象指针技术将堆内存指针压缩到 4 字节（利用 8 字节对齐右移 3 位），最大寻址空间为 $2^{32} \times 8\text{ bytes} = \mathbf{32GB}$；
  >    - 一旦 JVM 堆内存超过 32GB（通常在 31GB~32GB 之间），指针压缩机制会被强制关闭，所有对象指针瞬间膨胀为 8 字节，**内存占用凭空增加 40% 以上，GC 垃圾回收暂停时间急剧延长，反而导致系统可用内存严重缩水**！
  > 2. **必须给 OS Cache 预留充足内存**：
  >    - Lucene 底层的 Segment 文件、FST 词典索引以及 Doc Values 列存极度依赖操作系统内核的文件系统缓存（OS Cache）；
  >    - 标准最佳实践是：**单机如果是 64GB 物理内存，分配 31GB 给 ES 堆内存，剩下的 33GB 全部留给操作系统做文件缓存**，才能发挥 ES 的巅峰性能！”

### Q14：MySQL 与 Elasticsearch 数据同步有哪些常见方案？你们项目中为什么选 Canal？
* **满分回答**：
  > “1. **三大主流同步方案对比**：
  >    - **方案一：业务代码双写（同步写 MySQL 后写 ES）**：业务代码强侵入，网络抖动容易出现‘MySQL 成功但 ES 失败’的脏数据，分布式长事务导致性能低下；
  >    - **方案二：定时任务扫表（Logstash / XXL-Job 轮询 update_time）**：实时性差（分钟级延迟），且高频扫千万级大表会导致 MySQL 慢查询 CPU 打满，无法捕获物理硬删除；
  >    - **方案三：基于 MySQL Binlog 增量监听（Canal / Debezium + MQ 【大厂标准首选】）**：完全零业务侵入，性能极高，毫秒级异步准实时同步，天然支持捕获 UPDATE/DELETE 事件。
  > 2. **本项目选型落地**：
  >    - 在《荒天商城》中，我们选用 **Canal 伪装成 MySQL Slave 监听 Binlog**，将增量变更投递至消息队列削峰缓冲，由数据同步服务扁平化组装多表字段批量写入 ES，兼顾了事务库高可用与搜索端的极致性能。”

### Q15：ES 的分片数（Primary Shards）可以在创建索引后随意修改吗？分片数设置多少合适？
* **满分回答**：
  > “1. **主分片数严禁随意直接修改**：
  >    - 因为 ES 文档的路由公式是：`shard = hash(routing) % number_of_primary_shards`；
  >    - 如果直接更改了主分片数，后续相同的文档 ID 计算出来的分片槽位会完全错乱，导致历史数据彻底无法被路由检索！若要调整主分片，必须使用 **Reindex API（索引重建）**；（注：副本分片数 `number_of_replicas` 允许随时动态热调）；
  > 2. **分片数量评估黄金经验法则**：
  >    - **单个分片的大小控制在 20GB ~ 50GB 之间**：分片过小会导致产生大量碎片元数据消耗内存，分片过大会导致集群重平衡（Rebalance）分片迁移时网络耗时巨大；
  >    - **单节点每 GB 堆内存维护的分片数不超过 20~25 个**（如 30GB 堆内存的节点，承载的分片总数尽量控制在 600 个以内）。”
