## 一、 字节/小红书核心高频：亿级点赞与实时计数系统架构设计

```
                         高并发点赞系统整体架构流转
┌─────────────┐       ┌─────────────────┐       ┌───────────────────────────────┐
│ 用户点击点赞 │ ───► │ API 网关 (限流)  │ ───► │ 点赞微服务                    │
└─────────────┘       └─────────────────┘       └──────────────┬────────────────┘
                                                               │
                     ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
                     ▼                                                                                    ▼
     【极速读写：Redis 缓存层】                                                              【异步削峰：持久化落库】
  1. Set/Bitmap: 判断是否已点赞                                                           RocketMQ 批量聚合消息
     SISMEMBER like:post:{id} {uid}                                                                       │
  2. String / Slot Sharding: 点赞数原子自增                                                               ▼
     INCRBY like:count:{id}:slot_1 1                                                       批量写回 MySQL (点赞表/计数表)
                                                                                             INSERT INTO like_record ...
```

### 1.1 趣味现实生活比喻（小白零门槛理解）
* 想象一下学校开运动会，操场中央竖起了一块大黑板（**Redis 缓存**），旁边还放着一本厚厚的纸质档案簿（**MySQL 数据库**）。
* 当全校几万名同学路过想要给高三（1）班加油点赞时：
  - 如果大家都挤去档案簿上签名写字（**直接写 MySQL**），档案簿只有一支笔，同学们排队推搡、争夺纸笔（**行锁竞争**），甚至把桌子挤塌了（**数据库连接池打满、宕机**）；
  - **聪明做法**：大家直接在大黑板上画个“正”字（**Redis `INCR` 计数器**），同时在黑板右侧的小格子里贴一张写有自己学号的便利贴（**Redis `Set` 判断是否已点过赞**）。等到晚上放学没人的时候，班长把黑板上的“正”字汇总，一次性抄写登记到纸质档案簿里（**RocketMQ 异步批量落库**）。

### 1.2 业务痛点与技术挑战
1. **写并发极高（热点行锁打崩数据库）**：一条爆款视频（如明星发布结婚喜讯），每秒有 30 万人同时点击点赞。若执行 `UPDATE video SET like_count = like_count + 1 WHERE id = ?`，MySQL 针对同一行数据施加排他排队行锁，行锁阻塞队列瞬间打爆，整个数据库瘫痪。
2. **防重复点赞与状态快速查询**：用户刷新视频时，界面必须秒级展示“当前红心是否已点亮”（我点过赞没有？）。
3. **数据最终一致性**：点赞数不需要像银行账户余额那样 100% 强实时精准，允许几秒钟延迟，但**最终总数绝不能丢**，且 Redis 宕机后数据必须能恢复。

---

### 1.3 工业级标准架构与工程落地细节

#### 1. 数据结构选型（Redis）
* **记录“谁点过赞”**：
  - **中小型数据量**：使用 Redis `Set`，Key 为 `like:post:{videoId}`，Value 为 `userId`。
    - 判断是否点赞：`SISMEMBER like:post:{videoId} {userId}`（时间复杂度 $O(1)$）。
    - 点赞加入：`SADD like:post:{videoId} {userId}`。
    - 取消点赞：`SREM like:post:{videoId} {userId}`。
  - **亿级海量点赞（内存极致优化）**：若单个视频几千万点赞，Set 占用内存极大，改用 **RoaringBitmap** 或压缩位图，将用户整型 ID 映射到位图的一个 bit 位（1 代表点赞，0 代表未点赞）。
* **记录“点赞总数”**：
  - 采用 Redis String，Key 为 `like:count:{videoId}`。
  - 点赞加一：`INCR like:count:{videoId}`。
  - 取消减一：`DECR like:count:{videoId}`。

#### 2. 热点单 Key 分片优化（Slot Sharding）
* 如果单个视频 QPS 达到 20 万以上，单台 Redis 节点的单线程 CPU 会被打满（热点 Key 倾斜）。
* **破局解法**：将单个 Key 拆分成 10 个子 Key（分片计数器）：
  - 写入时：根据用户 ID 哈希随机打散到子分片：`like:count:{videoId}:{userId % 10}`，执行 `INCR`。
  - 读取总数时：服务端并发 `MGET` 这 10 个子 Key，内存求和返回给前端；或者由定时后台线程每秒聚合一次写到总 Key 中。

#### 3. Lua 脚本保证“防重与计数”原子性
```lua
-- KEYS[1]: like:post:{videoId} (Set)
-- KEYS[2]: like:count:{videoId} (String)
-- ARGV[1]: userId
if redis.call("SISMEMBER", KEYS[1], ARGV[1]) == 0 then
    redis.call("SADD", KEYS[1], ARGV[1])
    redis.call("INCR", KEYS[2])
    return 1 -- 点赞成功
else
    return 0 -- 已经点过赞，幂等忽略
end
```

#### 4. 异步落库削峰（RocketMQ 批量刷盘）
* 用户点赞成功后，Redis 立即返回客户端成功，并在后台向 RocketMQ 发送一条事件消息 `LikeEvent(videoId, userId, type=LIKE, timestamp)`。
* 消费者服务拉取消息后，在内存中使用环形队列或定时窗口，**每累积 500 条或每隔 2 秒批量执行一条 SQL**：
  ```sql
  INSERT INTO video_like (video_id, user_id, status, create_time)
  VALUES (101, 1, 1, NOW()), (101, 2, 1, NOW())
  ON DUPLICATE KEY UPDATE status = VALUES(status);
  ```

### 1.4 面试官高频追问与生产暗坑反杀
* **追问 1**：“如果 Redis 突发宕机，黑板上的点赞数还没来得及刷到数据库，数据丢失了怎么办？”
  - **反杀话术**：“我们会采用**双重兜底策略**：第一，点赞事件在写 Redis 的同时已经通过事务消息同步发送到了 RocketMQ（持久化在 Broker 磁盘上），即便 Redis 挂掉，下游消费者依然可以通过回溯 MQ 消息重新将点赞记录持久化进 MySQL；第二，每天凌晨会有离线定时对账任务（如 Spark/Flink 或定时批处理脚本），通过 `SELECT COUNT(*) FROM video_like WHERE video_id = ? AND status = 1` 重新校准 Redis 中的总计数字。”
* **追问 2**：“如果一个调皮的用户用脚本疯狂点赞、取消、再点赞，怎么防恶意刷接口？”
  - **反杀话术**：“第一在网关层通过 **令牌桶限流**，针对单一 `userId` 限制每秒最多触发 3 次点赞动作；第二在前端按钮做防抖与乐观变色，点击后立即灰化 1 秒并本地红心高亮，避免重复请求冲击网络；第三在后端接口通过 Redis 设置防重标志位（带 500ms 过期时间），重复请求直接快速失败拦截。”

### 1.5 🎙️【面试满分背诵模版】4 步标杆话术
> 1. **Headline（直击结论）**：  
>    “设计抖音/小红书亿级点赞系统的核心原则是**‘读写分离、内存抗压、异步落库、最终一致’**。面对高达数十万的瞬时点赞 QPS，绝对不能直连数据库，必须通过 Redis 的 Set + String 结构在内存中完成状态校验与计数原子更新，再通过 MQ 削峰批量异步落库。”
> 2. **Architecture（架构设计）**：  
>    “整体链路分为三层：**接入层**做网关防刷与针对用户维度的令牌桶限流；**缓存层**由 Redis 负责处理 99% 的高频读写，用 Set 结构通过 `SISMEMBER` $O(1)$ 判定用户是否已点赞，用 String 结构 `INCR` 累加点赞总数，利用 Lua 脚本保证防重与加计数的原子性；针对超高热点视频，采用 **Slot 分片计数器**（拆成 10 个子 Key）打散单节点热点压力；**持久层**通过 RocketMQ 收集点赞事件，下游批量聚合刷入 MySQL 数据库，保证最终一致性。”
> 3. **Engineering（工程落地细节）**：  
>    “在持久化落地中，为了避免海量单条 `INSERT` 压垮数据库，消费者端采用了**‘按批次聚合落库’**策略：内存窗口每积攒 500 条点赞事件或等待 2 秒，拼装一条 `ON DUPLICATE KEY UPDATE` 批量 SQL 入库；点赞关系表以 `(video_id, user_id)` 作为联合唯一索引，从数据库物理层兜底幂等性；凌晨配合离线任务比对 DB 记录总数对 Redis 做静默校准与冷热数据淘汰。”
> 4. **Follow-up（追问反杀）**：  
>    “如果面试官追问系统容灾与极端异常，我会从两点补充：若 Redis 节点故障，直接从本地 MQ 消费端或者备用从节点恢复，且在点赞这种弱一致性业务中，宁可牺牲极端几秒的计数精度，也绝不能让数据库被打爆影响主流程的播放与消费体验。”

## 二、 社交平台命脉：小红书/抖音 Feed 流系统设计（推模式 vs 拉模式 vs 推拉结合）

```
                     Feed 流推拉结合 (Hybrid) 经典模型
       ┌────────────────────────┐
       │   博主发布新笔记/视频   │
       └───────────┬────────────┘
                   │
         [粉丝量级判定]
         ┌─────────┴─────────┐
         ▼ (粉丝数 < 10万)    ▼ (粉丝数 >= 10万 大V)
   【普通用户：推模式 (写扩散)】   【超级大V：拉模式 (读扩散)】
         │                         │
         ▼                         ▼
   异步推送到每个在线粉丝的           仅写入大V自己的【发件箱】
   【收件箱 (Inbox)】                 (Outbox: Redis ZSet)
   (Redis ZSet: Score=时间戳)             │
                                          │
 ═════════════════════════════════════════╪═════════════════════════════════════════
                                          │
       ┌────────────────────────┐         │
       │  粉丝打开首页/刷新关注流  │ ◄───────┘
       └───────────┬────────────┘
                   │
                   ▼
     【读取并多路归并排序 (Merge)】:
      1. 从自己的收件箱拿出已推送的普通博主动态
      2. 实时拉取自己关注列表中所有大V发件箱的最新几条动态
      3. 在内存中按发布时间戳倒序合并 (K-way Merge Sort)，分页返回展示！
```

### 2.1 趣味现实生活比喻（小白零门槛理解）
* 想象你在一个超大居民小区里订阅报纸和明星签名照：
  - **推模式（写扩散 / 送货上门）**：你订了隔壁邻居王阿姨的自制食谱（王阿姨粉丝只有 10 个人），王阿姨每次写完，邮递员分别跑到这 10 个人的门前信箱（**收件箱 Inbox**）里各塞一份。你早上开门打开信箱，拿出来就能看，超级爽快、毫无延迟！
  - **推模式的灾难（大 V 崩盘）**：如果刘德华也在小区里，他有 1000 万个粉丝。如果也用推模式，刘德华发了一张自拍，邮递员要在 1 秒内跑到 1000 万个信箱里塞信件，邮递员当场累死，整条马路被堵死，全小区系统瘫痪！
  - **拉模式（读扩散 / 自提展台）**：刘德华发自拍，邮递员不送了，刘德华直接把照片挂在小区的中央广场展台（**发件箱 Outbox**）上。哪个粉丝想看，哪个粉丝自己溜达去展台看。
  - **推拉结合（终极智慧）**：普通邻居发动态用**推模式**送进信箱；超级明星大 V 发动态用**拉模式**挂在展台；你早上出门时，看一眼自己的信箱，再去广场展台瞄一眼大 V，把两边的内容按时间先后合在一起看！

### 2.2 业务痛点与三大模式横向对比

| 模式 | 工作原理 | 优点 | 致命缺陷 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **推模式 (Push / 写扩散)** | 博主发动态时，系统查出其所有粉丝，把动态 ID 写入**每个粉丝的收件箱 (Inbox)**。 | **读性能极高 ($O(1)$)**！用户打开 Feed 流秒开，无需任何聚合计算。 | **写放大灾难**！一个千万粉丝博主发文，瞬间引发上千万次写操作；且僵尸粉常年不登录，推送白白浪费存储！ | 早期系统、粉丝量小、好友关系严格对等的熟人社交（如早期微信朋友圈）。 |
| **拉模式 (Pull / 读扩散)** | 博主发动态仅写入**自己的发件箱 (Outbox)**。粉丝刷新 Feed 流时，实时遍历自己关注的所有人并拉取最新动态，在内存中归并排序。 | **写性能极高 ($O(1)$)**，存储完全不冗余，彻底消灭大 V 发文写膨胀问题。 | **读延迟极高、读压力巨大**！如果一个用户关注了 1000 个人，每次刷新需要并发发 1000 次查询再在内存做多路归并，数据库瞬间被拖死！ | 微博早期、粉丝数极其庞大但用户关注数较少的场景。 |
| **推拉结合 (Hybrid) 【行业标配】** | **分人群区别对待**：<br>1. 粉丝数 $< 10$ 万的普通用户 $\rightarrow$ **推模式**；<br>2. 粉丝数 $\ge 10$ 万的超级大 V $\rightarrow$ **拉模式**；<br>3. 活跃用户与沉睡用户分流。 | **兼顾极致的读体验与可控的写入开销**，彻底铲平大 V 发文洪峰与僵尸粉存储浪费。 | 系统架构复杂度高，需要维护粉丝等级划分与端侧/网关侧的归并排序逻辑。 | **小红书、抖音、新浪微博、Twitter/X**。 |

---

### 2.3 核心数据结构与存储选型
1. **收件箱 (Inbox) 与发件箱 (Outbox)**：
   - 一律采用 **Redis `ZSet` (Sorted Set)**！
   - Key 设计：
     - 用户收件箱：`feed:inbox:{userId}`
     - 大 V 发件箱：`feed:outbox:{vUserId}`
   - **Member 存放**：动态内容 ID（`postId`）；
   - **Score 存放**：发布时间戳（`timestamp`）。
   - **分页拉取**：直接使用 `ZREVRANGEBYSCORE feed:inbox:{userId} +inf -inf LIMIT 0 20`（按照时间倒序滑动翻页）。
2. **收件箱容量上限保护（截断机制）**：
   - 绝不能让每个用户的 ZSet 无限膨胀，通常只保留用户最近的 **500 ~ 1000 条动态**；
   - 超过容量时，通过 `ZREMRANGEBYRANK feed:inbox:{userId} 0 -501` 剪掉尾部老旧数据，节约 Redis 内存。更老的内容若用户继续往下拉，降级走数据库冷查询。

### 2.4 面试官高频追问与生产暗坑反杀
* **追问 1**：“如果小红书某个明星有 5000 万粉丝，他如果发了一条笔记，推拉结合模式下后台到底怎么处理？”
  - **反杀话术**：“第一，系统检测到该博主粉丝数超过阈值（如 10 万），标记为大 V，**严禁触发任何写扩散推流**，仅将其笔记 ID 写入该明星自己的 Redis 发件箱 `feed:outbox:{starId}`；第二，当这 5000 万粉丝中的某个在线活跃用户打开小红书刷新关注流时，服务端一边从该用户的 `feed:inbox` 读取已经推过来的普通好友动态，一边并发向该用户关注的这几位大 V 的 `feed:outbox` 分别发起拉取（只取最新 20 条），随后在内存中采用**堆排序（小顶堆/K路归并排序）**在数十毫秒内合并成一个有序时间轴，下发客户端。”
* **追问 2**：“对于半年都不打开 App 的僵尸用户/不活跃用户，我们还在拼命往他的收件箱推动态，这不是严重浪费存储吗？”

### 3.1 趣味现实生活比喻（小白零门槛理解）
* 想象大年三十火车站窗口只有 **100 张春运特快车票**，外面却有 **10 万人**在寒风中排队抢购：
  - **最蠢的做法**：把 10 万人全部放进售票大厅，让他们一窝蜂挤到售票员跟前（**直接打到 MySQL**），大门被挤烂，柜台被掀翻，售票员当场被踩伤（**数据库行锁打死、连接池爆炸、服务器宕机**）；
  - **工业级聪明做法（层层关卡拦截）**：
    1. **门口保安验身份证（网关限流+验证码防刷）**：让排队的人先算一道算术题（图形验证码），把那些找托代排的黄牛机器人当场抓走；
    2. **发排队号码牌（Redis 预扣库存）**：售票大厅门口的考官手里只拿着 100 张带有印章的排队纸条（**Redis 里放 100 个库存**）。前 100 个人一人领走一张纸条（**Lua 脚本原子扣减**），第 101 个人开始，考官直接用大喇叭大喊：“票已抢光，大家请回吧！”（**直接拦截了 99.9% 的流量**）；
    3. **拿到号牌的人慢悠悠进大厅买票（MQ 削峰异步落库）**：这 100 个拿到纸条的幸运儿，在引导员指挥下一个接一个有序去窗口付款出票（**RocketMQ 匀速消费入库**）；
    4. **验票闸机底线防伪（MySQL `WHERE stock >= 1`）**：售票电脑在出票时最后核验一次票数是否大于 0，哪怕有小偷伪造纸条混进来，也绝对打不出第 101 张票（**绝无可能超卖**）！

### 3.2 核心痛点与四大技术防线

#### 1. 防线一：前端与 CDN 动静分离（挡住 80% 静态请求）
* 秒杀详情页的 HTML、CSS、JS、商品主图等全部推送到 **CDN 边缘节点**，设置强缓存；
* 用户频繁点刷新，请求全部由 CDN 节点就近返回，**根本不会有任何流量打到公司的源站服务器**；
* 秒杀按钮在倒计时结束前置灰不可点，秒杀开始瞬间由 JS 动态请求获取一个临时的**随机秒杀动态 Path（防黑客提前抓包脚本刷单）**。

#### 2. 防线二：网关层限流与防刷（挡住恶意流量）
* **接口限流**：通过 Sentinel 或 Nginx 配置令牌桶算法，设定系统最大承载上限（如 5000 QPS），超出容量的请求直接返回“排队中，请稍后再试”；
* **用户维度频控**：基于 IP 和 UserID，单用户 1 秒内限制只能发起 1 次有效秒杀请求。

#### 3. 防线三：Redis + Lua 脚本原子预扣库存（核心抗压阵地）
* 活动开始前，通过定时任务将秒杀商品信息与库存预热加载到 Redis 中：`seckill:stock:{goodsId} = 100`；
* 用户发起秒杀，调用如下 Lua 脚本，保证“判断库存 + 扣减库存 + 防重复购买”在 Redis 单线程中**原子执行**：

```lua
-- KEYS[1]: seckill:stock:{goodsId} (库存 Key)
-- KEYS[2]: seckill:users:{goodsId} (已购买用户 Set)
-- ARGV[1]: userId
-- 1. 校验是否已购买过（一人限购一件）
if redis.call("SISMEMBER", KEYS[2], ARGV[1]) == 1 then
    return -1 -- 重复秒杀
end
-- 2. 校验库存是否充足
local stock = tonumber(redis.call("GET", KEYS[1]))
if stock <= 0 then
    return 0 -- 库存售罄
end
-- 3. 原子扣减库存并记录购买用户
redis.call("DECRBY", KEYS[1], 1)
redis.call("SADD", KEYS[2], ARGV[1])
return 1 -- 秒杀成功，允许进入下单流程
```

#### 4. 防线四：RocketMQ 异步削峰与 MySQL 条件更新底线
* Lua 脚本返回 1 的成功请求，秒杀服务向 RocketMQ 发送一条 `OrderCreateMessage`，接口立刻向用户返回“秒杀成功，订单正在生成中”；
* 下游订单中心以稳定的速率（如 500 QPS）拉取消息，开启本地数据库事务：
  ```sql
  -- 关键底线：必须增加 AND stock >= 1 条件更新！
  UPDATE seckill_goods 
  SET stock = stock - 1 
  WHERE goods_id = 1001 AND stock >= 1;
  ```
* 执行结果 `rowsAffected == 1` 时才真正插入 `order_info` 记录。如果返回 0 说明数据库无库存，事务回滚。

### 3.3 面试官高频追问与生产暗坑反杀
* **追问 1**：“如果用户在 Redis 扣减了库存，但在 30 分钟内一直没有去支付，怎么把库存还回去？”
  - **反杀话术**：“我们会启动**‘分布式延时关单机制’**。在创建订单发送 MQ 的同时，向延迟队列（RocketMQ 延迟消息或 Redis ZSet）投递一条 30 分钟检查事件。30 分钟到期后，消费端校验订单状态：若订单仍为‘未支付’，则在数据库层面将订单标记为‘已取消’，同时执行补偿操作：在 MySQL 执行 `stock = stock + 1`，并在 Redis 中通过 Lua 脚本执行 `INCRBY stock 1` 并且从购买用户 Set 中 `SREM` 剔除该用户，将库存平滑退回公池。”
* **追问 2**：“如果极端情况下 Redis 节点发生主从切换，Master 挂掉前有几笔扣减没来得及同步到 Slave，Slave 顶上后库存变多了，会不会导致超卖？”
  - **反杀话术**：“即使由于 Redis 异步主从复制延迟导致 Redis 里的库存比真实值多了 5 件，**底层 MySQL 也绝对不会超卖！** 因为我们在数据库执行扣减时加了终极安全锁 `WHERE stock >= 1`，数据库是单条行锁串行执行的，一旦库存减到 0，多出来的 5 笔订单在执行 SQL 时影响行数必然为 0，程序捕获后会直接抛出‘库存不足’异常并执行补偿，**MySQL 的 ACID 锁机制是守住公司资金安全的绝对最后一道底线！**”

### 4.2 微信二倍均值算法核心逻辑
* **为什么不能直接用完全随机？**
  - 如果发 100 块钱 10 个人分，第一个人直接随机到了 99 元，剩下的 9 个人分 1 块钱，极端不均，用户体验极差！
* **二倍均值法规则**：
  - 设剩余红包总金额为 $M$ 分，剩余未抢人数为 $N$；
  - 每次为当前人随机分配的金额范围为：
    $$\mathbf{[1\text{分}, \quad \frac{M}{N} \times 2 - 1\text{分}]}$$
  - **数学证明**：每次随机的数学期望值永远是 $\frac{M}{N}$（即剩余人均值），既保证了每个人的金额充满随机未知刺激，又在统计学上保证了每个人拿到的金额期望绝对公平！最后一人直接拿走剩余的全部尾数，杜绝分不尽的精度偏差。

### 4.3 工业级两阶段架构落地
1. **第一阶段：发红包（写数据库 + 预拆包入缓存）**
   - 调用微信支付扣除发红包者账户余额 100 元（本地事务保证强一致）；
   - 在内存中执行二倍均值算法，拆出 10 个具体金额（如：`[12.50, 8.30, 21.00, ...]`）；
   - 执行 Redis 命令：`RPUSH redpacket:{id}:pool 12.50 8.30 21.00 ...`；
   - 设置过期时间（通常为 24 小时）：`EXPIRE redpacket:{id}:pool 86400`。
2. **第二阶段：抢红包（纯内存原子操作，无锁高并发）**
   - 编写一段精简的 Lua 脚本：
     ```lua
     -- KEYS[1]: redpacket:{id}:users (记录已领过用户的 Set)
     -- KEYS[2]: redpacket:{id}:pool (红包金额队列 List)
     -- ARGV[1]: userId
     if redis.call("SISMEMBER", KEYS[1], ARGV[1]) == 1 then
         return -1 -- 已经领过，防重复领
     end
     local money = redis.call("LPOP", KEYS[2])
     if money == nil then
         return 0 -- 红包已被抢光
     end
     redis.call("SADD", KEYS[1], ARGV[1])
     return money -- 成功抢到金额
     ```
   - **核心优势**：`LPOP` 是 Redis 内部单线程原子的弹出操作，速度极快（$O(1)$，单节点可抗 10 万 QPS），不需要加任何分布式锁，天然杜绝超发！
3. **第三阶段：异步入账（RocketMQ 削峰记账）**
   - 抢到金额后，立即发送 MQ 消息到财务记账服务；
   - 记账服务异步执行：给抢到者的钱包余额 `balance = balance + money`，并插入一条流水记录；
   - 哪怕记账系统由于负载繁忙延迟了 1 秒钟到账，前端展示也早已变绿成功，兼顾了极致性能与数据安全。

### 5.3 基于 Redis ZSet 的轻量级工程实现（面试必问代码）

```java
@Component
public class RedisDelayQueueService {
    @Autowired
    private StringRedisTemplate redisTemplate;
    private static final String DELAY_QUEUE_KEY = "order:delay:cancel";

    // 1. 提交延时任务 (Score 为到期绝对时间戳)
    public void addDelayOrder(String orderId, long delaySeconds) {
        long expireAt = System.currentTimeMillis() + (delaySeconds * 1000);
        redisTemplate.opsForZSet().add(DELAY_QUEUE_KEY, orderId, expireAt);
    }

    // 2. 定时扫描线程 (推荐使用 Lua 脚本保证拉取与删除原子性，防止集群多实例重复消费)
    public void scanAndCancelOrders() {
        long now = System.currentTimeMillis();
        // 核心 Lua：拿到小于等于当前时间的前 100 个元素，并立即从 ZSet 中移除
        String luaScript = 
            "local orders = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, 100) \n" +
            "if #orders > 0 then \n" +
            "    redis.call('ZREM', KEYS[1], unpack(orders)) \n" +
            "    return orders \n" +
            "else \n" +
            "    return {} \n" +
            "end";
        
        List<String> expiredOrders = redisTemplate.execute(
            new DefaultRedisScript<>(luaScript, List.class),
            Collections.singletonList(DELAY_QUEUE_KEY),
            String.valueOf(now)
        );

        if (expiredOrders != null && !expiredOrders.isEmpty()) {
            for (String orderId : expiredOrders) {
                // 执行取消订单与库存回滚逻辑 (保证幂等)
                cancelOrderService.cancelAndRollbackStock(orderId);
            }
        }
    }
}
```

### 6.1 趣味现实生活比喻（小白零门槛理解）

### 6.2 核心技术剖析：为什么是 62 进制（Base62）？
* **字符字典**：`[0-9, a-z, A-Z]`（数字 10 个 + 小写字母 26 个 + 大写字母 26 个 = 共 **62 个安全字符**）。为什么不加 `+`、`/`、`?`？因为这些是 URL 特殊保留字符，容易引发转义乱码。
* **容量计算公式**：
  - 一个 6 位的 Base62 短链，能表示的不同组合数为：
    $$\mathbf{62^6 = 56,800,235,584 \quad (\approx 568 亿条！)}$$
  - 即使整个互联网每天生成 1000 万条短链，568 亿也足够全人类平稳使用 **15 年以上**！
* **生成算法：发号器 + 进制转换（工业界唯一标准）**：
  1. 每来一个新的长链接，通过分布式 ID 发号器（如雪花算法 Snowflake 或 美团 Leaf 号段模式）获取一个全局唯一的十进制数字 ID（例如 `10000000`）；
  2. 将十进制数字 `10000000` 按照 62 取模除法转成 Base62 字符串，得到纯短码 `FX6a`；
  3. **天然杜绝哈希碰撞**！纯数学进制转换，绝对一一对应，根本不需要考虑 MurmurHash 等哈希函数的碰撞死循环！

### 6.3 为什么必须用 302 重定向，而绝不能用 301？（面试必考题）
* **301 Moved Permanently（永久重定向）**：
  - 浏览器收到 301 后，会**在本地浏览器硬盘中死死强缓存**该映射关系！
  - 用户下一次再点击该短链时，浏览器直接在本地读出目标长链接跳走了，**请求根本不会再发到我们的短链服务器**！导致我们耗费巨资搭建的系统彻底无法统计点击量（PV）、独立访客数（UV）、转化率与地域分布，营销系统全部报废！
* **302 Found（临时重定向 【唯一标准】）**：
  - 浏览器不会缓存跳转关系，每一次用户点击短链，都会**老老实实向短链服务器发起真实网络请求**。服务器在几十毫秒内记录一条异步埋点日志，然后再返回 302 让用户跳转，两全其美！

### 6.4 面试官高频追问与生产暗坑反杀
* **追问 1**：“同一个长链接，如果被不同的人提交了 10 次，你的系统会生成 10 个不同的短链吗？怎么保证同一个长链接只生成一个短链？”
  - **反杀话术**：“为了避免短链码池浪费，我们会引入**‘长链反查与布隆过滤器’**。在数据库表中建立 `(short_code)` 为主键，同时对 `(long_url_hash)` 建立普通索引（存储长链的 64 位整型 MurmurHash 减少索引体积）。生成新短链前，先通过布隆过滤器或查询 Hash 索引判定该长链是否已经存在：若已存在且未过期，直接复用旧短码返回；若不存在，再通过发号器生成新短链入库。”
* **追问 2**：“如果有黑客用脚本恶意请求几亿个根本不存在的短码，你的短链系统怎么防止数据库被缓存穿透打死？”
  - **反杀话术**：“第一，在网关层做**‘短码合法性正则校验’**，凡是不符合 6 位 Base62 字符集规则的非法请求直接原地返回 404；第二，接入**布隆过滤器（Bloom Filter）**，系统每生成一个合法短码都会预先写入布隆过滤器中，未命中的请求 100% 认定为不存在，直接拦截，绝不放行至数据库；第三，对于穿透过去的空值，在 Redis 中写入带 30 秒短过期的空对象缓存，三道防护密不透风。”

> 3. **Engineering（工程落地细节）**：  
>    “在工程实现中，严格遵守三大原则：第一，**重定向状态码选型 302 而非 301**，规避浏览器本地强缓存，确保每次访问都能穿透至服务端完成 PV/UV 异步 MQ 埋点；第二，**短码生成规避 Hash 碰撞**，放弃 MurmurHash 碰撞补偿重算方案，全面采用‘发号器 + 进制转换’的数学单向映射；第三，**针对海量未知短码攻击**，前置部署 Redis 布隆过滤器并辅以空值缓存，筑牢缓存穿透防线。”
> 4. **Follow-up（追问反杀）**：  
>    “针对同一长链防重复生成，我们通过对长链接计算 MurmurHash64 建立数据库辅助索引并维护反向缓存映射；针对高并发跳转性能，利用 Nginx 边缘层做短链正则分发与静态代理，保障单机超 5 万 QPS 的毫秒级重定向响应。”

### 7.2 热点 Key 探测与防护全景对比

| 防御阶段 | 核心技术方案 | 原理与实现手段 | 解决的根本问题 |
| :--- | :--- | :--- | :--- |
| **1. 实时热点探测** | **客户端埋点 / Sentinel / Jvm-Sandbox** | 在客户端发起 Redis 调用前，在内存中使用滑动窗口统计最近 10 秒内每个 Key 的访问频次。一旦某个 Key 的 QPS 超过阈值（如 3000），自动上报给配置中心并判定为“热点”。 | 彻底解决“不知道哪个 Key 什么时候会突然变成热点”的盲盒问题。 |
| **2. 多级本地缓存** | **Caffeine / Guava Cache** | 一旦热点 Key 被发现，通过 MQ 广播或配置中心通知所有微服务实例，将该 Key 的数据写入每台 JVM 实例的堆内内存。 | **性能之王！** 请求直接在应用本地内存以纳秒级完成响应，**网络 I/O 为 0，Redis 流量降为 0！** |

| **4. 缓存击穿互斥锁** | **分布式锁 / SingleFlight (防击穿)** | 若本地缓存与 Redis 均失效，只允许 1 个线程拿锁去查 DB 回写缓存，其余线程原地等待。 | 杜绝上万并发同时穿透到数据库，死守数据库最后一条生命线。 |

### 8.2 核心技术剖析：GeoHash 与 Redis GEO

#### 1. GeoHash 的底层数学本质
* **二维降为一维**：计算机无法给二维平面（经度、纬度）建立传统的 B+ 树单值排序索引。
* **二分切分法（皮亚诺空间填充曲线）**：
  - 纬度范围 $[-90^\circ, +90^\circ]$，经度范围 $[-180^\circ, +180^\circ]$；
  - 落在左半区间标为 `0`，落在右半区间标为 `1`；
  - 不断将区间一分为二，经纬度二进制交叉编织合并；
  - 将最终得到的长二进制串用 **Base32 编码（0-9, a-z 去掉 a, i, l, o）** 压缩成一个短字符串（如 `wx4g0s`）；
* **【铁律特性】**：**字符串的前缀匹配越长，代表两点在物理空间上越接近！** 比如拥有相同前缀 `wx4g` 的所有点，全都在同一个大约 30 平方公里的矩形区域内！

#### 2. Redis GEO 的底层真相
* **底层数据结构一律是 `zset`（Sorted Set）！**
* 为什么？因为 Redis 把经纬度算成了一个 **52 位的整型数字（GeoHash 值）**，把这个整型数字当成 `score` 存进了跳表里；
* **核心常用命令**：
  - `GEOADD riders 116.404 39.915 "rider_1001"`：记录骑手坐标；
  - `GEODIST riders "rider_1001" "rider_1002" km`：计算两个骑手之间的距离；
  - `GEORADIUS riders 116.404 39.915 3 km WITHDIST WITHCOORD`：查找某个坐标附近 3 公里内的所有骑手并附带距离。

### 8.3 复杂多边形电子围栏为什么必须用 PostgreSQL + PostGIS？
* **Redis GEO 的局限性**：Redis 只能做“以某点为圆心的圆形半径搜索”，**完全无法支持任意不规则的多边形（Polygon）电子围栏**（例如某外卖区域避开了河流、某共享单车禁停区是梯形）！
* **PostgreSQL + PostGIS 破局**：
  - 使用标准的 `geometry(Polygon, 4326)` 字段存储商圈和围栏多边形；
  - 建立 **`GiST` (Generalized Search Tree) / R-Tree 空间索引**；
  - 执行空间拓扑计算：
    ```sql
    -- 判断骑手当前坐标点是否在配送区域围栏内
    SELECT fence_id, fence_name 
    FROM delivery_fence 
    WHERE ST_Contains(fence_geom, ST_SetSRID(ST_Point(116.404, 39.915), 4326));
    ```

## 九、 游戏与社区中枢：全服千万级实时积分排行榜系统 (Leaderboard 与同分平局打破)

### 9.1 趣味现实生活比喻（小白零门槛理解）
* 想象全校运动会跳高比赛（**全服排行榜**）：
  - **传统数据库排序（死慢死慢）**：每跳完一个人，裁判拿着铅笔把全校 1 万名学生的成绩单从头到尾重排一次（**`SELECT * FROM rank ORDER BY score DESC` 全表排序**），操场上比赛全都停下来等裁判算算术；
  - **Redis 跳表（神奇电梯）**：操场边有一座带分层跳板的高速电梯（**Redis SkipList 跳表**）。每来一个新成绩，只用几毫秒就能顺着跳板精准滑到他该站的楼层；
  - **同分打破平局（谁先跳过谁更强）**：如果小明和小刚都跳了 1.80 米，怎么排第一名？看手表！小明是上午 9 点跳过去的，小刚是上午 10 点跳过去的，小明先达到，小明排前面！

### 9.2 工业级核心技术设计

#### 1. Redis `Sorted Set` 数据结构全貌
* **底层两大基石**：**跳表（SkipList）** + **字典（Hash Map）**。
  - 字典用于 $O(1)$ 查找玩家当前的积分；
  - 跳表用于 $O(\log N)$ 插入、删除以及极速范围检索。
* **常用核心指令**：
  - 更新/新增积分：`ZADD rank:2026 {score} {userId}`
  - 获取前 100 名：`ZREVRANGE rank:2026 0 99 WITHSCORES`
  - 获取自己的排名：`ZREVRANK rank:2026 {userId}`（返回的是从 0 开始的索引，真实名次需加 1）。

#### 2. 同分平局打破策略（Tie-breaking Algorithm）
* **痛点**：若两个人都是 100 分，Redis 默认会按照 Member 的字典序（ASCII 码）排序，这在业务逻辑上是极其不公平的！业务要求通常是：**“同分情况下，先达到该积分的玩家排在前面！”**
* **工业级终极解法：Score 浮点数拼接时间戳逆序值**：
  - 设定一个未来的基准时间戳常量 $T_{\max} = 9999999999$（10 位秒级时间戳）；
  - 当前时间戳为 $t$（显然越早达到的玩家，$t$ 越小，则 $(T_{\max} - t)$ 越大）；
  - **最终存储在 Redis 中的 Score 计算公式**：
    $$\mathbf{\text{FinalScore}} = \text{RealScore} + \frac{T_{\max} - t}{10^{10}}$$
  - **效果演示**：
    - 玩家 A 在 10:00:00 达到 100 分，FinalScore = `100.82880000`；
    - 玩家 B 在 10:00:10 达到 100 分，FinalScore = `100.82879990`；
    - Redis 比较浮点数大小，玩家 A 的 Score 略大于玩家 B，**无需任何额外代码，天然先达到的排在前面！**

### 10.1 趣味现实生活比喻（小白零门槛理解）
* 想象你要把一套 100 本的《大英百科全书》（**4GB 大文件**）搬运到山顶的图书馆（**云存储服务器**）：
  - **传统单连接上传（笨办法）**：你一个人一次性抱着全部 100 本书爬山。半路走到第 99 本时突然下大雨摔倒了（**网络中断**），所有书掉进泥潭里（**整个文件废弃**），你必须回到山脚下把 100 本书重新抱一遍（**重传整包，用户抓狂崩溃**）；
  - **断点续传（切成 100 个小箱子）**：你把每本书单独装一个小箱子（**切成 5MB 的分片 Chunk**），箱子外贴上编号 1 到 100。你请了 5 个快递员并发去送（**多线程并发上传**）。即便半路摔了，只有摔掉的那 1 本需要补送，已经送到山顶的 99 本全都有效（**断点续传**）；
  - **秒传（发现山顶本来就有一套一模一样的）**：你出发前，先打个电话问图书馆管理员：“你们这有没有编号叫 `ISBN-998877` 的这套书？”（**比对文件 MD5 指纹**）。管理员一看电脑：“有啊，昨天张三刚捐了一套一模一样的！” 于是管理员直接在借书卡上写上你的名字（**建立引用关系**），你一秒钟都不用跑，直接大功告成（**秒传**）！

### 10.2 核心技术剖析：分片、抽样 Hash 与状态追踪

#### 1. 前端分片切块（Blob Chunking）
* 利用 HTML5 的 `File.prototype.slice()` API，在前端浏览器内存中按固定步长（如每片 5MB）将大文件切成连续的二进制数据块（Chunk 0, Chunk 1, ... Chunk N）。
* 每一个分片携带自身元数据：`fileHash`、`chunkIndex`（分片序号）、`totalChunks`。

#### 2. 秒传与快速 Hash 抽样计算（Fast Hash）
* **痛点**：若在前端读取一个 20GB 的完整大文件计算 MD5，浏览器 JavaScript 线程会卡死几分钟！
* **抽样 Hash（极速秒出）**：
  - 读取文件**头部的 2MB** + **中间的 2MB** + **尾部的 2MB**；
  - 结合文件总大小 `file.size`，三者拼在一起送进 MD5 计算；
  - 仅耗费不到 100ms 即可生成独一无二的文件抽样指纹，实现秒级校验！

#### 3. Redis 位图（Bitmap）记录分片进度
* 使用 Redis 的 `Bitmap` 记录某个文件哪些分片已上传：
  - Key：`upload:progress:{fileHash}`
  - 分块 0 传成功：`SETBIT upload:progress:{fileHash} 0 1`
  - 分块 1 传成功：`SETBIT upload:progress:{fileHash} 1 1`
* **断点恢复时**：客户端掉线重连，先发请求获取已上传分片列表，服务端通过 `BITFIELD` 或 `GETBIT` 秒级返回已完成分片编号，客户端直接跳过这些分片，只补传剩余未上传分块！

#### 4. 对象存储服务端合并（OSS Multipart Upload）
* 分片数据不经过业务后端应用服务器的中转（避免吃满业务网卡），而是**由后端生成带有预签名的 OSS UploadUrl，客户端直接向阿里云 OSS 或 MinIO 并发上传分片**；
* 全部分片上传完毕后，客户端调用后端的 `CompleteMultipartUpload` 接口，通知对象存储在云端底层完成文件块物理合并，落库生成可访问链接。

### 10.3 面试官高频追问与生产暗坑反杀
* **追问 1**：“如果两个用户上传了内容一模一样但文件名不同的视频，触发了秒传，其中一个用户后来把视频删了，另一个用户的视频会不会也丢失？”
  - **反杀话术**：“**绝对不会！** 我们在数据库层采用**‘文件物理元数据与用户逻辑引用解耦（引用计数器模型）’**：
    1. 物理表 `file_storage`：记录实际存储在 OSS 上的文件信息（`file_hash`, `oss_url`, `reference_count` 引用计数）；
    2. 业务表 `user_file`：记录属于该用户的文件视图（`user_id`, `custom_file_name`, `file_hash`）；
    3. 当触发秒传时，物理文件只有一份，但在 `user_file` 插入一条新记录，并将物理表的 `reference_count + 1`；
    4. 当某用户删除文件时，只删除其在 `user_file` 的记录，并将物理表的 `reference_count - 1`；**只有当引用计数真正归零时，后台异步任务才会真正向 OSS 下发物理删除命令**，彻底杜绝数据误删。”

### 10.4 🎙️【面试满分背诵模版】4 步标杆话术
> 1. **Headline（直击结论）**：  
>    “大文件海量数据断点续传与秒传系统的核心设计模型是**‘前端切片并发直传、抽样指纹极速秒传、位图追踪断点增量、对象存储底层合成分块’**。系统旨在攻克弱网环境上传中断重传成本过高、服务器 I/O 与网卡带宽被大文件挤占以及重复文件过度占用云存储空间的痛点。”
> 2. **Architecture（架构设计）**：  
>    “链路分为三步：**预检查阶段**，前端利用局部抽样算法秒级计算文件 Hash，请求服务端判定是否已存在物理副本，命中则直接秒传成功并增加引用计数；**切片直传阶段**，未命中则将文件以 5MB 为单位拆分，服务端下发带有临时凭证的 OSS/MinIO 预签名 URL，前端多线程并发直传云存储，避开业务服务器带宽瓶颈；**断点与合并阶段**，Redis Bitmap 动态记录已到达分片，支持网络抖动后的增量补传；全部分块到达后，调用云存储 API 原地执行底层多段合并。”
> 3. **Engineering（工程落地细节）**：  
>    “在工程设计中落实三大防线：第一，**避免大文件前端 MD5 卡顿**，采用‘首中尾抽样 + 文件尺寸’的组合指纹算法，将指纹计算开销压缩至百毫秒内；第二，**杜绝秒传误删**，存储层解耦物理文件表与用户引用表，基于引用计数（Reference Count）实施安全的垃圾回收与清理；第三，**分片传输幂等**，OSS 原生支持根据分片编号（PartNumber）进行幂等覆盖，网络超时重复传输安全无副作用。”
> 4. **Follow-up（追问反杀）**：  
>    “若面试官追问上传过程中用户中途放弃导致大量无用分片堆积在 OSS 怎么处理？我会说明：在对象存储桶上配置**‘碎片生命周期管理策略（Lifecycle Rule）’**，设定凡是处于未完全合并状态超过 72 小时的 Multipart 分块碎片，由云存储底层自动异步批量清理，杜绝无用冷存储费用积压。”

### 💡 字节一面致胜金律（考前心法）：
1. **回答问题先抛结论（Headline First）**：面试官问一个问题，千万不要从盘古开天辟地扯起。第一句话直接用加粗的专业术语定性（如：“这个问题的核心本质是……我们在工程上主要通过三层架构来破局……”），瞬间给面试官建立“这小伙子逻辑极强”的第一印象！
2. **场景题画出清晰的三层走势**：听到场景题，在脑海里或者共享草稿纸上迅速勾勒三层：**接入层（网关限流防刷） $\rightarrow$ 缓存层（Redis 内存抗压与原子计算） $\rightarrow$ 存储底线层（MQ 异步削峰与 MySQL 条件更新强一致）**。万变不离其宗！
3. **把项目引向你最熟悉的战场**：当面试官问到项目时，主动抛出你下过苦功的技术难点（如库存防超卖的 Lua 原子操作、Spring三级缓存的循环依赖、OpsMind 的 Agent 闭环排障），引导面试官顺着你的优势长处深入提问！
4. **算法手撕先讲思路再动笔**：面试官给出题目后，先花 1 分钟跟面试官口述核心思路和时间复杂度（如：“这道题我考虑用双指针/滑动窗口，时间复杂度是 $O(N)$，空间复杂度是 $O(1)$，您看这个方向符合预期吗？”），得到面试官点头肯定后再流畅敲出规范、带异常校验的生产级代码！
