## 二、电信级综合网管系统（OSS/NMS）宏观全景与系统架构设计（面试全局白板画图专备）

### 2.1 什么是电信级 OSS/NMS 综合网管？它与互联网电商架构的本质区别
面试官通常会试探：“**你之前做过物联网，后来又去了凯通做电信综合网管，网管系统到底是干什么的？架构有什么不同？**”

1. **业务本质**：
   - **OSS（Operations Support System，运营支撑系统） / NMS（Network Management System，网络管理系统）** 是电信运营商（中国电信、中国移动、中国联通）的“生命中枢”。
   - 它的核心职责是对全省/全国的数百万台核心通信设备（基站、传输网元、IPRAN 路由器、云池宿主机、动环机房）进行 **7×24 小时毫秒级故障感知、告警压缩关联、割接调度、工单派发与应急容灾调度**。
2. **架构特征与互联网电商的本质区别**：

| 对比维度 | 互联网高并发电商（如淘宝、京东） | 电信级综合网管系统（OSS/NMS） |
| :--- | :--- | :--- |
| **数据流量模型** | **下行读多写少，读热点极高**（商品浏览、秒杀抢购，依靠 CDN 与分布式缓存抗量）。 | **上行写极其频繁，流式突发**（全省通信故障瞬间，数万台设备在一秒内暴发数万条告警）。 |
| **核心技术挑战** | 高并发高可用（QPS/TPS）、超卖控制、分布式事务、微秒级响应。 | **拓扑关联图谱分析、海量告警流式压缩、规则引擎链匹配、异构历史协议兼容、数据主权与分域隔离**。 |
| **容错与可用性** | 允许有损降级（如排队、限流返回请稍后重试）。 | **极度严苛的 SLA（99.999%），绝对不允许漏报重大通信故障**，割接恢复比对必须同事务严丝合缝。 |
| **系统演进包袱** | 快速迭代重构，遗留系统较容易废弃重写。 | **历史老系统（十几年前的 Struts2、GBK、SOAP 协议）与新微服务（Spring Cloud、Vue3）长期并存并网运行**。 |

### 2.3 存储与数据架构选型哲学（ES 多版本集群 + MySQL/Flyway + Redis + 4A）
1. **Elasticsearch（海量网络告警的流式聚合引擎）**：
   - **职责**：全网设备每秒都在产生海量硬件指标与网络 Trap 告警，历史告警数据达到数千万甚至数亿级别。
   - **选型原因**：关系型数据库无法承受如此高吞吐的倒排索引与多维组合查询。系统依赖 ES 进行全文检索与组合过滤；利用 ES 6.2.2 的 `composite` 聚合能力突破传统 `terms` 聚合无法同时按多维度（`I_ALARM_ID + I_DATA_DOMAIN_ID`）分桶的瓶颈；
   - **版本兼容挑战**：现场不同省份部署的 ES 版本割裂（老系统 ES 5.x/6.2.2，新集群 ES 7.7）。我们在代码中特别重构了 `EsHandler`，针对 ES 7.7 将 `hits.total` 从单个整数改写为包含 `{value, relation}` 对象的兼容反序列化，抹平集群版本差异。
2. **MySQL + Flyway（电信元数据基石与数据库版本化双规管理）**：
   - **职责**：存储割接计划单据、规则编排流程、网元设备基础配置（`PeerNe`、`PeerLink`）、政企组织架构。
   - **Flyway 双版本解耦**：电信项目中多个需求经常并行分支研发。在 IPRAN 比对改造中，曾发生并行版本冲突（V1.0.136 与 V1.0.163）。通过设计 Flyway 增量幂等脚本与动态版本校验，确保 SQL 迁移脚本在各省份现场按序幂等执行，避免脚本冲突导致服务启动失败。
3. **电信 4A 集中管控系统与 RBAC 数据域**：
   - 电信运营商系统严禁私自设立账号体系，所有操作人员必须通过集团 4A 系统（Authentication 认证、Account 账号、Authorization 授权、Audit 审计）做统一凭证托管。
   - 系统通过 `Login4AFeignApi` 与 4A 网关通信，解析出当前用户的 `iDomainId`，驱动系统内部的数据分域鉴权。

### 2.4 新老架构共存与双协议适配（Spring Cloud 微服务 + Struts2-on-Spring-MVC GBK 老系统）
在凯通科技实习中最考验工程韧性的一点是：**新老系统跨代并网共存**。
- **老系统（jzgj，集中告警系统）**：基于十几年前的 Struts2 构架在 Spring MVC 之上，采用 Hibernate 5 做 ORM，底层全站强制使用 **GBK 字符编码**，构建工具采用 Apache Ant 打成 WAR 包运行在 Tomcat/WebLogic 上；
- **新系统（service-zhwg-*）**：纯正的 Spring Boot 2.x / Spring Cloud 微服务，UTF-8 编码，Maven 构建，前后端分离（Vue3 + Element Plus）；
- **你的工程破局贡献**：
  在“告警规则匹配”需求中，客户既希望在老系统 jzgj 的 JSP 页面中打开规则编排，又希望在新微服务大屏中调用。你在 `jzgj` 中补齐了从 `RuleFlowDao $\to$ Service $\to$ Action` 完整的五层 Struts2 链路，使用 `RequestUtil.responseOut("GBK", ...)` 保证字符集不乱码；并在新微服务中通过 `sysconfig` 配置开关动态路由双端协议，实现了**跨系统平滑共存**！

## 三、设计模式全景速查与源码级实战对照表（含真实项目代码）

电信级系统极其庞大，设计模式的运用比纯互联网业务更加密集和规范。以下为你项目中**真实落地**的 5 大核心设计模式：

| 设计模式 | 业务落地类名 | 解决的痛点 | 架构与工程设计价值 |
| :--- | :--- | :--- | :--- |
| **策略模式+工厂路由**<br>(Strategy + Factory) | `InitViewDataService`<br>`InitYcViewDataServiceImpl`<br>`InitVolteViewDataServiceImpl`<br>`YcViewDataServiceConfiguration` | 几十个不同专业、不同省份的拓扑视图（viewCode 71~79）组装逻辑各异，容易堆叠成万行大类。 | 将每个云池视图的拓扑初始化逻辑解耦到独立的 Service 实现类中，通过 Spring 工厂依据 `viewCode` 动态路由。 |
| **过滤器链模式**<br>(Chain of Responsibility) | `service-gateway` 响应式网关中的 11 个过滤器（`PermissionFilter`、`CsrfFilter` 等） | 电信网关需兼顾身份鉴权、防重放、加解密、限流与老系统 GBK 编码转换，逻辑强耦合。 | 基于 Spring Cloud Gateway 的 `GatewayFilterChain`，每个过滤器职责单一，支持链式插入、短路与顺序微调。 |
| **外观模式/门面模式**<br>(Facade Pattern) | `YcTopologyDeviceUtil` | 拓扑出图时需要判断某个网元到底是真实硬件宿主机、虚拟占位网元还是连线中间节点，判断逻辑复杂。 | 提供一个高聚合静态门面工具类，对外暴露统一的 `isSpecificDevice` / `isVirtualNode` 判定接口，被 3 个微服务通用复用。 |
| **上下文对象模式**<br>(Context Object Pattern) | `ViewTopologyContext`<br>`PowerAlarmRoomContext` | 拓扑装配链路上需要透传几十个查询条件（用户域、时间区间、网元列表、链路状态），导致方法参数爆炸。 | 将多维状态收敛为统一的不可变上下文对象（Context），在私有方法与流处理间干净流转。 |

## 四、电信级海量告警与拓扑大屏高可用白皮书

### 4.1 拓扑大屏性能灾难：为什么“拓扑与告警必须异步解耦”？
- **业务痛点（REQ_2606160005）**：
  在原设计中，前端访问 `/view/cloud/merge/topo` 请求大屏拓扑数据时，后端在同一个接口内：
  1. 先查数据库构建成千上万个节点（`PeerNe`）和连线（`PeerLink`）；
  2. **致命耦合**：接着循环遍历所有节点，并发调用外部 ES 查询每个节点当前的活动告警数，再去查割接单和操作日志；
  3. **后果**：整个接口耗时被最慢的数据源（ES 慢查询、割接单超时）卡住，首屏出图长达 **15～30 秒**，前端大屏长时间处于“白屏加载菊花”，调度运维人员无法容忍！
- **你主导的技术解耦方案（一张图拓扑告警分离）**：
  - **职责剥离（静态出图 vs 动态状态）**：
    - `/view/cloud/merge/topo`：彻底剥离所有告警、日志、割接查询，**纯粹只查基础拓扑结构**，接口响应瞬间压降到 **200ms 以内**，前端 G6 图引擎在半秒内迅速完成骨架首屏绘制出图！
    - `/view/cloud/merge/status`：剥离出专门的“拓扑动态状态”统一接口。前端页面渲染完拓扑骨架后，异步触发状态请求，局部给节点和链路打上动态红色警报角标与黄色割接标记；
  - **容错隔离**：告警源即使超时，仅影响角标展示，**绝不影响整张网络拓扑的大屏出图**，做到了完美的架构解耦与故障隔离。

### 4.2 ES 深度聚合调优：composite 分桶与 after_key 翻页设计
- **痛点**：在告警规则统计（REQ_2510210019）中，客户要求按 `I_ALARM_ID`（告警ID）与 `I_DATA_DOMAIN_ID`（数据域ID）两个字段进行联合分组统计，并对统计结果进行分页下钻。
  - 原生 ES `terms` 聚合只能对单一字段分桶，嵌套子聚合在千万级数据下极易引发 JVM 堆内存暴涨引发 OOM；
  - 传统的 `from + size` 在深度分页下存在“跳页代价过大”的致命限制。
- **你的解决方案**：
  - 采用 **ES 6.2.2 的 `composite` 复合聚合**：
    ```json
    {
      "composite": {
        "size": 500,
        "sources": [
          { "alarm_id": { "terms": { "field": "I_ALARM_ID" } } },
          { "domain_id": { "terms": { "field": "I_DATA_DOMAIN_ID" } } }
        ],
        "after": { "alarm_id": "xxx", "domain_id": "xxx" }
      }
    }
    ```
  - **基于 `after_key` 游标翻页**：每批流式拉取 500 个桶，记录上一批次最后一条桶的 `after_key`，下一次请求带着 key 继续往后捞取，彻底解决了全量数据拉入内存的 OOM 风险；
  - **字段白名单 + 内存稳定二级排序**：由于 ES 原生不支持对 composite 的子聚合计数结果直接排序，你在服务端设计了内存排序支持类（`AlarmMatchRuleStatisticsPageSupport`），定义字段白名单（`alarmNum`、`eventNum`），在服务端内存安全完成二级稳定排序。

### 4.3 电信级数据分域安全与垂直越权绝对收敛
- **安全红线背景（REQ_2606280001）**：
  政企客户网络涉及高度机密。地市运维人员（如金华市账号）在登录政企主动监控系统时，只能看到金华本地市的政企电路故障。
  旧系统存在严重安全漏洞：查询条件由前端通过 HTTP 参数传入 `city=B`。如果有恶意人员通过抓包工具篡改入参为 `city=ALL` 或全省其他地市，就能越权查看到全省的政企专线数据！
- **你设计的服务端强制安全收敛体系（`ActiveMonitorDataDomainService`）**：
  1. **彻底废除对前端入参的信任**：服务端从请求上下文的 JWT / 4A 登录态中提取登录账号，反查数据库 `tbOsStaff.iDomainId`；
  2. **交集强制收敛算法**：
     - 若该账号为“省公司超级管理域（`1030005`）”，放开所有权限；
     - 若为普通地市账号，将系统计算出的 `allowedCityIds` 与前端请求传入的 `reqCity` 取**严格交集（Intersection）**：
       $$\text{effectiveCityIds} = \text{allowedCityIds} \cap \text{reqCity}$$
     - 若普通地市账号企图伪造他人地市，交集计算结果为**空集**，服务端直接强制返回空列表，杜绝任何越权可能！
  3. **三处读路径物理锁定**：在分页查询、报表导出、关联记录查询 3 处读路径的 MyBatis XML 中，服务端底层强制拼装 `AND I_CITY IN (effectiveCityIds)`，坚决杜绝越权漏洞。

### 4.4 告警“以子查根”对称路径与割接自动化比对同事务覆盖
- **痛点一：工单告警丢漏（BUG_2607165）**：
  - 现象：在重大割接或故障排查时，工单详情页关联的告警清单频繁丢失根故障告警；
  - 根因：原系统只设计了“以根查子”的单向关联链路（从根告警查找派生出的子告警）。当现场运维人员首先发现并上报的是一条子告警时，系统因缺失逆向追溯能力，无法定位其父级根告警；
  - **你的修复落地**：新增 `getRootSubRelByAlarmIdsAsSub` 对称追溯链路，合并派单关联、压缩关联、根子拓扑三方 ID；并在 `filterAlarmIdsForBill` 中设计黑名单策略，过滤掉已被其他工单认领的告警，闭环补全了完整的根子故障树。
- **痛点二：IPRAN 割接比对覆盖一致性（REQ_2606240003）**：
  - 在割接恢复自动化比对时，如果采用“逐条更新状态”，一旦执行到一半网络断开，会导致新旧快照并存的数据污染；
  - **你的同事务覆盖设计**：采用标准的“**同事务原子覆盖策略**”——在同一个 `@Transactional` 事务内，首先按割接单 ID 定位并执行 `DELETE WHERE type='IPRAN'` 物理清理旧结果，紧接着执行批量 `INSERT` 插入最新比对快照；任何一条设备比对插入失败，事务立即自动整体回滚，保留原旧快照不变，彻底规避脏数据中间态。

#### 追问 2：ES 5.x/6.x 与 ES 7.7 在 Java 客户端反序列化时到底有什么差异？你是怎么做兼容的？

### 地狱拷问 2：为什么 Zuul 必须迁到 Spring Cloud Gateway？响应式编程（WebFlux）下写了阻塞代码会产生什么灾难？
- **面试官施压**：“你们把 12 个生产环境从 Zuul 迁到了 Spring Cloud Gateway。Netty 响应式模型号称高吞吐，但如果某个实习生在 Gateway 的 GlobalFilter 里随手写了一行 `restTemplate.getForObject(...)` 或 `jdbcTemplate.query(...)`，网关会发生什么后果？怎么排查？”
- **满分反杀**：
  > 1. **【迁移核心收益】**：Zuul 1.x 基于经典的 Servlet 单线程单请求阻塞模型，在长连接与突发海量请求下容易把 Tomcat 工作线程池打满；Spring Cloud Gateway 基于 Netty NIO 事件循环（EventLoop），极少数线程即可支撑数万并发；
  > 2. **【阻塞代码的毁灭性灾难（EventLoop Starvation）】**：
     Netty 的 EventLoop 线程数通常只有 `CPU核心数 * 2`。如果有人在 Filter 中写了同步阻塞代码，**短短几个并发阻塞请求就会把这几个稀缺的 EventLoop 线程全部卡死**！导致原本能够承载数万并发的网关瞬间瘫痪，所有进入网关的请求全部超时，引发全局大雪崩！
  3. **【防范与排查机制】**：
     - **代码规范**：所有外部调用必须使用非阻塞的 `WebClient`，严禁使用 RestTemplate 或普通 JDBC；
     - **检测工具**：在测试环境中引入 **BlockHound** 字节码探针，一旦在 Reactor 调度线程中检测到任何阻塞调用（如 `Thread.sleep`、`SocketInputStream.read`），探针立刻抛出运行时异常并在单测中熔断报警，防患于未然。

### 地狱拷问 3：Flyway 双版本冲突（V1.0.136 vs V1.0.163），为什么并行开发会冲突？怎么解耦？
- **面试官施压**：“在 IPRAN 需求中你提到了 Flyway 双版本兼容。为什么团队并行开发会导致 Flyway 迁移冲突？如果一个先合入了更高的版本号，本地代码怎么保证不报错？”
- **满分反杀**：
  > 1. **【冲突根因】**：
     Flyway 默认严格按照版本号升序执行，并在 `flyway_schema_history` 表记录每次迁移的校验和（checksum）与执行顺序。
     如果开发分支 A 写了 `V1.0.163__ipran.sql` 并提前部署到了测试库；而开发分支 B 还在使用较旧的基线 `V1.0.136__cutover.sql`，当分支 B 部署时，Flyway 默认会检测到‘版本倒退（Out of Order）’，直接抛出 `FlywayException` 拒绝启动并强行终止！
  2. **【解耦方案】**：
     - 在 Spring Boot 配置中开启 `spring.flyway.out-of-order = true`，允许 Flyway 执行版本号较低的未执行脚本；
     - 在我们的提交中，针对并行需求编写了版本检测与幂等补丁，在 SQL 内部加入 `IF NOT EXISTS` 与元数据状态检查，确保脚本即便在不同分支之间乱序被执行，也能保证 DDL 的最终幂等收敛。

### 地狱拷问 4：割接自动化比对“先删后插”如果事务执行到一半机器挂了，会不会把历史比对结果搞丢了？
- **面试官施压**：“你在 IPRAN 割接比对中采用同事务‘先删旧结果再批量插新快照’。如果删完旧结果后，正在插入新数据时数据库节点发生 OOM 宕机或者网络中断，历史结果丢了，新结果没插完，你怎么保证高可用？”
- **满分反杀**：
  > 1. **【关系型数据库 ACID 事务的原子性（Atomicity）保障】**：
     首先明确，在同一个 `@Transactional` 物理事务内：`DELETE` 和 `INSERT` 并不是脱离事务独立提交的。在未执行最后的 `COMMIT` 之前，所有的改动都仅存在于数据库的 Undo Log / Redo Log 与事务私有缓冲区中；
  2. **【宕机崩溃恢复（Crash Recovery）】**：
     如果服务器突发断电或 OOM，数据库实例在重启后会触发 Crash Recovery 机制。PostgreSQL / MySQL 会扫描 WAL / Redo 日志，发现该事务处于未提交（Uncommitted）状态，**自动执行 Undo 回滚操作，将此前 DELETE 删除的数据完好无损地还原回磁盘**！因此绝对不会出现‘旧数据丢了、新数据没有’的中间破损态；
  3. **【双活备份表策略】**：针对极端高保密割接，可以采用‘带版本号插入 + 指针切换（Shadow Table / Version Pointer）’，直接插入版本 V2，成功后将有效指针从 V1 指向 V2，彻底实现无缝零缝隙切换。

### 地狱拷问 5：政企数据分域如果采用 SQL 动态拼接 `AND I_CITY IN (...)`，怎么防范 SQL 注入攻击？
- **面试官施压**：“你在数据分域时把计算出的地市 ID 拼装进 SQL 的 IN 条件中。如果有恶意用户在参数中构造 `'1' OR '1'='1'`，会不会把全省数据泄露出去？底层是怎么防注入的？”
- **满分反杀**：
  > 1. **【严禁字符串拼接（String Concatenation）】**：
     我们在 MyBatis XML 中绝对不使用 `${}` 语法做直接字符串拼接！
  2. **【预编译参数绑定（PreparedStatement `#{}`）】**：
     底层严格使用 MyBatis 的 `<foreach>` 动态标签生成安全的参数占位符：

     ```xml
     AND I_CITY IN
     <foreach item="item" collection="effectiveCityIds" open="(" separator="," close=")">
         #{item}
     </foreach>
     ```
     在 JDBC 底层被解析为 `AND I_CITY IN (?, ?, ?)` 预编译 SQL；
  3. **【Java 类型强约束】**：在 Java 代码中，`effectiveCityIds` 的类型被严格声明为 `List<Long>`，在入参阶段就彻底杜绝了任何包含单引号、分号等恶意 SQL 片段的字符串混入可能。

### 地狱拷问 6：ES composite 聚合分页每批 500，如果在深翻页时网络断了，下一次怎么续接？

### 地狱拷问 7：为什么大屏拓扑不直接用 WebSocket 实时推送，而是让前端异步拉取？
- **面试官施压**：“既然是网络告警大屏，实时性要求极高。为什么你们不直接在服务端和前端建立 WebSocket 长连接做事件推流，反而采用 HTTP 轮询/异步拉取的方式？”
- **满分反杀**：
  > 1. **【并发连接数与服务端资源隔离（C10K 考验）】**：
     全省各级调度室、地市局、保障中心有数千台监控大屏。如果每台大屏都维持 WebSocket 长连接，每个连接在服务端都需要占用内存和心跳线程。一旦突发全省告警风暴，服务端向几千台大屏同时推流，网络出网带宽会瞬间被打穿；
  2. **【合并防抖与削峰（Batching & Debounce）】**：
     电信告警每秒产生数百条，如果每来一条就通过 WebSocket 推送一次，前端 G6 图引擎会以每秒几十次的频率疯狂重绘，前端立刻发生严重掉帧卡死；
  3. **【架构权衡】**：
     采用“轻量 HTTP 轮询（带有 10～30 秒自适应节流）”不仅天然起到了**聚合防抖**的作用，使前端每次拉取到的是一个窗口内的稳定态汇总；而且 HTTP 请求能够完美借力 Nginx 与网关层面的负载均衡与静态缓存，架构鲁棒性远胜长连接推流。
