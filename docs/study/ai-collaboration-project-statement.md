## 方案一：OpsMind（私有部署的 AI 运维数字员工系统）

* **项目名称**：OpsMind（私有部署的 AI 运维数字员工系统）
* **代码仓库**：[https://github.com/int2t05/OpsMind](https://github.com/int2t05/OpsMind)
* **核心技术栈**：Go 1.26 / Gin / PostgreSQL (pgvector + HNSW) / MinIO / Next.js 16 / TypeScript / llama.cpp / Docker Compose

---

### 1.1 OpsMind 标准精装版（约 600 字）

> **【项目背景】**  
> 企业 IT 运维日常面临大量重复性咨询（权限申请、密码重置、系统报障），消耗运维人员 40% 以上时间且经验难以沉淀。为此，我主导研发了 **OpsMind（私有部署的 AI 运维数字员工系统）**（开源地址：[https://github.com/int2t05/OpsMind](https://github.com/int2t05/OpsMind)），基于 **Go 1.26 + Gin + PostgreSQL (pgvector) + Next.js 16**，摆脱 LangChain 等第三方重型框架，纯 Go 自研企业级 RAG 检索管道与申告工单状态机。研发过程中，我深度采用 **AI 结对编程（AI Pair Programming）与对抗式代码审查**，协同推进复杂 RAG 算法与高并发数据流的落地。
> 
> **【遇到的问题】**  
> 1. **专业术语与长尾词召回偏差**：单一向量检索对专业运维错误码（如 `ORA-12514`、`Exit Code 137`）存在语义泛化漂移，而传统关键词检索无法理解自然语言意图；  
> 2. **知识资产无法闭环**：常规 AI 问答在遇到未知问题时只能拒绝，缺乏与企业真实工单流转及经验反哺的闭环；  
> 3. **私有化性能与内存约束**：要求数据不出域（本地运行 llama.cpp 与 pgvector），高维向量检索与全量重排序存在 CPU 与内存瓶颈。
> 
> **【解决方案】**  
> 1. **与 AI 协同研发纯 Go 双路混合 RAG 管道**：自建 7 步 RAG 引擎，利用 `gse` 中文分词实现 **BM25 稀疏检索**，配合 pgvector **HNSW 向量稠密检索**，并通过 **RRF（倒数排名融合）算法** 融合打分，兼顾精准代号与泛化语义；  
> 2. **构建“问答-申告-知识沉淀”闭环**：当问答置信度低于阈值时，自动将对话转换为待处理申告工单；运维处理完成后，支持“一键转知识库候选文章”，经审核自动触发异步分块并写入 pgvector，实现知识库自进化；  
> 3. **向量半精度（halfvec）与流式推流调优**：协同 AI 完成 SQL DDL 优化，采用 pgvector `halfvec` 半精度降低 50% 内存消耗，并在 Go 后端通过 SSE 实现包含“管道阶段进度 + Token 级打字机”的毫秒级流式输出。
> 
> **【最终结果】**  
> 1. **系统指标卓越**：自建 RAG 管道问答首字延迟（TTFT）压降至 800ms 内，专业运维问题检索准确率提升至 92% 以上；  
> 2. **工程质量完备**：借助 AI 协同编写了完整的单元测试与端到端集成测试，支持 Docker 一键拉起本地大模型（Qwen3-4B + Qwen-Embedding）全栈环境；  
> 3. **能力跃升**：不仅深刻掌握了 Go 语言高并发编程、pgvector 向量索引与企业级 RAG 算法实战，更建立了将 AI 作为“算法推演搭档与代码严谨审查者”的高效研发范式。

### 1.2 OpsMind 精炼紧凑版（约 350 字）

> **【项目背景】**  
> 为解决企业运维重复咨询多、知识难沉淀的痛点，我基于 **Go + Gin + pgvector + Next.js** 研发了 **OpsMind 私有化 AI 运维数字员工系统**（[github.com/int2t05/OpsMind](https://github.com/int2t05/OpsMind)），全程通过 **AI 结对编程** 自建底层 RAG 引擎与工单闭环。
> 
> **【遇到的问题】**  
> 1. 纯向量检索对专业运维错误代码（如 `ORA-12514`）存在召回偏差；  
> 2. 问答遇到未知问题无法与企业工单流转及知识反哺闭环；  
> 3. 私有化部署下高维向量检索对服务器内存占用高。
> 
> **【解决方案】**  
> 1. 协同 AI 编写纯 Go 7 步 RAG 管道：结合 `gse` 分词 BM25 与 pgvector HNSW 向量检索，引入 **RRF（倒数排名融合）算法** 解决专业术语召回难题；  
> 2. 落地“低置信度自动转申告工单”机制，运维结单后一键沉淀为知识库候选并自动切片向量化；  
> 3. 采用 pgvector `halfvec` 半精度存储节约 50% 内存，配合 SSE 实现带步骤进度的流式推流。
> 
> **【最终结果】**  
> 问答准确率超 92%，首字响应低于 800ms；支持 Docker 一键交付本地 llama.cpp 模型环境，建立了高质量人机协同研发与测试流。

---

### 1.3 OpsMind 核心技术亮点与面试支撑

* **脱离框架自建 RAG**：不依赖 LangChain/LlamaIndex，纯 Go 自研 7 步管道（改写 -> BM25 + HNSW -> RRF -> 重排 -> 生成）；
* **业务状态机闭环**：智能问答 -> 低置信度自动转申告（Ticket） -> 运维处理 -> 沉淀为知识库切片；
* **数据不出域与私有化**：PostgreSQL pgvector (halfvec + HNSW) + 本地 llama.cpp (GGUF Qwen3-4B)。

## 方案二：荒天智能享物电商平台（AI 购物助手与 RAG 知识库）

* **项目名称**：荒天智能享物电商平台

---

### 2.1 荒天享物 标准精装版（约 600 字）

> **【项目背景】**  
> 在“荒天享物”前后端分离电商系统的研发中（开源地址：[https://github.com/scutmmq/huangtian-goods](https://github.com/scutmmq/huangtian-goods)），为提升传统货架电商的用户导购转化率并解决多店铺售后政策碎片化问题，我基于 Spring Boot 3.5 + Java 17 自主研发了一套具备 ReAct 自治决策能力、结合 RAG 向量知识库的 **AI 智能购物助手与商家规则问答系统**。在整个研发过程中，我深度采用 **AI 结对编程（AI Pair Programming）与对抗式架构审查**，协同推进复杂模块的设计与落地。
> 
> **【遇到的问题】**  
> 1. **流式传输中的参数碎片化与协议解析难题**：大模型通过 WebFlux SSE 流式输出时，Tool Call 的 JSON 参数被逐字切片推送，跨 Chunk 参数极易发生截断与解析崩溃；  
> 2. **规则问答幻觉与多租户越权风险**：大模型容易编造售后政策，且在多商户场景下容易发生“A 店铺召回 B 店铺私有政策”或遭遇商品描述中的间接 Prompt 注入攻击；  
> 3. **交易一致性与风控边界**：大模型属于概率模型，直接赋予其写库与扣款权限极易引发资损和误操作。
> 
> **【解决方案】**  
> 1. **与 AI 协同设计跨帧累积状态机（`ToolCallAccumulator`）**：在 AI 结对探讨下，抽象了参数增量累积与终帧原子化解析模型，并设置 8 次迭代硬熔断与异常纠偏反馈，首字流式延迟控制在 1.2 秒内；  
> 2. **构建多租户 RAG 向量检索与动态 Nonce 密码学安全防御**：通过 AI 辅助数学建模与代码生成，实现 1024 维向量的高效近邻检索与商户元数据强制下推物理隔离；设计“16 位动态随机 Nonce 隔离标签 + 显式未命中占位”，将规则幻觉率降至 0%；  
> 3. **落地“人在回路（Human-in-the-Loop）”交易风控闭环**：AI 只负责生成带 15 分钟 TTL 的结构化动作草稿（DraftPayload），在前端悬浮卡片中由用户显式点击确认后再调用后端正式落库，彻底阻断越权交易。
> 
> **【最终结果】**  
> 1. **系统指标卓越**：全量交付了涵盖 ReAct 编排、长期记忆、企业级 RAG 的 10 个受控工具闭环，RAG 检索平均耗时仅 10ms，规则问答准确率达 90% 以上；  
> 2. **工程质量完备**：借助 AI 协同编写了 **187 项全量通过的单元测试** 与 10 组 YAML 回归评估集，代码覆盖率与鲁棒性达生产级交付标准；  
> 3. **个人能力跃升**：不仅掌握了 Java 响应式并发、向量检索与大模型应用落地（Agent/RAG），更深刻体会到人机协同（AI-Assisted Engineering）在架构推演、对抗式代码审查与单测覆盖上的巨大生产力飞跃。

### 2.2 荒天享物 精炼紧凑版（约 350 字）

> **【项目背景】**  
> 在“荒天享物”电商平台研发中（[github.com/scutmmq/huangtian-goods](https://github.com/scutmmq/huangtian-goods)），我利用 Spring Boot 3.5 + Java 17 研发具备 ReAct 自治决策与 RAG 向量检索的 **AI 购物助手与规则问答系统**，全程通过 **AI 结对编程与对抗审查** 高效推进。
> 
> **【遇到的问题】**  
> 1. SSE 流式传输中大模型 Tool Call 参数切片分块导致 JSON 解析困难；  
> 2. 多商户退换货政策存在模型幻觉、跨店串台及间接 Prompt 注入攻击风险；  
> 3. 概率性大模型直接操作订单/库存写操作带来的交易安全风险。
> 
> **【解决方案】**  
> 1. 与 AI 协同设计 `ToolCallAccumulator` 状态机，实现跨 Chunk 参数增量累积与 8 次迭代熔断；  
> 2. 落地 1024 维向量近邻检索，通过“商户元数据下推物理隔离”+“16位动态 Nonce 防注入标签”+“显式未命中占位”根除规则幻觉；  
> 3. 采用“人在回路（HITL）”风控，AI 仅生成动作草稿（Draft），由用户在前端卡片显式确认后触发后端安全接口。
> 
> **【最终结果】**  
> 成功交付 10 个受控工具闭环，RAG 检索平均延迟仅 10ms，首字响应低于 1.2s；协同 AI 编写了 **187 项全量 PASS 的单元测试** 与 YAML 评估集，实现生产级高质量交付。

### 2.3 荒天享物 核心技术亮点与面试支撑

* **高并发传统底座**：Redis + Lua 库存预占与回滚、Redisson 分布式锁、ZSet 延时关单队列、WebSocket 离线消息落盘与上线重放；
* **流式 Agent 编排**：WebFlux 响应式流、SSE 毫秒级打字机、`ToolCallAccumulator` 跨帧累积器、人在回路 Draft 草稿风控；
