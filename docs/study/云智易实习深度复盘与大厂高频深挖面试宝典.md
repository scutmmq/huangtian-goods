## 二、物联微服务中台所用核心设计模式与工程落地

在面试中，如果面试官问及“**你在项目中用到了哪些设计模式？怎么落地的？**”，切忌背诵课本概念。以下是你代码库中**真实落地**的 5 大设计模式，直接拿出来讲，极具说服力：

### 1. 单例模式（Singleton Pattern）
- **落地类**：`FmKafkaListener`、`FmKafkaEventHandler`、`FmIdempotentManager`、`FmDeviceOperationManager`、`FmOperationHandlerManager`。
- **面试话术**：
  > “在 `yuexiu-rtu-xagent` 中，由于物联边缘代理服务需要常驻后台监听硬件消息，核心组件全部采用了**单例模式**：
  > - `FmKafkaListener` 采用饿汉/同步懒汉单例，保证全局只有一个后台守护线程 `fm-kafka-listener` 驱动 `KafkaConsumer` 实例，防止多线程并发抢占同一个未隔离的 Consumer 造成不可预期的位点冲突；
  > - `FmIdempotentManager` 单例内部维护了全局唯一的 `ConcurrentHashMap` 本地缓存，并在私有构造器中拉起名为 `fm-idempotent-cleanup` 的后台清理线程，严格保障每小时定时做过期剔除，避免重复创建线程导致句柄耗尽。”

### 2. 策略模式 + 注册表模式（Strategy + Registry Pattern）
- **落地类**：`FmOperationHandler` 接口与 `FmOperationHandlerManager` 管理器。
- **面试话术**：
  > “在处理 Kafka 接收到的资产变更消息时，外部操作类型繁多（`ADD` 新增设备、`EDIT` 修改属性、`DEL` 删除设备、`ADD_CHILD` 挂载子设备、`DEL_CHILD` 解绑子设备）。
  > 传统的写法是几百行混乱的 `switch-case` 或 `if-else`，可维护性极差。我采用了**策略模式**：
  > - 定义统一的 `FmOperationHandler` 接口，暴露 `handle(FmDeviceData)` 与 `getSupportedOpType()` 方法；
  > - 分别实现 `FmAddOperationHandler`、`FmEditOperationHandler`、`FmDelOperationHandler` 等独立策略类；
  > - 在 `FmOperationHandlerManager` 中利用 `Map<String, FmOperationHandler>` 建立操作类型到策略实现的注册表。当新事件到来时直接通过 `opType` 动态分发。这不仅消除了嵌套分支，而且后续新增物联操作时只需扩展新的 Handler 类，严格遵循**开闭原则（OCP）**。”

### 3. 状态机模式（State / State Machine Pattern）
- **落地类**：访客生命周期状态流转、RTU 同步状态机与设备拓扑判定机。
- **面试话术**：
  > “物联业务有极其严格的状态流转约束，我们在多个模块应用了**状态机思想**：
  > 1. **访客通行状态机**：严格按照 `预约待审(1) -> 审核通过待到访(5) -> 通行激活中(6) -> 已到访完成(7) -> 超时作废(4)` 驱动。定时任务 `VisitorRecordUpdateStatusTask` 依据 `plan_end_time` 和当前状态精准推动逆向作废状态机；
  > 2. **设备拓扑推断状态机**：在 `determineDeviceType` 中，依据外部数据的 `deviceTag`（gateway/device）与 `parentDeviceCode` 是否为空，结合容错逻辑推断设备是属于 `RTU` 网关还是 `COLLECTION_DEVICE` 采集设备；
  > 3. **台账同步状态机**：维护全量/手动同步的状态（`IDLE -> RUNNING -> COMPLETED / FAILED`），在多线程和手动触发时防止重入冲突，并实时记录同步失败计数。”

### 4. 适配器 / 转换器模式（Adapter / Converter Pattern）
- **落地类**：`FmDeviceConverter.java`。
- **面试话术**：
  > “越秀外部资产 FM 系统推送的 JSON 结构与云智易物联平台底层的 `DRTU`、`DCollectionDevice` 数据结构差异极大（字段命名不统一、空间结构嵌套层级不同）。
  > 我设计了 `FmDeviceConverter` 转换器层，先将非标的原始数据转换为系统内部标准的 `FmDeviceDTO`，再适配组装为物联平台需要的空间配置 JSON。这种**防腐层（Anticorruption Layer）**设计，使外部系统的数据模型变动被死死隔绝在 Converter 内部，上层业务核心逻辑无需改动一行。”

### 5. 建造者模式（Builder Pattern）
- **落地类**：Guava 本地缓存流式配置（`CacheBuilder.newBuilder().maximumSize(5000).expireAfterWrite(5, TimeUnit.MINUTES).recordStats().build()`）。

### 3. Kafka 消费链路可靠性治理
- **面试官提问**：“你们 Kafka 消费链路做了哪些可靠性治理？解决了什么风险？”
- **1 分钟标准应答**：
  > “**【背景痛点】**：台账同步对设备数据的准确性要求极高。原消费链路存在‘重复消费导致脏数据’、‘偶发异常丢消息’以及‘某条格式错误的消息卡死整个分区’三类生产风险。
  > **【核心治理】**：
  > 1. **自主封装原生 KafkaConsumer 循环**：废弃简单注解，按 `TopicPartition` 逐分区严格有序拉取，业务处理成功后手动执行单步 `commitSync(offset + 1)`，守住 At-Least-Once 底线；
  > 2. **Seek 位点回拨自愈与队头防阻塞**：单条消息处理失败时，通过 `consumer.seek(partition, offset)` 精准回拨该分区位点重试；当同一消息达到 3 次最大重试后，强制打印错误日志、提交 offset 越过毒丸，杜绝队头阻塞；
  > 3. **双层原子幂等**：设计‘本地 ConcurrentHashMap 内存快速过滤（带后台清理）+ MongoDB 唯一索引原子兜底’，并在批次部分失败时支持逆向删除幂等记录重试。
  > **【结果】**：线上台账同步消息零丢失、零脏数据，服务稳定运行至今。”

### 4. 线上接口响应慢定位与优化
- **面试官提问**：“你简历上写的‘线上接口响应慢排查’，具体指的是哪个接口？排查思路是什么？”
- **1 分钟标准应答**：
  > “**【真实案例】**：我们重点攻坚了两个核心瓶颈：一是**二维码权限下发接口耗时 38 秒**，二是**访客记录分页查询 `/queryVisitorRecord` 耗时 30 秒**。
  > **【排查方法论】**：
  > 1. **日志时间戳分段追踪**：在二维码接口中，通过打印关键步骤毫秒差，抓到了中间长达 18 秒的静默，深入代码锁定了 59 台设备引发的 **3 处致命 N+1 数据库往返**；
  > 2. **PostgreSQL 内核指标与执行计划分析**：针对分页慢查询，利用 `EXPLAIN (ANALYZE, BUFFERS)` 发现查询走了全表顺序扫描与外部文件排序，并在 `pg_stat_activity` 捕获到大量 `DataFileRead` 物理磁盘读等待。
  > **【治理落地】**：
  > 通过单批次 `insertBatch` 内存映射消灭 N+1；将复杂 SQL 伪条件改写，并使用 `CREATE INDEX CONCURRENTLY` 在生产无锁创建复合索引。
  > **【成效】**：二维码接口从 38s 降至 <7s，分页查询从 30s 降至 2.8s，性能提升超 80%。”

### 4.3 Kafka 消费链路可靠性治理：原生驱动与双层幂等防竞态

#### 追问 1：你在 `FmIdempotentManager` 里先查本地 ConcurrentHashMap，再去插 MongoDB，这在高并发下难道没有“竞态条件（Race Condition）”吗？你是怎么解决的？
- **破局回答（直击 Git 提交 `c9ddd4d` 核心！）**：
  > “面试官您看得很准！早期未重构的代码中，确实存在 `isProcessed(eventId)` 先查询、后插入的两阶段非原子缺陷。在并发场景下，两个线程同时判定不存在，随后同时进入业务处理，造成了幂等穿透！
  > 在我的提交 `c9ddd4d` 中，我彻底重构了该逻辑，核心就是**消除检查与写入的时间窗口，改用原子操作**：
  > 1. **废弃单纯查询**：将原本的 `isProcessed` 标记为 `@Deprecated`，新写了原子方法 `tryMarkProcessed(eventId)`；
  > 2. **利用数据库唯一索引实现原子占位**：本地缓存仅作为‘已存在时的快速跳出通道’；若未命中，不执行 SELECT，而是**直接执行 `FmIdempotentDao.insertIfAbsent(record)`**！
  > 3. **捕获底层唯一索引异常**：MongoDB 在并发插入相同 `eventId` 时，内核底层通过唯一索引保证只能有 1 个成功，第 2 个并发写入必抛出 `MongoWriteException`（错误码 `11000 Duplicate Key`）。我捕获该异常并返回 `false`，从而在硬件内核层彻底根除了竞态条件！”

#### 追问 2：如果一个 Kafka 分区里有 100 条消息，第 50 条消息消费报错了，你调用了 `consumer.seek(partition, 50)`，那拉出来的批次里第 51 到 100 条消息会怎么样？
- **破局回答**：
  > “这正是我们在 `FmKafkaListener` 循环里严格设计的细节！
  > 1. **当第 50 条报错并触发 Seek 时**：我们当前的分区内循环是立即 `break` 终止的，**第 51 到 100 条在当前批次中坚决不继续向下处理**！
  > 2. **位点提交保障**：前 49 条已处理成功的消息，其位点已经在每条成功时通过 `commitSync(offset + 1)` 提交至 Broker（提交到了 50）；
  > 3. **Seek 的本质**：`consumer.seek(partition, 50)` 实际上是将客户端内存中该分区的 Fetch Position 强制重置回 50。当下一次循环调用 `consumer.poll()` 时，Broker 返回给我们的第一条消息就是 offset 50；
  > 4. **避免乱序**：如果不 break 强行继续处理 51～100 条，一旦 51 条成功并提交了 52 的 offset，那么第 50 条消息就会被 Broker 永久跳过，造成**彻底丢消息（Message Loss）**！因此遇到异常必须单分区立即挂起并回拨重试。”

### 4.4 线上接口响应慢定位与优化：N+1 消除与 PostgreSQL 调优

#### 追问 1：在 PostgreSQL 生产环境下，为什么必须用 `CREATE INDEX CONCURRENTLY`？它内部的实现原理是什么？有什么副作用？
- **破局回答**：
  > “**【锁冲突原理】**：
  > - 默认的 `CREATE INDEX` 会对表加 `SHARE` 锁。而在线业务执行 `INSERT` / `UPDATE` / `DELETE` 需要申请 `ROW EXCLUSIVE` 锁，这两者是**完全互斥**的。在几千万行的大表上，常规建索引耗时数分钟，整张表的在线写入就会被全部卡死，连接池瞬间打满导致雪崩；
  > **【CONCURRENTLY 实现原理】**：
  > - `CONCURRENTLY` 仅申请最低级的 `SHARE UPDATE EXCLUSIVE` 锁，该锁与写入事务完全兼容，**生产读写完全零阻塞**；
  > - 它的底层分**两个独立阶段**：第一阶段扫描表构建索引元数据；第二阶段等待所有在第一阶段之前开启的事务全部提交后，再次扫描表补齐增量数据。
  > **【代价与副作用】**：
  > 1. 构建耗时是普通建索引的 2～3 倍，且更耗 CPU；
  > 2. 如果建索引过程中发生网络闪断或唯一键冲突，索引会残留并被标记为 `INVALID`。因此上线脚本必须配套检查 `pg_index.indisvalid`，若失效需先 `DROP INDEX CONCURRENTLY` 再重新执行。”

#### 追问 2：你们是怎么消除 `VisitorRecordServiceImpl` 里的 N+1 查询的？代码是怎么写的？
- **破局回答**：
  > “原先的代码逻辑是分页查出 20 条访客记录后，写了一个 `for (VisitorRecord r : records)` 循环，在循环体内调用 `personService.getPersonName(r.getAuthId())`。20 条记录就向数据库发起 20 次独立 SELECT，网络往返（RTT）耗费近 2 秒！
  > **重构为标准三步法**：
  > 1. **提取唯一键集合**：
  >    ```java
  >    Set<String> authIds = records.stream()
  >        .map(VisitorRecord::getAuthId)
  >        .filter(StringUtils::isNotBlank)
  >        .collect(Collectors.toSet());
  >    ```
  > 2. **单次批量 IN 查询**：
  >    `List<Person> persons = personService.selectBatchIds(authIds);` 一次网络请求拉回所有人员实体；
  > 3. **内存 Map 投影与回填**：
  >    在 JVM 内存中构建 `Map<String, String> nameMap = persons.stream().collect(Collectors.toMap(Person::getId, Person::getName))`，最后在原循环中直接从 Map 里 `O(1)` 取值回填。20 次网络往返瞬间削减为 1 次！”

  2. **【执行机制】**：内存维护 `retryCountMap`（Key: partition-offset），重试 <3 次通过 `consumer.seek(partition, offset)` 回拨；
  3. **【熔断自愈】**：重试达到 3 次，输出 ERROR 级全量 Payload 日志，强制提交 offset+1 越过毒丸；
  4. **【收益】**：既保障偶发异常能自动重试修复，又坚决防止坏消息彻底堵死整个消费分区的后续所有业务。

### Q4: 详细讲讲双层幂等（`FmIdempotentManager`）的设计细节？
- **满分回答模板**：
  1. **【架构分层】**：L1 本地内存快速路径（`ConcurrentHashMap`） + L2 持久化原子兜底（MongoDB 唯一索引）；
  2. **【L1 防泄漏】**：内存缓存设置 24 小时 TTL，通过私有构造函数拉起后台单守护线程每小时批量清理过期 key；
  3. **【L2 原子操作】**：废弃 `isProcessed`，直接使用 `insertIfAbsent` 原子占位，捕获错误码 11000 判定重复；
  4. **【容错哲学】**：遇到非冲突类数据库异常向上抛出触发 Kafka 重试，坚持“宁可重复消费，绝不丢失数据”。

### Q5: Kafka 批次包含 5 台设备，前 2 台成功第 3 台失败，如何保障事务与幂等？
- **满分回答模板**：
  1. **【单设备隔离】**：循环处理单台设备，`try-catch` 隔离异常，记录失败设备编码，不阻断后续处理；
  2. **【逆向补偿】**：遍历结束发现有失败设备，调用 `deleteProcessedMark(eventId)` **先删 Mongo 再删本地缓存**，解除幂等占位；
  3. **【抛出重试】**：向上抛错阻止位点提交，触发 `consumer.seek` 回退整条消息；
  4. **【幂等吸纳】**：下次重试时，已成功的设备通过底层 `upsertDevice` 幂等更新状态不变，失败的设备获得重新修复。

### Q6: 为什么删除采集设备时，必须“先断 MQTT，再调 IoT 平台，最后删本地 DB”？
- **满分回答模板**：
  1. **【核心原则】**：先断输入源、再注销凭证、最后清理本体；
  2. **【反证分析】**：若先删本地 DB，长连接未断的硬件设备下一秒继续上报数据，服务因查不到元数据会抛出大量 NPE 脏数据；
  3. **【长连接治理】**：先调 `MqttClientManager.offline` 踢设备下线切断数据流，再注销平台三元组凭证，最后删数据库；
  4. **【异常防御】**：前两步均用 try-catch 包裹，外部接口偶发报错不阻断本地最终清理。

### Q7: 为什么全量同步要用预构建的 `FmSpaceIdMapping`，增量同步用单设备实时查询？
- **满分回答模板**：
  1. **【核心定性】**：高吞吐批处理（以空间换时间） vs 低延迟流处理（按需懒加载）的经典权衡；
  2. **【全量批处理】**：数万台设备如果逐台 RPC 查空间中台，将产生数十万次网络往返，打爆连接池；预热拉取整树扁平映射，实现全内存 `O(1)` 比对；
  3. **【增量流处理】**：增量每次推送仅个别设备，按需查询只查涉及的楼层，避免频繁拉取全量树造成网络与内存浪费。

### Q8: 二维码权限下发 38 秒的问题怎么排查出来的？怎么优化的？
- **满分回答模板**：
  1. **【排查定位】**：通过关键步骤时间戳日志比对，发现保存二维码后静默 18 秒，响应后更新耗时 13.5 秒；
  2. **【三大根因】**：59 台设备引发 59 次独立 SELECT 查设备（8.9s） + 59 次单条 INSERT 权限（8.9s） + 59 次单条 UPDATE 状态（13.5s），共 177 次数据库往返；
  3. **【批量重构】**：1 次批量查询所有设备并在内存建立 Map 映射 + `insertBatch` 批量提交 + 分组批量更新；
  4. **【收益】**：177 次往返缩减为 3 次，本地耗时从 31.3s 降至 <0.8s，接口总耗时从 38s 降至 6.8s（6s 为外部海康硬件网络开销）。

### Q9: 骑手认证为什么用 Guava 本地缓存而不用 Redis？怎么防 OOM 和穿透？
- **满分回答模板**：
  1. **【技术权衡】**：午高峰 100 QPS 下每秒 200 次 RSA 2048 位加密，极度消耗 CPU（200～500ms/s）。Redis 引入 1～2ms 网络往返与连接池竞争；
  2. **【容量评估】**：手机号加密串缓存 5000 条仅占 **1.5MB** 堆内存，内存读取只需 0.01ms，午高峰命中率 30%～50%，削减 40% CPU 负载；
  3. **【防 OOM】**：配置 `maximumSize(5000)` + `expireAfterWrite(5, MINUTES)`，利用 LRU 驱逐保证内存绝对有界；
  4. **【安全红线】**：美团与淘宝公钥和 Base64 规则不同，缓存实例严格物理隔离；地理围栏涉及安防红线，坚决不缓存，必须实时计算。

### Q10: 生产多容器部署时，定时任务出现并发冲突和数据库 IO 飙高怎么解决？
- **满分回答模板**：
  1. **【核心根因】**：K8s 多 Pod 集群下未加分布式控制引发的**惊群效应（Thundering Herd）**，多节点同时全表扫描；
  2. **【互斥收敛】**：非实时任务引入 Redis 分布式锁，同一时间仅允许 1 个 Pod 获得执行权；
  3. **【滑动窗口】**：访客状态任务增加 14 天滑动窗口过滤，历史全表千万级扫描降到不足 1 万条，过滤 99% 冷数据；
  4. **【削峰限速】**：单页分页设为 1000，批次间休眠 50ms 缓冲数据库 IO，凌晨 2:30 设立独立补偿任务处理历史冷数据。

### Q11: `/queryVisitorRecord` 接口从 30 秒优化至 5 秒内，具体做了哪三件事？
- **满分回答模板**：
  1. **【消灭 N+1】**：分页查出 20 条记录后，由循环逐条调接口查人名改为提取 `authId` 集合一次批量 IN 查询，内存 Map 回填；
  2. **【Mapper SQL 重写】**：三表 UNION ALL 清理冗余字段，将极其不规范的伪分支条件 `pk_id='1'` 重写为常量假条件 `1=0`，降低优化器代价；
  3. **【生产无锁索引】**：针对三张表基于 `(project_id, update_time DESC, pk_id)` 采用 `CREATE INDEX CONCURRENTLY` 在线无锁建索引，并执行 `ANALYZE` 刷新统计信息；

### Q12: 线上 PostgreSQL 出现 `DataFileRead` 和 `WALWriteLock` 等待，怎么排查解决？
- **满分回答模板**：
  1. **【指标捕获】**：`pg_stat_activity` 筛选 `wait_event_type = 'IO'`，锁定发生物理读和刷盘锁竞争的 query；
  2. **【排查 DataFileRead】**：通过 `EXPLAIN (ANALYZE, BUFFERS)` 确认大量 `shared read` 全表扫描，补充匹配的高选择性复合索引，转变为内存命中（`shared hit`）；
  3. **【排查 WALWriteLock】**：排查出大表清理任务单次大事务 DELETE 5 万条产生海量 WAL 刷盘竞争，拆解为每次 1000 条小批量分批删除提交，锁争用彻底消除。

### Q13: 在生产环境给千万级大表加索引有什么风险？你们怎么加的？
- **满分回答模板**：
  1. **【生产风险】**：默认 `CREATE INDEX` 申请 `SHARE` 锁，与在线业务写入申请的 `ROW EXCLUSIVE` 锁强冲突，建索引期间整张表写入全部卡死，连接池雪崩；
  2. **【标准操作】**：必须使用 `CREATE INDEX CONCURRENTLY idx_name ON table (col)` 在线无锁创建；
  3. **【代价与验证】**：耗时更长且经历两次表扫描，建完后必须查询 `pg_index.indisvalid` 验证是否为有效索引；
  4. **【刷新统计】**：执行 `ANALYZE table;` 确保优化器立刻获知最新分布直方图。
