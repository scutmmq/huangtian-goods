### 2.2 存储选型哲学：为什么同时使用 PG + MongoDB + Redis + Kafka？
面试官极其喜欢考察候选人对**多存储异构选型（Polyglot Persistence）**的理解：
1. **PostgreSQL（关系与业务强一致的核心基石）**：
   - **职责**：存储智慧通行、访客记录（`tb_visitor`、`tb_visitor_record`）、人员组织（`tb_person`、`tb_org`）与门禁权限（`tb_auth_record`）。
   - **选型原因**：C 端业务涉及人员隐私与门禁通行权限，对事务 ACID、外键约束、悲观/乐观并发控制要求极高；支持通过 `CREATE INDEX CONCURRENTLY` 在线无锁优化复杂查询。
2. **MongoDB（海量异构物模型与设备台账的敏捷载体）**：
   - **职责**：在 `yuexiu-rtu-xagent` 中存储数万台 RTU 边缘网关台账、下属采集设备参数、以及 `FmIdempotentRecord` 全局幂等记录。
   - **选型原因**：物联网设备的物模型属性极其异构（温湿度传感器、电表、水表的参数定义千差万别），关系型数据库频繁 ALTER TABLE 加字段是灾难。MongoDB 的 Document 模式天然支持动态 schema；同时其对单字段的 Unique Index（唯一索引）在超高写入并发下具备极高的原子排他性能。
3. **Redis（分布式协调、频控与极速内存缓冲）**：
   - **职责**：
     - 分布式互斥锁：防止全量同步重入与 Kubernetes 多 Pod 集群定时任务的“惊群效应”；
     - 抽帧冷却时间戳：维护 `ai:capture:last:{pointId}:{configId}`，执行毫秒级过期频控；
     - 通行流水准实时计数聚合缓冲区。
4. **Kafka（高吞吐异步解耦与削峰填谷）**：
   - **职责**：承接上游资产管理中台（FM）推送的数万台设备资产变更事件。
   - **选型原因**：资产系统可能一次性批量推送成千上万条设备变更，Kafka 的高吞吐日志模型能完美起到蓄水池削峰作用；其基于 Partition 的分区模型能够天然保障同分区消息严格有序。

### 2.3 硬件边缘感知与 Netty TCP 工业级服务端架构（Pipeline 6 层机制）
虽然你的核心任务在台账同步与业务中台，但作为团队核心研发，你对底层的 `RTUServer` 网络层了如指掌：
- 越秀 RTU 硬件设备通过 TCP 端口接入系统，系统底层基于 **Netty 4** 搭建了高并发非阻塞 NIO 服务端，设计了经典的 **6 层 ChannelPipeline 工业级处理流水线**：
  1. `IdleStateHandler`（空闲连接检测）：配置 10 分钟读超时。若硬件 10 分钟无心跳或上行数据，自动触发空闲事件，主动剔除死链接，释放 Socket 文件句柄；
  2. `LengthFieldBasedFrameDecoder`（定长帧解码器）：采用**小端字节序（LITTLE_ENDIAN）**，根据报文头部长度字段自动切分完整数据包，彻底根除 TCP 底层的**粘包与拆包（TCP Sticky / Fragmented Packets）**问题；
  3. `RtuMessageDecoder`（协议解码器）：将二进制字节流（ByteBuf）解析为 Java 内存中的强类型 `RtuMessage` 领域对象；
  4. `ConnectionHandler`（连接生命周期管理）：监听 `channelActive` 与 `channelInactive`，在内存中维护设备 MAC 与 Channel 映射，实时统计全网活跃连接数；
  5. `IdleStateEventHandler`（空闲事件处理器）：捕获读超时事件并安全调用 `ctx.close()` 实施优雅断开；
  6. `RtuMessageHandler`（业务分发处理器）：将解码后的 RTU 遥测报文分发至业务线程池，驱动 Modbus 寄存器解析与指标持久化。

### 2.4 外部生态协同：海康威视、招商云、阿里 IoT、美团/淘宝契约防腐层
在物联网微服务中，大量业务需要与外部第三方异构系统打交道，我们建立了完善的**防腐层（Anticorruption Layer）与防御性契约设计**：
- **海康威视（Hikvision OpenAPI）**：对接海康门禁与安防平台，通过 `AuthDownloadUtils` 屏蔽海康私有设备协议。针对其硬件下发可能存在的长耗时（约 6 秒），主干业务采用批量收集与异步处理，避免上层 HTTP 连接长时间挂起；

// 核心源码：FmIdempotentManager.java
public class FmIdempotentManager {
    private static final FmIdempotentManager INSTANCE = new FmIdempotentManager();
    private final ConcurrentHashMap<String, Long> processedEvents = new ConcurrentHashMap<>();
    private static final long CACHE_EXPIRE_TIME = 24 * 60 * 60 * 1000L; // 24小时过期

    private FmIdempotentManager() {
        startCleanupTask(); // 构造时启动后台单守护清理线程
    }

    public static FmIdempotentManager getInstance() {
        return INSTANCE;
    }

    private void startCleanupTask() {
        Thread cleanupThread = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                try {
                    Thread.sleep(60 * 60 * 1000L); // 每小时执行一次
                    long expiredThreshold = System.currentTimeMillis() - CACHE_EXPIRE_TIME;
                    processedEvents.entrySet().removeIf(entry -> entry.getValue() < expiredThreshold);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
        });
        cleanupThread.setDaemon(true);
        cleanupThread.setName("fm-idempotent-cleanup");
        cleanupThread.start();
    }
}

1. **组合拳一：多级缓存与动静分离（消灭 CPU 密集型计算）**：

2. **组合拳二：异步化解耦与削峰填谷**：

3. **组合拳三：批量化（Batching）与网络往返消灭战**：

4. **组合拳四：定时任务削峰与滑动窗口剪枝（防堆叠）**：

5. **组合拳五：生产在线无锁索引保障高并发写入**：
   - 高并发下最忌讳死锁与阻塞。针对核心访客表通过 `CREATE INDEX CONCURRENTLY` 创建覆盖复合索引，完全不阻塞在线高并发写入，执行耗时从 30 秒降至 2.8 秒。

### 4.3 分布式环境下数据一致性立体防御体系
在跨边缘网关、物联中台、第三方外卖平台与数据库的复杂链路上，如何做到数据不乱、不重、不丢？
1. **最终一致性与逆向补偿机制（Compensating Action）**：
   - 在 Kafka 批次同步中，若出现部分设备成功、个别设备挂载失败，系统绝不提交位点；
   - 严格遵循**逆向补偿时序**：调用 `deleteProcessedMark` 先删 MongoDB 持久层幂等记录，再删本地 ConcurrentHashMap 内存标记，然后抛出异常触发 `consumer.seek` 回滚位点；
   - 下次重试时，已成功的设备通过 `upsertDevice` 幂等更新保持不变，失败的设备获得自愈修复，实现分布式最终一致性。
2. **分布式排他与集群防惊群**：
   - 针对非实时数据治理任务与全量设备同步，统一引入带有自动租约续期的 **Redis 分布式锁**，确保在 Kubernetes 多 Pod 容器部署环境下，同一时刻只有一个节点在执行重度任务，杜绝数据被重复消费或并发覆写。
3. **存储层原子唯一约束双保险兜底**：
   - **关系库层面**：PostgreSQL 通行记录表 `tb_pass_record` 对 `(device_name, pass_time, visitor_id)` 建立联合唯一索引，海康硬件网络重发直接被内核级幂等拦截；
   - **文档库层面**：MongoDB `fm_idempotent_record` 对 `eventId` 建立全局唯一索引，并发插入通过错误码 `11000 DuplicateKeyException` 实现严格的单原子胜出。
4. **硬件设备生命周期有序注销**：
   - 删除采集设备时，严格遵循**“先断 MQTT 长连接踢下线 $\to$ 再调物联平台注销凭证 $\to$ 最后清理本地数据库”**，杜绝产生硬件长连接僵尸通道与孤儿上报数据。

### 6.3 Kafka 消费链路可靠性治理：原生驱动与双层幂等防竞态

#### 追问 1：你在 `FmIdempotentManager` 里先查本地 ConcurrentHashMap，再去插 MongoDB，这在高并发下难道没有“竞态条件（Race Condition）”吗？你是怎么解决的？
- **破局回答（直击 Git 提交 `c9ddd4d` 核心！）**：
  > “面试官您看得很准！早期未重构的代码中，确实存在 `isProcessed(eventId)` 先查询、后插入的两阶段非原子缺陷。在并发场景下，两个线程同时判定不存在，随后同时进入业务处理，造成了幂等穿透！
  > 在我的提交 `c9ddd4d` 中，我彻底重构了该逻辑，核心就是**消除检查与写入的时间窗口，改用原子操作**：
  > 1. **废弃单纯查询**：将原本的 `isProcessed` 标记为 `@Deprecated`，新写了原子方法 `tryMarkProcessed(eventId)`；
  > 2. **利用数据库唯一索引实现原子占位**：本地缓存仅作为‘已存在时的快速跳出通道’；若未命中，不执行 SELECT，而是**直接执行 `FmIdempotentDao.insertIfAbsent(record)`**！
  > 3. **捕获底层唯一索引异常**：MongoDB 在并发插入相同 `eventId` 时，内核底层通过唯一索引保证只能有 1 个成功，第 2 个并发写入必抛出 `MongoWriteException`（错误码 `11000 Duplicate Key`）。我捕获该异常并返回 `false`，从而在硬件内核层彻底根除了竞态条件！”

#### 追问 2：如果一个 Kafka 分区里有 100 条消息，第 50 条消息消费报错了，你调用了 `consumer.seek(partition, 50)`，那拉出来的批次里第 51 到 100 条消息会怎么样？
- **破局回答**：
  > “这正是我们在 `FmKafkaListener` 循环里严格设计的细节！
  > 1. **当第 50 条报错并触发 Seek 时**：我们当前的分区内循环是立即 `break` 终止的，**第 51 到 100 条在当前批次中坚决不继续向下处理**！
  > 2. **位点提交保障**：前 49 条已处理成功的消息，其位点已经在每条成功时通过 `commitSync(offset + 1)` 提交至 Broker（提交到了 50）；
  > 3. **Seek 的本质**：`consumer.seek(partition, 50)` 实际上是将客户端内存中该分区的 Fetch Position 强制重置回 50。当下一次循环调用 `consumer.poll()` 时，Broker 返回给我们的第一条消息就是 offset 50；
  > 4. **避免乱序**：如果不 break 强行继续处理 51～100 条，一旦 51 条成功并提交了 52 的 offset，那么第 50 条消息就会被 Broker 永久跳过，造成**彻底丢消息（Message Loss）**！因此遇到异常必须单分区立即挂起并回拨重试。”

### 6.4 线上接口响应慢定位与优化：N+1 消除与 PostgreSQL 调优

#### 追问 1：在 PostgreSQL 生产环境下，为什么必须用 `CREATE INDEX CONCURRENTLY`？它内部的实现原理是什么？有什么副作用？
- **破局回答**：
  > “**【锁冲突原理】**：
  > - 默认的 `CREATE INDEX` 会对表加 `SHARE` 锁。而在线业务执行 `INSERT` / `UPDATE` / `DELETE` 需要申请 `ROW EXCLUSIVE` 锁，这两者是**完全互斥**的。在几千万行的大表上，常规建索引耗时数分钟，整张表的在线写入就会被全部卡死，连接池瞬间打满导致雪崩；
  > **【CONCURRENTLY 实现原理】**：
  > - `CONCURRENTLY` 仅申请最低级的 `SHARE UPDATE EXCLUSIVE` 锁，该锁与写入事务完全兼容，**生产读写完全零阻塞**；
  > - 它的底层分**两个独立阶段**：第一阶段扫描表构建索引元数据；第二阶段等待所有在第一阶段之前开启的事务全部提交后，再次扫描表补齐增量数据。
  > **【代价与副作用】**：
  > 1. 构建耗时是普通建索引的 2～3 倍，且更耗 CPU；
  > 2. 如果建索引过程中发生网络闪断或唯一键冲突，索引会残留并被标记为 `INVALID`。因此上线脚本必须配套检查 `pg_index.indisvalid`，若失效需先 `DROP INDEX CONCURRENTLY` 再重新执行。”

#### 追问 2：你们是怎么消除 `VisitorRecordServiceImpl` 里的 N+1 查询的？代码是怎么写的？
- **破局回答**：
  > “原先的代码逻辑是分页查出 20 条访客记录后，写了一个 `for (VisitorRecord r : records)` 循环，在循环体内调用 `personService.getPersonName(r.getAuthId())`。20 条记录就向数据库发起 20 次独立 SELECT，网络往返（RTT）耗费近 2 秒！
  > **重构为标准三步法**：
  > 1. **提取唯一键集合**：
  >    ```java
  >    Set<String> authIds = records.stream()
  >        .map(VisitorRecord::getAuthId)
  >        .filter(StringUtils::isNotBlank)
  >        .collect(Collectors.toSet());
  >    ```
  > 2. **单次批量 IN 查询**：
  >    `List<Person> persons = personService.selectBatchIds(authIds);` 一次网络请求拉回所有人员实体；
  > 3. **内存 Map 投影与回填**：
  >    在 JVM 内存中构建 `Map<String, String> nameMap = persons.stream().collect(Collectors.toMap(Person::getId, Person::getName))`，最后在原循环中直接从 Map 里 `O(1)` 取值回填。20 次网络往返瞬间削减为 1 次！”

### 地狱拷问 1：早高峰 10 万住户同时刷码开门，你的系统哪个环节先挂？怎么扛？

- **满分反杀**：
  > 1. **【瓶颈预判：最先挂的一定是‘外部硬件中台 HTTP 往返’与‘数据库连接池’】**：

  3. **【防线二：通行流水异步延时落盘】**：
     刷卡/刷码记录由闸机异步批量回传，进入服务端的通行流水直接写入 Kafka 或 Redis List 缓冲，异步批次写入 PostgreSQL，主链路实现 100% 纯内存低延迟放行；
  4. **【极端降级】**：若遇到园区大断网，门禁闸机自动降级为‘白名单脱机离线开闸’，网络恢复后再通过断点续传补偿上行数据。

### 地狱拷问 2：Kafka 单线程消费太慢导致消息积压怎么办？为什么不用多线程？多线程怎么保序？
- **面试官施压**：“你在 `FmKafkaListener` 里用单个守护线程拉取并单条消费。如果资产系统一下子推了 10 万台设备，你的单线程消费发生严重积压怎么办？为什么不用多线程并发消费？多线程下怎么保证同设备消息的顺序性？”
- **满分反杀**：
  > 1. **【单线程的合理性权衡】**：
     首先澄清，我们的单线程是针对当前实例而言的，Kafka 天然通过横向扩展**分区分片（Partitions）**来实现集群并行吞吐。一个 Topic 划分为 8 个分区，起 8 个 Pod 实例即可达到 8 节点水平并行；
  2. **【单容器内多线程保序重构方案】**：
     若单 Pod 内部需要进一步压榨 CPU 性能，传统的 `ExecutorService` 无脑并发会导致同设备的 ADD 和 DEL 乱序交错！标准解法是**‘内存 Hash 路由环’**：
     - 在拉取到批次消息后，根据设备唯一编码 `deviceCode.hashCode() % N`，将消息精准路由到固定的 N 个内部单线程内存队列（`BlockingQueue`）中；
     - 保证同一台设备的所有操作严格由同一个 Worker 线程串行执行；
     - 提交位点时，设计全局位点跟踪器（Sliding Window Offset Tracker），只有当某位点之前的所有并发任务全部完成后，才向 Broker 推进提交，杜绝乱序与位点超前。

### 地狱拷问 3：双层幂等逆向补偿时，先删 Mongo 再删本地缓存，中间并发插入脏读怎么办？
- **面试官施压**：“你提到批次内有设备失败时，调用 `deleteProcessedMark` 先删 MongoDB 记录再删本地内存。如果在删完 Mongo、但还没删本地内存的这个微小毫秒窗口内，Kafka 刚好重发了这条消息并被另一个线程拉到，会发生什么？会不会把本来应该重试的设备给跳过了？”
- **满分反杀**：
  > 1. **【精准分析时间窗口】**：
     面试官您指出的这个边界非常尖锐！如果在删完 Mongo 但未删本地缓存时，另一个并发请求进来，该请求会命中本地缓存从而返回‘已处理’跳过，确实存在漏处理的风险；
  2. **【防线一：Kafka 分区串行锁定了消息并发】**：
     在架构层面上，同一条消息（同 partition）的重试是在**同一个单线程循环内**通过 `seek` 顺序发起的，当前线程抛出异常触发重试前，当前消费线程根本还没发起下一次 `poll`，因此当前实例绝对不可能有并发线程在消费同一条消息；
  3. **【防线二：多实例再平衡（Rebalance）极端防御】**：
     如果恰好发生集群 Rebalance，消息被漂移到了实例 B：由于实例 B 根本没有实例 A 的本地内存缓存，它会直接查 MongoDB。而此时 MongoDB 已经被实例 A 删除了！所以实例 B 依然能正常执行插入并完成重试；
  4. **【终极改进方案】**：若要实现理论上的零缝隙，可以在调用删除前，将本地缓存的状态置为一个特殊的过渡态 `COMPENSATING`，或者结合 Redis 引入一个带有 5 秒短 TTL 的‘重试屏障锁’。

### 地狱拷问 6：PostgreSQL `CREATE INDEX CONCURRENTLY` 失败残留 INVALID 索引会有什么危害？线上怎么监控排查？
- **面试官施压**：“你提到了 CONCURRENTLY，那你知道如果并发建索引遇到锁超时或唯一键冲突失败了，PostgreSQL 内部会怎么处理？INVALID 索引有危害吗？线上怎么监控？”
- **满分反杀**：
  > 1. **【INVALID 索引致命危害】**：
     `CONCURRENTLY` 建索引失败时，Postgres 不会自动回滚，而是会将该索引保留在系统目录中，并在 `pg_index.indisvalid` 标记为 `false`。
     **危害在于**：查询优化器绝不会使用这个失效索引，但**随后的所有 INSERT / UPDATE / DELETE 写入操作，数据库依然要强行为这个失效索引维护底层 B+树数据**，白白消耗大量的磁盘 IOPS，导致写入性能严重劣化！
  2. **【排查监控 SQL】**：
     我们建立了定期数据库巡检脚本，查询系统视图：
     ```sql
     SELECT indisvalid, indexrelid::regclass 
     FROM pg_index 
     WHERE indisvalid = false;
     ```
  3. **【线上自愈处理】**：
     一旦发现失效索引，绝不能直接置之不理。必须先使用 `DROP INDEX CONCURRENTLY idx_name;` 清理残留死索引，排查底层数据是否存在未清洗的重复项，修复后再重新触发构建。

### 地狱拷问 7：园区断电恢复，数万台 RTU 同时重连，Netty 服务端发生“重连风暴”怎么扛？
- **面试官施压**：“越秀地产一个大园区突发停电，恢复供电后 2 万台 RTU 边缘网关在同一秒发起 TCP 建联握手，你的 Netty RTUServer 会不会把 Linux 连接队列打满甚至被直接打死？怎么防范重连风暴？”
- **满分反杀**：
  > 1. **【操作系统与 Netty 队列调优】**：
     - 在操作系统内核层增大 TCP 全连接队列：`sysctl -w net.core.somaxconn=2048`；
     - 在 Netty 的 `ServerBootstrap` 中显式设置 `.option(ChannelOption.SO_BACKLOG, 1024)`，防止三次握手成功的连接因为应用层未及时 accept 而被系统直接丢弃；
  2. **【硬件边缘端：指数退避与随机抖动（Jittered Backoff）】**：
     在固件与设备交互协议设计中，严禁硬件掉线后立刻无脑每秒重试。硬件 SDK 必须内置**带随机抖动的指数退避算法**：
     $$T_{retry} = \min(T_{max}, 2^n \times T_{base}) + \text{random}(0, 5000\text{ms})$$
     将数万台设备的重连请求在时间轴上均匀打散到 1～5 分钟内，彻底平抑接入尖刺；
  3. **【服务端连接鉴权限流】**：
     在 Netty 的 `ChannelInitializer` 顶部挂载连接频控处理器，单秒建立新连接数超过阈值时，安全延迟 accept 或配合负载均衡将建联流量分摊到不同的网关接入节点。

### 地狱拷问 8：全量同步用 Redis 锁防重入，如果执行了 35 分钟但锁只有 30 分钟过期怎么办？
- **面试官施压**：“你在全量同步上加了带有 30 分钟过期的 Redis 分布式锁。如果数万台设备同步因为网络慢执行了 35 分钟，第 30 分钟锁自动失效了，另一个管理员点击了同步，你的系统会产生什么灾难？Redisson 是怎么解决这个问题的？”
- **满分反杀**：
  > 1. **【灾难复盘】**：
     锁提前释放会导致**分布式锁失效**，第 2 个任务并发进入，与第 1 个正在执行的任务同时修改设备台账，产生脏读、死锁和数据覆盖覆盖；
  2. **【解决方案：Redisson 看门狗（Watchdog）自动续租原理】**：
     - 严禁在耗时任务上使用无续租机制的死 TTL 锁。在生产中我们采用 Redisson 的分布式锁，**不显式传入 leaseTime**；
     - Redisson 会启动一个后台定时任务线程（Watchdog，看门狗），默认每隔 `lockWatchdogTimeout / 3`（通常是 10 秒）向 Redis 发送 Lua 脚本刷新锁的过期时间（重新充值为 30 秒）；
     - 只要当前执行全量同步的 JVM 进程没有挂掉，锁就会被自动无限续租，绝不发生提前释放；
     - 当业务处理完毕主动调用 `unlock()` 时，看门狗定时器被 cancel，锁立即正常释放；如果服务器突发宕机，看门狗随之死亡，30 秒后锁自然失效，避免死锁。

### 地狱拷问 11：数据库和缓存双写一致性你们是怎么保证的？为什么不用 Canal 监听 Binlog？
- **面试官施压**：“在访客通行或者台账同步中，数据库和 Redis 缓存如果同时更新，先更数据库还是先更缓存？怎么保证强一致性？为什么不直接用 Canal 监听 Binlog？”
- **满分反杀**：
  > 1. **【策略定性：Cache-Aside 模式（先更 DB，再删缓存）】**：
     对于分布式缓存，我们严格遵循**‘先更新数据库，再淘汰缓存（Delete Cache）’**的策略，坚决不直接更新缓存（避免高并发下写入顺序颠倒引发脏数据）；
  2. **【为什么不是先删缓存？】**：
     先删缓存会导致严重的并发脏读：线程 A 刚删缓存，还没来得及更 DB；线程 B 进来查缓存未命中，去 DB 查出旧数据回填缓存，导致缓存永久变为脏数据；
  3. **【为什么不引入 Canal 监听 Binlog？（成本与权衡 Trade-off）】**：
     - Canal 虽好，但会引入额外的中间件集群运维成本、高可用保障与延迟（Binlog 同步通常有数百毫秒延迟）；
     - 我们的物联场景（如门禁凭证、防抖锁）天然具有**‘自失效特征（短 TTL）’**。访客 Token 本身带有 5 分钟过期时间，结合短时间 TTL 兜底，即可满足绝大多数业务对最终一致性的诉求，在架构复杂度和一致性之间取得了最佳平衡。

### Q3: 消费 Kafka 遇到毒丸消息如何防止无限重试与队头阻塞？

### Q5: Kafka 批次包含 5 台设备，前 2 台成功第 3 台失败，如何保障事务与幂等？

  2. **【逆向补偿】**：遍历结束发现有失败设备，调用 `deleteProcessedMark(eventId)` **先删 Mongo 再删本地缓存**，解除幂等占位；
  3. **【抛出重试】**：向上抛错阻止位点提交，触发 `consumer.seek` 回退整条消息；
  4. **【幂等吸纳】**：下次重试时，已成功的设备通过底层 `upsertDevice` 幂等更新状态不变，失败的设备获得重新修复。

### Q8: 二维码权限下发 38 秒的问题怎么排查出来的？怎么优化的？
- **满分回答模板**：

### Q9: 骑手认证为什么用 Guava 本地缓存而不用 Redis？怎么防 OOM 和穿透？
- **满分回答模板**：
  1. **【技术权衡】**：午高峰 100 QPS 下每秒 200 次 RSA 2048 位加密，极度消耗 CPU（200～500ms/s）。Redis 引入 1～2ms 网络往返与连接池竞争；
  2. **【容量评估】**：手机号加密串缓存 5000 条仅占 **1.5MB** 堆内存，内存读取只需 0.01ms，午高峰命中率 30%～50%，削减 40% CPU 负载；
  3. **【防 OOM】**：配置 `maximumSize(5000)` + `expireAfterWrite(5, MINUTES)`，利用 LRU 驱逐保证内存绝对有界；
  4. **【安全红线】**：美团与淘宝公钥和 Base64 规则不同，缓存实例严格物理隔离；地理围栏涉及安防红线，坚决不缓存，必须实时计算。

### Q11: `/queryVisitorRecord` 接口从 30 秒优化至 5 秒内，具体做了哪三件事？

### Q12: 线上 PostgreSQL 出现 `DataFileRead` 和 `WALWriteLock` 等待，怎么排查解决？

### Q13: 在生产环境给千万级大表加索引有什么风险？你们怎么加的？
- **满分回答模板**：
  1. **【生产风险】**：默认 `CREATE INDEX` 申请 `SHARE` 锁，与在线业务写入申请的 `ROW EXCLUSIVE` 锁强冲突，建索引期间整张表写入全部卡死，连接池雪崩；
  2. **【标准操作】**：必须使用 `CREATE INDEX CONCURRENTLY idx_name ON table (col)` 在线无锁创建；
  3. **【代价与验证】**：耗时更长且经历两次表扫描，建完后必须查询 `pg_index.indisvalid` 验证是否为有效索引；
  4. **【刷新统计】**：执行 `ANALYZE table;` 确保优化器立刻获知最新分布直方图。
