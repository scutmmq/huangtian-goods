## 三、核心项目深挖一：越秀 RTU 设备台账同步与空间拓扑挂载治理

### 1. 业务场景痛点
在越秀地产项目中，物业线下安装了数以万计的 RTU（Remote Terminal Unit，远程测控终端网关）以及挂载在网关下方的各种传感器、采集设备（电表、水表、环境温湿度传感器等）。
传统线下安装往往存在：
- 设备信息经常在资产管理系统（FM，Facility Management）中发生增删改；
- 物联设备与智慧空间（项目 $\to$ 分期 $\to$ 楼栋 $\to$ 楼层 $\to$ 房屋）的树形结构存在动态绑定与解绑；
- 网关与子设备存在强从属依赖，子设备不能脱离网关独立存在；
- 设备网络状态和云端配置需要多方协同（平台卸载、MQTT 下线通知、数据库删除）。

### 2. 核心架构设计与关键技术落地

#### 2.1 全量批量预加载 vs 增量实时查询的双轨空间映射机制
物联平台的设备必须挂载在空间树上（五级拓扑：Project $\to$ Stage/Area $\to$ Building $\to$ Floor $\to$ House）。
在代码 `FmDeviceOperationManager.java` 中设计了两种通道：
1. **全量同步通道（Batch Pipeline）**：
   - 痛点：一次性同步数千台设备，如果每台设备都调用微服务接口查询 SpaceManager，将导致数千次 RPC 远程网络调用，网络 IO 耗尽且极易超时崩溃。
   - 破局：设计 `FmSpaceIdMapping` 预构建容器。在全量任务启动前，预先批量捞取项目级空间树映射表传入 `upsertDevice(fmDevice, mapping)`，将数千次网络调用降为 **0 次远程 RPC**，全内存纯哈希匹配！
2. **增量事件通道（Kafka Stream Pipeline）**：
   - 针对 Kafka 单条事件推送，设计 `buildSingleDeviceMapping(fmDevice)` 进行按需加载。
   - **防御性容错设计（模糊名称兜底）**：如果前端或资产系统推送的 `projectCode` 未能在物联平台找到对应映射，底层自动触发 `sm.queryProjectIdByName(projectName)` 模糊匹配兜底，防止因为第三方编码变更导致设备同步大面积失败！
   - **楼层多层级依赖解析**：楼层无法独立全局唯一定位，必须先依赖楼栋解析出 `buildingId`，通过 `SpaceManager.normalizeFloorCode(floorCode)` 进行楼层编码规范化清洗（如兼容 `F01`、`-1F`、`1层` 等异构格式），再调用 `queryFloorIdsByBuildingAndName` 完成二级绑定。

#### 2.2 智能设备拓扑决策状态机 (`determineDeviceType`)
外部推送的报文往往存在字段缺失或不规范，系统通过严密的逻辑推断设备类型：
```java
// 核心逻辑参考：FmDeviceOperationManager.java
private DeviceType determineDeviceType(FmDeviceDTO fmDevice) {
    String parentDeviceCode = fmDevice.getParentDeviceCode();
    String deviceTag = fmDevice.getDeviceTag();
    if ("gateway".equals(deviceTag)) {
        // 明确标记为网关 (RTU)，且绝不允许有父设备
        return (parentDeviceCode == null) ? DeviceType.RTU : DeviceType.UNKNOWN;
    } else if (deviceTag == null) {
        // deviceTag 缺失时，通过拓扑层级容错推断：无父设备视为主网关，有父设备视为子采集设备
        return (parentDeviceCode == null) ? DeviceType.RTU : DeviceType.COLLECTION_DEVICE;
    } else if ("device".equals(deviceTag)) {
        return DeviceType.COLLECTION_DEVICE;
    }
    return DeviceType.UNKNOWN;
}
```

#### 2.3 防孤儿挂载机制与原子失败回滚
在创建子采集设备（`upsertCollectionDevice`）时，若数据中携带了 `parentDeviceCode`，系统强制校验其父 RTU 是否已在数据库中落地：
```java
DRTU parentRtu = RTUDao.instance().findByFmDeviceCode(parentDeviceCode);
if (parentRtu == null) {
    log.error("子设备 {} 对应的父设备 {} 不存在，无法建立关联", deviceCode, parentDeviceCode);
    throw new RuntimeException("父设备不存在: " + parentDeviceCode);
}
```
**深度设计考量**：这里绝不降级为“先创建一个游离的孤儿设备”，而是直接抛出异常！因为一旦抛出异常，外层 Kafka 消费链路将感知失败，触发幂等清理与位点回拨重试（稍后详述）。等待父设备完成同步后，子设备自然成功绑定，杜绝产生历史脏数据。

#### 2.4 设备销毁的三步下线协调机制
删除一个物联采集设备（`deleteCollectionDevice`）不是简单地执行一条 SQL `DELETE`，而是跨系统的三步分布式协作：
1. **MQTT 协议主动断连下线**：调用 `MqttClientManager.instance().offline(device.getDeviceId())`，主动切断硬件长连接，防止设备继续上报指标产生空指针或脏数据；
2. **物联平台资产注销**：调用 `IoTApiManager.getInstance().deleteDevice(...)`，同步注销云端三元组与设备物模型凭证；
3. **本地持久化清理**：从本地 MongoDB 物理删除台账记录。
4. **RTU 级联删除机制**：当删除主网关 RTU 时，底层自动触发级联清理器（`CollectionDeviceDao.deleteByRtuCode` 与 `CollectorDao.deleteByRtuCode`），先清理所有子采集器和下属设备，再清理网关自身，确保数据库无死锁与外键/逻辑孤儿。

## 四、核心项目深挖二：Kafka 消费链路工业级可靠性与双层幂等架构（源码级）

这是面试时最能体现你分布式基础与架构实战能力的黄金亮点。在 `yuexiu-rtu-xagent` 中，由你亲自负责编写维护了原生的 `FmKafkaListener` 与 `FmKafkaEventHandler`。

### 1. 为什么不用 Spring `@KafkaListener`？面试秒杀点！
面试官经常会问：“Spring Boot 提供了成熟的 `@KafkaListener` 注解，你们为什么要自己写一个后台守护线程去运行原生的 `KafkaConsumer` 循环？”
**标准满分回答**：
> “Spring `@KafkaListener` 虽然开箱即用，但在这种工业级物联台账同步场景下有三个严重痛点：
> 1. **位点精准控制受限**：我们需要实现‘消息消费失败时，仅回拨该分区位点（`consumer.seek`）重试，而不能粗暴打断整个容器其他分区的拉取’；
> 2. **跨批次逐条精细提交**：我们需要在单条事件处理完毕后，精确构造 `OffsetAndMetadata(record.offset() + 1)` 进行同分区单步同步提交，严格实现 `At-Least-Once`；
> 3. **毒丸消息的熔断自愈**：当某条格式错误的‘毒丸消息’连续 3 次处理失败时，我们需要在 Native 循环内实施精确位点越过（Force Skip Offset Commit），既不阻塞后续消息，又保留现场日志，并支持平滑接入 DLQ（死信队列）。
> 原生驱动使我们对消费生命周期、拉取间隔、重试计数及分区隔离拥有 100% 的底层掌控力。”

### 2. 四大工业级可靠性防护机制全拆解

#### 防护机制 1：分区隔离消费与精准逐条同步提交
在 `FmKafkaListener.java` 中，消费循环绝不无脑遍历整批 `ConsumerRecords`，而是按分区（`TopicPartition`）分组处理：
```java
// 核心源码参考：FmKafkaListener.java
for (TopicPartition partition : records.partitions()) {
    List<ConsumerRecord<String, String>> partitionRecords = records.records(partition);
    for (ConsumerRecord<String, String> record : partitionRecords) {
        String retryKey = record.partition() + "-" + record.offset();
        try {
            // 业务处理
            FmKafkaEventHandler.getInstance().handle(record.value());

            // 成功：清除重试计数，精确构造 offset+1 手动提交
            retryCountMap.remove(retryKey);
            Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
            offsets.put(partition, new OffsetAndMetadata(record.offset() + 1));
            consumer.commitSync(offsets);
        } catch (Exception e) {
            // 触发精准重试与位点回拨
        }
    }
}
```

#### 防护机制 2：Seek 位点回退与防头阻断（Head-of-Line Blocking）熔断器
当某条消息处理发生异常（如 DB 瞬时抖动、RPC 超时）：
1. **未达最大重试次数时**：
   记录该分区与位点的重试计数（`retryCountMap`），调用 `consumer.seek(partition, record.offset())`，将该分区的消费游标向后回滚！下一次 `consumer.poll()` 就会重新拉取该条消息进行重试，而不是漏掉消息。
2. **超过最大重试次数（`MAX_RETRY_COUNT = 3`）时**：
   如果一条消息因为字段非法无法解析，或者业务逻辑出现不可逆异常，无限回退会导致整个分区永远卡在这一条消息上（**队头阻塞 Head-of-Line Blocking**），导致该分区后续数万条正常消息全部严重延迟！
   **自愈熔断设计**：打印 `ERROR` 级异常堆栈，移除重试计数，**强制提交该消息的 offset+1**，将毒丸越过，保障后续业务流转不被打断，同时在代码中预留 DLQ（死信队列）落盘逻辑。

```java
// 核心代码：FmKafkaListener.java
int retryCount = retryCountMap.getOrDefault(retryKey, 0) + 1;
retryCountMap.put(retryKey, retryCount);

if (retryCount >= MAX_RETRY_COUNT) {
    log.error("消息已达最大重试次数({})，强制跳过: partition={}, offset={}",
            MAX_RETRY_COUNT, record.partition(), record.offset(), e);
    retryCountMap.remove(retryKey);
    // 强制提交位点，防止分区堵死
    Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
    offsets.put(partition, new OffsetAndMetadata(record.offset() + 1));
    consumer.commitSync(offsets);
} else {
    log.warn("消息处理失败，第 {}/{} 次重试，将重新消费: partition={}, offset={}",
            retryCount, MAX_RETRY_COUNT, record.partition(), record.offset());
    // 核心位点回拨
    consumer.seek(partition, record.offset());
}
```

#### 防护机制 3：双层原子幂等防御体系 (`FmIdempotentManager`)
在大规模并发推送下，Kafka 可能会因为网络波动发生 At-Least-Once 重复投递。我们设计了**两级幂等过滤机制**：
- **Level 1（快速路径 - 本地内存）**：
  基于 `ConcurrentHashMap<String, Long>` 记录已消费的 `eventId` 及时间戳。
  - TTL 设置为 24 小时；
  - 配套独立的后台守护清理线程（`fm-idempotent-cleanup`），每小时定期通过 `removeIf` 清理过期 entry，严格杜绝内存泄漏（OOM）；
  - 拦截 99% 的短时间内重复投递，零 IO 损耗返回。
- **Level 2（原子兜底 - MongoDB 唯一索引）**：
  - 内存缓存重启会丢失，且多实例下不共享。因此通过 MongoDB 表创建针对 `eventId` 的**全局唯一索引（Unique Index）**。
  - 在处理业务前执行原子插入：`FmIdempotentDao.instance().insertIfAbsent(record)`。
  - **异常区分与容错哲学**：
    - 若捕获 `com.mongodb.MongoWriteException` 且错误码为 `11000`（Duplicate Key），说明其他实例或此前已处理成功，判定为重复消息，安全跳过；
    - 若遇到网络连接超时等非唯一键异常，则**绝不吞掉**，抛出运行时异常触发 Kafka 重试。“**宁可重复消费，绝不丢失数据**”。

```java
// 核心源码：FmIdempotentManager.java
try {
    FmIdempotentRecord inserted = FmIdempotentDao.instance().insertIfAbsent(record);
    if (inserted != null) {
        processedEvents.put(eventId, System.currentTimeMillis());
        return true; // 首次处理成功
    } else {
        return false; // 已存在
    }
} catch (com.mongodb.MongoWriteException e) {
    if (e.getCode() == 11000) {
        log.debug("事件已处理过(唯一索引冲突): {}", eventId);
        return false;
    }
    throw e; // 其他DB错误必须抛出触发重试
}
```

#### 防护机制 4：批次逐设备异常隔离与逆向补偿（Compensating Action）
在 `FmKafkaEventHandler.java` 中，外部一个 `FmKafkaMessage` 内的 `data` 数组可能挂载多台设备。
- **逐设备隔离**：如果一个批次有 5 台设备，遍历处理时用 `try-catch` 包裹单台设备的处理过程，单台设备异常记录进 `failedDeviceCodes` 列表，不阻断后续其他设备的同步。
- **逆向补偿删除幂等记录**：如果有任何一台设备处理失败，整个事件就不能算作完全成功！此时系统会调用 `idempotentService.deleteProcessedMark(eventId)`：
  - **严格时序**：先删 MongoDB 持久化记录，再删本地内存缓存，消除并发竞态窗口；
  - 随后向上抛出异常，阻止位点提交，并触发上层的 `consumer.seek` 回滚重新拉取整条消息。下次重试时，此前已成功的设备通过业务层的 `upsert`（幂等更新）保证状态不变，而失败的设备则得到重新修复的机会！

#### 1.1 问题现场还原

   单次查询约 150ms，59 台设备连续往返网络 59 次，纯查询耗时高达 **8.9 秒**！
2. **致命伤 2：`AuthRecord` 逐条单条 INSERT**：

1. **批量查询 + 内存投影构建**：

2. **批量收集与 `insertBatch` / `updateBatch`**：

3. **优化结果**：

### 2. 战役二：外卖骑手认证 CPU 打满与 Guava 本地缓存设计（2026-04-13 线上实战）

#### 2.1 问题背景与高并发评估
在美团外卖、淘宝/饿了么闪购对接中，为了让外卖骑手能快速扫码通过社区人行闸机，系统暴露了骑手身份认证接口。
在午高峰（11:30～13:00）的流量评估中发现：
- 骑手每次核验通行，系统必须将骑手手机号通过 **RSA 2048 位公钥** 进行加密后调用第三方中台校验；
- RSA 属于极其昂贵的 **CPU 密集型加解密计算**，单次耗时在 1～5ms；
- 在 100 QPS 的午高峰场景下，每秒需要并发执行 200 次 RSA 计算，每秒将霸占服务器高达 **200～500ms 的纯 CPU 计算时间**，导致 CPU 核心使用率飙高，拖慢同一容器内的其他 HTTP 实时业务线程！

#### 2.2 为什么否定 Redis，毅然选择 Guava 本地缓存？
业务讨论时，有工程师提议：“直接把手机号加密结果存进 Redis，过期时间 5 分钟”。
**你在技术评审中的深度权衡思考（面试亮点）**：
1. **网络 IO 开销反噬**：Redis 虽好，但每次读取至少引入 1～2ms 的跨节点网络往返（Network Round-Trip），在高并发下还会引起连接池等待；
2. **本地缓存绝对优势**：
   - 手机号（11 字节）+ 密文（200 字节），即使缓存 5000 条，内存消耗也仅约 **1.5MB**！
   - 驻留于 JVM 堆内存（`Guava CacheBuilder`），内存读取仅需 **0.01ms**，零网络开销，零序列化成本；
   - 午高峰同一小区的核心骑手往往具有高复访特征（同一骑手送同一栋楼或附近几家），缓存命中率可稳定达到 30%～50%。

#### 2.3 严密的工程细节避坑设计
1. **美团 vs 淘宝缓存实例物理隔离**：
   绝不能贪图省事共用同一个本地缓存对象！因为两者的加密实现有底层差异：
   - **美团**：使用 Base64 URL 安全编码，去除末尾填充符（`getUrlEncoder().withoutPadding()`）；
   - **淘宝**：使用标准 Base64 编码，保留 `=` 填充符（`getEncoder()`）；
   - 两者公钥不同，加密串完全不同。因此在 `MeituanServiceImpl` 和 `TaobaoServiceImpl` 内部各自实例化独立的 `phoneRsaCache`。
2. **为什么地理围栏（Fence）AES 加密绝不缓存？（安全权衡）**：
   虽然地理围栏也用了加密，但围栏范围涉及物业安防红线。一旦物业在后台临时缩小或调整门禁通行围栏，若本地缓存有 5 分钟 TTL 且无分布式失效订阅，将导致外卖骑手携带过期围栏非法进入未授权区域。**安全等级高于性能，围栏坚持实时计算，手机号认证享受缓存加速**。
3. **缓存击穿与内存防溢出保护**：
   配置 `maximumSize(5000)` 配合 `expireAfterWrite(5, TimeUnit.MINUTES)`，自带 LRU（最近最少使用）剔除，即使遇到爬虫扫手机号，内存占用也被死死锁死在 3MB 以内，永不 OOM。
4. **效果**：
   午高峰 CPU 消耗降低 40%，接口 P99 响应延迟从 5ms 降低至 2ms，稳如磐石。

### 3. 战役三：访客状态更新定时任务治理（从分钟级雪崩到秒级收敛，优化 98%）

#### 3.1 原始灾难剖析
原定时任务 `VisitorRecordUpdateStatusTask` 用于将超期的访客记录更新为“超时作废”状态。生产环境暴露出严重的性能隐患：
- **触发频率极高**：cron 设置为 `0 0/1 * * * ?`（每分钟执行一次，每天触发 1440 次）；
- **全表扫描无窗口**：查询 SQL 未加时间限制，对累计达千万级的历史大表执行 `WHERE visit_status IN (...) AND plan_end_time <= NOW()`；
- **任务堆叠与线程池耗尽**：单次处理需 30 秒至 2 分钟，远超 1 分钟的调度周期。Quartz 共享调度线程池被彻底占死，导致其他核心定时任务（如门禁设备心跳拉取、考勤同步）被大面积阻塞！

#### 3.2 组合拳治理方案
1. **调度降频**：将触发周期从“每分钟执行”调整为“每小时整点执行一次”（`0 0 * * * ?`），日触发频次从 1440 次暴降至 24 次，降幅达 **98.3%**；
2. **滑动时间窗口剪枝**：生产调研发现近 14 天过期的数据不足 1 万条，超过 14 天的历史数据属于冷数据。在 SQL 中强加滑动窗口下限：
   ```java
   Date recentDate = new Date(System.currentTimeMillis() - (long)recentDays * 24 * 60 * 60 * 1000);
   wrapper.ge("plan_end_time", recentDate); // 仅拉取近14天数据
   ```
   直接过滤掉 99% 的冷数据扫描！
3. **分页限速与数据库削峰缓冲**：
   单页批量从 500 调优至 1000，并在批次之间加入 50ms 休眠（`batch-interval: 50`），主动让出数据库 CPU 与 IO 缓冲，消除数据库瞬时尖刺；
4. **双轨补偿机制（分层治理）**：
   针对超过 14 天未处理的极端历史遗留数据，不放在高峰期主链路，而是独立设计 `VisitorRecordUpdateCompensateTask`，安排在**凌晨 2:30** 业务极低谷期单实例静默执行，实现高可用闭环。

## 六、核心项目深挖四：生产慢 SQL、等待事件与 PostgreSQL 性能调优实战

### 1. 线上数据库瓶颈定位：四大等待事件分析
在微服务压测和现场运维过程中，PostgreSQL 连接池频繁告警打满，API 延迟拉长。你通过查询 PostgreSQL 系统视图 `pg_stat_activity` 和 `pg_stat_statements`，捕获到了核心数据库瓶颈：
- **`DataFileRead` 严重飙升**：表明大量的查询无法在操作系统 Page Cache 或 Postgres `shared_buffers` 中命中，必须从底层物理磁盘发起同步 IO 读，原因正是高频 SQL 缺少复合索引导致的全表顺序扫描（Seq Scan）；
- **`buffer_io` 等待**：多个并发后台进程同时尝试从磁盘换入同一数据块到内存，产生锁争用；
- **`WALWriteLock` 等待**：某些非实时历史数据清理任务使用“大事务单次 DELETE 数万条”，导致大量 WAL（Write-Ahead Logging）日志同步刷盘，堵塞其他在线业务事务的提交；
- **集群“惊群效应（Thundering Herd）”**：由于服务在 Kubernetes 集群中部署了多 Pod 容器，原本用于纠正重复人员数据的后台任务没有加分布式锁，导致 5 个 Pod 在同一秒内同时触发大表全量聚合扫描，数据库 IOPS 瞬间被打穿！

### 2. 手术级实战：`/queryVisitorRecord` 接口从 30 秒优化至 5 秒内

#### 2.1 原始 SQL 的三处致命设计
该接口在数据量达到 4 万条时，耗时竟高达 30 秒。深入分析 `VisitorRecordMapper.xml`：
1. **三张大表外层嵌套 `UNION ALL` + 排序跳页**：
   主查询将 `tb_visitor`（邀约表）、`tb_visitor_record`（登记表）、`tb_visitor_register`（注册表）通过 `UNION ALL` 拼在一起，在外层执行 `ORDER BY update_time DESC LIMIT 10 OFFSET 0`。
   在没有有效索引的情况下，Postgres 必须对三张表全部做顺序全量扫描，在内存临时文件（Temp File）中进行高成本的外部归并排序（External Sort）；
2. **奇葩占位符 `pk_id='1'` 干扰优化器**：
   历史代码为了在动态 SQL 中实现“禁用某些分支”，拼入了 `AND pk_id='1'`。优化器无法在解析阶段将其推导为常量假，强行执行了索引查找评估，大幅增加了优化器生成执行计划的开销；
3. **业务层恶魔 N+1 查询**：
   在分页拉取到 20 条记录后，Java 代码中竟然循环遍历该 List，每一条都单独调用一次 `getPersonName(authId)` 去查询人员表，20 条记录产生 20 次网络往返！

#### 2.2 优化落地三步曲
- **第一步：消除 N+1 查询**：
  在 `VisitorRecordServiceImpl` 中，遍历分页结果，通过 Stream 流萃取出所有唯一的 `authId` 集合，调用 `personService.selectBatchIds(authIds)` 发起**单次批量 IN 查询**，在内存中使用 `Map<Long, String>` 进行回填，瞬间抹平 20 次网络往返。
- **第二步：SQL 等价重写与伪条件清理**：
  将无效分支的 `pk_id='1'` 直接优化为数据库内核能够秒级识别的常量假条件 `1=0`，消除冗余计算；将查询字段收敛，避免不必要的外连接。
- **第三步：在线生产无锁建索引 (`CREATE INDEX CONCURRENTLY`)**：
  在 PostgreSQL 生产环境下，若直接执行 `CREATE INDEX`，会持有表的 `SHARE` 锁，**阻断所有的写入与更新（INSERT / UPDATE / DELETE）操作**，在数万级生产表上极易造成在线业务大面积超时！
  **专业操作手法**：必须采用 `CONCURRENTLY` 关键字进行在线并发建索引，虽然耗费更多的 CPU 和两次扫描，但**完全不阻塞生产写入**：
  ```sql
  -- 针对三张访客表，依据 (project_id, update_time DESC, pk_id) 建立覆盖复合索引
  CREATE INDEX CONCURRENTLY idx_tb_visitor_pjt_time 
  ON tb_visitor (project_id, update_time DESC, pk_id);

  CREATE INDEX CONCURRENTLY idx_tb_visitor_rec_pjt_time 
  ON tb_visitor_record (project_id, update_time DESC, pk_id);

  CREATE INDEX CONCURRENTLY idx_tb_visitor_reg_pjt_time 
  ON tb_visitor_register (project_id, create_time DESC, pk_id);
  ```
- **第四步：刷新优化器统计信息**：
  建完索引后，立即执行 `ANALYZE tb_visitor; ANALYZE tb_visitor_record;`，让优化器的代价模型准确获知最新的数据分布直方图，执行计划彻底从 `Seq Scan`（全表扫描）蜕变为 `Index Scan using idx_tb_visitor_rec_pjt_time`！
  **成效**：执行耗时从 30 秒直接降至 **2.8 秒**，顺利交付！

### 1. 业务场景与方案决策（方案 A vs 方案 B）

### 2. 工业级告警风暴抑制三大黄金参数设计
在将图片喂给 AI 视觉模型后，如何防止系统被海量误报打垮？底层落地了三大机制：
1. **抽帧间隔控制 (`frame_interval`)**：
   同一点位同一算法，两次识别之间强制间隔 N 秒（如 30 秒）。在 Redis 中记录 `ai:capture:last:{pointId}:{configId}` 时间戳。即使摄像头画面有变动，在未达到抽帧窗口前坚决不请求 AI 模型，**避免相似连续帧对大模型算力与 Token 造成惊人浪费**。
2. **滑动防抖告警阈值 (`alarm_threshold`)**：
   现实中经常有落叶飘过、猫狗走动导致单帧被判定为“疑似消防通道占用”。系统设计了“连续异常计数”：只有在最近的连续 N 张图片中识别结果均为异常（`status=0`），才正式判定为真实险情，**消除单帧误报**。
3. **告警抑制冷静期 (`suppress_minute`)**：
   当某处违停或垃圾满溢已经被触发并推送工单到物业人员手机后，系统自动在该点位打上 N 分钟（如 30 分钟）的“告警抑制标记”。在此期间即使异常依然存在，也不再重复上报事件中心，**彻底杜绝物业管家手机遭遇“告警风暴轰炸”**。

### Q2: 为什么在 RTU 台账同步中，你们没有用 Spring 的 `@KafkaListener`，而是自主封装原生 `KafkaConsumer` 线程循环？

#### 面试官心智
考察候选人是只会无脑使用框架注解的“API Caller”，还是真正理解 Kafka 底层消费模型与线程模型的合格工程师。

#### 满分回答模板
1. **【核心定性】**：选择自主封装原生 `KafkaConsumer` 线程循环，是为了获得对**分区隔离处理、精确手动位点提交、以及异常局部 Seek 位点回退**的 100% 底层掌控力，这是高层框架注解难以低成本兼顾的。
2. **【原理解析】**：
   - Spring `@KafkaListener` 的默认确认机制通常是针对整个批次（`Batch`）或者由框架代理调用 `ack.acknowledge()`。但在我们的工业级物联场景中，一个拉取批次（`ConsumerRecords`）内包含多个不同分区的消息；
   - 我们必须按照 `for (TopicPartition partition : records.partitions())` 严格在分区内按顺序串行处理；
   - 处理完单条消息后，我们要精确向 Broker 提交该分区对应的 `OffsetAndMetadata(record.offset() + 1)`，实现精准的单步前进。
3. **【生产实战】**：在我的 `FmKafkaListener` 实现中，我们把 `isListening` 声明为 `volatile`，将消费循环托管在后台名为 `fm-kafka-listener` 的守护线程中，支持优雅停机（`stopListening` 时通过 `join(5000)` 等待当前位点提交完毕）。
4. **【避坑与反思】**：更关键的是，原生客户端允许我们在捕获异常时，直接调用 `consumer.seek(partition, record.offset())` 针对单个分区精准倒回游标。如果用 Spring 注解，一旦抛出异常，默认的错误处理器往往会重试整个监听器批次或暂停容器，不仅容易跨分区互相影响，还难以做到我们自定义的“单消息重试 3 次后强制跳过防死锁”的熔断策略。

### Q3: 生产环境中，如果某条 Kafka 消息内容有问题导致业务一直抛异常，你们怎么防止消息丢失？又怎么防止消费队列被卡死？

#### 面试官心智
考察“毒丸消息（Poison Pill）”的处理思路、位点回拨与死信队列机制。

#### 满分回答模板
1. **【核心定性】**：针对消息异常，我们采取了**“有限次数局部 Seek 回退重试 + 超阈值熔断提交位点 + DLQ 死信日志告警”**的自愈策略，在保障“临时故障不丢消息”的前提下，彻底杜绝“毒丸消息阻塞队列”。
2. **【机制展开】**：
   - **重试阶段（未达阈值）**：我们在内存中维护了一个线程安全的 `retryCountMap`，Key 构造为 `partition + "-" + offset`。当业务处理抛出异常时，重试计数器 +1。若 `retryCount < 3`，调用 `consumer.seek(partition, record.offset())` 回滚位点。由于没有提交 offset，下次 `consumer.poll()` 会重新拉取这一条，有效应对数据库临时死锁或网络偶发抖动；
   - **熔断阶段（达到阈值）**：若同一条消息重试达到 `MAX_RETRY_COUNT = 3`，说明这是数据结构破损或不可逆逻辑错误的“毒丸消息”。此时若继续 seek，整个消费分区将陷入无限死循环，导致该分区后续数万条正常设备数据发生严重的**队头阻塞（Head-of-Line Blocking）**！
3. **【自愈动作】**：此时系统会强制记录完整的 ERROR 级告警日志，将消息 Payload 打印，移除重试计数，并**主动构造 offset+1 执行 `consumer.commitSync()` 越过该消息**。
4. **【演进设计】**：同时在代码中预留了 DLQ 逻辑，未来将这些坏消息转发至专用的死信队列 Topic，供离线脚本或人工介入补偿，既保障了线上吞吐的连续性，又守住了数据可审计的底线。

### Q4: 详细讲讲你们的二层幂等架构（`FmIdempotentManager`），为什么在本地内存缓存之外，还要加一层 MongoDB 唯一索引？

#### 面试官心智
考察分布式环境下的防重设计、缓存穿透/重启失效思考，以及多级架构设计的严谨性。

#### 满分回答模板
1. **【核心定性】**：二层幂等是**“本地高性能快路径”与“持久层强一致兜底”**的黄金组合。本地缓存是为了**保护底层数据库**，而 MongoDB 唯一索引是为了**保障跨实例与重启后的绝对准确性**。
2. **【原理解析】**：
   - **第一层（Local Fast-Path）**：基于 `ConcurrentHashMap<String, Long>` 记录已处理的 `eventId`。物联事件在高并发下常常出现秒级内的连续重复推送（如网络抖动导致上游重发）。99% 的重复请求在这一层被拦截，内存比对耗时 0.01ms，避免了对数据库的并发连接冲击；
   - **第二层（Persistent Atomic-Path）**：本地内存具有“进程隔离”与“重启易失”的天然缺陷。在多容器集群部署下，实例 A 处理过的消息如果被 Kafka 重新分配给实例 B，本地缓存直接失效；且服务重启后内存清空。因此必须依赖 MongoDB 对 `eventId` 建立的**全局唯一索引（Unique Index）**。
3. **【源码细节】**：在我的 `tryMarkProcessed` 实现中，两层之间严格原子协作：先查本地缓存；未命中则调用 `FmIdempotentDao.insertIfAbsent(record)`。
   - 若捕获到 MongoDB 错误码 `11000`（唯一索引冲突），判定为重复消息，返回 `false`；
   - 若遇到其他 DB 异常则抛出触发重试，秉持“宁可重复处理，绝不丢数据”的原则。
4. **【内存泄漏防御】**：针对本地缓存可能无限膨胀引发 OOM 的问题，我设计了 24 小时 TTL，并启动了名为 `fm-idempotent-cleanup` 的单守护线程，每小时定时调用 `removeIf` 清除超期 Entry，确保内存开销受控。

### Q5: 如果一个 Kafka 报文里包含 5 台设备的数据，前 2 台处理成功，第 3 台失败了，此时怎么保障事务和幂等？

#### 面试官心智
考察分布式批处理中的部分失败处理、补偿事务与重试语义。

#### 满分回答模板
1. **【核心定性】**：我们采取了**“批次内设备异常隔离 + 逆向补偿删除幂等标记 + 向上抛出触发 Kafka 位点回拨 + 业务层 Upsert 幂等吸纳”**的闭环方案。
2. **【链路剖析】**：
   - 在 `FmKafkaEventHandler.java` 中，我们遍历报文中的 `data` 列表时，单台设备的处理用独立 `try-catch` 包裹。前 2 台执行成功，第 3 台失败时，将其加入 `failedDeviceCodes` 列表，继续尝试处理后续设备，最大限度隔离异常扩散；
   - 遍历结束后，检测到 `!failedDeviceCodes.isEmpty()`，说明该事件未完全成功。此时**决不能向 Kafka 提交该消息的 offset**！
3. **【关键补偿动作】**：由于在进入批处理前，事件已被预先打上了幂等标记（`tryMarkProcessed`）。如果此时直接回退位点，下次 Kafka 重新投递该消息时，幂等管理器就会认为“该 eventId 已处理过”而直接跳过，导致失败的设备永远无法被创建！
   因此我实现了 `idempotentService.deleteProcessedMark(eventId)` 补偿机制：**严格按照“先删持久层 MongoDB，再删本地内存”的时序清除幂等占位**，消除并发竞态窗口。
4. **【最终一致性保证】**：幂等标记删除后，代码抛出运行时异常，触发 `FmKafkaListener` 执行 `consumer.seek` 回滚。下次整条消息重新拉取时：前 2 台已成功的设备，由于底层采用的是 `upsertDevice`（基于设备编码查询，存在即更新，字段无变化则幂等），重复执行毫无副作用；而此前失败的第 3 台设备则获得重新修复入库的机会，从而达成最终一致！

### Q6: 为什么删除采集设备时，要先调用 MQTT 离线指令，再调用 IoT 平台注销，最后才删本地数据库？顺序反了会怎样？

#### 面试官心智
考察候选人对硬件设备长连接生命周期、物联分布式交互时序与防御性编程的深度思考。

#### 满分回答模板
1. **【核心定性】**：这个顺序体现了物联领域的**“先断输入源、再注销凭证、最后清理本体”**的防御性销毁原则。
2. **【时序拆解与反推分析】**：
   - **设想：如果先删本地数据库**：
     硬件设备通常是通过 TCP/MQTT 维持着长连接，并且会定时上报采集数据报文（如电表读数）。如果本地 DB 先删了，但连接没断、IoT 平台设备未注销，设备下一秒继续上报一条采集数据进来，服务在处理入库时由于查不到对应的设备台账元数据，就会产生海量空指针异常、脏数据甚至抛错报警！
   - **设想：如果不调 MQTT 离线，只删 IoT 平台**：
     边缘网关或设备可能长时间驻留在连接网关上形成“僵尸长连接”，占用网关的物理连接数配额与内存，直到 TCP KeepAlive 超时；
3. **【标准实现】**：
   - 第一步：`MqttClientManager.offline(deviceId)`，主动发送断连信令踢设备下线，并在 MQTT Broker 侧断开通道，切断所有上行数据流；
   - 第二步：`IoTApiManager.deleteDevice(...)`，注销该设备在云端物模型平台的三元组密钥凭证，使其无法再通过鉴权重新建联；
   - 第三步：`CollectionDeviceDao.deleteById(...)`，清理本地持久化记录。
4. **【健壮性设计】**：在代码实现中，第一步和第二步均加了 `try-catch` 包裹并打印告警，即使外部 IoT 接口因偶发网络波动报错，也绝不阻断核心持久化数据的清理，保证操作幂等与最终收敛。

### Q7: 为什么全量设备同步要传入预构建的 `FmSpaceIdMapping`，而增量同步却用单设备实时查询？

#### 面试官心智
考察系统架构设计中对“高吞吐批处理（Batch）”与“低延迟流处理（Stream）”的场景化权衡能力。

#### 满分回答模板
1. **【核心定性】**：这是典型的**“以空间换时间（预热批处理）”与“按需实时计算（懒加载）”**的经典架构权衡。
2. **【全量场景剖析】**：
   - 全量同步面临的是**数万台设备的大吞吐初始化**。
   - 如果每一台设备都按 `projectCode $\to$ buildingCode $\to$ floorCode` 去跨微服务调用 `SpaceManager` 查询真实的 UUID，数万台设备将产生几十万次 RPC 远程调用！不仅耗尽 HTTP 连接池，还会对空间中台造成灾难性的流量冲击，耗时拉长到数十分钟；
   - 因此在全量任务启动前，预先将整个项目的空间拓扑树整树拉取，在内存中构建 `FmSpaceIdMapping` 扁平映射表。每台设备直接在 JVM 内存中进行 `O(1)` 的哈希比对，将外部网络 IO 降为 0，数万台设备的挂载可以在数十秒内完成。
3. **【增量场景剖析】**：
   - 增量同步是由 Kafka 事件驱动的，通常每次推送只有 1 台或几台设备，频率低、随机性大；
   - 如果每次收到一条增量消息都去全量拉取一次几百 KB 的空间树，反而造成极大的网络浪费和内存开销；
   - 因此设计了 `buildSingleDeviceMapping` 单设备按需解析器，仅针对这单条消息涉及的楼栋和楼层发起精准反查，兼顾了内存占用与实时响应。

### Q8: 你们在排查二维码权限下发接口耗时 38 秒时，是如何逐步定位出瓶颈的？优化收益有多大？

#### 面试官心智
考察线上性能瓶颈的系统化定位手段（日志埋点、分段追踪）以及代码级重构收益。

#### 满分回答模板
1. **【现象与定位手段】**：
   - 在 59 台门禁闸机示范区的联调压测中，前台响应长达 38 秒，濒临网关超时；
   - 我们通过开启针对 visitorId 的 DEBUG 跟踪日志，比对关键链路的时间戳差值：
     - 二维码生成（`generateQrCode`）耗时 200ms；
     - 本地插入二维码表耗时 550ms；
     - **发现断崖静默**：从保存二维码成功到发出中台权限请求，中间出现 **长达 18 秒的完全静默！**
     - 中台 HTTP 返回后，到最终接口返回，又发生了 **13.5 秒的漫长等待**。
2. **【代码根因拆解】**：
   - 静默 18 秒的原因：`transQrcodeIotDn` 在循环中针对 59 台设备，每台执行一次单条 SELECT 查设备表（耗时 8.9s），接着又循环 59 次单条 INSERT 插入权限记录表（耗时 8.9s）；
   - 响应后慢 13.5 秒的原因：对中台返回结果又循环 59 次逐条执行 UPDATE。
   - 整个流程在 59 台设备下发生了 **177 次独立的数据库网络交互**！
3. **【优化策略】**：
   - 将 59 次设备查询重构为：按 `(projectId, category=4)` 执行 **1 次全量批量查询**，在内存中用 Map 建立投影映射（耗时从 8.9s 降到 <100ms）；
   - 将 59 次单条 INSERT 重构为 MyBatis-Plus 的 `insertBatch` **一次性批量提交**；
   - 将 59 次 UPDATE 按成功/失败状态在内存分类后，执行 **批量条件更新**。
4. **【优化结果】**：
   将 177 次数据库往返削减为仅 3 次批量交互。本地计算与 DB 耗时从 **31.3 秒暴降至 0.8 秒以内**，接口总耗时从 38 秒直接降至 6.8 秒（剩下的 6 秒是海康硬件物理通信刚性延迟），整体性能提升超过 **81%**！

### Q9: 骑手认证为什么不用 Redis 缓存 RSA 加密结果，而选用了 Guava 本地缓存？你们怎么防范内存溢出和穿透？

#### 面试官心智
考察多级缓存选型、本地缓存边界与安全性/内存容量评估。

#### 满分回答模板
1. **【核心定性】**：选用 Guava 本地缓存而不用 Redis，核心权衡是**“以极低的内存代价消灭网络 IO 往返，极致释放 CPU 密集型开销”**。
2. **【原理解析与技术权衡】**：
   - 午高峰 100 QPS 下，每秒需执行 200 次 RSA 2048 位加密，严重挤占 CPU 资源（200～500ms/s）；
   - 如果放 Redis：每次校验都要经历一次网络往返（Network RTT，通常 1～3ms），在高并发时还容易引起 Redis 连接池争用；
   - 评估内存容量：一个手机号（11 字节）对应密文（约 200 字节），Guava 缓存上限设为 5000 条，算上内部 Node 开销，**整体内存占用仅约 1.5MB**！相比容器数个 G 的堆内存完全九牛一毛；
   - 内存读取耗时仅需 0.01ms，午高峰骑手复访率高，命中率达 30%～50%，直接削减近半数的 CPU 密集型加密计算。
3. **【防御性设计与避坑】**：
   - **防 OOM 溢出**：配置 `maximumSize(5000)` 配合 `expireAfterWrite(5, TimeUnit.MINUTES)`，利用内置的 LRU（最近最少使用）算法自动驱逐冷数据，容量绝对有界；
   - **防业务混淆**：美团（URL-safe Base64 无 padding）与淘宝闪购（标准 Base64 有 padding，公钥不同）使用隔离的两个 Cache 实例，严禁混用；
   - **安全红线权衡**：手机号加密结果可以容忍 5 分钟缓存，但**地理围栏（Fence）AES 加密坚决不缓存**，确保物业对门禁通行区域的变更能在秒级内硬核生效。

### Q10: 生产多容器部署时，定时任务出现并发冲突和数据库 IO 飙高，你们怎么解决的？

#### 面试官心智
考察容器化（Kubernetes）集群部署下的定时任务治理、分布式锁与调度优化。

#### 满分回答模板
1. **【核心定性】**：生产环境下的多容器并发冲突，本质是**“单机调度思维误代入分布式集群”**导致的**惊群效应（Thundering Herd）**。我们通过**“分布式锁单实例收敛 + 错峰低谷调度 + 分批限速 + 滑动窗口剪枝”**实施了体系化治理。
2. **【事故复盘】**：
   - 我们的服务在生产部署了多个 Pod 副本。此前“重复人员纠错”以及“通行统计”任务配置为每隔固定时间执行全表扫描；
   - 多个 Pod 在同一秒被 Quartz 触发，5 个容器同时向同一个 PostgreSQL 实例发起全量聚合扫描，数据库物理磁盘 IO 直接打到 100%，引发大面积 `buffer_io` 与 `DataFileRead` 等待，直接拖慢所有在线 C 端通行接口！
3. **【治理举措】**：
   - **治理 1（执行互斥）**：针对非实时数据治理任务，引入 Redis 分布式锁（带租约时间 Lease Time），确保集群在同一时刻仅有 1 个 Pod 实例获得执行权，其余 Pod 自动放弃；
   - **治理 2（错峰与降频）**：将重度扫描任务移至凌晨 2:00～4:00 低峰期执行；
   - **治理 3（限流与分批）**：针对通行统计，控制单次消费 Redis 的上限，分页处理并引入 50ms 的 `batch-interval` 批次间隔，给数据库提供缓冲；
   - **治理 4（窗口剪枝）**：如访客任务，通过 `ge("plan_end_time", recentDate)` 强行锁定近 14 天活跃数据，将历史千万级扫描降到数千条，彻底平抑了数据库尖刺。

### Q11: `/queryVisitorRecord` 接口此前需要 30 秒，优化后降至 5 秒内，具体做了哪三件事？

#### 面试官心智
考察 SQL 重构实战、N+1 消除以及真实索引落地的综合能力。

#### 满分回答模板
1. **【核心定性】**：在不改接口出入参、不改业务语义的前提下，我们打出了一套**“Mapper SQL 等价重写 + Service 层消灭 N+1 + 生产无锁复合索引”**的组合拳。
2. **【三项关键动作】**：
   - **动作一（Service 去 N+1）**：原代码在分页查出 20 条记录后，循环内逐条调用 `getPersonName`，造成 20 次网络往返。改造为收集 `authId` 集合，执行 1 次批量查询并在内存用 Map 映射回填，彻底干掉 N+1；
   - **动作二（Mapper SQL 等价重写）**：主查询由三张表（`tb_visitor`、`tb_visitor_record`、`tb_visitor_register`）`UNION ALL` 构成。原 SQL 中为了禁用分支拼装了极其不规范的 `pk_id='1'`，我们等价改写为常量假条件 `1=0`，降低优化器生成代价树的开销；同时清理冗余 Join，让优化器集中评估高选择性字段；
   - **动作三（复合索引在线补齐）**：分析发现由于缺少匹配排序和过滤的复合索引，优化器走了全表顺序扫描并在内存临时文件中做大排序。针对三张表分别创建了 `(project_id, update_time DESC, pk_id)` 复合索引，并使用 `CREATE INDEX CONCURRENTLY` 避免锁表，随后执行 `ANALYZE` 刷新统计信息。
3. **【成果验证】**：
   优化后再次执行 `EXPLAIN (ANALYZE, BUFFERS)`，三张表全部精准命中新索引（`Index Scan`），外部文件排序彻底消失，4 万级数据量下接口响应时间从 30 秒直接降至 **2.8 秒**。

### Q12: 线上 PostgreSQL 出现 `DataFileRead` 和 `WALWriteLock` 等待，你怎么排查并解决？

#### 面试官心智
考察 PostgreSQL 内部原理、内核等待事件定位以及数据库调优的高阶深度。

#### 满分回答模板
1. **【核心定性】**：
   - `DataFileRead` 代表**“磁盘物理读等待”**，通常由全表顺序扫描或索引失效引发；
   - `WALWriteLock` 代表**“预写日志锁争用”**，通常由超大事务、大批量并发写导致 WAL 刷盘阻塞引发。
2. **【排查定位链路】**：
   - **第一步**：通过查询 `pg_stat_activity` 视图，筛选 `wait_event_type = 'IO'` 或 `wait_event = 'DataFileRead'`，立即抓取到当前正在发生物理读的 `query` 内容和客户端 PID；
   - **第二步**：结合 `pg_stat_statements` 调出该类 SQL 的平均执行耗时（`mean_time`）和调用次数（`calls`）；
   - **第三步**：使用 `EXPLAIN (ANALYZE, BUFFERS)` 评估执行计划，发现大量 `Buffers: shared read=XXXX`，证明其未命中共享内存缓存，存在大规模 `Seq Scan`。
3. **【针对性治理方案】**：
   - **解决 `DataFileRead`**：补充贴合过滤与排序的高选择性复合索引（覆盖索引），使查询从直接读物理磁盘文件转变为从索引树读内存块（`shared hit`）；
   - **解决 `WALWriteLock`**：排查发现有历史数据清理任务单次 `DELETE` 5 万条记录。大事务产生了巨大的 WAL 日志，导致刷盘锁竞争。我们将大事务拆解为**每次小批量（如 1000 条）分批删除分批提交**，并在批次间加微小延时，平摊 WAL 刷盘压力，锁争用瞬间消失。

### Q13: 在生产环境下给千万级大表加索引有什么风险？你们是怎么加的？

#### 面试官心智
考察候选人是否有真正的生产敬畏心与真实生产运维实操经验。

#### 满分回答模板
1. **【生产风险揭示】**：
   在 PostgreSQL 生产环境下，如果直接使用常规的 `CREATE INDEX` 命令：
   - 该命令默认会向目标表申请 **`SHARE` 锁**；
   - 该锁会与所有的写入事务（`INSERT`、`UPDATE`、`DELETE`）申请的 `ROW EXCLUSIVE` 锁发生互斥冲突！
   - 对于几千万行的大表，建索引可能需要几分钟甚至半小时，这意味着在建索引期间，**整张表的所有在线写入请求全部被阻塞卡死**，数据库连接池瞬间被打爆，引发全站雪崩事故！
2. **【标准落地实践：`CONCURRENTLY`】**：
   在生产环境下必须使用在线并发建索引命令：
   ```sql
   CREATE INDEX CONCURRENTLY idx_name ON table_name (column_name);
   ```
3. **【原理与代价权衡】**：
   - `CONCURRENTLY` 会放宽锁级别，仅持有最低级别的 `SHARE UPDATE EXCLUSIVE` 锁，**完全不阻塞在线业务的 INSERT / UPDATE / DELETE 写入**；
   - 它的代价是：内部需要对表进行两次全表扫描，构建时间更长，且消耗略多的 CPU 和 IO；
   - **防御性检查**：如果构建过程中被手动中断或出现唯一键冲突，索引会被标记为 `INVALID`（无效）。因此建完后必须执行 `\d table_name` 或查询 `pg_index.indisvalid` 进行核验，若无效则先 `DROP INDEX CONCURRENTLY` 再重试；
   - 成功后必须执行 `ANALYZE table_name;` 刷新统计信息，确保优化器能够立刻采纳新索引。

### Q14: AI 视频巡检中，如何防止相似帧重复消耗大模型算力，以及防止物业人员遭遇告警风暴？

#### 面试官心智
考察 AI 大模型与视觉算法落地工程化时的成本控制与用户体验防御设计。

#### 满分回答模板
1. **【核心定性】**：大模型与视觉算法工程化落地，最核心的不是模型本身，而是**“调用成本控制（防冗余算力消耗）”与“告警防抖与收敛（防告警风暴）”**。我们通过三大黄金参数实现了完整的工程闭环。
2. **【机制一：抽帧间隔过滤（`frame_interval`）——省算力】**：
   摄像头每秒产生 25 帧视频流，相邻几秒内的画面 99% 是高度相似的。我们以 `(pointId, algorithmConfigId)` 为维度，在 Redis 中维护上一次调用的毫秒级时间戳。通过 `frame_interval`（如设定为 30 秒）做硬性拦截：未达到抽帧冷却时间，一律不调用大模型推理接口，**节省了 80% 以上的无意义 API 费用与算力**。
3. **【机制二：滑动窗口告警防抖（`alarm_threshold`）——防误报】**：
   真实室外场景常有树影晃动、飞鸟掠过，容易造成单帧的“假阳性”判定。系统设计了告警阈值计数器：只有当该点位在连续 N 张（如连续 3 张）抽检图中均被模型判定为异常时，才判定为真正险情，有效过滤瞬时噪点。
4. **【机制三：告警抑制冷静期（`suppress_minute`）——防风暴】**：
   当某处违停或垃圾满溢已经被触发并推送工单到物业人员手机后，系统自动在该点位激活一个例如 30 分钟的“抑制窗口”。在此窗口期内，算法即便检测到异常也仅做内部状态记录，不再往事件中心重复上报工单，**杜绝管家手机一分钟收到几十条重复报警的恶劣体验**。
