### 1. 广州云智易物联网：智慧社区门禁链路、RTU设备台账与Kafka治理

#### 追问 1：你在云智易负责的“访客通行链路”具体业务是怎样的？怎么对接门禁硬件回调的？
- **真实业务场景**：
  - 支撑招商蛇口智慧社区 C 端小程序与物业端，覆盖“访客线上预约 $	o$ 业主确认邀访 $	o$ 物业审核放行 $	o$ 生成动态通行凭证（二维码/人脸） $	o$ 线下闸机核验通行”全流程。
- **门禁硬件回调与高并发优化**：
  1. **硬件回调接口设计**：门禁硬件（如海康威视闸机）在访客刷码/刷脸通行后，会向后端发起 HTTP/RESTful 事件回调。
  2. **防重与幂等处理**：硬件在弱网环境下可能会多次重发通行流水。后端通过 `device_id + voucher_code + event_time` 生成业务防重 Key，存入 Redis 原子判断，杜绝重复写入通行记录；
  3. **灰度发布与权限下发**：利用物业项目/楼栋白名单机制进行逐步灰度放量，分批下发二维码通行权限到闸机边缘端，避免瞬间批量下发导致设备端带宽跑满。

#### 追问 2：RTU 设备台账同步服务你是怎么独立建设的？
- **背景痛点**：越秀地产海量 RTU（远程测控终端）设备以往靠人工录入 Excel 表格维护，极易出现设备编码重复、空间归属错误、维护成本极高。
- **落地方案**：
  1. **三种同步策略**：
     - **全量同步**：每日凌晨通过定时任务从 FM 资产系统拉取全量台账做比对更新；
     - **增量同步**：监听资产变动的 Kafka 消息，实时更新变动设备；
     - **手动同步**：支持物业管理人员在后台指定项目（Project）、分期（Stage）进行定向触发同步。
  2. **五级空间树形绑定（先父后子）**：
     - 设备不能孤立存在，必须挂载在“项目 $	o$ 分期 $	o$ 楼栋 $	o$ 楼层 $	o$ 房间”五级空间树上；
     - 解析 `floorCode` 和名称兜底逻辑，保证关联的节点如果父节点缺失先自动补齐父节点，避免外键孤儿数据；
  3. **全局唯一设备编码生成**：编写 `RTUManager` 工具类，基于项目代号 + 楼栋编码 + 设备类型 + 自增序列生成规范化的业务主键 `rtu_code`。

#### 追问 3：Kafka 消费链路可靠性治理：你是如何避免重复处理、丢失与同步中断的？
> 🌟 **高分面试点**：这是后端通用核心技术，面试官必问！
- **治理前痛点**：
  - 默认开启了自动提交位移（`enable.auto.commit = true`），消费者拉取到消息就自动提交 offset。如果业务处理中途崩溃，**消息直接丢失**；
  - 遇到单条脏数据抛异常时，整个批次循环中断，导致后面的正常设备数据全部被阻塞（同步中断）；
  - 消费者重启再平衡（Rebalance）时拉取旧消息，缺乏幂等，导致**重复插入设备记录**。
- **治理三步法（原创 `FmKafkaListener` 核心类）**：
  1. **手动提交位移（Manual ACK）**：
     - 关闭自动提交，改为业务全流程处理完毕后显式调用 `acknowledgment.acknowledge()`，确保“不漏消息”；
  2. **业务双层幂等防竞态**：
     - 第一层：Redis 分布式锁/原子标记（`SET event_id EX 300 NX`），并发消息先到先得；
     - 第二层：PostgreSQL 唯一联合索引（`UNIQUE (source_id, event_type, version)`），即使 Redis 抖动，数据库层也能通过 `ON CONFLICT DO NOTHING` 保障绝对幂等；
  3. **Seek 回退与批次逐设备隔离重试**：
     - 循环批次数据时，将单设备逻辑用 `try-catch` 包裹，某台设备数据错误不中断后续设备；
     - 连续异常触发计数器，失败消息自动转入死信队列（DLQ），记录日志报警，防止 offset 长期卡死。

#### 追问 4：线上慢接口你是如何排查的？Postgres 等待事件怎么分析？
- **排查路径**：
  1. 查看微服务慢接口监控，发现访客记录查询接口在早高峰耗时超过 3 秒；
  2. 结合 `jstack` 打印 JVM 线程栈，排查是否存在大量线程阻塞在锁等待或数据库连接池等待；
  3. 打开 PostgreSQL 的 `pg_stat_activity` 查看当前正在执行的 SQL 及其 `wait_event_type`（如发现大量的 `Lock: relation` 锁等待或 `IO: DataFileRead` 磁盘读取等待）；
  4. 使用 `EXPLAIN ANALYZE` 抓取慢 SQL，发现大表 `t_visitor_record` 缺少针对 `(tenant_id, create_time)` 的复合索引，导致走全表扫描（Seq Scan）；
  5. **生产调优**：为大表建立复合索引时，采用 `CREATE INDEX CONCURRENTLY`（并发创建索引），**不锁表**，平滑消除慢查询，耗时从 3 秒多降至 50 毫秒以内。

### 2. 凯通科技：电信级综合网管（OSS/NMS）、拓扑大屏与以子查根

---

#### 追问 2：浙江电信 8 个云池的“事件监控一张图（拓扑大屏）”前后端联动是怎么实现的？
- **技术难点**：
  - 浙江电信 8 个云池管理着成千上万台批量宿主机（Host）。一旦底层网络设备故障，会瞬间诱发大面积宿主机不可用事件；
  - 旧接口把“静态拓扑结构”和“动态告警状态”揉在一起查询，每次大屏刷新都要做全量拓扑计算，直接导致大屏接口超时卡死。
- **架构重构动作**：
  1. **拓扑与状态彻底解耦**：
     - 前端进入时只加载一次基础静态拓扑结构（机房、机架、宿主机节点连线）；
     - 后端独立剥离出**拓扑动态状态模块**，前端每隔 10 秒仅轮询增量动态告警状态，极大降低网络带宽与后端计算压力；
  2. **抽离通用设备识别口径工具（`YcTopologyDeviceUtil`）**：
     - 不同云池的设备命名规范和专业分类极其混乱（如 EPC 核心网设备、动环机房监控、网元 IP）；
     - 抽离出统一的口径识别工具类，按 IP、网管名和视图代码进行标准化归一化，极大提高了复用性与准确度；
  3. **聚合维度收敛**：从最初无脑的机房维度切换为站点维度聚合，大屏数据渲染速度提升 60% 以上。

---

#### 追问 3：什么是“以子查根”？你闭环的线上 Bug 是怎么回事？
- **电信告警风暴痛点**：

## 五、简历必问 Java 后端核心八股速通（30分钟快问快答级别）

### 1. JVM 核心：运行时内存区域、GC 垃圾回收与分代模型
- **运行时数据区**：
  - 线程私有：程序计数器（**唯一不报 OOM**）、虚拟机栈（StackOverflowError/OOM）、本地方法栈；
  - 线程共享：堆（存放几乎所有实例，最常报 `OOM: Java heap space`）、方法区/元空间（类元数据，报 `OOM: Metaspace`）。
- **新生代与垃圾回收**：
  - 新生代切分为 **Eden(80%) + S0(10%) + S1(10%)**，采用**标记-复制算法**；
  - 每次 Minor GC 存活对象年龄 $+1$，达阈值（默认 15）晋升老年代。
- **CMS vs G1**：
  - CMS：老年代标记-清除，并发收集低停顿，但有内存碎片；
  - G1：堆划分为成千上万个 **Region**，标记-整理无碎片，支持预测停顿时间（`-XX:MaxGCPauseMillis`）。

### 2. Java 并发：volatile、ThreadLocal、线程池参数与锁膨胀流程
- **`volatile`**：保证**可见性**（CPU 内存屏障 + 缓存一致性协议 MESI）与**禁止指令重排**；**不保证原子性**。
- **`ThreadLocal` 内存泄漏**：Key 为弱引用，Value 为强引用。线程池复用线程时，若不手动调用 `remove()`，Value 强引用链一直存在导致 OOM。
- **线程池 7 参数与调度口诀**：
  - 核心线程 $	o$ 阻塞队列 $	o$ 最大线程（救火临时工） $	o$ 拒绝策略（`AbortPolicy` 抛异常，`CallerRunsPolicy` 调用者执行）。
- **`synchronized` 锁升级（不可逆）**：
  - 无锁(001) $	o$ 偏向锁(101, 记录线程ID) $	o$ 轻量级锁(000, 栈帧 Lock Record CAS 自旋) $	o$ 重量级锁(010, 申请 OS Mutex，线程阻塞挂起)。

### 4. Redis 缓存：五大数据类型、持久化机制与缓存三大灾难治理
- **五大数据类型底层**：String (SDS)、List (QuickList 双向+压缩列表)、Hash (Dict/Listpack)、Set (IntSet/Dict)、ZSet (**SkipList 跳表 + Dict**)。
- **持久化机制**：RDB 全量快照（`bgsave` 写时复制 COW，恢复快） + AOF 增量追加写日志（高可靠，配 `everysec`）。生产采用混合持久化。
- **缓存三大灾难**：
  - **穿透**（查不存在数据）：布隆过滤器 + 空值缓存（`EX 60s`）；
  - **击穿**（热点 Key 过期）：互斥锁（`SETNX` 分布式锁）/ 逻辑不过期；
  - **雪崩**（大量 Key 同时到期）：过期时间加 **1~5 分钟随机扰动值** + 集群高可用。

### 5. MySQL 核心：ACID 底层支撑、事务隔离级别与索引失效场景
- **ACID 底层支撑**：A 原子性（Undo Log 回滚）、C 一致性（目标）、I 隔离性（锁 + MVCC）、D 持久性（Redo Log 预写 WAL）。
- **四种隔离级别**：读未提交、读已提交、可重复读（RR，默认，通过 MVCC + Next-Key Lock 解决不可重复读与大部分幻读）、串行化。

## 六、计算机网络全栈协议与普联“特产”高频 4 问

### 1. 数据包跨路由器转发全链路（IP vs MAC 变化深度剖析）
- **口答黄金结论**：
  1. **源 IP 和目的 IP 保持不变**（全局端到端寻址，标识最终发端与收端）；
  2. **源 MAC 和目的 MAC 逐跳重写**（局域网点到点寻址，每经一个路由器，源 MAC 变为路由器出接口 MAC，目的 MAC 变为下一跳网关/主机 MAC）；
  3. 路由器转发时，IP 报头 **TTL 减 1**，并重新计算首部校验和。

---

### 2. ARP 协议工作原理与免费 ARP（Gratuitous ARP）的作用
- **正常 ARP**：局域网内广播发送 ARP Request（目的 MAC 全 F），目标主机单播回复 ARP Reply，更新本地 ARP 缓存。
- **免费 ARP**：源 IP 和目的 IP 都是自己。作用：① 检测局域网 IP 冲突；② VRRP/Keepalived 主备切换时广播通知交换机刷新 MAC 映射表。

---

### 3. CIDR 子网掩码与网络号速算实战
- **速算考题**：`192.168.1.130/26`：
  - `/26` 代表前 26 位为 1，第四字节借用 2 位主机位：`11000000` = 192，子网掩码为 `255.255.255.192`；
  - 块跨度：$256 - 192 = 64$；
  - `130` 落在 `128 ~ 191` 区间：网络地址为 `192.168.1.128`，广播地址为 `192.168.1.191`，可用主机数 $2^6 - 2 = 62$ 台。

---

### 4. NAT 与 NAPT（端口映射）原理与内网穿透机制
- **NAPT（家用路由器核心）**：多个内网私有 IP（`192.168.x.x`）共享单个公网 IP。路由器根据**五元组**维护转换表，出网替换源 IP 并分配临时端口，回包查表还原真实内网 IP 与端口。

---

### 5. TCP 协议核心：三次握手/四次挥手/TIME_WAIT/可靠传输四大法宝
- **三次握手**：防历史失效连接请求突然到达服务端浪费资源；双向同步初始序列号（ISN）。
- **四次挥手**：TCP 全双工，被动方收到 FIN 回复 ACK 后，仍可继续发送未传输完的残留数据，发完后再独立发 FIN。
- **TIME_WAIT 2MSL 两大意义**：① 确保最后一个 ACK 能送达被动方；② 保证本次连接产生的所有延迟数据包在网络中彻底消亡，防新连接串包。
- **CLOSE_WAIT 泄漏**：被动关闭方（服务端）代码 BUG，未显式调 `close()`。

---

### 6. 现代通信协议对比：HTTP 1.0~3.0 / HTTPS / SSE / WebSocket
- **HTTP/1.1 vs 2.0 vs 3.0**：
  - 1.1 默认 Keep-Alive，但有应用层队头阻塞；
  - 2.0 二进制分帧、多路复用，但单 TCP 流丢包会导致**传输层队头阻塞**；
  - 3.0 放弃 TCP，改用基于 **UDP 的 QUIC 协议**，彻底根除队头阻塞，支持 0-RTT 握手与连接迁移。
- **SSE vs WebSocket**：
  - **SSE（Server-Sent Events）**：基于标准 HTTP/1.1 长连接，`Content-Type: text/event-stream`，纯文本格式以 `

` 分隔。**大模型流式打字机标配**，原生 `EventSource` 自动断线重连；局限为单向推流（Server $	o$ Client）。
  - **WebSocket**：基于 TCP 的独立应用层协议，HTTP 101 升级握手，收发轻量二进制帧（最小仅 2B），真正的**全双工双向通信**，适合在线聊天、协同与游戏。

### 1. 翻转单链表（迭代双指针）

```java
public ListNode reverseList(ListNode head) {
    ListNode prev = null, curr = head;
    while (curr != null) {
        ListNode next = curr.next;
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}
```

### 2. 快慢指针检测单链表环入口
```java
public ListNode detectCycle(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) {
            ListNode ptr = head;
            while (ptr != slow) {
                ptr = ptr.next;
                slow = slow.next;
            }
            return ptr;
        }
    }
    return null;
}
```

### 3. 严格二分查找左侧边界
```java
public int searchLeftBound(int[] nums, int target) {
    int left = 0, right = nums.length - 1;
    while (left <= right) {
        int mid = left + ((right - left) >> 1);
        if (nums[mid] >= target) {
            right = mid - 1;
        } else {
            left = mid + 1;
        }
    }
    return left;
}
```
