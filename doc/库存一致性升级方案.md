# 库存一致性升级方案

本文档用于规划库存系统的第一阶段升级：在保留现有“下单预占库存”思路的基础上，补齐 Redis、MySQL、订单状态之间的一致性闭环。第二阶段再单独建设秒杀链路，避免把普通商城下单和秒杀抢购揉成同一套流程。

## 结论

现有思路是正确的：用户下单后先冻结库存，支付成功后确认占用，取消或超时后释放冻结库存。需要升级的不是业务方向，而是状态归属和异常恢复能力。

升级后的核心原则：

- MySQL 是订单状态、库存预占、库存流水的主事实。
- Redis 只做快速判断、限流、缓存和触发器，不能作为唯一库存事实。
- 所有支付、取消、超时动作都先通过订单状态 CAS 抢处理权。
- 库存预占必须有 MySQL 账本记录，Redis 预占可以短暂不一致，但必须能由 MySQL 重建。
- 第一阶段目标是普通商城高并发下最终不超卖；秒杀流量走第二阶段独立链路。

## 目标

第一阶段需要达成：

1. 普通高并发下最终不超卖。
2. 下单、支付、取消、超时之间不会重复扣减或重复释放库存。
3. Redis 宕机、消息丢失、服务重启后，库存状态可以从 MySQL 恢复。
4. 订单状态、库存预占状态、库存流水之间可以被审计和对账。
5. 保留 Redis Lua 的快速库存判断能力，但不让 Redis 单独决定最终订单成功。

第一阶段不追求：

1. Redis 和 MySQL 每一毫秒都完全一致。
2. 使用 XA/2PC 分布式事务。
3. 秒杀级瞬时流量直接打普通下单接口。

现实目标应该是：

```text
不超卖，状态可恢复，失败可补偿，用户结果最终一致。
```

## 当前问题摘要

当前实现的主要流程是：

```text
下单:
Redis available 扣减
Redis reserve hash 写入 tempOrderId
MySQL 创建订单和订单项

支付:
删除 Redis reserve
扣减 MySQL product.stock_quantity
订单 PENDING -> PAID

取消/超时:
订单 PENDING -> CANCELLED
Redis available 加回
删除 Redis reserve
```

这套流程解决了“多个用户同时下单时，Redis 层不要同时占用同一份库存”的问题，也解决了“待支付订单占住库存”的业务语义。

但它存在几个一致性缺口：

1. Redis 预占成功后，MySQL 订单保存失败时，Redis 预占可能残留。
2. 支付时先删 Redis 预占，再扣 MySQL 库存，中间存在库存被重新放出的窗口。
3. MySQL 库存扣减是先读后 set，不是条件原子扣减，存在并发丢失更新风险。
4. 支付、取消、超时没有共享同一个订单状态处理权，可能同时处理同一订单。
5. 超时任务依赖 Redis ZSet 和 Stream，消息丢失后缺少 DB 兜底扫描。
6. Redis 预占记录没有 MySQL 对应账本，无法稳定审计、恢复和补偿。

## 升级策略

推荐采用“保留预占业务模型，升级一致性边界”的方案。

```text
业务模型: 下单预占库存
主事实: MySQL
加速层: Redis
一致性保障: 订单状态 CAS + 库存预占表 + 幂等库存流水 + 对账补偿
秒杀能力: 第二阶段独立建设
```

### 为什么不是纯 Redis 方案

纯 Redis 预占能提高下单阶段性能，但一旦订单、支付、超时、退款这些状态落在 MySQL，Redis 就不能单独作为库存事实。否则服务崩溃、DB 事务回滚、消息丢失都会让库存状态分裂。

### 为什么不是完全推翻现有思路

库存预占本身是正确模型。普通商城里，用户下单后获得一个支付窗口，这段时间库存应该被冻结，不能继续卖给别人。升级的重点是把“冻结事实”持久化到 MySQL，并让 Redis 变成可重建的加速镜像。

## 数据模型设计

### product 表

保留现有 `product.stock_quantity` 字段，但在升级后明确其含义为“可售库存”。

建议新增：

```sql
ALTER TABLE product
  ADD COLUMN reserved_quantity int NOT NULL DEFAULT 0 COMMENT '已冻结库存',
  ADD COLUMN stock_version bigint NOT NULL DEFAULT 0 COMMENT '库存版本号';
```

字段语义：

| 字段 | 含义 |
|---|---|
| `stock_quantity` | 当前可售库存，可以被新订单预占 |
| `reserved_quantity` | 已下单但未支付、未取消的冻结库存 |
| `stock_version` | 可选，用于乐观锁、审计或缓存版本判断 |

核心约束：

```text
stock_quantity >= 0
reserved_quantity >= 0
```

第一阶段不强制新增 `total_quantity`。如果后续要做更完整的仓储模型，可以再引入：

```text
total_quantity = stock_quantity + reserved_quantity + sold_or_outbound_quantity
```

但当前商城订单场景中，用“可售库存 + 冻结库存”已经足够防止超卖。

### stock_reservation 表

新增库存预占表，作为冻结库存的 MySQL 账本。

```sql
CREATE TABLE stock_reservation (
  id bigint unsigned NOT NULL AUTO_INCREMENT,
  order_id bigint unsigned NOT NULL,
  product_id bigint unsigned NOT NULL,
  user_id bigint unsigned NOT NULL,
  quantity int NOT NULL,
  status varchar(20) NOT NULL,
  expire_time datetime NOT NULL,
  created_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_product (order_id, product_id),
  KEY idx_product_status (product_id, status),
  KEY idx_expire_status (expire_time, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='库存预占表';
```

状态枚举：

| 状态 | 含义 |
|---|---|
| `FROZEN` | 下单成功，库存已冻结，等待支付 |
| `CONFIRMED` | 支付成功，冻结库存转为真实售出 |
| `RELEASED` | 取消、超时、下单失败补偿后释放冻结库存 |

### inventory_logs 表

现有 `inventory_logs` 可以继续使用，但建议增强幂等能力。

推荐新增：

```sql
ALTER TABLE inventory_logs
  ADD COLUMN business_type varchar(32) DEFAULT NULL COMMENT '业务类型',
  ADD COLUMN business_id varchar(64) DEFAULT NULL COMMENT '业务幂等ID',
  ADD UNIQUE KEY uk_inventory_business (business_type, business_id, product_id);
```

示例幂等键：

| 场景 | business_type | business_id |
|---|---|---|
| 下单冻结 | `ORDER_FREEZE` | `order:{orderId}` |
| 支付确认 | `ORDER_CONFIRM` | `order:{orderId}` |
| 取消释放 | `ORDER_RELEASE` | `order:{orderId}` |
| 退货入库 | `RETURN_IN` | `order:{orderId}` |

这样即使消息重试、接口重复提交，也不会重复写库存流水。

### stock_event_outbox 表

建议新增本地消息表，用于把 MySQL 成功后的库存变化可靠同步到 Redis。

```sql
CREATE TABLE stock_event_outbox (
  id bigint unsigned NOT NULL AUTO_INCREMENT,
  event_type varchar(32) NOT NULL,
  aggregate_id varchar(64) NOT NULL,
  payload_json json NOT NULL,
  status varchar(20) NOT NULL DEFAULT 'PENDING',
  retry_count int NOT NULL DEFAULT 0,
  next_retry_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_event (event_type, aggregate_id),
  KEY idx_status_retry (status, next_retry_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='库存事件本地消息表';
```

作用：

- MySQL 事务提交库存变化和 outbox 事件。
- 后台任务读取 outbox，同步 Redis 库存快照。
- Redis 更新失败时重试。
- Redis 数据丢失时也可以从 MySQL 重建。

## 状态机

订单状态和库存预占状态必须一起设计。

```text
下单成功:
orders:            PENDING
stock_reservation: FROZEN
product:           stock_quantity - n, reserved_quantity + n

支付成功:
orders:            PAID
stock_reservation: CONFIRMED
product:           reserved_quantity - n

取消/超时:
orders:            CANCELLED
stock_reservation: RELEASED
product:           stock_quantity + n, reserved_quantity - n
```

关键不变量：

1. `PENDING` 订单必须有 `FROZEN` 预占记录。
2. `PAID` 订单不能保留 `FROZEN` 预占记录。
3. `CANCELLED` 订单不能保留 `FROZEN` 预占记录。
4. 对同一个订单，支付、取消、超时只能有一个动作成功。
5. `product.reserved_quantity` 应等于该商品所有 `FROZEN` 预占记录数量之和。

## 关键流程

### 下单流程

下单必须先做输入收敛：

1. 校验商品数量 `quantity > 0`。
2. 合并同一订单内重复商品。
3. 按 `product_id` 排序处理库存，降低死锁概率。
4. 校验商品存在、上架、商家归属、不能购买自己商品。

一致性优先版本：

```text
1. 开启 MySQL 事务
2. 创建 orders，状态为 PENDING
3. 创建 order_items
4. 对每个商品执行 MySQL 条件冻结
5. 插入 stock_reservation，状态为 FROZEN
6. 写 inventory_logs 幂等流水
7. 写 stock_event_outbox
8. 提交事务
9. outbox 后台同步 Redis
```

库存冻结 SQL：

```sql
UPDATE product
SET stock_quantity = stock_quantity - ?,
    reserved_quantity = reserved_quantity + ?,
    stock_version = stock_version + 1
WHERE id = ?
  AND stock_quantity >= ?;
```

影响行数为 1，说明冻结成功。影响行数为 0，说明库存不足，整个订单事务回滚。

Redis 在第一阶段可以参与快速判断：

```text
Redis 判断库存不足 -> 直接拒绝，减少 DB 压力
Redis 判断库存足够 -> 继续进入 MySQL 条件冻结
```

但下单最终成功的唯一标准是 MySQL 事务提交成功。

如果希望保留当前 Redis Lua 预扣体验，也必须满足：

1. Redis 预扣只是快速准入，不代表订单最终成功。
2. MySQL 冻结失败后必须立即回补 Redis。
3. 服务崩溃导致 Redis 未回补时，由对账任务从 MySQL 重建 Redis。

第一阶段建议先采用“Redis 只快速判断，MySQL 真冻结”的实现，代码更稳，风险更小。

### 支付流程

支付必须先抢订单状态。

```sql
UPDATE orders
SET status = 'paid',
    payment_status = 'paid',
    paid_time = NOW()
WHERE id = ?
  AND user_id = ?
  AND status = 'pending';
```

影响行数为 1，说明当前请求拿到了订单处理权。随后确认库存预占：

```sql
UPDATE stock_reservation
SET status = 'CONFIRMED'
WHERE order_id = ?
  AND status = 'FROZEN';
```

然后扣减冻结库存：

```sql
UPDATE product
SET reserved_quantity = reserved_quantity - ?,
    stock_version = stock_version + 1
WHERE id = ?
  AND reserved_quantity >= ?;
```

注意：支付阶段不再扣 `stock_quantity`，因为下单冻结时已经从可售库存中扣掉了。支付只是把冻结库存确认成真实售出。

如果订单状态更新影响行数为 0：

- 如果订单已经是 `PAID`，幂等返回成功。
- 如果订单已经是 `CANCELLED`，返回订单已取消，不允许支付。
- 不允许继续处理库存。

### 用户取消流程

取消也必须先抢订单状态。

```sql
UPDATE orders
SET status = 'cancelled',
    payment_status = 'cancelled'
WHERE id = ?
  AND user_id = ?
  AND status = 'pending';
```

影响行数为 1，说明取消拿到处理权。随后释放预占库存：

```sql
UPDATE stock_reservation
SET status = 'RELEASED'
WHERE order_id = ?
  AND status = 'FROZEN';
```

```sql
UPDATE product
SET stock_quantity = stock_quantity + ?,
    reserved_quantity = reserved_quantity - ?,
    stock_version = stock_version + 1
WHERE id = ?
  AND reserved_quantity >= ?;
```

如果订单状态更新影响行数为 0：

- 已支付订单不能按待支付取消处理。
- 已取消订单幂等返回成功。
- 不允许重复释放库存。

### 超时取消流程

超时任务不能只依赖 Redis ZSet/Stream。Redis 可以继续作为触发器，但 DB 的 `expire_time` 才是权威来源。

推荐流程：

```text
1. Redis ZSet 扫描到超时订单，推送处理消息
2. 超时消费者调用 cancelExpiredOrder(orderId)
3. cancelExpiredOrder 使用 orders.status = PENDING 做 CAS
4. CAS 成功才释放 FROZEN 预占
5. CAS 失败说明支付或取消已经先完成，不处理库存
```

兜底任务：

```sql
SELECT order_id
FROM stock_reservation
WHERE status = 'FROZEN'
  AND expire_time <= NOW()
LIMIT 100;
```

这样即使 Redis 消息丢失，DB 兜底扫描也能处理超时订单。

### 退货入库流程

支付成功后，预占已经变为 `CONFIRMED`，商品已从可售库存中移出。因此退货入库不再处理 `stock_reservation`，只做可售库存增加和库存流水。

```sql
UPDATE product
SET stock_quantity = stock_quantity + ?,
    stock_version = stock_version + 1
WHERE id = ?;
```

并写入幂等库存流水：

```text
business_type = RETURN_IN
business_id = order:{orderId}
```

## Redis 设计

第一阶段 Redis 仍然保留，但职责调整。

| Key | 用途 | 是否主事实 |
|---|---|---|
| `product:stock:available:{productId}` | 可售库存快照，用于快速拒绝明显库存不足请求 | 否 |
| `product:stock:reserve:{productId}` | 可选，调试或快速查看冻结量 | 否 |
| `order:timeout:trigger` | 超时触发器 | 否 |
| `order:timeout:stream` | 超时处理消息 | 否 |

Redis 写入原则：

1. MySQL 事务提交后再更新 Redis。
2. Redis 更新失败不回滚 MySQL。
3. Redis 更新失败写 outbox 重试。
4. 定时任务可以从 MySQL 重建 Redis 库存快照。

重建逻辑：

```sql
SELECT stock_quantity, reserved_quantity
FROM product
WHERE id = ?;
```

然后写入：

```text
product:stock:available:{productId} = product.stock_quantity
```

如果保留 reserve hash，则应由 `stock_reservation` 中的 `FROZEN` 记录重建，而不是信任旧 Redis hash。

## 对账补偿

必须增加定时对账任务。对账不需要每秒跑，普通商城可以每 1 到 5 分钟执行一次。

### 订单与预占状态对账

检查 `PENDING` 订单是否缺少 `FROZEN` 预占：

```sql
SELECT o.id
FROM orders o
LEFT JOIN stock_reservation r
  ON r.order_id = o.id AND r.status = 'FROZEN'
WHERE o.status = 'pending'
  AND r.id IS NULL;
```

这类数据说明订单创建链路异常，应报警或取消订单。

### 冻结库存汇总对账

检查 `product.reserved_quantity` 是否等于 `FROZEN` 预占汇总：

```sql
SELECT p.id,
       p.reserved_quantity,
       COALESCE(SUM(r.quantity), 0) AS frozen_quantity
FROM product p
LEFT JOIN stock_reservation r
  ON r.product_id = p.id AND r.status = 'FROZEN'
GROUP BY p.id, p.reserved_quantity
HAVING p.reserved_quantity <> frozen_quantity;
```

发现不一致时，先报警，再按业务规则修复。自动修复前必须记录审计日志。

### Redis 库存对账

Redis 可售库存应等于 MySQL 的 `product.stock_quantity`。Redis 不一致时可以直接覆盖，因为 Redis 不是主事实。

```text
Redis available != MySQL stock_quantity
-> set Redis available = MySQL stock_quantity
```

## 是否能防止超卖

第一阶段升级后，可以防止普通商城场景下的最终超卖。

原因是最终成功订单必须满足：

1. MySQL 条件冻结库存成功。
2. 订单状态为 `PENDING`。
3. 存在 `FROZEN` 预占记录。
4. 支付、取消、超时通过订单状态 CAS 互斥。
5. 库存释放和确认都基于 `FROZEN` 记录幂等执行。

即使 Redis 短暂错误，也不会直接造成最终超卖，因为 Redis 不再单独决定订单成功。

## 是否能顶住秒杀

第一阶段不作为秒杀最终方案。

第一阶段能提升普通高并发下的正确性，但热点商品仍然会集中竞争 MySQL 的单行库存。它能防超卖，但不适合承受秒杀峰值。

秒杀应作为第二阶段独立链路：

```text
请求进入秒杀接口
-> Redis Lua 判断活动、库存、用户限购、重复购买
-> Redis 原子扣减秒杀库存
-> 写入 Redis Stream 或 MQ
-> 立即返回“排队中/抢购资格成功”
-> 后台消费者异步创建订单和 MySQL 预占记录
-> 前端轮询最终结果
```

秒杀链路的关键原则：

1. 秒杀接口不直接同步创建最终订单。
2. Redis Lua 负责抢资格，不负责最终订单事实。
3. MQ/Stream 负责削峰填谷。
4. MySQL 条件冻结仍然作为最终兜底。
5. 如果异步落库失败，必须补回 Redis 秒杀库存或标记失败结果。

第二阶段需要新增：

| 能力 | 说明 |
|---|---|
| 秒杀活动表 | 活动时间、库存、限购规则 |
| 秒杀库存预热 | 活动开始前写入 Redis |
| 秒杀 Lua 脚本 | 原子判断库存、限购、重复购买 |
| 排队结果查询 | 用户看到排队中、成功、失败 |
| 异步订单消费者 | 从 Stream/MQ 创建订单 |
| 失败补偿 | 落库失败后补回资格或库存 |

## 推荐实施顺序

### 第一阶段：一致性升级

1. 新增 `reserved_quantity`、`stock_reservation`、库存流水幂等字段、可选 outbox 表。
2. 将下单库存处理改为 MySQL 条件冻结。
3. 支付改为确认预占，不再扣可售库存。
4. 取消和超时统一走释放预占流程。
5. Redis 改为可重建缓存和触发器。
6. 增加 DB 兜底超时扫描。
7. 增加库存对账任务。
8. 增加并发测试、重复请求测试、异常恢复测试。

### 第二阶段：秒杀链路

1. 新增秒杀活动模型。
2. 活动库存预热到 Redis。
3. 秒杀接口使用 Lua 抢资格。
4. 抢购成功写入 Stream/MQ。
5. 后台异步创建普通订单和 `stock_reservation`。
6. 用户通过结果查询接口获取最终结果。
7. 增加秒杀压测和失败补偿测试。

## 测试清单

第一阶段必须覆盖：

1. 库存为 1，两个用户并发下单，只有一个订单成功。
2. 同一用户重复提交同一订单请求，不重复冻结库存。
3. 同一订单内重复商品被合并，不覆盖预占数量。
4. 下单事务失败后，库存不减少，预占记录不残留。
5. 支付和超时同时发生，只有一个状态转换成功。
6. 取消和支付同时发生，只有一个状态转换成功。
7. 重复支付不会重复确认预占。
8. 重复取消不会重复释放库存。
9. Redis 库存被手动改错后，对账任务能恢复。
10. Redis 超时消息丢失后，DB 兜底扫描能取消过期订单。

第二阶段必须覆盖：

1. 秒杀库存为 100，10000 个请求并发，最多 100 个资格成功。
2. 同一用户重复请求秒杀，只能成功一次。
3. Lua 成功但异步落库失败，库存或结果能补偿。
4. 消费者重启后 pending 消息不会丢。
5. MySQL 最终订单数不超过活动库存。

## 面试或项目表述

可以这样描述升级后的设计：

> 原系统使用 Redis Lua 做库存预占，解决了普通并发下单时的快速库存扣减问题。后续我将其升级为 Redis 加速、MySQL 兜底的库存状态机：下单时通过 MySQL 条件更新冻结库存并写入预占账本，支付、取消、超时都先通过订单状态 CAS 抢处理权，再幂等确认或释放预占；Redis 只作为可重建缓存和超时触发器，通过 outbox 和定时对账保持最终一致。这样普通商城链路可以防止最终超卖，秒杀场景再单独使用 Redis Lua 加队列异步落库实现削峰。

## 最终判断

第一阶段升级方案可以解决数据一致性和普通高并发防超卖问题。它不是秒杀最终方案，但它是秒杀链路的可靠基础。

合理路线是：

```text
先把普通下单链路做正确
再把秒杀流量从普通下单链路中拆出去
最后用 Redis Lua + MQ/Stream + MySQL 兜底实现秒杀
```
